# contacts

## Purpose

Определяет агрегат «Контакт» BUDB: состав полей и лимиты, идентификатор, создание, чтение, изменение с проверкой версии, удаление в корзину, восстановление writer и admin, окно восстановления и подсказку о возможных дубликатах.

## ADDED Requirements

### Requirement: CON-01 Состав агрегата контакта
Контакт SHALL состоять ровно из полей `id`, `display_name` (обязательно), необязательных `given_name`, `family_name`, `middle_name`, списка `phones` из 0–10 элементов, `version`, `created`, `updated`; у контакта в корзине есть ещё `deleted_at` и `purge_after` (CON-16). Контакт с 11 и более телефонами MUST отклоняться с ошибкой валидации.
Трассировка: CUJ-03, CUJ-05; ADR-0007; D-009, D-022, D-064
Источник: docs/research/03 §2.6, §3.1, §8.3

#### Scenario: Контакт без телефонов
- **WHEN** клиент создаёт контакт только с `display_name` = «Иван Петров»
- **THEN** контакт сохраняется с пустым списком `phones`
- **AND** `given_name`, `family_name`, `middle_name` отсутствуют

#### Scenario: Одиннадцатый телефон
- **WHEN** клиент создаёт контакт с 11 корректными телефонами
- **THEN** операция отклоняется с ошибкой валидации поля `phones`
- **AND** контакт не создаётся

### Requirement: CON-02 Идентификатор контакта
Система SHALL назначать `id` при создании: монотонно растущее целое без знака 64 бита, в JSON — десятичная строка. `id` MUST быть уникальным, неизменяемым и не переиспользоваться ни после очистки контакта, ни после восстановления базы из бэкапа (BKP-13). Значение `id` от клиента MUST NOT влиять на назначенный `id`.
Трассировка: CUJ-03, CUJ-05, CUJ-07; ADR-0007; D-009, D-057, D-075

#### Scenario: Одинаковые данные дают разные id
- **WHEN** клиент дважды создаёт контакт «Анна» с телефоном `+79123456789`
- **THEN** создаются два контакта с разными `id`

#### Scenario: id десятичной строкой
- **WHEN** контакту назначен `id` 1050
- **THEN** представление контакта содержит `"id":"1050"`

#### Scenario: id очищенного контакта не возвращается
- **WHEN** контакт с `id` X очищен из корзины, а затем создаются новые контакты
- **THEN** ни одному новому контакту не назначается `id` X

#### Scenario: id после восстановления из бэкапа
- **WHEN** после бэкапа B1 создан и очищен контакт с `id` 1050, затем база восстановлена из B1 и создан новый контакт
- **THEN** новому контакту назначается `id` больше 1050, а не 1050

### Requirement: CON-03 Лимиты имени
После обработки по name-normalization (NAM-01…NAM-04) `display_name` MUST содержать от 1 до 256 кодовых точек и не более 1024 байт UTF-8, а каждое из `given_name`, `family_name`, `middle_name` — не более 128 кодовых точек. Нарушение SHALL отклонять операцию с ошибкой валидации, указывающей поле. Пустая после очистки часть имени считается отсутствующей [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-03, CUJ-06; ADR-0007; D-022

#### Scenario: Граница длины display_name
- **WHEN** `display_name` состоит из 256 символов «я»
- **THEN** контакт сохраняется

#### Scenario: Превышение длины display_name
- **WHEN** `display_name` состоит из 257 символов «я»
- **THEN** операция отклоняется с ошибкой валидации поля `display_name`

#### Scenario: Длинная фамилия
- **WHEN** `family_name` содержит 129 кодовых точек
- **THEN** операция отклоняется с ошибкой валидации поля `family_name`

### Requirement: CON-04 Состав телефона
Телефон SHALL содержать `e164`, `extension`, `raw_input`, `label`, `is_primary`; на входе задаются `raw_input`, необязательные `label`, `is_primary` и `region` (PHN-08). `e164` и `extension` система MUST вычислять из `raw_input` по phone-normalization, а их входные значения игнорировать. `label` — `mobile`, `home`, `work` или `other`, по умолчанию `other` [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-03; ADR-0007, ADR-0008; D-009, D-010, D-071

#### Scenario: Телефон с меткой по умолчанию
- **WHEN** клиент передаёт телефон `8 (912) 345-67-89` без метки при регионе RU
- **THEN** сохраняется телефон с `e164` = `+79123456789`, `raw_input` = `8 (912) 345-67-89`, `label` = `other`

#### Scenario: Недопустимая метка
- **WHEN** клиент передаёт телефон с `label` = `fax`
- **THEN** операция отклоняется с ошибкой валидации поля `label`

#### Scenario: Входное e164 игнорируется
- **WHEN** клиент передаёт телефон с `raw_input` = `+79123456789` и `e164` = `+70000000000`
- **THEN** сохраняется телефон с `e164` = `+79123456789`, ошибки нет

### Requirement: CON-05 Отказ при недопустимом телефоне
Если хотя бы один телефон не проходит нормализацию (PHN-14), операция создания или изменения SHALL отклоняться целиком с ошибкой, указывающей позицию телефона в списке. Частичное сохранение контакта MUST NOT происходить.
Трассировка: CUJ-03, CUJ-05; ADR-0008; D-010

#### Scenario: Второй телефон недопустим
- **WHEN** клиент создаёт контакт с телефонами `+79123456789` и `12`
- **THEN** операция отклоняется с ошибкой для `phones[1]` и кодом `phone.invalid_length`
- **AND** контакт не создаётся

### Requirement: CON-06 Уникальность телефона внутри контакта
Пара (`e164`, `extension`) MUST быть уникальной в пределах одного контакта. Повтор пары SHALL отклонять операцию с ошибкой валидации, указывающей повторный элемент. Один и тот же `e164` с разными `extension` допустим.
Трассировка: CUJ-03; ADR-0007; D-009, D-059
Источник: docs/research/03 §3.1

#### Scenario: Один номер в двух записях ввода
- **WHEN** клиент передаёт в одном контакте `8 912 345-67-89` и `+7 912 345 67 89` при регионе RU
- **THEN** операция отклоняется с ошибкой для `phones[1]`

#### Scenario: Разные добавочные номера
- **WHEN** клиент передаёт `+74951234567;ext=101` и `+74951234567;ext=102`
- **THEN** контакт сохраняется с двумя телефонами

### Requirement: CON-07 Общий телефон у нескольких контактов
Система SHALL разрешать один и тот же `e164` в разных контактах (например, семейный телефон) и MUST NOT требовать глобальной уникальности номера.
Трассировка: CUJ-01, CUJ-03; ADR-0007; D-009

#### Scenario: Семейный телефон
- **WHEN** контакты «Иван Петров» и «Мария Петрова» создаются с телефоном `+74951234567`
- **THEN** оба контакта сохраняются
- **AND** поиск по `+74951234567` (SRCH-01) возвращает оба

### Requirement: CON-08 Основной телефон
Если у контакта есть телефоны, ровно один из них MUST иметь `is_primary` = true; у контакта без телефонов основного нет. Два и более основных SHALL отклоняться с ошибкой валидации. Если основной не указан, система SHALL сделать основным первый телефон списка [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-03; ADR-0007; D-009, D-059

#### Scenario: Основной не указан
- **WHEN** клиент создаёт контакт с телефонами `+79123456789` и `+74951234567` без `is_primary`
- **THEN** `is_primary` = true только у `+79123456789`

#### Scenario: Два основных
- **WHEN** клиент передаёт два телефона с `is_primary` = true
- **THEN** операция отклоняется с ошибкой валидации

#### Scenario: Основной телефон убран при изменении
- **WHEN** контакт с основным телефоном A и телефоном B изменяется запросом только с телефоном B без `is_primary`
- **THEN** у контакта один телефон B, и он основной

### Requirement: CON-09 Запрет заметок и неизвестных полей
Контакт MUST NOT иметь поля свободной заметки. Входные данные с полем, не перечисленным в CON-01 и CON-04 (например, `note`), SHALL отклоняться с ошибкой валидации, называющей это поле. Поля только для чтения из CON-01 неизвестными не считаются (CON-19).
Трассировка: CUJ-03, CUJ-09; ADR-0007; D-016, D-071
Источник: docs/research/03 §6.5 п. 4

#### Scenario: Попытка сохранить заметку
- **WHEN** клиент создаёт контакт с полем `note` = «звонить после 18:00»
- **THEN** операция отклоняется с ошибкой валидации, называющей поле `note`
- **AND** контакт не создаётся

### Requirement: CON-10 Создание контакта
Создание SHALL сохранять новый контакт с `version` = 1 и `created` = `updated` и возвращать его полное представление. Подтверждение создания MUST выдаваться клиенту только после долговечной фиксации (storage-engine).
Трассировка: CUJ-03, CUJ-07; ADR-0005, ADR-0007; D-019

#### Scenario: Успешное создание
- **WHEN** клиент создаёт контакт «Олег» с телефоном `+79001112233`
- **THEN** ответ содержит назначенный `id`, `version` = 1 и одинаковые `created` и `updated`

#### Scenario: Сбой после подтверждения
- **WHEN** создание подтверждено, а затем процесс аварийно завершается и перезапускается
- **THEN** контакт читается по своему `id` с теми же данными

### Requirement: CON-11 Чтение контакта
Чтение по `id` SHALL возвращать последнее зафиксированное состояние активного контакта. Для контакта в корзине, очищенного или несуществующего `id` чтение SHALL возвращать ошибку «не найден»; контакты в корзине доступны через CON-16.
Трассировка: CUJ-01, CUJ-05; ADR-0007; D-009, D-012

#### Scenario: Чтение активного контакта
- **WHEN** клиент читает существующий активный контакт
- **THEN** ответ содержит все поля CON-01 и телефоны со всеми полями CON-04

#### Scenario: Чтение контакта из корзины
- **WHEN** клиент читает по `id` контакт, удалённый в корзину
- **THEN** возвращается ошибка «не найден»

### Requirement: CON-12 Изменение контакта
Изменение SHALL атомарно заменять все изменяемые поля (`display_name`, части имени, `phones`) значениями из запроса; не переданные необязательные поля становятся пустыми [ПРЕДЛОЖЕНИЕ АГЕНТА]. При успехе `version` MUST увеличиваться ровно на 1, `updated` — обновляться, а `id` и `created` — не меняться.
Трассировка: CUJ-03, CUJ-05; ADR-0007, ADR-0010; D-009

#### Scenario: Замена телефонов
- **WHEN** контакт версии 3 с телефонами A и B изменяется запросом только с телефоном C
- **THEN** у контакта остаётся один телефон C и `version` = 4
- **AND** `created` не изменился, `updated` больше прежнего

### Requirement: CON-13 Проверка версии при изменении
Изменение, удаление в корзину и восстановление MUST требовать ожидаемую версию контакта. При несовпадении с текущей операция SHALL отклоняться ошибкой конфликта с текущей версией без изменения данных; без ожидаемой версии — ошибкой «требуется предусловие». Отображение на HTTP задаёт http-api.
Трассировка: CUJ-04, CUJ-05; ADR-0010; D-009, D-041
Источник: docs/research/03 §4.3

#### Scenario: Параллельная правка
- **WHEN** пользователи A и B прочитали контакт версии 3, A сохранил изменение (версия стала 4), затем B сохраняет своё с ожидаемой версией 3
- **THEN** операция B отклоняется ошибкой конфликта с текущей версией 4
- **AND** данные контакта равны сохранённым пользователем A

#### Scenario: Изменение без версии
- **WHEN** клиент изменяет контакт, не передав ожидаемую версию
- **THEN** операция отклоняется ошибкой «требуется предусловие», контакт не меняется

### Requirement: CON-14 Удаление в корзину
Удаление SHALL одной атомарной фиксацией переводить контакт в корзину: записывать `deleted_at`, увеличивать `version` на 1 и удалять записи контакта из индексов поиска по имени и телефону, так что поиск (SRCH-15) и чтение по `id` его не находят. Данные контакта в корзине MUST сохраняться без изменений до восстановления или очистки.
Трассировка: CUJ-03, CUJ-09; ADR-0012; D-012, D-064

#### Scenario: Удаление с верной версией
- **WHEN** клиент удаляет контакт версии 5 с ожидаемой версией 5
- **THEN** контакт находится в корзине с `deleted_at` и `version` = 6
- **AND** поиск по его имени и телефону его не возвращает

#### Scenario: Повторное удаление
- **WHEN** клиент удаляет контакт, который уже в корзине
- **THEN** возвращается ошибка «не найден»

### Requirement: CON-15 Восстановление из корзины
Writer и admin SHALL восстанавливать контакт из корзины до `purge_after` (CON-17): контакт снова активен с прежними `id`, именем и телефонами, `version` + 1, новым `updated` и возвращёнными записями индексов поиска. Восстановление активного контакта SHALL отклоняться ошибкой «не в корзине», очищенного или просроченного — ошибкой «не найден» [ПРЕДЛОЖЕНИЕ АГЕНТА: как в API-22].
Трассировка: CUJ-03; ADR-0012; D-012, D-041, D-064

#### Scenario: Успешное восстановление
- **WHEN** writer восстанавливает контакт из корзины с версией 6
- **THEN** контакт снова активен с `version` = 7 и находится поиском по имени и телефону

#### Scenario: Восстановление очищенного контакта
- **WHEN** клиент восстанавливает контакт, очищенный автоочисткой
- **THEN** возвращается ошибка «не найден»

#### Scenario: Восстановление активного контакта
- **WHEN** writer восстанавливает контакт, который не в корзине
- **THEN** возвращается ошибка «не в корзине», контакт не меняется

#### Scenario: Reader не восстанавливает
- **WHEN** reader пытается восстановить контакт из корзины
- **THEN** операция отклоняется по правам доступа (access-control), контакт остаётся в корзине

### Requirement: CON-16 Просмотр корзины
Writer и admin SHALL видеть постраничный список контактов в корзине с полями `id`, `display_name`, `version`, `deleted_at` и `purge_after`, упорядоченный по `deleted_at` от новых к старым [ПРЕДЛОЖЕНИЕ АГЕНТА]. Размер страницы и курсор — по SRCH-09, SRCH-10; reader MUST получать отказ по правам (access-control).
Трассировка: CUJ-03, CUJ-09; ADR-0012; D-012, D-041, D-047

#### Scenario: Порядок корзины
- **WHEN** контакт A удалён в 10:00, контакт B — в 11:00
- **THEN** список корзины возвращает B, затем A, у каждого указан `purge_after`

#### Scenario: Версия для восстановления
- **WHEN** writer получает список корзины
- **THEN** каждый элемент содержит `version`, которую можно передать как ожидаемую при восстановлении (CON-13)

### Requirement: CON-17 Окно восстановления из корзины
Контакт в корзине SHALL быть восстановимым строго до `purge_after` = `deleted_at` + срок хранения корзины (PRV-03: 1…28 дней, по умолчанию 7). Начиная с `purge_after` восстановление MUST отклоняться ошибкой «не найден», даже если автоочистка (PRV-04, не позднее 25 ч после `purge_after`) ещё не выполнена или система была остановлена.
Трассировка: CUJ-03, CUJ-09; ADR-0012; D-012, D-049, D-119

#### Scenario: Граница окна
- **WHEN** контакт удалён 2026-10-01 10:00:00 при сроке хранения 7 дней
- **THEN** 2026-10-08 09:59:59 его можно восстановить
- **AND** 2026-10-08 10:00:00 восстановление отклоняется ошибкой «не найден»

#### Scenario: Система была остановлена
- **WHEN** система остановлена до `purge_after` контакта в корзине и запущена после него
- **THEN** попытка восстановить этот контакт отклоняется ошибкой «не найден»

### Requirement: CON-18 Подсказка о возможных дубликатах
При создании и изменении система SHALL возвращать вместе с результатом до 10 активных контактов — возможных дубликатов: с тем же полным ключом имени (NAM-05) или хотя бы одним общим `e164`. Подсказка MUST NOT блокировать операцию; сам контакт в неё не входит.
Трассировка: CUJ-03; ADR-0007; D-009, D-051
Источник: docs/research/03 §3.1

#### Scenario: Похожее имя
- **WHEN** существует «Семёнов Пётр», а клиент создаёт «СЕМЕНОВ ПЕТР»
- **THEN** контакт создаётся
- **AND** подсказка содержит `id` контакта «Семёнов Пётр»

#### Scenario: Совпадений нет
- **WHEN** клиент создаёт контакт с уникальным именем и телефоном
- **THEN** контакт создаётся, подсказка пуста

### Requirement: CON-19 Служебные метаданные
`created` и `updated` SHALL выставляться системой в UTC с точностью до миллисекунды [ПРЕДЛОЖЕНИЕ АГЕНТА]; `updated` MUST меняться при изменении, удалении в корзину и восстановлении как max(now, прежний `updated`) и не быть меньше `created`. Поля только для чтения (`id`, `version`, `created`, `updated`, `deleted_at`, `purge_after`) во входных данных создания, изменения и импорта SHALL игнорироваться без ошибки.
Трассировка: CUJ-03, CUJ-05, CUJ-06; ADR-0007; D-009, D-071

#### Scenario: Клиент подставляет created
- **WHEN** клиент создаёт контакт с `created` = `2000-01-01T00:00:00Z`
- **THEN** сохранённый `created` равен моменту создания, а не переданному значению

#### Scenario: Тело из ответа чтения
- **WHEN** клиент изменяет контакт `id` 9 с ожидаемой версией 5, передав тело, где `id` = `"7"` и `version` = 3
- **THEN** изменяется контакт 9 со сверкой по версии 5, значения `id` и `version` из тела не применяются, ошибки нет

#### Scenario: Часы ушли назад
- **WHEN** контакт изменён в 12:00, затем системные часы откатились на 1 ч, и контакт изменён снова
- **THEN** новый `updated` не меньше прежнего значения (12:00) и не меньше `created`
