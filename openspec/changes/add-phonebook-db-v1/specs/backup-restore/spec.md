# backup-restore

## Purpose
Онлайн-бэкап, проверка бэкапа, восстановление с атомарной подменой файла, проверка целостности и офлайн-компактизация BUDB, чтобы администратор мог пережить сбой или потерю носителя без потери подтверждённых данных и без «воскрешения» удалённых ПДн.

## ADDED Requirements

### Requirement: BKP-01 Онлайн-бэкап из MVCC-снимка
Команда бэкапа SHALL создавать согласованную копию БД на снимке последнего подтверждённого txid в момент старта, не останавливая приём записей. Записи, зафиксированные во время бэкапа, MUST NOT попадать в него частично.
Трассировка: CUJ-07; ADR-0013, ADR-0003; D-025, D-018
Источник: docs/research/02 §9 Q9

#### Scenario: Бэкап под нагрузкой записи
- **WHEN** бэкап стартует на снимке txid 1000, а за время его работы фиксируются txid 1001–1500
- **THEN** бэкап содержит ровно состояние txid 1000
- **AND** ни одна запись за время бэкапа не получает отказа из-за бэкапа

### Requirement: BKP-02 Формат файла бэкапа
Файл бэкапа SHALL быть самодостаточным файлом БД в формате STO-01…STO-04, содержащим только страницы, достижимые из снимка, и мета-страницу с txid снимка и временем создания. [ПРЕДЛОЖЕНИЕ АГЕНТА: бэкап — компактная копия живых страниц, а не побайтная копия файла.]
Трассировка: CUJ-07; ADR-0013; D-025

#### Scenario: Открытие бэкапа как БД
- **WHEN** офлайн-проверка целостности запускается прямо на файле бэкапа
- **THEN** файл открывается как БД с txid снимка и проходит проверку

#### Scenario: Размер бэкапа
- **WHEN** бэкап делается с файла, где половина страниц свободна
- **THEN** размер бэкапа не превышает объём живых страниц плюс страницы заголовка и мета-страниц

### Requirement: BKP-03 Атомарная и долговечная запись бэкапа
Бэкап SHALL записываться во временный файл, затем сбрасываться на устройство, переименовываться в итоговое имя и сопровождаться сбросом каталога по STO-15. Файл с итоговым именем MUST существовать только у полностью записанного бэкапа.
Трассировка: CUJ-07; ADR-0013, ADR-0005; D-019, D-025

#### Scenario: Сбой во время бэкапа
- **WHEN** процесс убит, когда записана половина бэкапа
- **THEN** файла с итоговым именем бэкапа нет, а временный файл удаляется при следующем запуске бэкапа

#### Scenario: Нет места на диске
- **WHEN** во время записи бэкапа запись возвращает ENOSPC
- **THEN** бэкап завершается ошибкой, временный файл удаляется, а работа основной БД продолжается

### Requirement: BKP-04 Проверка созданного бэкапа
По завершении записи команда бэкапа SHALL проверять созданный файл по BKP-08 и сообщать успех только после прохождения проверки. Время последнего успешного бэкапа (OBS-11) MUST обновляться только после неё. [ПРЕДЛОЖЕНИЕ АГЕНТА]
Трассировка: CUJ-07, CUJ-08; ADR-0013; D-025

#### Scenario: Бэкап прошёл проверку
- **WHEN** бэкап записан и проверка не нашла ошибок
- **THEN** команда завершается с кодом 0 и печатает txid, время и размер бэкапа

#### Scenario: Бэкап испорчен при записи
- **WHEN** в симуляции одна страница бэкапа записана с ошибкой
- **THEN** команда завершается с ненулевым кодом, бэкап не считается успешным, а метрика времени последнего бэкапа не меняется

### Requirement: BKP-05 Восстановление в новый файл с атомарной подменой
Восстановление SHALL выполняться при остановленном сервере: бэкап копируется в новый файл рядом с рабочим, проверяется по BKP-08, сбрасывается, атомарно переименовывается поверх рабочего, затем сбрасывается каталог. При сбое на любом шаге рабочий файл MUST остаться либо прежним, либо новым целиком.
Трассировка: CUJ-07; ADR-0013, ADR-0005; D-025, D-019

#### Scenario: Успешное восстановление
- **WHEN** администратор восстанавливает БД из проверенного бэкапа txid 1000
- **THEN** после запуска сервера видно состояние txid 1000 с учётом BKP-07

#### Scenario: Сбой до переименования
- **WHEN** процесс восстановления убит до rename
- **THEN** рабочий файл БД побайтно совпадает с прежним

#### Scenario: Сервер запущен
- **WHEN** восстановление запускается, пока сервер держит блокировку БД по STO-20
- **THEN** восстановление отказывается работать и рабочий файл не меняется

### Requirement: BKP-06 Отказ восстанавливать из негодного бэкапа
Восстановление MUST отказать, если бэкап не проходит проверку целостности, имеет неподдерживаемую версию формата или не является файлом BUDB. Рабочий файл БД при этом SHALL оставаться неизменным.
Трассировка: CUJ-07; ADR-0013; D-025, D-019

#### Scenario: Повреждённый бэкап
- **WHEN** в бэкапе повреждена одна страница данных
- **THEN** восстановление завершается ошибкой с номером страницы, и рабочий файл не меняется

### Requirement: BKP-07 Повторное применение журнала purge после восстановления
После восстановления и до первого открытия БД для клиентов система MUST повторно применить журнал purge (data-privacy): контакты, очищенные после создания бэкапа, физически удаляются. Если журнал purge недоступен, восстановление SHALL отказать [ПРЕДЛОЖЕНИЕ АГЕНТА: журнал хранится в отдельном файле рядом с БД].
Трассировка: CUJ-07, CUJ-09; ADR-0012, ADR-0013; D-012, D-025
Источник: docs/research/03 §6.5 п. 2

#### Scenario: Purge после бэкапа
- **WHEN** контакт X очищен по запросу субъекта после бэкапа txid 1000, и БД восстанавливается из этого бэкапа
- **THEN** после восстановления X не находится ни поиском, ни сканированием байтов файла БД

#### Scenario: Журнал purge отсутствует
- **WHEN** при восстановлении файл журнала purge не найден и путь к его копии не задан
- **THEN** восстановление завершается ошибкой, и рабочий файл не меняется

### Requirement: BKP-08 Офлайн-проверка целостности
Команда `verify` SHALL проверять закрытый файл БД или бэкап: CRC32C всех страниц, обе мета-страницы, порядок ключей в каждом дереве, взаимное соответствие трёх деревьев и учёт каждой страницы как достижимой либо свободной. Она MUST открывать файл только на чтение.
Трассировка: CUJ-07, CUJ-08; ADR-0015, ADR-0013; D-025, D-026
Источник: docs/research/02 §4 (офлайн-верификатор)

#### Scenario: Целый файл
- **WHEN** `verify` запускается на файле без повреждений
- **THEN** код выхода 0, а отчёт содержит txid, число контактов, страниц и свободных страниц

#### Scenario: Потерянная страница
- **WHEN** страница не достижима ни из деревьев, ни из списка свободных страниц
- **THEN** `verify` сообщает об утечке страницы с её номером и завершается с ненулевым кодом

### Requirement: BKP-09 Отчёт verify без ПДн и без изменения файла
При обнаружении повреждения `verify` SHALL завершаться ненулевым кодом и перечислять номера страниц и виды нарушений. Отчёт MUST NOT содержать имён и телефонов, а файл MUST NOT меняться: `verify` ничего не чинит.
Трассировка: CUJ-07, CUJ-09; ADR-0015; D-025, D-013

#### Scenario: Индекс ссылается на несуществующий id
- **WHEN** в `phone_idx` есть ключ с id, которого нет в primary
- **THEN** отчёт содержит номер страницы и id, но не цифры телефона
- **AND** хеш файла после проверки совпадает с исходным

### Requirement: BKP-10 Онлайн-проверка целостности
Сервер SHALL выполнять проверку целостности BKP-08 на MVCC-снимке без остановки записи по команде администратора. Результат и время проверки MUST публиковаться в метриках по OBS-11; найденное повреждение переводит движок в fail-stop по STO-19.
Трассировка: CUJ-07, CUJ-08; ADR-0013, ADR-0015; D-025

#### Scenario: Проверка под нагрузкой
- **WHEN** онлайн-проверка идёт на снимке txid 500, а клиенты фиксируют новые записи
- **THEN** записи продолжают подтверждаться, а проверка завершается с результатом по txid 500

### Requirement: BKP-11 Офлайн-компактизация
Команда компактизации SHALL при остановленном сервере копировать живые страницы в новый файл, сбрасывать его, атомарно переименовывать поверх рабочего и сбрасывать каталог. При сбое на любом шаге рабочий файл MUST остаться прежним либо новым целиком.
Трассировка: CUJ-07, CUJ-08; ADR-0003, ADR-0005; D-018, D-019
Источник: docs/research/02 §2.4 п. 6

#### Scenario: Уменьшение файла
- **WHEN** после удаления 50 % контактов и очистки корзины выполняется компактизация
- **THEN** размер файла уменьшается до объёма живых страниц плюс служебные страницы, а набор контактов и txid не меняются

#### Scenario: Сбой между fsync и rename
- **WHEN** процесс убит после сброса нового файла, но до rename
- **THEN** при следующем запуске открывается прежний рабочий файл, и он проходит verify

### Requirement: BKP-12 Ротация бэкапов и срок хранения ПДн
Система SHALL удалять бэкапы старше настроенного срока хранения со сбросом каталога после удаления. Срок MUST NOT превышать 180 дней (152-ФЗ, ст. 21 ч. 6). [ПРЕДЛОЖЕНИЕ АГЕНТА: по умолчанию 30 дней.]
Трассировка: CUJ-07, CUJ-09; ADR-0013, ADR-0012; D-012, D-025
Источник: docs/research/03 §6.5 (ст. 21 ч. 6), п. 2

#### Scenario: Истёк срок бэкапа
- **WHEN** срок хранения 30 дней, а в каталоге бэкапов есть бэкап 31-дневной давности
- **THEN** при очередной ротации он удаляется, а более новые бэкапы сохраняются

#### Scenario: Недопустимый срок
- **WHEN** в конфигурации задан срок хранения бэкапов 365 дней
- **THEN** процесс не запускается и сообщает о верхней границе 180 дней
