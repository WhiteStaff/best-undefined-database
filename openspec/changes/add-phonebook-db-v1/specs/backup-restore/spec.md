# backup-restore

## Purpose
Онлайн-бэкап, проверка бэкапа, восстановление с атомарной подменой файла, проверка целостности и офлайн-компактизация BUDB, чтобы администратор мог пережить сбой или потерю носителя без потери подтверждённых данных и без «воскрешения» удалённых ПДн.

## ADDED Requirements

### Requirement: BKP-01 Онлайн-бэкап из MVCC-снимка
Команда бэкапа SHALL создавать согласованную копию БД на снимке последнего подтверждённого txid в момент старта, не останавливая приём записей. Записи, зафиксированные во время бэкапа, MUST NOT попадать в него частично. Если снимок отозван по STO-24 или STO-32, бэкап MUST перезапускаться на новом снимке.
Трассировка: CUJ-07; ADR-0013, ADR-0003; D-025, D-018, D-056, D-093
Источник: docs/research/02 §9 Q9

#### Scenario: Бэкап под нагрузкой записи
- **WHEN** бэкап стартует на снимке txid 1000, а за время его работы фиксируются txid 1001–1500
- **THEN** бэкап содержит ровно состояние txid 1000
- **AND** ни одна запись за время бэкапа не получает отказа из-за бэкапа

#### Scenario: Отзыв снимка бэкапа
- **WHEN** снимок идущего бэкапа отозван с ошибкой `snapshot-expired`
- **THEN** временный файл удаляется, бэкап начинается заново на снимке последнего подтверждённого txid, а метрика времени последнего бэкапа не меняется до его успеха

### Requirement: BKP-02 Формат файла бэкапа
Бэкап SHALL состоять из пары файлов: `<ts>.budb` — самодостаточный файл БД в формате STO-01…STO-04 со страницами, достижимыми из снимка, и двумя одинаковыми мета-страницами с txid снимка и временем создания; `<ts>.purge` — копия журнала purge на момент снимка. [ПРЕДЛОЖЕНИЕ АГЕНТА: компактная копия живых страниц.]
Трассировка: CUJ-07; ADR-0013; D-025, D-036, D-063

#### Scenario: Открытие бэкапа как БД
- **WHEN** офлайн-проверка целостности запускается прямо на файле бэкапа
- **THEN** файл открывается как БД с txid снимка и проходит проверку

#### Scenario: Оба слота мета-страниц
- **WHEN** открывается файл бэкапа
- **THEN** оба слота валидны и содержат один txid, поэтому выбирается слот A без события отката и без роста `budb_meta_fallback_total`

#### Scenario: Размер бэкапа
- **WHEN** бэкап делается с файла, где половина страниц свободна
- **THEN** размер бэкапа не превышает объём живых страниц плюс страницы заголовка и мета-страниц

### Requirement: BKP-03 Атомарная и долговечная запись бэкапа
Бэкап SHALL записываться во временный файл, затем сбрасываться на устройство, переименовываться в итоговое имя и сопровождаться сбросом каталога по STO-15. Файл с итоговым именем MUST существовать только у полностью записанного бэкапа. Файлы бэкапа MUST создаваться с правами только для владельца. [ПРЕДЛОЖЕНИЕ АГЕНТА: 0600 на POSIX.]
Трассировка: CUJ-07; ADR-0013, ADR-0005; D-019, D-025

#### Scenario: Сбой во время бэкапа
- **WHEN** процесс убит, когда записана половина бэкапа
- **THEN** файла с итоговым именем бэкапа нет, а временный файл удаляется при следующем запуске бэкапа

#### Scenario: Нет места на диске
- **WHEN** во время записи бэкапа запись возвращает ENOSPC
- **THEN** бэкап завершается ошибкой, временный файл удаляется, а работа основной БД продолжается

#### Scenario: Права на файлы бэкапа
- **WHEN** на Linux создан бэкап
- **THEN** файлы `<ts>.budb` и `<ts>.purge` доступны на чтение и запись только владельцу процесса

### Requirement: BKP-04 Проверка созданного бэкапа
По завершении записи команда бэкапа SHALL проверить файл по BKP-08 и сверить его со снимком: число записей в каждом дереве и скользящую контрольную сумму логических записей, вычисленные при копировании. Успех и время последнего успешного бэкапа (OBS-11) MUST фиксироваться только после обеих проверок.
Трассировка: CUJ-07, CUJ-08; ADR-0013; D-025, D-096

#### Scenario: Бэкап прошёл проверку
- **WHEN** бэкап записан, проверка не нашла ошибок, а число записей и контрольные суммы совпали со снимком
- **THEN** команда завершается с кодом 0 и печатает txid, время и размер бэкапа

#### Scenario: Бэкап испорчен при записи
- **WHEN** в симуляции одна страница бэкапа записана с ошибкой
- **THEN** команда завершается с ненулевым кодом, бэкап не считается успешным, а метрика времени последнего бэкапа не меняется

#### Scenario: Согласованный, но неверный бэкап
- **WHEN** в симуляции копирование потеряло одну запись `primary`, а бэкап внутренне согласован и проходит BKP-08
- **THEN** сверка числа записей и контрольной суммы со снимком не проходит, и команда завершается с ненулевым кодом

### Requirement: BKP-05 Восстановление в новый файл с атомарной подменой
Восстановление SHALL выполняться при остановленном сервере: бэкап копируется в новый файл рядом с рабочим, проверяется по BKP-08, сбрасывается, атомарно переименовывается поверх рабочего, затем сбрасывается каталог. При сбое на любом шаге рабочий файл MUST остаться либо прежним, либо новым целиком.
Трассировка: CUJ-07; ADR-0013, ADR-0005; D-025, D-019

#### Scenario: Успешное восстановление
- **WHEN** администратор восстанавливает БД из проверенного бэкапа txid 1000
- **THEN** после запуска сервера видно состояние txid 1000 с учётом BKP-07, BKP-13, BKP-14 и BKP-15

#### Scenario: Сбой до переименования
- **WHEN** процесс восстановления убит до rename
- **THEN** рабочий файл БД побайтно совпадает с прежним

#### Scenario: Сервер запущен
- **WHEN** восстановление запускается, пока сервер держит блокировку БД по STO-20
- **THEN** восстановление отказывается работать и рабочий файл не меняется

### Requirement: BKP-06 Отказ восстанавливать из негодного бэкапа
Восстановление MUST отказать, если бэкап не проходит проверку целостности, имеет неподдерживаемую версию формата или не является файлом BUDB. Рабочий файл БД при этом SHALL оставаться неизменным.
Трассировка: CUJ-07; ADR-0013; D-025, D-019

#### Scenario: Повреждённый бэкап
- **WHEN** в бэкапе повреждена одна страница данных
- **THEN** восстановление завершается ошибкой с номером страницы, и рабочий файл не меняется

### Requirement: BKP-07 Повторное применение журнала purge после восстановления
До открытия восстановленной БД для клиентов restore MUST применить объединение всех доступных журналов purge (`<ts>.purge`, копия в каталоге бэкапов, `--purge-journal`) с затиранием до rename. Запись SHALL применяться, только если совпадают `contact_id` и `created_at`. [ПРЕДЛОЖЕНИЕ АГЕНТА: записи «pending» тоже применяются.]
Трассировка: CUJ-07, CUJ-09; ADR-0012, ADR-0013; D-012, D-036, D-042, D-075, D-076
Источник: docs/research/03 §6.5 п. 2

#### Scenario: Purge после бэкапа
- **WHEN** контакт X очищен по запросу субъекта после бэкапа txid 1000, и БД восстанавливается из этого бэкапа
- **THEN** после восстановления X не находится ни поиском, ни сканированием байтов файла БД

#### Scenario: Журнал purge отсутствует
- **WHEN** при восстановлении нет ни одного журнала purge и не задан `--accept-purge-gap`
- **THEN** восстановление завершается ошибкой, и рабочий файл не меняется

#### Scenario: Несовпадение created_at
- **WHEN** журнал purge содержит запись (`id` 1050, `created_at` C1), а у контакта 1050 в бэкапе `created_at` C2 ≠ C1
- **THEN** контакт 1050 не удаляется, а в отчёт restore попадает предупреждение без ПДн

### Requirement: BKP-08 Офлайн-проверка целостности
Команда `verify` SHALL только на чтение проверять закрытый файл БД или бэкап: CRC32C, `page_no` и `write_txid` страниц (STO-03, STO-25), обе мета-страницы, порядок ключей и отсутствие циклов в деревьях, соответствие деревьев по STO-06 и вхождение каждой страницы < `page_count` ровно в одно множество STO-27.
Трассировка: CUJ-07, CUJ-08; ADR-0015, ADR-0013; D-025, D-026, D-085, D-086, D-091
Источник: docs/research/02 §4 (офлайн-верификатор)

#### Scenario: Целый файл
- **WHEN** `verify` запускается на файле без повреждений
- **THEN** код выхода 0, а отчёт содержит txid, число контактов, страниц, свободных и отложенных страниц

#### Scenario: Потерянная страница
- **WHEN** страница с номером < `page_count` не входит ни в одно из множеств STO-27
- **THEN** `verify` сообщает об утечке страницы с её номером и завершается с ненулевым кодом

#### Scenario: Цикл в дереве
- **WHEN** ветвь ссылается на свою страницу-предка
- **THEN** `verify` сообщает о цикле с номерами страниц и завершается с ненулевым кодом, не зависая

### Requirement: BKP-09 Отчёт verify без ПДн и без изменения файла
При обнаружении повреждения `verify` SHALL завершаться ненулевым кодом и перечислять номера страниц и виды нарушений. Отчёт MUST NOT содержать имён и телефонов, а файл MUST NOT меняться: `verify` ничего не чинит.
Трассировка: CUJ-07, CUJ-09; ADR-0015; D-025, D-013

#### Scenario: Индекс ссылается на несуществующий id
- **WHEN** в `phone_idx` есть ключ с id, которого нет в primary
- **THEN** отчёт содержит номер страницы и id, но не цифры телефона
- **AND** хеш файла после проверки совпадает с исходным

### Requirement: BKP-10 Онлайн-проверка целостности
Сервер SHALL по команде администратора выполнять проверку BKP-08 на MVCC-снимке без остановки записи, читая страницы с диска в обход собственного кэша. Результат и время MUST публиковаться по OBS-11; найденное повреждение переводит движок в degraded-read-only по STO-35. [ПРЕДЛОЖЕНИЕ АГЕНТА: O_DIRECT на Linux, иначе ограничение кэша ОС документируется.]
Трассировка: CUJ-07, CUJ-08; ADR-0013, ADR-0015; D-025, D-078, D-089

#### Scenario: Проверка под нагрузкой
- **WHEN** онлайн-проверка идёт на снимке txid 500, а клиенты фиксируют новые записи
- **THEN** записи продолжают подтверждаться, а проверка завершается с результатом по txid 500

#### Scenario: Повреждение при онлайн-проверке
- **WHEN** онлайн-проверка нашла страницу с неверной CRC32C
- **THEN** движок переходит в degraded-read-only, записи получают 503, а чтения продолжают обслуживаться

### Requirement: BKP-11 Офлайн-компактизация
Команда компактизации SHALL при остановленном сервере копировать живые страницы в новый файл, сбрасывать его, атомарно переименовывать поверх рабочего и сбрасывать каталог. При сбое на любом шаге рабочий файл MUST остаться прежним либо новым целиком. Компактизация MUST сохранять txid и `db_lineage_id` (STO-38).
Трассировка: CUJ-07, CUJ-08; ADR-0003, ADR-0005; D-018, D-019, D-095
Источник: docs/research/02 §2.4 п. 6

#### Scenario: Уменьшение файла
- **WHEN** после удаления 50 % контактов и очистки корзины выполняется компактизация
- **THEN** размер файла уменьшается до объёма живых страниц плюс служебные страницы, а набор контактов, txid и `db_lineage_id` не меняются

#### Scenario: Сбой между fsync и rename
- **WHEN** процесс убит после сброса нового файла, но до rename
- **THEN** при следующем запуске открывается прежний рабочий файл, и он проходит verify

### Requirement: BKP-12 Ротация бэкапов и срок хранения ПДн
Система SHALL удалять бэкапы старше срока хранения (по умолчанию 30 дней) со сбросом каталога. Срок MUST NOT превышать 180 дней (152-ФЗ, ст. 21 ч. 6). Если системные часы расходятся с монотонными больше чем на 1 ч, ротация MUST приостанавливаться до подтверждения администратора (OBS-21, API-41).
Трассировка: CUJ-07, CUJ-09; ADR-0013, ADR-0012; D-012, D-025, D-037, D-081, D-117
Источник: docs/research/03 §6.5 (ст. 21 ч. 6), п. 2

#### Scenario: Истёк срок бэкапа
- **WHEN** срок хранения 30 дней, а в каталоге бэкапов есть бэкап 31-дневной давности
- **THEN** при очередной ротации он удаляется, а более новые бэкапы сохраняются

#### Scenario: Недопустимый срок
- **WHEN** в конфигурации задан срок хранения бэкапов 365 дней
- **THEN** процесс не запускается и сообщает о верхней границе 180 дней

#### Scenario: Скачок часов вперёд
- **WHEN** системные часы скачком ушли на 400 дней вперёд относительно монотонных
- **THEN** ни один бэкап не удаляется, поднимается алерт, и ротация ждёт подтверждения администратора

### Requirement: BKP-13 next_contact_id после восстановления
После restore `next_contact_id` SHALL быть равен максимуму из трёх значений: значение в бэкапе; наибольший `contact_id` в применённых журналах purge + 1; наибольший `contact_id` в журнале аудита + 1. Restore MUST NOT допускать повторной выдачи `id`, выданного до restore.
Трассировка: CUJ-03, CUJ-07; ADR-0007, ADR-0013; D-057, D-075

#### Scenario: Id, выданный после бэкапа
- **WHEN** после бэкапа B1 (`next_contact_id` 1050) создан и очищен контакт 1050, и БД восстановлена из B1
- **THEN** следующий созданный контакт получает `id` не меньше 1051

### Requirement: BKP-14 Новая линия БД после восстановления
Restore SHALL задавать восстановленному файлу новый `db_lineage_id` (STO-38) и писать событие аудита «restore» со старой и новой линией и txid до и после. Компенсирующие записи «rolled_back» MUST относиться только к намерениям прерванного запуска той же линии с txid больше восстановленного (PRV-20).
Трассировка: CUJ-07, CUJ-09; ADR-0013, ADR-0012; D-080, D-095

#### Scenario: Restore к более раннему txid
- **WHEN** БД с последним txid 2000 восстановлена из бэкапа txid 1000
- **THEN** события аудита txid 1001–2000 прежней линии не помечаются «rolled_back», а новые транзакции пишутся с новым `db_lineage_id`

### Requirement: BKP-15 Отзыв токенов и сессий после восстановления
После restore все API-токены и сессии SHALL считаться отозванными, и об этом пишется событие аудита. Учётные записи и пароли из бэкапа MUST сохраняться; администратор выпускает токены заново. Вход пользователей — по ACL-27: блокируется до подтверждения, кроме admin, выполнившего restore.
Трассировка: CUJ-07, CUJ-10; ADR-0011, ADR-0013; D-079, D-117

#### Scenario: Токен из бэкапа
- **WHEN** после restore клиент обращается к API с токеном, который был действителен в бэкапе
- **THEN** ответ 401

#### Scenario: Вход после restore
- **WHEN** после restore с `--as-admin root` пользователи `root` и `anna` вводят верные логин и пароль из бэкапа
- **THEN** вход `root` работает, а вход `anna` отклонён до подтверждения admin (ACL-27)

### Requirement: BKP-16 Отказ при неподтверждённой актуальности журнала purge
Restore SHALL брать актуальный журнал purge из каталога бэкапов (он дописывается при каждом purge) или из `--purge-journal`. Если актуальность доказать нельзя (каталог не настроен или недоступен и `--purge-journal` не задан), restore MUST отказать без флага `--accept-purge-gap`; с флагом он пишет событие аудита. Недоставленные копии purge (OBS-23) делают каталог неактуальным: нужен `--purge-journal`.
Трассировка: CUJ-07, CUJ-09; ADR-0012, ADR-0013; D-036, D-069, D-120

#### Scenario: Новая машина только с бэкапом
- **WHEN** на новой машине есть только `<ts>.budb` и `<ts>.purge`, каталог бэкапов недоступен, и флаги не заданы
- **THEN** restore отказывает и называет `--purge-journal` и `--accept-purge-gap`, а рабочий файл не меняется

#### Scenario: Недоставленная копия purge
- **WHEN** сработал алерт OBS-23, и оператор запускает restore из каталога бэкапов без `--purge-journal`
- **THEN** руководство оператора требует основной `purge.journal` в `--purge-journal`; без него применяется только разрыв по `--accept-purge-gap`

#### Scenario: Явное согласие на разрыв
- **WHEN** тот же restore запущен с `--accept-purge-gap`
- **THEN** восстановление выполняется с применением `<ts>.purge`, и в журнал аудита пишется событие о разрыве журнала purge

### Requirement: BKP-17 Периодический бэкап
Сервер SHALL выполнять встроенный бэкап по расписанию (`backup_interval_hours`, по умолчанию 24, CLI-18) в настроенный каталог бэкапов [ПРЕДЛОЖЕНИЕ АГЕНТА: RPO при потере носителя ≤ 24 ч]. Возраст последнего успешного бэкапа MUST публиковаться по OBS-11, а превышение порога — входить в правила алертов OBS-20.
Трассировка: CUJ-07, CUJ-08; ADR-0013; D-025, D-118
Источник: docs/reviews/round1-goldfish-critic.md GF2-17

#### Scenario: Бэкап по расписанию
- **WHEN** сервер работает 49 ч с расписанием раз в 24 ч
- **THEN** в каталоге бэкапов есть два новых проверенных бэкапа, и метрика времени последнего бэкапа обновлялась после каждого
