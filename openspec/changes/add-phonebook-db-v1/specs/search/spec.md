# search

## Purpose

Определяет поиск BUDB: контакты по телефону (точно и по префиксу цифр E.164) и по имени (точно и по префиксу ключа), порядок выдачи, пагинацию курсором на одном согласованном снимке, лимиты и видимость записей. Целевые задержки поиска задаёт performance-capacity (PERF).

## ADDED Requirements

### Requirement: SRCH-01 Точный поиск по телефону
Система SHALL нормализовать запрос по phone-normalization (с регионом операции или по умолчанию) и возвращать все активные контакты, у которых есть телефон с тем же `e164` при любом `extension`. Каждый контакт MUST входить в результат не более одного раза; добавочный номер в запросе не учитывается [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-01, CUJ-05; ADR-0008; D-009, D-010
Источник: docs/research/03 §4.7, §8.1

#### Scenario: Кто звонит с семейного номера
- **WHEN** контакты «Иван Петров» и «Мария Петрова» имеют телефон `+74951234567`, и выполняется поиск `8 (495) 123-45-67` при регионе RU
- **THEN** результат содержит оба контакта, каждый один раз

#### Scenario: Добавочный номер не мешает
- **WHEN** у контакта сохранён `+74951234567` с `extension` = `101`, и выполняется поиск `+74951234567`
- **THEN** результат содержит этот контакт

### Requirement: SRCH-02 Недопустимый телефон в запросе
Если запрос точного поиска по телефону не проходит нормализацию, система SHALL возвращать ошибку валидации с кодом из PHN-14 и MUST NOT возвращать вместо неё пустой результат.
Трассировка: CUJ-01, CUJ-05; ADR-0008, ADR-0010; D-010

#### Scenario: Слишком короткий номер
- **WHEN** выполняется точный поиск по телефону `12`
- **THEN** возвращается ошибка валидации с кодом `phone.invalid_length`

### Requirement: SRCH-03 Префиксный поиск по телефону
Префикс телефона SHALL пониматься как начальные цифры `e164`, начиная с кода страны: допускаются ведущий `+` и разделители PHN-03, национальные форматы и регион не применяются. Результат — пары «совпавший `e164` + контакт»; контакт с двумя подходящими номерами входит дважды [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-01, CUJ-05; ADR-0008; D-010, D-011
Источник: docs/research/02 §8 ADR-005

#### Scenario: Префикс с кодом страны
- **WHEN** выполняется поиск по префиксу `+7 912` и есть телефоны `+79123456789`, `+79129998877`, `+74951234567`
- **THEN** результат содержит пары для `+79123456789` и `+79129998877`, но не для `+74951234567`

#### Scenario: Национальный префикс не преобразуется
- **WHEN** выполняется поиск по префиксу `8912`
- **THEN** ищутся номера, начинающиеся с `+8912`, а не с `+7912`

#### Scenario: Два номера одного контакта
- **WHEN** у контакта есть `+79121111111` и `+79122222222`, и выполняется поиск по префиксу `+7912`
- **THEN** контакт входит в результат дважды, с каждым совпавшим `e164`

### Requirement: SRCH-04 Точный поиск по имени
Система SHALL возвращать активные контакты, ключ `display_name` которых (NAM-05) равен ключу запроса (NAM-12). Поиск по `given_name`, `family_name` и `middle_name` в v1 MUST NOT выполняться [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-02, CUJ-05; ADR-0009; D-011

#### Scenario: Совпадение без учёта регистра и ё
- **WHEN** выполняется точный поиск «семенов пётр», а в базе есть «Семёнов Пётр» и «Семёнов Пётр Ильич»
- **THEN** результат содержит только «Семёнов Пётр»

### Requirement: SRCH-05 Префиксный поиск по имени
Система SHALL возвращать активные контакты, ключ `display_name` которых начинается с ключа запроса; совпадение MUST проверяться по целым кодовым точкам ключа.
Трассировка: CUJ-02, CUJ-05; ADR-0009; D-011

#### Scenario: Начало фамилии
- **WHEN** выполняется поиск по префиксу «Сем», а в базе есть «Семёнов», «семенова» и «Иван Семёнов»
- **THEN** результат содержит «Семёнов» и «семенова», но не «Иван Семёнов»

#### Scenario: Префикс после полной свёртки
- **WHEN** выполняется поиск по префиксу «Straß», а в базе есть «Straße»
- **THEN** результат содержит «Straße» (ключ запроса «strass» — префикс ключа «strasse»)

### Requirement: SRCH-06 Границы длины запроса
Префикс телефона MUST содержать от 3 до 15 цифр, а ключ префикса имени — не менее 1 кодовой точки [ПРЕДЛОЖЕНИЕ АГЕНТА]; строка запроса по имени MUST быть не длиннее 256 кодовых точек (CON-03). Запрос вне этих границ SHALL отклоняться с ошибкой валидации, а не давать пустой результат.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-022
Источник: docs/research/03 §4.7, §6.1 (API4)

#### Scenario: Короткий префикс телефона
- **WHEN** выполняется поиск по префиксу телефона `+7`
- **THEN** возвращается ошибка валидации

#### Scenario: Пустой префикс имени
- **WHEN** выполняется поиск по префиксу имени из одних пробелов
- **THEN** возвращается ошибка валидации

#### Scenario: Одна буква
- **WHEN** выполняется поиск по префиксу имени «А»
- **THEN** поиск выполняется и возвращает контакты, ключ которых начинается с «а»

### Requirement: SRCH-07 Состав результата поиска
Каждый элемент результата SHALL содержать полное представление контакта, как при чтении по `id` (CON-11): `id`, имя и его части, все телефоны с полями CON-04 и `version`. В префиксном поиске по телефону элемент MUST дополнительно содержать совпавший `e164`.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0007; D-009

#### Scenario: Телефоны в результате поиска по имени
- **WHEN** поиск по имени находит контакт с двумя телефонами
- **THEN** элемент результата содержит оба телефона с `e164`, `label` и `is_primary`

### Requirement: SRCH-08 Порядок выдачи
Результаты поиска по имени SHALL упорядочиваться по возрастанию ключа имени в побайтовом сравнении UTF-8, при равных ключах — по возрастанию `id`. Результаты поиска по телефону SHALL упорядочиваться по цифрам `e164`, затем по `id`. Сортировка по правилам языка (UCA) MUST NOT применяться.
Трассировка: CUJ-01, CUJ-02; ADR-0009; D-011
Источник: docs/research/03 §2.5

#### Scenario: Одинаковые ключи
- **WHEN** «Анна» имеет `id` A, «АННА» — `id` B, и A < B
- **THEN** «Анна» выдаётся раньше «АННА»

#### Scenario: Порядок по телефону
- **WHEN** поиск по префиксу `+7912` находит `+79125550000` у контакта с `id` 9 и `+79121110000` у контактов с `id` 3 и 2
- **THEN** порядок выдачи: (`+79121110000`, 2), (`+79121110000`, 3), (`+79125550000`, 9)

#### Scenario: Место «ё»
- **WHEN** в результат входят «Ежов», «Ёлкин» и «Жуков»
- **THEN** порядок выдачи: «Ежов», «Ёлкин», «Жуков»

### Requirement: SRCH-09 Размер страницы
Размер страницы SHALL быть равен 20, если он не указан или равен 0, и не более 100: большее значение MUST уменьшаться до 100, а отрицательное — отклоняться с ошибкой валидации.
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-024
Источник: docs/research/03 §4.4, §6.1 (API4)

#### Scenario: Размер по умолчанию
- **WHEN** поиск находит 35 контактов, а размер страницы не указан
- **THEN** первая страница содержит 20 элементов

#### Scenario: Слишком большой размер
- **WHEN** запрошен размер страницы 1000
- **THEN** страница содержит не более 100 элементов

#### Scenario: Отрицательный размер
- **WHEN** запрошен размер страницы −5
- **THEN** возвращается ошибка валидации

### Requirement: SRCH-10 Курсор пагинации
Если результатов больше, чем поместилось на страницу, ответ SHALL содержать непрозрачный курсор следующей страницы; его отсутствие означает конец выдачи. Курсор MUST быть защищён от подделки и не раскрывать имена и телефоны в открытом виде; запрос с курсором и изменёнными параметрами поиска SHALL отклоняться с ошибкой валидации.
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-013
Источник: docs/research/03 §4.4

#### Scenario: Последовательные страницы
- **WHEN** поиск находит 45 контактов при размере страницы 20
- **THEN** страницы содержат 20, 20 и 5 элементов, и у последней нет курсора

#### Scenario: Подделанный курсор
- **WHEN** клиент изменяет хотя бы один символ курсора
- **THEN** возвращается ошибка валидации

#### Scenario: Курсор с другим запросом
- **WHEN** курсор, полученный для префикса «Сем», передаётся с префиксом «Пет»
- **THEN** возвращается ошибка валидации

### Requirement: SRCH-11 Поиск на одном снимке
Все страницы одного поиска SHALL читаться с одного согласованного снимка данных, взятого при запросе первой страницы: изменения, подтверждённые позже, MUST NOT появляться на следующих страницах, а элементы MUST NOT дублироваться или пропускаться.
Трассировка: CUJ-02, CUJ-05; ADR-0003; D-018, D-032

#### Scenario: Создание между страницами
- **WHEN** получена первая страница поиска «Сем», затем подтверждено создание «Семенихин», затем запрошена вторая страница
- **THEN** «Семенихин» не входит ни в одну страницу этого поиска
- **AND** объединение страниц совпадает с результатом на момент первой страницы

#### Scenario: Удаление между страницами
- **WHEN** после первой страницы контакт со второй страницы удалён в корзину
- **THEN** вторая страница этого поиска всё равно содержит этот контакт

### Requirement: SRCH-12 Срок действия курсора
Курсор SHALL оставаться действительным, пока открыт снимок поиска (SRCH-11), но не дольше лимита длительности снимка интерактивного чтения (STO-24, по умолчанию 30 с). Истёкший курсор MUST отклоняться с ошибкой `cursor_expired`, после которой клиент начинает поиск заново.
Трассировка: CUJ-02, CUJ-05, CUJ-08; ADR-0003, ADR-0010; D-018, D-032
Источник: docs/research/03 §4.4; docs/research/02 §2.4 п. 5

#### Scenario: Курсор в пределах срока
- **WHEN** при лимите по умолчанию вторая страница запрошена через 20 с после первой
- **THEN** она возвращается с того же снимка

#### Scenario: Истёкший курсор
- **WHEN** при лимите по умолчанию следующая страница запрошена через 40 с после первой
- **THEN** возвращается ошибка `cursor_expired`

### Requirement: SRCH-13 Пустой результат
Поиск без совпадений SHALL завершаться успешно с пустым списком и без курсора; ошибкой MUST считаться только недопустимый запрос.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-011

#### Scenario: Неизвестный номер
- **WHEN** выполняется точный поиск `+79990000000`, которого нет в базе
- **THEN** поиск завершается успешно с пустым списком и без курсора

### Requirement: SRCH-14 Чтение своих записей
Поиск, начатый после того, как клиенту подтверждена запись (создание, изменение, удаление в корзину, восстановление), SHALL учитывать эту запись независимо от соединения, сессии или интерфейса, через который она сделана.
Трассировка: CUJ-01, CUJ-02, CUJ-03; ADR-0003, ADR-0005; D-018, D-019

#### Scenario: Новый контакт сразу находится
- **WHEN** через UI подтверждено создание «Зоя» с телефоном `+79001234567`, а затем через API выполняется поиск `+79001234567`
- **THEN** результат содержит «Зоя»

#### Scenario: Переименование
- **WHEN** подтверждено изменение имени «Петров» на «Сидоров», затем выполняется точный поиск «Петров»
- **THEN** этот контакт в результат не входит

### Requirement: SRCH-15 Корзина не участвует в поиске
Контакты в корзине и очищенные контакты MUST NOT попадать в результаты ни одного режима поиска; восстановленный контакт SHALL снова находиться всеми режимами.
Трассировка: CUJ-01, CUJ-02, CUJ-09; ADR-0012; D-012

#### Scenario: Контакт в корзине
- **WHEN** контакт с телефоном `+79123456789` удалён в корзину
- **THEN** точный и префиксный поиск по телефону и имени его не возвращают

#### Scenario: Восстановленный контакт
- **WHEN** этот контакт восстановлен из корзины
- **THEN** точный поиск `+79123456789` снова его возвращает
