# search

## Purpose

Определяет поиск BUDB: контакты по телефону (точно и по префиксу цифр E.164 с нормализацией национального префикса) и по имени (точно и по префиксу полного ключа и слов), порядок и ранжирование выдачи, keyset-пагинацию с зашифрованным курсором, тайм-аут, квоту выдачи, лимиты и видимость записей. Целевые задержки поиска задаёт performance-capacity (PERF).

## ADDED Requirements

### Requirement: SRCH-01 Точный поиск по телефону
Система SHALL нормализовать запрос по phone-normalization (с регионом операции или по умолчанию) и возвращать все активные контакты, у которых есть телефон с тем же `e164` при любом `extension`. Каждый контакт MUST входить в результат не более одного раза; добавочный номер в запросе не учитывается [ПРЕДЛОЖЕНИЕ АГЕНТА].
Трассировка: CUJ-01, CUJ-05; ADR-0008; D-009, D-010
Источник: docs/research/03 §4.7, §8.1

#### Scenario: Кто звонит с семейного номера
- **WHEN** контакты «Иван Петров» и «Мария Петрова» имеют телефон `+74951234567`, и выполняется поиск `8 (495) 123-45-67` при регионе RU
- **THEN** результат содержит оба контакта, каждый один раз

#### Scenario: Добавочный номер не мешает
- **WHEN** у контакта сохранён `+74951234567` с `extension` = `101`, и выполняется поиск `+74951234567`
- **THEN** результат содержит этот контакт

### Requirement: SRCH-02 Недопустимый телефон в запросе
Если запрос точного поиска по телефону не проходит нормализацию, система SHALL возвращать ошибку валидации с кодом из PHN-14 и MUST NOT возвращать вместо неё пустой результат.
Трассировка: CUJ-01, CUJ-05; ADR-0008, ADR-0010; D-010

#### Scenario: Слишком короткий номер
- **WHEN** выполняется точный поиск по телефону `12`
- **THEN** возвращается ошибка валидации с кодом `phone.invalid_length`

### Requirement: SRCH-03 Префиксный поиск по телефону
Префикс телефона SHALL нормализоваться по PHN-17 с регионом операции или по умолчанию и пониматься как начальные цифры `e164`, начиная с кода страны. Результат — пары «совпавший `e164` + контакт» в порядке SRCH-08; контакт с двумя подходящими номерами входит дважды [ПРЕДЛОЖЕНИЕ АГЕНТА]. Размер страницы MUST считаться в парах.
Трассировка: CUJ-01, CUJ-05; ADR-0008; D-010, D-066, D-074
Источник: docs/research/02 §8 ADR-005

#### Scenario: Префикс с кодом страны
- **WHEN** выполняется поиск по префиксу `+7 912` и есть телефоны `+79123456789`, `+79129998877`, `+74951234567`
- **THEN** результат содержит пары для `+79123456789` и `+79129998877`, но не для `+74951234567`

#### Scenario: Национальный префикс преобразуется
- **WHEN** при регионе RU выполняется поиск по префиксу `8912`, и есть телефон `+79123456789`
- **THEN** ищутся номера, начинающиеся с `+7912`, и результат содержит пару для `+79123456789`

#### Scenario: Два номера одного контакта
- **WHEN** у контакта есть `+79121111111` и `+79122222222`, и выполняется поиск по префиксу `+7912`
- **THEN** контакт входит в результат дважды, с каждым совпавшим `e164`

### Requirement: SRCH-04 Точный поиск по имени
Система SHALL возвращать активные контакты, полный ключ `display_name` которых (NAM-05) равен ключу запроса (NAM-12). Ключи слов (NAM-13) MUST NOT участвовать в точном поиске; `given_name`, `family_name` и `middle_name` отдельно не ищутся.
Трассировка: CUJ-02, CUJ-05; ADR-0009; D-011, D-051

#### Scenario: Совпадение без учёта регистра и ё
- **WHEN** выполняется точный поиск «семенов пётр», а в базе есть «Семёнов Пётр» и «Семёнов Пётр Ильич»
- **THEN** результат содержит только «Семёнов Пётр»

#### Scenario: Слово не даёт точного совпадения
- **WHEN** выполняется точный поиск «семенов», а в базе есть только «Пётр Семёнов»
- **THEN** результат пуст

### Requirement: SRCH-05 Префиксный поиск по имени
Система SHALL возвращать активные контакты, у которых с ключа запроса начинается полный ключ (класс 0) или ключ хотя бы одного слова (класс 1, NAM-13), по целым кодовым точкам. Контакт MUST входить в результат один раз, в наименьшем своём классе. Порядок: класс 0 по (полный ключ, `id`), затем класс 1 по (наименьший совпавший ключ слова, `id`) [ПРЕДЛОЖЕНИЕ АГЕНТА: ключ класса 1].
Трассировка: CUJ-02, CUJ-05; ADR-0009; D-051, D-062, D-074

#### Scenario: Начало фамилии и начало слова
- **WHEN** выполняется поиск по префиксу «Сем», а в базе есть «Семёнов», «семенова» и «Иван Семёнов»
- **THEN** результат по порядку: «Семёнов», «семенова» (класс 0), «Иван Семёнов» (класс 1)

#### Scenario: Совпадение и полным ключом, и словом
- **WHEN** выполняется поиск по префиксу «иван», а в базе есть «Иван Иванов» и «Пётр Иванов»
- **THEN** результат по порядку: «Иван Иванов» один раз (класс 0), «Пётр Иванов» (класс 1)

#### Scenario: Несколько совпавших слов
- **WHEN** выполняется поиск по префиксу «иван», а в базе есть «Пётр Иванов-Иванченко»
- **THEN** контакт входит в результат один раз

#### Scenario: Префикс после полной свёртки
- **WHEN** выполняется поиск по префиксу «Straß», а в базе есть «Straße»
- **THEN** результат содержит «Straße» (ключ запроса «strass» — префикс ключа «strasse»)

### Requirement: SRCH-06 Границы длины запроса
Префикс телефона после нормализации (PHN-17) MUST содержать от 3 до 15 цифр, а ключ префикса имени — не менее 1 кодовой точки; строка запроса по имени MUST быть не длиннее 256 кодовых точек (CON-03). Запрос вне этих границ SHALL отклоняться с ошибкой валидации, а не давать пустой результат.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-022, D-058, D-083
Источник: docs/research/03 §4.7, §6.1 (API4)

#### Scenario: Короткий префикс телефона
- **WHEN** выполняется поиск по префиксу телефона `+7`
- **THEN** возвращается ошибка валидации

#### Scenario: Короткий национальный префикс
- **WHEN** при регионе RU выполняется поиск по префиксу телефона `8 9` (после нормализации `79`)
- **THEN** возвращается ошибка валидации

#### Scenario: Пустой префикс имени
- **WHEN** выполняется поиск по префиксу имени из одних пробелов
- **THEN** возвращается ошибка валидации

#### Scenario: Одна буква
- **WHEN** выполняется поиск по префиксу имени «А»
- **THEN** поиск выполняется и возвращает контакты, у которых полный ключ или ключ слова начинается с «а»

### Requirement: SRCH-07 Состав результата поиска
Каждый элемент результата SHALL содержать полное представление контакта, как при чтении по `id` (CON-11): `id`, имя и его части, все телефоны с полями CON-04 и `version`. В префиксном поиске по телефону элемент MUST дополнительно содержать совпавший `e164`.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0007; D-009, D-057

#### Scenario: Телефоны в результате поиска по имени
- **WHEN** поиск по имени находит контакт с двумя телефонами
- **THEN** элемент результата содержит оба телефона с `e164`, `label` и `is_primary`

### Requirement: SRCH-08 Порядок выдачи
Точный поиск по имени SHALL упорядочиваться по ключу имени в побайтовом сравнении UTF-8, при равных ключах — по `id`; префиксный поиск по имени — по SRCH-05. Поиск по телефону SHALL упорядочиваться по цифрам `e164`, затем по `id`. Сортировка по правилам языка (UCA) MUST NOT применяться.
Трассировка: CUJ-01, CUJ-02; ADR-0009; D-011, D-062
Источник: docs/research/03 §2.5

#### Scenario: Одинаковые ключи
- **WHEN** «Анна» имеет `id` A, «АННА» — `id` B, и A < B
- **THEN** «Анна» выдаётся раньше «АННА»

#### Scenario: Порядок по телефону
- **WHEN** поиск по префиксу `+7912` находит `+79125550000` у контакта с `id` 9 и `+79121110000` у контактов с `id` 3 и 2
- **THEN** порядок выдачи: (`+79121110000`, 2), (`+79121110000`, 3), (`+79125550000`, 9)

#### Scenario: Место «ё»
- **WHEN** упорядочиваются ключи имён «Ежов», «Ёлкин» и «Жуков»
- **THEN** порядок: «Ежов», «Ёлкин», «Жуков»

### Requirement: SRCH-09 Размер страницы
Размер страницы SHALL быть равен 20, если он не указан или равен 0, и не более 100: большее значение MUST уменьшаться до 100, а отрицательное — отклоняться с ошибкой валидации. Размер считается в элементах результата: в контактах или, в префиксном поиске по телефону, в парах (SRCH-03).
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-024, D-047
Источник: docs/research/03 §4.4, §6.1 (API4)

#### Scenario: Размер по умолчанию
- **WHEN** поиск находит 35 контактов, а размер страницы не указан
- **THEN** первая страница содержит 20 элементов

#### Scenario: Слишком большой размер
- **WHEN** запрошен размер страницы 1000
- **THEN** страница содержит не более 100 элементов

#### Scenario: Отрицательный размер
- **WHEN** запрошен размер страницы −5
- **THEN** возвращается ошибка валидации

### Requirement: SRCH-10 Курсор пагинации
Если элементов больше страницы, ответ SHALL содержать непрозрачный keyset-курсор: позицию последнего элемента (префикс имени — класс, ключ, `id`; телефон — `e164`, `id`; иначе — `id`) и параметры запроса, зашифрованные AEAD ключом экземпляра. Пустой курсор — конец выдачи. Изменённый курсор или курсор с другими параметрами MUST отклоняться ошибкой `invalid-page-token`.
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-013, D-048, D-074, D-082

#### Scenario: Последовательные страницы
- **WHEN** поиск находит 45 контактов при размере страницы 20
- **THEN** страницы содержат 20, 20 и 5 элементов, и у последней курсор пуст

#### Scenario: Подделанный курсор
- **WHEN** клиент изменяет хотя бы один символ курсора
- **THEN** возвращается ошибка `invalid-page-token`

#### Scenario: Курсор с другим запросом
- **WHEN** курсор, полученный для префикса «Сем», передаётся с префиксом «Пет»
- **THEN** возвращается ошибка `invalid-page-token`

#### Scenario: Курсор не раскрывает ПДн
- **WHEN** тест декодирует из base64 курсор поиска по префиксу `+7916123` и курсор поиска по имени «Семёнов»
- **THEN** результат не содержит подстрок `7916123` и «семенов»

### Requirement: SRCH-11 Страницы на свежих снимках
Каждая страница SHALL читаться на своём свежем снимке и продолжать выдачу строго после позиции курсора (SRCH-10); снимок на весь поиск MUST NOT удерживаться. Элементы, не менявшиеся между запросами страниц, MUST NOT дублироваться и пропускаться. Удалённые до запроса страницы на ней не появляются, а изменённые и новые выдаются по своей новой позиции.
Трассировка: CUJ-02, CUJ-05; ADR-0003; D-018, D-048

#### Scenario: Неизменные элементы
- **WHEN** поиск «Сем» выдан тремя страницами, и между запросами изменялись только контакты, не входящие в результат
- **THEN** объединение страниц содержит каждый подходящий контакт ровно один раз

#### Scenario: Удаление между страницами
- **WHEN** после первой страницы контакт, который попал бы на вторую, удалён в корзину
- **THEN** вторая страница этого контакта не содержит

#### Scenario: Создание после позиции курсора
- **WHEN** первая страница поиска «Сем» закончилась на «Семёнов», затем подтверждено создание «Семенюк», затем запрошена вторая страница
- **THEN** «Семенюк» входит во вторую или следующую страницу, так как его ключ больше позиции курсора

#### Scenario: Создание до позиции курсора
- **WHEN** первая страница поиска «Сем» закончилась на «Семёнов», затем подтверждено создание «Семак»
- **THEN** «Семак» не входит в следующие страницы этого поиска

### Requirement: SRCH-12 Срок действия курсора
Курсор SHALL быть действителен 24 ч с момента выдачи страницы, к которой он приложен, и не зависит от снимков чтения. Просроченный курсор MUST отклоняться ошибкой `page-token-expired`, после которой клиент начинает поиск заново. Отображение ошибок курсора на HTTP задаёт http-api (API-13).
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-048
Источник: docs/research/03 §4.4

#### Scenario: Курсор в пределах срока
- **WHEN** следующая страница запрошена через 23 ч после выдачи курсора
- **THEN** она возвращается

#### Scenario: Истёкший курсор
- **WHEN** следующая страница запрошена через 25 ч после выдачи курсора
- **THEN** возвращается ошибка `page-token-expired`

### Requirement: SRCH-13 Пустой результат
Поиск без совпадений SHALL завершаться успешно с пустым списком и пустым курсором; ошибкой MUST считаться только недопустимый запрос.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-011, D-048

#### Scenario: Неизвестный номер
- **WHEN** выполняется точный поиск `+79990000000`, которого нет в базе
- **THEN** поиск завершается успешно с пустым списком и пустым курсором

### Requirement: SRCH-14 Чтение своих записей
Поиск, начатый после того, как клиенту подтверждена запись (создание, изменение, удаление в корзину, восстановление), SHALL учитывать эту запись независимо от соединения, сессии или интерфейса, через который она сделана.
Трассировка: CUJ-01, CUJ-02, CUJ-03; ADR-0003, ADR-0005; D-018, D-019

#### Scenario: Новый контакт сразу находится
- **WHEN** через UI подтверждено создание «Зоя» с телефоном `+79001234567`, а затем через API выполняется поиск `+79001234567`
- **THEN** результат содержит «Зоя»

#### Scenario: Переименование
- **WHEN** подтверждено изменение имени «Петров» на «Сидоров», затем выполняется точный поиск «Петров»
- **THEN** этот контакт в результат не входит

### Requirement: SRCH-15 Корзина не участвует в поиске
Контакты в корзине и очищенные контакты MUST NOT попадать в результаты ни одного режима поиска: их записи удалены из индексов поиска (CON-14). Восстановленный контакт SHALL снова находиться всеми режимами.
Трассировка: CUJ-01, CUJ-02, CUJ-09; ADR-0012; D-012, D-041, D-064

#### Scenario: Контакт в корзине
- **WHEN** контакт с телефоном `+79123456789` удалён в корзину
- **THEN** точный и префиксный поиск по телефону и имени его не возвращают

#### Scenario: Восстановленный контакт
- **WHEN** этот контакт восстановлен из корзины
- **THEN** точный поиск `+79123456789` снова его возвращает

### Requirement: SRCH-16 Тайм-аут поиска
Поиск, не завершённый за 2 с от начала обработки запроса, SHALL прерываться: снимок чтения освобождается, клиент получает ошибку `query-timeout` (HTTP — API-36) без частичного результата. Тайм-аут MUST действовать во всех режимах поиска.
Трассировка: CUJ-01, CUJ-02, CUJ-08; ADR-0017; D-078, D-112

#### Scenario: Долгий поиск
- **WHEN** обработка поискового запроса длится дольше 2 с
- **THEN** запрос прерывается с ошибкой `query-timeout`, частичный результат не возвращается, а снимок чтения освобождён

### Requirement: SRCH-17 Квота выдачи результатов
Каждый выданный в результатах поиска контакт SHALL учитываться в квоте выдачи токена или сессии (access-control): для reader по умолчанию 10 000 контактов в час, значение настраивается. При исчерпании квоты поиск MUST отклоняться ошибкой `quota-exceeded` (HTTP — API-36) без результатов и с событием аудита. [ПРЕДЛОЖЕНИЕ АГЕНТА: скользящее окно 1 ч]
Трассировка: CUJ-01, CUJ-02, CUJ-10; ADR-0011; D-083, D-112

#### Scenario: Квота исчерпана
- **WHEN** reader за последний час получил в результатах поиска 10 000 контактов и выполняет ещё один поиск
- **THEN** поиск отклоняется ошибкой `quota-exceeded`, результаты не выдаются, событие записано в аудит

#### Scenario: Окно квоты сдвинулось
- **WHEN** с момента выдачи первых учтённых результатов прошло больше часа
- **THEN** поиск reader снова выполняется в пределах освободившейся квоты
