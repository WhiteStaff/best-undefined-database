# access-control

## Purpose
Аутентификация, авторизация и защита транспорта и веб-интерфейса BUDB: локальные учётные записи с ролями reader/writer/admin, API-токены, UI-сессии, защита от CSRF и подбора, TLS, CSP и заголовки безопасности, первичная инициализация администратора. Механизмы хэширования и криптобиблиотеки выбирает ADR-0011; собственная криптография запрещена (D-015).

Соответствие OWASP API Security Top 10 (2023) (источник: docs/research/03 §6.1):

| Риск | Мера | Требования |
|---|---|---|
| API1 Broken Object Level Authorization | одна книга на экземпляр (D-014), проверка роли на каждом объекте; `id` перечислимы (u64, D-057), поэтому защита — только авторизация | ACL-04, CON |
| API2 Broken Authentication | хэши паролей и токенов, срок жизни и отзыв токенов, нарастающая задержка входа без жёсткой блокировки (D-104), защита входа от CSRF | ACL-05…ACL-10, ACL-14…ACL-16 |
| API3 Broken Object Property Level Authorization | строгие схемы: незнакомые поля — отказ, поля только для чтения игнорируются (D-071) | API-15 |
| API4 Unrestricted Resource Consumption | rate limit, лимит страницы, тела и импорта, запрет сжатого тела, квота результатов | API-12, API-18, API-19, ACL-25 |
| API5 Broken Function Level Authorization | матрица ролей, административные ресурсы отдельно, токен с областью `metrics` для мониторинга (D-103) | ACL-03, ACL-24, API-27 |
| API6 Unrestricted Access to Sensitive Business Flows | экспорт и данные субъекта только для admin, квота выданных контактов на токен (D-083), аудит чтений по событиям с `contact_id` (D-100) | ACL-03, ACL-25, API-26, PRV-12 |
| API7 Server Side Request Forgery | импорт только загрузкой файла, без загрузки по URL | ACL-22 |
| API8 Security Misconfiguration | localhost по умолчанию, обязательный TLS вне loopback, CSP, заголовки, без отладочных эндпоинтов, `public_origin` и проверка `Host`, CORS выключен | ACL-17…ACL-20, ACL-23, ACL-26 |
| API9 Improper Inventory Management | один документ OpenAPI, версия в пути | API-02, API-03 |
| API10 Unsafe Consumption of APIs | внешних API нет, файлы импорта недоверенные | ACL-22, IMP |

## ADDED Requirements

### Requirement: ACL-01 Локальные учётные записи
Система SHALL хранить локальные учётные записи с уникальным логином (сравнение без учёта регистра), ровно одной ролью и признаком «отключена». Отключённая учётная запись MUST не проходить аутентификацию ни паролем, ни токеном. Внешние поставщики учётных записей в v1 не поддерживаются.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Дубликат логина
- **WHEN** admin создаёт пользователя `Ivanov`, когда уже есть `ivanov`
- **THEN** операция отклоняется с ошибкой конфликта

#### Scenario: Отключённый пользователь
- **WHEN** отключённый пользователь вводит верный пароль
- **THEN** вход отклоняется так же, как при неверном пароле

### Requirement: ACL-02 Иерархия ролей
Система SHALL поддерживать ровно три роли: reader, writer и admin. Роли MUST быть иерархическими: writer имеет все права reader, admin — все права writer. Права токена равны текущей роли владельца, суженной областью токена (ACL-24), поэтому смена роли действует со следующего запроса.
Трассировка: CUJ-10; ADR-0011; D-015, D-103
Источник: docs/research/03 §6.2

#### Scenario: Понижение роли
- **WHEN** admin меняет роль пользователя с writer на reader
- **THEN** следующий `POST /api/v1/contacts` с токеном этого пользователя получает 403

### Requirement: ACL-03 Матрица прав по операциям
Права SHALL соответствовать матрице. reader: поиск, чтение, предпросмотр нормализации. writer: плюс создание, изменение, удаление, просмотр корзины и восстановление любого контакта, импорт. admin: плюс purge, экспорт, данные субъекта, пользователи и токены, бэкап и проверка, состояние, аудит, метрики. Прочее MUST давать 403.
Трассировка: CUJ-01, CUJ-03, CUJ-06, CUJ-09, CUJ-10; ADR-0011; D-015, D-041
Источник: docs/research/03 §6.1, §6.2

#### Scenario: Reader ищет
- **WHEN** reader вызывает `POST /api/v1/contacts:search`
- **THEN** сервер отвечает 200

#### Scenario: Writer импортирует
- **WHEN** writer вызывает `POST /api/v1/imports` с корректным файлом и `Idempotency-Key`
- **THEN** сервер отвечает 202

#### Scenario: Writer экспортирует
- **WHEN** writer вызывает `POST /api/v1/exports`
- **THEN** сервер отвечает 403

#### Scenario: Writer восстанавливает чужое удаление
- **WHEN** writer вызывает `POST /api/v1/contacts/{id}:restore` для контакта, удалённого другим пользователем
- **THEN** сервер отвечает 200

### Requirement: ACL-04 Проверка прав на каждом запросе
Сервер SHALL проверять аутентификацию и роль на каждом запросе к непубличному ресурсу, на стороне сервера и по принципу «запрещено всё, что не разрешено». Публичными MUST быть только вход (страница и `POST /api/v1/session`), ассеты UI, `GET /api/v1/openapi.json`, страницы `/problems/<code>` (API-14) и проверки живости и готовности (OBS).
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015, D-068, D-099
Источник: docs/research/03 §6.2

#### Scenario: Новый эндпоинт без правила
- **WHEN** для ресурса не задано правило доступа
- **THEN** аутентифицированный запрос к нему получает 403

#### Scenario: Публичный ресурс
- **WHEN** клиент без учётных данных запрашивает страницу входа
- **THEN** сервер отвечает 200

### Requirement: ACL-05 Хэширование паролей
Пароли SHALL храниться только как хэш с солью, вычисленный медленной функцией хэширования паролей из проверенной криптобиблиотеки (выбор — ADR-0011). Пароль MUST NOT храниться в открытом виде, возвращаться API или попадать в логи и аудит.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Хранение пароля
- **WHEN** admin создаёт пользователя с паролем
- **THEN** файл базы данных не содержит пароль в открытом виде

#### Scenario: Одинаковые пароли
- **WHEN** двум пользователям задан один и тот же пароль
- **THEN** их сохранённые хэши различаются

### Requirement: ACL-06 Политика паролей
Пароль SHALL содержать от 12 до 256 кодовых точек Unicode и MUST сравниваться после нормализации NFC. Требований к составу символов и принудительной периодической смены нет. [ПРЕДЛОЖЕНИЕ АГЕНТА: длины и отсутствие правил состава]
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Короткий пароль
- **WHEN** admin задаёт пароль из 8 символов
- **THEN** операция отклоняется с кодом ошибки `password.too_short`

#### Scenario: Пароль-фраза
- **WHEN** admin задаёт пароль `тихий кот спит на окне`
- **THEN** пароль принимается

### Requirement: ACL-07 Выдача API-токена
API-токен SHALL иметь вид `budb_<token_id>_<secret>`: `token_id` — строка из `[a-z0-9]` без `_`, секрет — не меньше 128 бит из криптостойкого генератора. При создании задаются область (ACL-24) и лимиты (API-19, ACL-25). Полный токен MUST показываться ровно один раз, при создании. [ПРЕДЛОЖЕНИЕ АГЕНТА: префикс, `token_id`]
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015, D-073, D-103
Источник: docs/research/03 §6.1 (API2), §6.2

#### Scenario: Создание токена
- **WHEN** admin создаёт токен для пользователя
- **THEN** ответ содержит полный токен и `token_id`

#### Scenario: Повторный просмотр
- **WHEN** admin запрашивает список токенов
- **THEN** список содержит `token_id`, владельца, область и срок действия, но не секрет

### Requirement: ACL-08 Хранение только хэшей токенов
Система SHALL хранить только хэш секрета токена и MUST сравнивать предъявленный секрет с хэшем за время, не зависящее от совпадения. Токен принимается только в заголовке `Authorization: Bearer`.
Трассировка: CUJ-05; ADR-0011; D-015
Источник: docs/research/03 §6.2 (требование OWASP хэшировать ключи — [НЕ ПОДТВЕРЖДЕНО])

#### Scenario: Утечка файла БД
- **WHEN** злоумышленник читает файл базы данных
- **THEN** он не находит в нём секретов токенов в открытом виде

#### Scenario: Правильный токен
- **WHEN** клиент передаёт `Authorization: Bearer budb_…` с действующим токеном
- **THEN** запрос аутентифицируется как владелец токена

### Requirement: ACL-09 Срок жизни токенов
Каждый токен SHALL иметь срок действия: по умолчанию 90 дней, не больше 365 дней. Просроченный токен MUST давать 401 так же, как неизвестный. [ПРЕДЛОЖЕНИЕ АГЕНТА: 90 и 365 дней]
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015

#### Scenario: Токен истёк
- **WHEN** клиент использует токен на следующий день после окончания срока
- **THEN** сервер отвечает 401

#### Scenario: Слишком долгий срок
- **WHEN** admin создаёт токен со сроком 400 дней
- **THEN** операция отклоняется

### Requirement: ACL-10 Отзыв токенов и сессий
Отзыв токена SHALL действовать не позже следующего запроса с ним. Отключение пользователя, смена пароля или удаление учётной записи MUST отзывать все его токены и сессии, кроме сессии, где он сменил свой пароль. Restore из бэкапа MUST отзывать все токены и сессии с событием аудита; учётные записи и пароли из бэкапа сохраняются, вход — по ACL-27.
Трассировка: CUJ-07, CUJ-10; ADR-0011; D-015, D-079, D-117
Источник: docs/research/03 §6.2

#### Scenario: Отзыв токена
- **WHEN** admin отзывает токен и клиент сразу отправляет запрос с ним
- **THEN** сервер отвечает 401

#### Scenario: Отключение пользователя
- **WHEN** admin отключает пользователя с открытой UI-сессией
- **THEN** следующий запрос этой сессии получает 401

#### Scenario: Токен после restore
- **WHEN** токен выпущен до бэкапа, отозван после него, а затем выполнен restore из этого бэкапа
- **THEN** токен получает 401, как и все остальные токены, а admin выпускает новые

### Requirement: ACL-11 Cookie UI-сессии
После входа (API-29) сервер SHALL выдавать cookie `HttpOnly; SameSite=Strict; Path=/` без `Domain`: при схеме `https` в `public_origin` — `__Host-budb_session` с `Secure`, при `http` на loopback — `budb_session` без `Secure`. Идентификатор MUST иметь ≥ 128 бит из CSPRNG, выдаваться заново при каждом входе и храниться только в памяти.
Трассировка: CUJ-01, CUJ-10; ADR-0011, ADR-0016; D-043, D-055, D-101
Источник: docs/research/03 §6.2

#### Scenario: Атрибуты cookie
- **WHEN** пользователь входит в UI при `public_origin` = `https://budb.corp`, даже если TLS завершает прокси
- **THEN** ответ содержит `Set-Cookie: __Host-budb_session=…; Secure; HttpOnly; SameSite=Strict; Path=/`

#### Scenario: Loopback без TLS
- **WHEN** сервер работает на `http://127.0.0.1:8080`, и пользователь входит
- **THEN** cookie называется `budb_session` и не имеет `Secure`, а e2e-тест подтверждает вход во всех поддерживаемых браузерах

#### Scenario: Перезапуск сервера
- **WHEN** сервер перезапущен
- **THEN** прежние сессии недействительны, и пользователь входит снова

#### Scenario: Фиксация сессии
- **WHEN** у браузера уже есть cookie сессии и пользователь входит снова
- **THEN** сервер выдаёт новый идентификатор, а старый перестаёт действовать

### Requirement: ACL-12 Тайм-ауты сессии
UI-сессия SHALL завершаться после 30 минут бездействия и через 8 часов после входа; значения MUST настраиваться в пределах 15–30 минут и 4–8 часов (CLI-18). Бездействие продлевает любой запрос сессии, кроме фоновых с заголовком `X-BUDB-Background: 1`; «Продлить» в UI-24 — это `GET /api/v1/session`. [ПРЕДЛОЖЕНИЕ АГЕНТА: заголовок]
Трассировка: CUJ-01; ADR-0011, ADR-0017; D-066, D-106
Источник: docs/research/03 §6.2

#### Scenario: Бездействие
- **WHEN** пользователь не отправлял запросов 31 минуту
- **THEN** следующий запрос сессии получает 401

#### Scenario: Абсолютный срок
- **WHEN** пользователь активно работает 8 часов и 1 минуту после входа
- **THEN** следующий запрос сессии получает 401

#### Scenario: Фоновый опрос
- **WHEN** страница 31 минуту отправляет только запросы с `X-BUDB-Background: 1`
- **THEN** следующий запрос сессии получает 401

### Requirement: ACL-13 Выход из системы
Выход SHALL уничтожать сессию на сервере и MUST отправлять cookie с истёкшим сроком. Повтор запроса со старым идентификатором сессии получает 401.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Повтор после выхода
- **WHEN** пользователь вышел, а затем запрос отправлен со старой cookie
- **THEN** сервер отвечает 401

### Requirement: ACL-14 Защита от CSRF
Каждый небезопасный запрос с cookie сессии, включая `POST /api/v1/contacts:search`, MUST содержать `X-CSRF-Token` из `GET /api/v1/session` и `Sec-Fetch-Site: same-origin`, а без него — `Origin`, равный `public_origin`. Вход `POST /api/v1/session` проверяется так же, кроме токена. Иначе — 403 `csrf-failed`. Изменение через GET MUST NOT поддерживаться; запросы с bearer-токеном от проверки освобождены.
Трассировка: CUJ-03; ADR-0011, ADR-0016; D-068, D-101, D-113
Источник: docs/research/03 §6.4

#### Scenario: Межсайтовый запрос
- **WHEN** сторонний сайт отправляет `POST /api/v1/contacts` с cookie сессии и `Sec-Fetch-Site: cross-site`
- **THEN** сервер отвечает 403, и контакт не создаётся

#### Scenario: Нет CSRF-токена
- **WHEN** запрос с cookie сессии и `Sec-Fetch-Site: same-origin` не содержит CSRF-токен
- **THEN** сервер отвечает 403

#### Scenario: Поиск с cookie без CSRF
- **WHEN** запрос `POST /api/v1/contacts:search` с cookie сессии не содержит CSRF-токен
- **THEN** сервер отвечает 403 `csrf-failed`

#### Scenario: Bearer-токен без CSRF
- **WHEN** изменяющий запрос с bearer-токеном не содержит CSRF-токен
- **THEN** проверка CSRF не применяется, запрос обрабатывается по правам токена

#### Scenario: Межсайтовый вход
- **WHEN** сторонний сайт отправляет `POST /api/v1/session` с логином атакующего и `Sec-Fetch-Site: cross-site`
- **THEN** сервер отвечает 403, и сессия не создаётся

### Requirement: ACL-15 Ограничение попыток входа
Жёсткой блокировки логина SHALL не быть. После 5 неудач для пары (логин, IP) за 15 минут каждая следующая попытка этой пары получает 429 с `Retry-After`, задержка удваивается от 1 с до 15 минут; с одного IP MUST приниматься не больше 20 попыток в минуту. Всплеск неудач отражается в метрике для алерта admin. [ПРЕДЛОЖЕНИЕ АГЕНТА: числа]
Трассировка: CUJ-01, CUJ-10; ADR-0011; D-104
Источник: docs/research/03 §6.1 (API2)

#### Scenario: Подбор пароля
- **WHEN** с IP `10.0.0.5` для логина `admin` введён неверный пароль 5 раз за 2 минуты
- **THEN** шестая попытка с этого IP, даже с верным паролем, получает 429 с `Retry-After`

#### Scenario: Злоумышленник не блокирует оператора
- **WHEN** после этого `admin` входит с верным паролем с другого IP `10.0.0.7`
- **THEN** вход выполняется без задержки

#### Scenario: Задержка истекла
- **WHEN** истёк `Retry-After`, и с `10.0.0.5` введён верный пароль
- **THEN** вход выполняется

### Requirement: ACL-16 Единый ответ при неудачном входе
Ответ на неудачный вход MUST быть одинаковым по коду и тексту для неизвестного логина, неверного пароля и отключённой учётной записи; для неизвестного логина сервер SHALL вычислять хэш пароля с теми же параметрами, чтобы время ответа не выдавало существование логина.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Неизвестный логин
- **WHEN** выполняется вход с несуществующим логином и с существующим логином и неверным паролем
- **THEN** оба ответа имеют одинаковый код 401 и одинаковый `code` = `invalid-credentials`, и в обоих случаях вычислен хэш пароля

### Requirement: ACL-17 Версии TLS
При включённом TLS сервер SHALL принимать TLS 1.3 и TLS 1.2 (минимум задаёт `tls_min_version`, по умолчанию 1.2, предпочтительна 1.3) и MUST отклонять TLS 1.1 и ниже. Сертификат и ключ задаются файлами в конфигурации. Обычный HTTP-запрос на порт TLS не перенаправляется, а отклоняется.
Трассировка: CUJ-05, CUJ-10; ADR-0011, ADR-0017; D-015, D-066
Источник: docs/research/03 §6.3

#### Scenario: Старый клиент
- **WHEN** клиент предлагает только TLS 1.1
- **THEN** рукопожатие завершается отказом

#### Scenario: Современный клиент
- **WHEN** клиент подключается по TLS 1.3
- **THEN** соединение устанавливается

### Requirement: ACL-18 Адрес прослушивания по умолчанию
По умолчанию сервер SHALL слушать только loopback-адрес и может работать без TLS. При настройке адреса вне loopback без сертификата сервер MUST отказаться запускаться с понятным сообщением и ненулевым кодом выхода; переопределения нет. [ПРЕДЛОЖЕНИЕ АГЕНТА: без флага обхода]
Трассировка: CUJ-07, CUJ-10; ADR-0011, ADR-0017; D-032, D-033
Источник: docs/research/03 §6.3

#### Scenario: Запуск по умолчанию
- **WHEN** `budb serve` запускается без настроек адреса
- **THEN** сервер принимает соединения только на `127.0.0.1` и `::1`

#### Scenario: Внешний адрес без TLS
- **WHEN** в конфигурации указан адрес `0.0.0.0:8443` без сертификата
- **THEN** сервер не запускается и завершается с кодом ошибки конфигурации

### Requirement: ACL-19 Политика CSP
Каждая HTML-страница SHALL отдаваться с `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`. Inline-скрипты и обработчики и внешние источники MUST NOT использоваться.
Трассировка: CUJ-01, CUJ-02; ADR-0011, ADR-0016; D-031
Источник: docs/research/03 §5.4, §6.4

#### Scenario: Заголовок на странице
- **WHEN** браузер загружает главную страницу UI
- **THEN** ответ содержит заголовок CSP с `script-src 'self'` и без `'unsafe-inline'`

#### Scenario: Внедрённый скрипт
- **WHEN** имя контакта содержит `<script>alert(1)</script>`
- **THEN** браузер не выполняет скрипт, а нарушений CSP со стороны самого UI нет

#### Scenario: Встроенные шрифты
- **WHEN** UI загружает шрифт из ассетов сервера
- **THEN** шрифт применяется, а браузер не сообщает о нарушении CSP

### Requirement: ACL-20 Заголовки безопасности
Каждый ответ SHALL содержать `X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`. Ответы API и страницы с ПДн MUST содержать `Cache-Control: no-store`. При TLS ответы MUST содержать `Strict-Transport-Security` с `max-age` не меньше года. [ПРЕДЛОЖЕНИЕ АГЕНТА: Referrer-Policy и max-age]
Трассировка: CUJ-05; ADR-0011; D-013, D-015
Источник: docs/research/03 §6.1 (API8), §6.2, §6.3

#### Scenario: Ответ поиска
- **WHEN** клиент получает ответ `POST /api/v1/contacts:search`
- **THEN** ответ содержит `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`

#### Scenario: HSTS
- **WHEN** сервер работает с TLS
- **THEN** ответы содержат `Strict-Transport-Security: max-age=31536000`

### Requirement: ACL-21 Первичная инициализация администратора
Система MUST NOT иметь учётных записей и паролей по умолчанию. Первого admin SHALL создавать команда `budb admin bootstrap` по admin-cli (CLI) на базе без администраторов; пароль вводится оператором. Пока admin нет, сервер работает, но любой вход отклоняется.
Трассировка: CUJ-10; ADR-0011; D-015, D-032
Источник: docs/research/03 §6.2

#### Scenario: Новая база
- **WHEN** сервер запущен на новой базе без bootstrap
- **THEN** попытка входа с логином `admin` и любым паролем отклоняется

#### Scenario: Повторный bootstrap
- **WHEN** `budb admin bootstrap` выполняется на базе, где уже есть admin
- **THEN** команда отказывает и не меняет учётные записи

### Requirement: ACL-22 Отсутствие исходящих запросов
Сервер MUST NOT выполнять исходящие сетевые запросы по данным пользователя: импорт SHALL принимать только загруженный файл, без загрузки по URL. Содержимое файлов импорта считается недоверенным и проверяется по import-export (IMP).
Трассировка: CUJ-06; ADR-0011; D-016
Источник: docs/research/03 §6.1 (API7, API10)

#### Scenario: Импорт по URL
- **WHEN** клиент передаёт в запросе импорта URL вместо файла
- **THEN** сервер отклоняет запрос и не обращается к этому URL

### Requirement: ACL-23 Публичный источник и доверенные прокси
Сервер SHALL знать `public_origin` и `trusted_proxies` (CLI-18): по схеме `public_origin` выбираются атрибуты cookie (ACL-11), с ним сверяется `Origin` (ACL-14). Адрес клиента для лимитов и аудита MUST браться из `X-Forwarded-For` только от доверенного прокси. Запрос с `Host` не из `public_origin` и loopback-имён получает 421, кроме `/livez`, `/readyz` и `/metrics` (пробы идут по IP; `/metrics` требует токен по OBS-03).
Трассировка: CUJ-05, CUJ-08, CUJ-10; ADR-0011, ADR-0017; D-043, D-101, D-119

#### Scenario: Доверенный прокси
- **WHEN** запрос приходит от `127.0.0.1` из `trusted_proxies` с `X-Forwarded-For: 10.0.0.5`
- **THEN** лимиты и аудит учитывают адрес `10.0.0.5`

#### Scenario: Подделка заголовка
- **WHEN** клиент `10.0.0.9`, не входящий в `trusted_proxies`, передаёт `X-Forwarded-For: 10.0.0.5`
- **THEN** лимиты и аудит учитывают адрес `10.0.0.9`

#### Scenario: Перепривязка DNS
- **WHEN** запрос приходит на loopback с `Host: evil.example`
- **THEN** сервер отвечает 421 и не обрабатывает запрос

#### Scenario: Проба по IP
- **WHEN** оркестратор запрашивает `GET /readyz` и `GET /livez` с `Host: 10.0.0.5:8443`, не равным `public_origin`
- **THEN** сервер отвечает по существу (200 при готовности), а не 421

#### Scenario: Метрики по IP без токена
- **WHEN** запрос `GET /metrics` приходит с `Host: 10.0.0.5:8443` без токена `metrics`
- **THEN** сервер отвечает 401, а не 421; с токеном `metrics` — 200

### Requirement: ACL-24 Область действия токена metrics
Токен SHALL иметь область `full` (права роли владельца) или `metrics`. Токен с областью `metrics` MUST получать доступ только к `GET /metrics` и проверкам здоровья, а на любой другой запрос — 403; такой токен выдаётся сборщику метрик вместо admin-токена. Сессии UI всегда имеют область `full`.
Трассировка: CUJ-08, CUJ-10; ADR-0011; D-103

#### Scenario: Сбор метрик
- **WHEN** Prometheus запрашивает `GET /metrics` с токеном области `metrics`
- **THEN** сервер отвечает 200

#### Scenario: Утечка токена мониторинга
- **WHEN** тот же токен используется для `POST /api/v1/exports` или `POST /api/v1/contacts:search`
- **THEN** сервер отвечает 403

### Requirement: ACL-25 Квота выданных контактов
Сервер SHALL считать для каждого токена и сессии любой роли число контактов, выданных поиском и чтением по `id` за скользящий час; экспорт не считается. Квота по умолчанию 10 000 (`result_quota_per_hour`, CLI-18), для токена задаётся по CLI-06. Это единственное место правил квоты. Сверх квоты MUST отвечать 429 `quota-exceeded` с `Retry-After` (API-36); признаки перебора дают событие аудита и метрику для алерта.
Трассировка: CUJ-01, CUJ-05, CUJ-09; ADR-0011; D-083, D-118

#### Scenario: Выкачивание перебором префиксов
- **WHEN** токен reader за час получил 10 000 контактов и отправляет следующий поиск
- **THEN** сервер отвечает 429 с `code` = `quota-exceeded`, и в аудите есть событие превышения

#### Scenario: Обычная работа оператора
- **WHEN** оператор за час выполняет 300 поисков по 1–3 результата
- **THEN** ни один запрос не получает `quota-exceeded`

#### Scenario: Квота writer и чтение по id
- **WHEN** токен writer за час получил 10 000 контактов чтением по `id` и поиском и читает ещё один контакт
- **THEN** сервер отвечает 429 с `code` = `quota-exceeded`, так же как для reader

### Requirement: ACL-26 CORS выключен
Сервер MUST NOT отдавать заголовки `Access-Control-Allow-*` ни на какие запросы, включая preflight `OPTIONS`: API и UI SHALL работать только с одного источника (`public_origin`).
Трассировка: CUJ-05; ADR-0011; D-101

#### Scenario: Запрос со стороннего сайта
- **WHEN** браузер отправляет `OPTIONS /api/v1/contacts:search` с `Origin: https://evil.example`
- **THEN** ответ не содержит ни одного заголовка `Access-Control-Allow-*`

### Requirement: ACL-27 Проверка учётных записей после restore
После restore из бэкапа все пользователи, кроме admin, выполнившего restore (CLI-07), SHALL получать пометку `review_required`, а вход таких пользователей MUST блокироваться до подтверждения admin (CLI-20, API-39). Токены и сессии отзываются по ACL-10; учётные записи и пароли из бэкапа сохраняются.
Трассировка: CUJ-07, CUJ-10; ADR-0011, ADR-0013; D-079, D-113, D-117

#### Scenario: Вход после restore
- **WHEN** выполнен restore, и пользователь вводит верный пароль до подтверждения admin
- **THEN** вход отклоняется, а в аудите есть событие блокировки

#### Scenario: Подтверждение admin
- **WHEN** admin подтверждает пользователя через CLI или API
- **THEN** пометка `review_required` снимается, и пользователь входит с прежним паролем

#### Scenario: Admin, выполнивший restore
- **WHEN** restore выполнен командой с `--as-admin root`, и `root` вводит верный пароль
- **THEN** вход разрешён без отдельного подтверждения, а остальные пользователи блокированы до подтверждения
