# access-control

## Purpose
Аутентификация, авторизация и защита транспорта и веб-интерфейса BUDB: локальные учётные записи с ролями reader/writer/admin, API-токены, UI-сессии, защита от CSRF и подбора, TLS, CSP и заголовки безопасности, первичная инициализация администратора. Механизмы хэширования и криптобиблиотеки выбирает ADR-0011; собственная криптография запрещена (D-015).

Соответствие OWASP API Security Top 10 (2023) (источник: docs/research/03 §6.1):

| Риск | Мера | Требования |
|---|---|---|
| API1 Broken Object Level Authorization | одна книга на экземпляр (D-014), проверка роли на каждом объекте, неугадываемые `id` | ACL-04, CON |
| API2 Broken Authentication | хэши паролей и токенов, срок жизни и отзыв токенов, лимит попыток входа | ACL-05…ACL-10, ACL-15, ACL-16 |
| API3 Broken Object Property Level Authorization | строгие схемы, отказ на лишние поля и поля только для чтения | API-15 |
| API4 Unrestricted Resource Consumption | rate limit, лимит страницы, тела и импорта | API-12, API-18, API-19 |
| API5 Broken Function Level Authorization | матрица ролей, административные ресурсы отдельно | ACL-03, API-27 |
| API6 Unrestricted Access to Sensitive Business Flows | экспорт и данные субъекта только для admin, аудит массового чтения | ACL-03, API-26, PRV |
| API7 Server Side Request Forgery | импорт только загрузкой файла, без загрузки по URL | ACL-22 |
| API8 Security Misconfiguration | localhost по умолчанию, обязательный TLS вне loopback, CSP, заголовки, без отладочных эндпоинтов | ACL-17…ACL-20 |
| API9 Improper Inventory Management | один документ OpenAPI, версия в пути | API-02, API-03 |
| API10 Unsafe Consumption of APIs | внешних API нет, файлы импорта недоверенные | ACL-22, IMP |

## ADDED Requirements

### Requirement: ACL-01 Локальные учётные записи
Система SHALL хранить локальные учётные записи с уникальным логином (сравнение без учёта регистра), ровно одной ролью и признаком «отключена». Отключённая учётная запись MUST не проходить аутентификацию ни паролем, ни токеном. Внешние поставщики учётных записей в v1 не поддерживаются.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Дубликат логина
- **WHEN** admin создаёт пользователя `Ivanov`, когда уже есть `ivanov`
- **THEN** операция отклоняется с ошибкой конфликта

#### Scenario: Отключённый пользователь
- **WHEN** отключённый пользователь вводит верный пароль
- **THEN** вход отклоняется так же, как при неверном пароле

### Requirement: ACL-02 Иерархия ролей
Система SHALL поддерживать ровно три роли: reader, writer и admin. Роли MUST быть иерархическими: writer имеет все права reader, admin — все права writer. Роль токена равна текущей роли его владельца, поэтому смена роли действует со следующего запроса.
Трассировка: CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.2

#### Scenario: Понижение роли
- **WHEN** admin меняет роль пользователя с writer на reader
- **THEN** следующий `POST /api/v1/contacts` с токеном этого пользователя получает 403

### Requirement: ACL-03 Матрица прав по операциям
Права SHALL соответствовать матрице. reader: поиск, чтение, предпросмотр нормализации. writer: плюс создание, изменение, удаление в корзину, отмена своего удаления, импорт. admin: плюс корзина, purge, экспорт, данные субъекта, пользователи и токены, бэкап и проверка, состояние, аудит. Прочее MUST давать 403.
Трассировка: CUJ-01, CUJ-03, CUJ-06, CUJ-09, CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.1 (API5, API6), §6.2

#### Scenario: Reader ищет
- **WHEN** reader вызывает `POST /api/v1/contacts:search`
- **THEN** сервер отвечает 200

#### Scenario: Writer импортирует
- **WHEN** writer вызывает `POST /api/v1/imports` с корректным файлом и `Idempotency-Key`
- **THEN** сервер отвечает 202

#### Scenario: Writer экспортирует
- **WHEN** writer вызывает `POST /api/v1/exports`
- **THEN** сервер отвечает 403

### Requirement: ACL-04 Проверка прав на каждом запросе
Сервер SHALL проверять аутентификацию и роль на каждом запросе к непубличному ресурсу, на стороне сервера и по принципу «запрещено всё, что не разрешено». Публичными MUST быть только страница входа, статические ассеты UI, `GET /api/v1/openapi.json` и проверки живости и готовности по observability (OBS).
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.2

#### Scenario: Новый эндпоинт без правила
- **WHEN** для ресурса не задано правило доступа
- **THEN** аутентифицированный запрос к нему получает 403

#### Scenario: Публичный ресурс
- **WHEN** клиент без учётных данных запрашивает страницу входа
- **THEN** сервер отвечает 200

### Requirement: ACL-05 Хэширование паролей
Пароли SHALL храниться только как хэш с солью, вычисленный медленной функцией хэширования паролей из проверенной криптобиблиотеки (выбор — ADR-0011). Пароль MUST NOT храниться в открытом виде, возвращаться API или попадать в логи и аудит.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Хранение пароля
- **WHEN** admin создаёт пользователя с паролем
- **THEN** файл базы данных не содержит пароль в открытом виде

#### Scenario: Одинаковые пароли
- **WHEN** двум пользователям задан один и тот же пароль
- **THEN** их сохранённые хэши различаются

### Requirement: ACL-06 Политика паролей
Пароль SHALL содержать от 12 до 256 кодовых точек Unicode и MUST сравниваться после нормализации NFC. Требований к составу символов и принудительной периодической смены нет. [ПРЕДЛОЖЕНИЕ АГЕНТА: длины и отсутствие правил состава]
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Короткий пароль
- **WHEN** admin задаёт пароль из 8 символов
- **THEN** операция отклоняется с кодом ошибки `password.too_short`

#### Scenario: Пароль-фраза
- **WHEN** admin задаёт пароль `тихий кот спит на окне`
- **THEN** пароль принимается

### Requirement: ACL-07 Выдача API-токена
API-токен SHALL иметь вид `budb_<token_id>_<secret>`, где секрет содержит не меньше 128 бит из криптостойкого генератора. Полный токен MUST показываться ровно один раз, при создании; повторно получить его нельзя. [ПРЕДЛОЖЕНИЕ АГЕНТА: префикс `budb_`]
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.1 (API2), §6.2

#### Scenario: Создание токена
- **WHEN** admin создаёт токен для пользователя
- **THEN** ответ содержит полный токен и `token_id`

#### Scenario: Повторный просмотр
- **WHEN** admin запрашивает список токенов
- **THEN** список содержит `token_id`, владельца и срок действия, но не секрет

### Requirement: ACL-08 Хранение только хэшей токенов
Система SHALL хранить только хэш секрета токена и MUST сравнивать предъявленный секрет с хэшем за время, не зависящее от совпадения. Токен принимается только в заголовке `Authorization: Bearer`.
Трассировка: CUJ-05; ADR-0011; D-015
Источник: docs/research/03 §6.2 (требование OWASP хэшировать ключи — [НЕ ПОДТВЕРЖДЕНО])

#### Scenario: Утечка файла БД
- **WHEN** злоумышленник читает файл базы данных
- **THEN** он не находит в нём секретов токенов в открытом виде

#### Scenario: Правильный токен
- **WHEN** клиент передаёт `Authorization: Bearer budb_…` с действующим токеном
- **THEN** запрос аутентифицируется как владелец токена

### Requirement: ACL-09 Срок жизни токенов
Каждый токен SHALL иметь срок действия: по умолчанию 90 дней, не больше 365 дней. Просроченный токен MUST давать 401 так же, как неизвестный. [ПРЕДЛОЖЕНИЕ АГЕНТА: 90 и 365 дней]
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015

#### Scenario: Токен истёк
- **WHEN** клиент использует токен на следующий день после окончания срока
- **THEN** сервер отвечает 401

#### Scenario: Слишком долгий срок
- **WHEN** admin создаёт токен со сроком 400 дней
- **THEN** операция отклоняется

### Requirement: ACL-10 Отзыв токенов и сессий
Отзыв токена SHALL действовать не позже следующего запроса с ним. Отключение пользователя, смена его пароля или удаление учётной записи MUST отзывать все его токены и сессии, кроме сессии, в которой пользователь сменил свой пароль.
Трассировка: CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.2

#### Scenario: Отзыв токена
- **WHEN** admin отзывает токен и клиент сразу отправляет запрос с ним
- **THEN** сервер отвечает 401

#### Scenario: Отключение пользователя
- **WHEN** admin отключает пользователя с открытой UI-сессией
- **THEN** следующий запрос этой сессии получает 401

### Requirement: ACL-11 Cookie UI-сессии
После входа сервер SHALL выдавать cookie `__Host-budb_session` с атрибутами `Secure; HttpOnly; SameSite=Strict; Path=/` без `Domain`. Идентификатор сессии MUST содержать не меньше 128 бит из криптостойкого генератора и выдаваться заново при каждом входе.
Трассировка: CUJ-01, CUJ-10; ADR-0011, ADR-0016; D-015
Источник: docs/research/03 §6.2 (OWASP Session Management)

#### Scenario: Атрибуты cookie
- **WHEN** пользователь успешно входит в UI
- **THEN** ответ содержит `Set-Cookie: __Host-budb_session=…; Secure; HttpOnly; SameSite=Strict; Path=/`

#### Scenario: Фиксация сессии
- **WHEN** у браузера уже есть cookie сессии и пользователь входит снова
- **THEN** сервер выдаёт новый идентификатор, а старый перестаёт действовать

### Requirement: ACL-12 Тайм-ауты сессии
UI-сессия SHALL завершаться после 30 минут бездействия и через 8 часов после входа независимо от активности. Оба значения MUST настраиваться в пределах, рекомендованных исследованием: 15–30 минут и 4–8 часов.
Трассировка: CUJ-01; ADR-0011, ADR-0017; D-015
Источник: docs/research/03 §6.2

#### Scenario: Бездействие
- **WHEN** пользователь не отправлял запросов 31 минуту
- **THEN** следующий запрос сессии получает 401

#### Scenario: Абсолютный срок
- **WHEN** пользователь активно работает 8 часов и 1 минуту после входа
- **THEN** следующий запрос сессии получает 401

### Requirement: ACL-13 Выход из системы
Выход SHALL уничтожать сессию на сервере и MUST отправлять cookie с истёкшим сроком. Повтор запроса со старым идентификатором сессии получает 401.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Повтор после выхода
- **WHEN** пользователь вышел, а затем запрос отправлен со старой cookie
- **THEN** сервер отвечает 401

### Requirement: ACL-14 Защита от CSRF
Каждый изменяющий запрос, аутентифицированный cookie сессии, MUST содержать CSRF-токен сессии в заголовке и иметь `Sec-Fetch-Site: same-origin`; если заголовка нет, проверяется совпадение `Origin`. Иначе ответ — 403 `csrf-failed`. Изменение состояния через GET MUST NOT поддерживаться. Запросы с bearer-токеном эту проверку не проходят.
Трассировка: CUJ-03; ADR-0011, ADR-0016; D-015
Источник: docs/research/03 §6.4

#### Scenario: Межсайтовый запрос
- **WHEN** сторонний сайт отправляет `POST /api/v1/contacts` с cookie сессии и `Sec-Fetch-Site: cross-site`
- **THEN** сервер отвечает 403, и контакт не создаётся

#### Scenario: Нет CSRF-токена
- **WHEN** запрос с cookie сессии и `Sec-Fetch-Site: same-origin` не содержит CSRF-токен
- **THEN** сервер отвечает 403

### Requirement: ACL-15 Ограничение попыток входа
После 5 неудачных попыток входа для логина за 15 минут вход по этому логину SHALL блокироваться на 15 минут, а с одного IP MUST приниматься не больше 20 попыток в минуту. Отказ — 429 с `Retry-After`. Блокировка не мешает уже выданным сессиям и токенам. [ПРЕДЛОЖЕНИЕ АГЕНТА: числа]
Трассировка: CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.1 (API2)

#### Scenario: Подбор пароля
- **WHEN** для логина `admin` введён неверный пароль 5 раз за 2 минуты
- **THEN** шестая попытка, даже с верным паролем, получает 429 с `Retry-After`

#### Scenario: Окно истекло
- **WHEN** после блокировки прошло 15 минут и введён верный пароль
- **THEN** вход выполняется

### Requirement: ACL-16 Единый ответ при неудачном входе
Ответ на неудачный вход MUST быть одинаковым по коду, тексту и порядку времени ответа для неизвестного логина, неверного пароля и отключённой учётной записи, чтобы по нему нельзя было перечислить логины.
Трассировка: CUJ-10; ADR-0011; D-015

#### Scenario: Неизвестный логин
- **WHEN** выполняется вход с несуществующим логином и с существующим логином и неверным паролем
- **THEN** оба ответа имеют одинаковый код 401 и одинаковый `type` = `urn:budb:problem:invalid-credentials`

### Requirement: ACL-17 Версии TLS
При включённом TLS сервер SHALL принимать только TLS 1.3 и TLS 1.2 и MUST отклонять рукопожатие TLS 1.1 и ниже. Сертификат и ключ задаются файлами в конфигурации. Обычный HTTP-запрос на порт TLS не перенаправляется, а отклоняется.
Трассировка: CUJ-05, CUJ-10; ADR-0011, ADR-0017; D-015
Источник: docs/research/03 §6.3

#### Scenario: Старый клиент
- **WHEN** клиент предлагает только TLS 1.1
- **THEN** рукопожатие завершается отказом

#### Scenario: Современный клиент
- **WHEN** клиент подключается по TLS 1.3
- **THEN** соединение устанавливается

### Requirement: ACL-18 Адрес прослушивания по умолчанию
По умолчанию сервер SHALL слушать только loopback-адрес и может работать без TLS. При настройке адреса вне loopback без сертификата сервер MUST отказаться запускаться с понятным сообщением и ненулевым кодом выхода; переопределения нет. [ПРЕДЛОЖЕНИЕ АГЕНТА: без флага обхода]
Трассировка: CUJ-07, CUJ-10; ADR-0011, ADR-0017; D-032, D-033
Источник: docs/research/03 §6.3

#### Scenario: Запуск по умолчанию
- **WHEN** `budb serve` запускается без настроек адреса
- **THEN** сервер принимает соединения только на `127.0.0.1` и `::1`

#### Scenario: Внешний адрес без TLS
- **WHEN** в конфигурации указан адрес `0.0.0.0:8443` без сертификата
- **THEN** сервер не запускается и завершается с кодом ошибки конфигурации

### Requirement: ACL-19 Политика CSP
Каждая HTML-страница SHALL отдаваться с `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`. Inline-скрипты, inline-обработчики событий и внешние источники MUST NOT использоваться.
Трассировка: CUJ-01, CUJ-02; ADR-0011, ADR-0016; D-031
Источник: docs/research/03 §5.4, §6.4

#### Scenario: Заголовок на странице
- **WHEN** браузер загружает главную страницу UI
- **THEN** ответ содержит заголовок CSP с `script-src 'self'` и без `'unsafe-inline'`

#### Scenario: Внедрённый скрипт
- **WHEN** имя контакта содержит `<script>alert(1)</script>`
- **THEN** браузер не выполняет скрипт, а нарушений CSP со стороны самого UI нет

### Requirement: ACL-20 Заголовки безопасности
Каждый ответ SHALL содержать `X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`. Ответы API и страницы с ПДн MUST содержать `Cache-Control: no-store`. При TLS ответы MUST содержать `Strict-Transport-Security` с `max-age` не меньше года. [ПРЕДЛОЖЕНИЕ АГЕНТА: Referrer-Policy и max-age]
Трассировка: CUJ-05; ADR-0011; D-013, D-015
Источник: docs/research/03 §6.1 (API8), §6.2, §6.3

#### Scenario: Ответ поиска
- **WHEN** клиент получает ответ `POST /api/v1/contacts:search`
- **THEN** ответ содержит `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`

#### Scenario: HSTS
- **WHEN** сервер работает с TLS
- **THEN** ответы содержат `Strict-Transport-Security: max-age=31536000`

### Requirement: ACL-21 Первичная инициализация администратора
Система MUST NOT иметь учётных записей и паролей по умолчанию. Первого admin SHALL создавать команда `budb admin bootstrap` по admin-cli (CLI) на базе без администраторов; пароль вводится оператором. Пока admin нет, сервер работает, но любой вход отклоняется.
Трассировка: CUJ-10; ADR-0011; D-015, D-032
Источник: docs/research/03 §6.2

#### Scenario: Новая база
- **WHEN** сервер запущен на новой базе без bootstrap
- **THEN** попытка входа с логином `admin` и любым паролем отклоняется

#### Scenario: Повторный bootstrap
- **WHEN** `budb admin bootstrap` выполняется на базе, где уже есть admin
- **THEN** команда отказывает и не меняет учётные записи

### Requirement: ACL-22 Отсутствие исходящих запросов
Сервер MUST NOT выполнять исходящие сетевые запросы по данным пользователя: импорт SHALL принимать только загруженный файл, без загрузки по URL. Содержимое файлов импорта считается недоверенным и проверяется по import-export (IMP).
Трассировка: CUJ-06; ADR-0011; D-016
Источник: docs/research/03 §6.1 (API7, API10)

#### Scenario: Импорт по URL
- **WHEN** клиент передаёт в запросе импорта URL вместо файла
- **THEN** сервер отклоняет запрос и не обращается к этому URL
