# http-api

## Purpose
Программный HTTP-интерфейс BUDB `/api/v1` для интеграторов и веб-UI: ресурсы, сессия UI, ошибки, условные и идемпотентные запросы, пагинация, лимиты, режимы деградации, фоновые задачи и совместимость версий. Семантику данных и поиска задают contacts (CON), phone-normalization (PHN), search (SRCH) и import-export (IMP), права — access-control (ACL), правила ПДн — data-privacy (PRV), ключи конфигурации — admin-cli (CLI-18).

## ADDED Requirements

### Requirement: API-01 Версионированный базовый путь и формат JSON
Все операции SHALL располагаться под префиксом `/api/v1` и обмениваться `application/json` в UTF-8, кроме загрузки и выгрузки файлов. Запрос с неподдерживаемым Content-Type MUST получать 415, запрос неразрешённым методом — 405 с заголовком `Allow`, где перечислены и `HEAD`, и `GET`.
Трассировка: CUJ-05; ADR-0010; D-059, D-099
Источник: docs/research/03 §4.1, §6.2

#### Scenario: Запрос в JSON принимается
- **WHEN** клиент отправляет `POST /api/v1/contacts` с `Content-Type: application/json` и корректным телом
- **THEN** сервер отвечает 201 с телом `application/json`

#### Scenario: Неподдерживаемый тип тела
- **WHEN** клиент отправляет `POST /api/v1/contacts` с `Content-Type: text/xml`
- **THEN** сервер отвечает 415 с `code` = `unsupported-media-type`

#### Scenario: Неразрешённый метод
- **WHEN** клиент отправляет `PATCH /api/v1/contacts/{id}`
- **THEN** сервер отвечает 405 с заголовком `Allow: GET, HEAD, PUT, DELETE`

### Requirement: API-02 Документ OpenAPI 3.1 отдаётся сервером
Сервер SHALL отдавать описание всего API в формате OpenAPI 3.1 по `GET /api/v1/openapi.json` без аутентификации. Этот документ — единственный источник правды о контракте: каждый ответ API MUST соответствовать его схемам, что проверяется контрактными тестами. [ПРЕДЛОЖЕНИЕ АГЕНТА: путь и доступ без аутентификации]
Трассировка: CUJ-05; ADR-0010; D-059
Источник: docs/research/03 §4.1, §6.1 (API9)

#### Scenario: Получение документа
- **WHEN** клиент без токена запрашивает `GET /api/v1/openapi.json`
- **THEN** сервер отвечает 200, а поле `openapi` в теле начинается с `3.1`

#### Scenario: Ответ расходится со схемой
- **WHEN** контрактный тест получает ответ, поле которого отсутствует в схеме OpenAPI
- **THEN** тест помечается как проваленный, и выпуск блокируется

### Requirement: API-03 Совместимость в рамках v1
В пределах `/api/v1` изменения MUST быть только аддитивными: новые необязательные поля, новые ресурсы, новые значения `code` ошибок. Удаление или переименование поля, смена типа или смысла поля SHALL выпускаться только в `/api/v2`, который какое-то время работает параллельно с v1. Клиент MUST игнорировать незнакомые поля ответа.
Трассировка: CUJ-05; ADR-0010; D-059, D-099
Источник: docs/research/03 §4.1 (AIP-185), §4.2

#### Scenario: Добавлено необязательное поле
- **WHEN** в ответ `GET /api/v1/contacts/{id}` добавляется новое необязательное поле
- **THEN** изменение выпускается в v1, а прежний клиент продолжает работать

#### Scenario: Ломающее изменение
- **WHEN** требуется переименовать поле `display_name`
- **THEN** переименование появляется только в `/api/v2`, а `/api/v1` отвечает в прежнем формате

### Requirement: API-04 Создание контакта
`POST /api/v1/contacts` с представлением контакта по contacts (CON) SHALL создавать контакт и отвечать 201 с заголовками `Location: /api/v1/contacts/{id}` и `ETag`, а в теле — сохранённым контактом по API-30 с нормализованными телефонами. Ответ 201 MUST отправляться только после долговечной фиксации по storage-engine (STO).
Трассировка: CUJ-03, CUJ-05; ADR-0010, ADR-0007; D-009, D-057
Источник: docs/research/03 §4.3

#### Scenario: Успешное создание
- **WHEN** writer отправляет `POST /api/v1/contacts` с `{"display_name":"Анна Петрова","phones":[{"raw_input":"8 916 123-45-67","label":"mobile"}]}`
- **THEN** сервер отвечает 201 с `Location`, `ETag: "1"`, `id` в виде десятичной строки (например, `"1050"`) и `phones[0].e164` = `+79161234567`

#### Scenario: Ошибка до фиксации
- **WHEN** фиксация записи на диск не завершилась
- **THEN** клиент не получает ответ 201

### Requirement: API-05 Чтение контакта
`GET /api/v1/contacts/{id}` SHALL возвращать 200 с представлением контакта по API-30 и строгим `ETag: "<version>"`. При `If-None-Match` с текущим ETag сервер MUST отвечать 304. Несуществующий контакт и контакт в корзине MUST давать 404 с `code` = `not-found`.
Трассировка: CUJ-01, CUJ-05; ADR-0010; D-009, D-012, D-099
Источник: docs/research/03 §4.3

#### Scenario: Контакт найден
- **WHEN** reader запрашивает `GET /api/v1/contacts/{id}` существующего контакта версии 3
- **THEN** сервер отвечает 200 с `ETag: "3"`

#### Scenario: Версия не изменилась
- **WHEN** клиент запрашивает тот же контакт с `If-None-Match: "3"`
- **THEN** сервер отвечает 304 без тела

#### Scenario: Контакт в корзине
- **WHEN** reader запрашивает контакт, перенесённый в корзину
- **THEN** сервер отвечает 404 с `code` = `not-found`

### Requirement: API-06 Изменение контакта полной заменой
`PUT /api/v1/contacts/{id}` SHALL заменять изменяемые поля контакта целиком и при успехе отвечать 200 с новым `ETag` и сохранённым контактом. `id` берётся из пути, ожидаемая версия — из `If-Match`; поля только для чтения в теле игнорируются (API-15). PATCH в v1 не поддерживается. Ответ 200 MUST отправляться только после долговечной фиксации. [ПРЕДЛОЖЕНИЕ АГЕНТА: только PUT]
Трассировка: CUJ-03, CUJ-04; ADR-0010; D-009, D-071

#### Scenario: Успешная замена
- **WHEN** writer отправляет `PUT /api/v1/contacts/{id}` с `If-Match: "3"` и корректным телом
- **THEN** сервер отвечает 200 с `ETag: "4"`

#### Scenario: Тело из ответа GET
- **WHEN** клиент получает контакт через GET, меняет `display_name` и отправляет всё тело, включая `id`, `version`, `created` и `updated`, с `If-Match: "3"`
- **THEN** сервер отвечает 200 с `ETag: "4"`, а значения служебных полей из тела не применяются

#### Scenario: Изменение несуществующего контакта
- **WHEN** writer отправляет `PUT` на несуществующий `id` с `If-Match: "1"`
- **THEN** сервер отвечает 404

### Requirement: API-07 Удаление контакта в корзину
`DELETE /api/v1/contacts/{id}` SHALL переносить контакт в корзину и отвечать 204 с новым `ETag`. После этого контакт MUST не находиться поиском и чтением; восстановление — по API-22, срок хранения в корзине и очистку определяет data-privacy (PRV).
Трассировка: CUJ-03, CUJ-09; ADR-0010, ADR-0012; D-012, D-041
Источник: docs/research/03 §6.5

#### Scenario: Удаление
- **WHEN** writer отправляет `DELETE /api/v1/contacts/{id}` с `If-Match: "4"`
- **THEN** сервер отвечает 204, а `POST /api/v1/contacts:search` по его телефону больше не возвращает этот контакт

#### Scenario: Повторное удаление
- **WHEN** writer повторно отправляет `DELETE` на тот же `id`
- **THEN** сервер отвечает 404

### Requirement: API-08 Отказ 412 при несовпадении версии
Для `PUT`, `DELETE` и `POST /api/v1/contacts/{id}:restore` сервер SHALL сравнивать `If-Match` с текущим ETag строго. При несовпадении он MUST отвечать 412 с `code` = `precondition-failed`, не меняя данные, и возвращать текущий ETag в заголовке `ETag`.
Трассировка: CUJ-04; ADR-0010; D-009, D-041, D-099
Источник: docs/research/03 §4.3 (RFC 9110 §13.1.1)

#### Scenario: Параллельная правка
- **WHEN** два клиента прочитали версию 4, первый успешно сохранил версию 5, а второй отправляет `PUT` с `If-Match: "4"`
- **THEN** второй получает 412 с заголовком `ETag: "5"`, а версия 5 остаётся без изменений

### Requirement: API-09 Отказ 428 без условия If-Match
Запрос `PUT`, `DELETE` или `:restore` без заголовка `If-Match` MUST отклоняться кодом 428 с `code` = `precondition-required` без изменения данных; `detail` SHALL объяснять, что нужно передать ETag из ответа GET в `If-Match`. `If-Match: *` SHALL считаться отсутствием условия.
Трассировка: CUJ-04, CUJ-05; ADR-0010; D-009, D-041, D-099
Источник: docs/research/03 §4.3 (RFC 6585)

#### Scenario: Изменение без If-Match
- **WHEN** клиент отправляет `PUT /api/v1/contacts/{id}` без `If-Match`
- **THEN** сервер отвечает 428 с непустым `detail`, и контакт не меняется

#### Scenario: Подстановочное условие
- **WHEN** клиент отправляет `DELETE /api/v1/contacts/{id}` с `If-Match: *`
- **THEN** сервер отвечает 428

### Requirement: API-10 Поиск только через POST contacts:search
Поиск SHALL выполняться только через `POST /api/v1/contacts:search` с телом `{"field":"phone"|"name","mode":"exact"|"prefix","value":…,"page_size":…,"page_token":…}`; ровно один критерий на запрос. Ответ MUST всегда содержать `contacts` и `next_page_token`, даже пустые. Семантика — по search (SRCH). [ПРЕДЛОЖЕНИЕ АГЕНТА: схема тела]
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-013, D-066
Источник: docs/research/03 §4.7

#### Scenario: Кто звонит
- **WHEN** reader отправляет `{"field":"phone","mode":"exact","value":"8 (916) 123-45-67"}`
- **THEN** сервер отвечает 200 со всеми контактами, у которых есть `+79161234567`

#### Scenario: Префикс номера в национальном формате
- **WHEN** reader отправляет `{"field":"phone","mode":"prefix","value":"8 916 12"}` при регионе по умолчанию `RU`
- **THEN** сервер ищет по префиксу `+791612` и отвечает 200 с контактами, чьи номера начинаются с него

#### Scenario: Префикс имени
- **WHEN** reader отправляет `{"field":"name","mode":"prefix","value":"Сем","page_size":20}`
- **THEN** сервер отвечает 200 с не более чем 20 контактами и полем `next_page_token`

#### Scenario: Ничего не найдено
- **WHEN** по запросу нет совпадений
- **THEN** сервер отвечает 200 с `{"contacts":[],"next_page_token":""}`

### Requirement: API-11 ПДн и секреты не передаются в URL
API MUST NOT принимать имена, телефоны и токены в пути или query-строке. Любой неописанный в OpenAPI query-параметр MUST отклоняться кодом 400 с `code` = `unknown-parameter`, а его значение MUST NOT попадать в логи.
Трассировка: CUJ-01, CUJ-05; ADR-0010, ADR-0011; D-013, D-099
Источник: docs/research/03 §4.7, §6.2

#### Scenario: Телефон в query
- **WHEN** клиент отправляет `GET /api/v1/contacts?phone=+79161234567`
- **THEN** сервер отвечает 400, а журнал запросов не содержит `79161234567`

#### Scenario: Токен в query
- **WHEN** клиент передаёт токен параметром `?access_token=…`
- **THEN** сервер отвечает 400 и не аутентифицирует запрос

### Requirement: API-12 Размер страницы
Списочные операции SHALL принимать необязательный `page_size`: при отсутствии или 0 используется 20, значение больше 100 уменьшается до 100, отрицательное или нецелое MUST давать 422 с кодом поля `page_size.invalid`.
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-024, D-047
Источник: docs/research/03 §4.4 (AIP-158)

#### Scenario: Размер по умолчанию
- **WHEN** клиент вызывает поиск без `page_size`
- **THEN** ответ содержит не более 20 контактов

#### Scenario: Слишком большой размер
- **WHEN** клиент передаёт `page_size: 10000`
- **THEN** ответ содержит не более 100 контактов

#### Scenario: Отрицательный размер
- **WHEN** клиент передаёт `page_size: -1`
- **THEN** сервер отвечает 422

### Requirement: API-13 Непрозрачный курсор страницы
`next_page_token` SHALL быть keyset-позицией, зашифрованной AEAD ключом экземпляра, без ПДн в открытом виде; пустая строка — конец выборки. Каждая страница читается на свежем снимке, токен живёт 24 ч. Изменённый или поданный с другими параметрами токен MUST давать 400 `invalid-page-token`, просроченный — 400 `page-token-expired`. [ПРЕДЛОЖЕНИЕ АГЕНТА: `page-token-expired`]
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-048, D-082

#### Scenario: Следующая страница
- **WHEN** клиент повторяет запрос с полученным `page_token` и теми же параметрами
- **THEN** сервер возвращает следующую страницу без повторов и пропусков записей, не менявшихся между запросами

#### Scenario: Токен не раскрывает ПДн
- **WHEN** тест декодирует из base64 токен страницы поиска по префиксу `+7916123`
- **THEN** результат не содержит подстроки `7916123` и ключа имени

#### Scenario: Смена параметров
- **WHEN** клиент подаёт `page_token` вместе с другим `value`
- **THEN** сервер отвечает 400 с `code` = `invalid-page-token`

#### Scenario: Токен просрочен
- **WHEN** клиент подаёт `page_token`, выданный 25 ч назад
- **THEN** сервер отвечает 400 с `code` = `page-token-expired`, и клиент начинает поиск заново

### Requirement: API-14 Ошибки в формате RFC 9457
Каждый ответ 4xx и 5xx SHALL иметь тип `application/problem+json` с полями `type`, `code`, `title`, `status` и при необходимости `detail`. `code` — стабильный код в kebab-case, клиенты MUST сравнивать именно его; `type` = `{public_origin}/problems/<code>`, и по этому адресу сервер отдаёт описание ошибки. Стектрейсы и ПДн MUST NOT попадать в ответ.
Трассировка: CUJ-05; ADR-0010; D-013, D-099, D-101

#### Scenario: Ресурс не найден
- **WHEN** клиент запрашивает несуществующий контакт с `Accept-Language: en` при `public_origin` = `https://budb.example`
- **THEN** сервер отвечает 404 с `code` = `not-found`, `type` = `https://budb.example/problems/not-found` и английским `title`

#### Scenario: Описание типа ошибки
- **WHEN** клиент без учётных данных открывает `https://budb.example/problems/not-found`
- **THEN** сервер отвечает 200 с описанием ошибки на языке из `Accept-Language`

#### Scenario: Внутренняя ошибка
- **WHEN** обработка запроса завершилась внутренней ошибкой
- **THEN** сервер отвечает 500 с `code` = `internal` без стектрейса

### Requirement: API-15 Ошибки валидации с кодами полей
Нарушение правил данных SHALL давать 422 с `code` = `validation-error` и `errors[]` из `{pointer, code}`: `pointer` — JSON Pointer, `code` — код из CON, PHN или NAM вида `поле.причина`. Незнакомые поля MUST давать 422. Поля только для чтения (`id`, `version`, `created`, `updated`) SHALL игнорироваться при создании и изменении. Неверный JSON — 400.
Трассировка: CUJ-03, CUJ-05; ADR-0010; D-022, D-071
Источник: docs/research/03 §4.2, §6.1 (API3)

#### Scenario: Невозможный номер
- **WHEN** writer создаёт контакт с телефоном `12`
- **THEN** сервер отвечает 422, и `errors` содержит элемент с `pointer` = `/phones/0/raw_input`

#### Scenario: Незнакомое поле
- **WHEN** тело содержит `"note":"…"`
- **THEN** сервер отвечает 422 и не сохраняет контакт

#### Scenario: Поле только для чтения
- **WHEN** тело `POST /api/v1/contacts` содержит `"id":"7"` и `"version":7`
- **THEN** сервер отвечает 201, назначает свой `id` и `ETag: "1"`

#### Scenario: Битый JSON
- **WHEN** тело запроса не является корректным JSON
- **THEN** сервер отвечает 400

### Requirement: API-16 Повтор запроса с Idempotency-Key
Создание контакта, импорт, экспорт и изменения по API-33 SHALL принимать `Idempotency-Key`; для импорта он обязателен. Повтор с тем же ключом и телом от того же субъекта в течение 24 ч MUST возвращать сохранённый ответ без повтора. Purge (API-24) и `subjects:erase` (API-34) MUST заменять запись ключа с данными субъекта надгробием без ПДн (ключ, субъект, `purged`) с прежним TTL: повтор получает 410 `purged`.
Трассировка: CUJ-05, CUJ-06; ADR-0010; D-055, D-059, D-065, D-110, D-116, D-120, D-121

#### Scenario: Повтор после обрыва связи
- **WHEN** клиент повторяет `POST /api/v1/contacts` с тем же `Idempotency-Key` и телом
- **THEN** сервер возвращает тот же 201 и тот же `Location`, а второй контакт не создаётся

#### Scenario: Ключ истёк
- **WHEN** клиент повторяет запрос с тем же ключом через 25 ч
- **THEN** сервер обрабатывает его как новый

#### Scenario: Повтор после purge
- **WHEN** контакт, созданный с ключом `K`, очищен, и клиент в пределах 24 ч повторяет создание с ключом `K` и тем же телом
- **THEN** сервер отвечает 410 с `code` = `purged`, и контакт не создаётся

#### Scenario: Надгробие без ПДн
- **WHEN** purge контакта выполнен, и проверяется запись его `Idempotency-Key`
- **THEN** запись не содержит сохранённого ответа, имени и телефонов, а только ключ, субъекта и признак `purged`, хэша тела нет

### Requirement: API-17 Ошибки использования Idempotency-Key
Сервер SHALL отвечать: 400 `idempotency-key-missing`, если обязательный ключ не передан или некорректен; 422 `idempotency-key-reused`, если ключ уже использован с другим телом; 409 `idempotency-request-in-progress`, если исходный запрос с этим ключом ещё выполняется. Ни в одном из этих случаев операция MUST NOT выполняться.
Трассировка: CUJ-05, CUJ-06; ADR-0010; D-059, D-099
Источник: docs/research/03 §4.5

#### Scenario: Импорт без ключа
- **WHEN** writer отправляет `POST /api/v1/imports` без `Idempotency-Key`
- **THEN** сервер отвечает 400 и не создаёт задачу

#### Scenario: Другое тело с тем же ключом
- **WHEN** клиент повторно использует ключ с другим телом
- **THEN** сервер отвечает 422

#### Scenario: Параллельный повтор
- **WHEN** повтор приходит, пока исходный запрос ещё выполняется
- **THEN** сервер отвечает 409

### Requirement: API-18 Лимит размера тела
Сервер MUST отклонять кодом 413 с `code` = `payload-too-large` JSON-тело больше 64 KiB и загрузку импорта больше 1 GiB, не читая тело дальше предела; оба лимита SHALL настраиваться (CLI-18). Тело с `Content-Encoding`, отличным от `identity`, MUST давать 415, чтобы лимит нельзя было обойти сжатием. [ПРЕДЛОЖЕНИЕ АГЕНТА: значения]
Трассировка: CUJ-05, CUJ-06; ADR-0010, ADR-0017; D-033, D-073
Источник: docs/research/03 §4.6, §6.1 (API4)

#### Scenario: Слишком большое тело
- **WHEN** клиент отправляет `POST /api/v1/contacts` с телом 100 KiB
- **THEN** сервер отвечает 413

#### Scenario: Тело в пределах лимита
- **WHEN** клиент отправляет корректное тело 2 KiB
- **THEN** запрос обрабатывается обычным образом

#### Scenario: Сжатое тело
- **WHEN** клиент отправляет `POST /api/v1/imports` с `Content-Encoding: gzip`
- **THEN** сервер отвечает 415 и не распаковывает тело

### Requirement: API-19 Ограничение частоты 429 с Retry-After
Сервер SHALL ограничивать частоту запросов на токен или сессию: по умолчанию 50 запросов/с с запасом 100, лимит настраивается для каждого токена, у токена бенчмарка лимита может не быть (CLI-06). Запросы без действительных учётных данных ограничиваются по IP (ACL-23). При превышении MUST отвечать 429 с `Retry-After` и `code` = `rate-limited`. [ПРЕДЛОЖЕНИЕ АГЕНТА: запас 100, IP]
Трассировка: CUJ-05, CUJ-08; ADR-0010, ADR-0017; D-032, D-073, D-101

#### Scenario: Превышение лимита
- **WHEN** один токен с лимитом по умолчанию отправляет 300 запросов за секунду
- **THEN** принимаются не больше 150 запросов, остальные получают 429 с заголовком `Retry-After`

#### Scenario: Обычная нагрузка
- **WHEN** токен отправляет 10 запросов в секунду
- **THEN** ни один из них не получает 429

#### Scenario: Токен бенчмарка
- **WHEN** токен, созданный без лимита частоты, отправляет 5 000 поисков в секунду
- **THEN** ни один из них не получает 429 с `code` = `rate-limited`

### Requirement: API-20 Перегрузка и неготовность 503 с Retry-After
При заполненной очереди записей сервер MUST отвечать 503 `overloaded`, пока не готов (открытие, восстановление) — 503 `not-ready`, а при переиндексации (NAM-10) на поиск по имени и записи, меняющие имя, — 503 `index-rebuilding`; purge и `subjects:erase` не отклоняются, а прерывают её. Ответы SHALL содержать `Retry-After`; операция не начинается. Деградация хранилища — по API-31.
Трассировка: CUJ-03, CUJ-08; ADR-0010, ADR-0017; D-032, D-099, D-120, D-121
Источник: docs/research/03 §4.6

#### Scenario: Очередь записей заполнена
- **WHEN** writer отправляет `PUT`, когда очередь фиксации заполнена
- **THEN** сервер отвечает 503 с `code` = `overloaded` и `Retry-After`, и контакт не меняется

#### Scenario: Сервер ещё открывает базу
- **WHEN** reader отправляет поиск до завершения открытия хранилища
- **THEN** сервер отвечает 503 с `code` = `not-ready` и `Retry-After`

#### Scenario: Смена имени при переиндексации
- **WHEN** идёт переиндексация (NAM-10), и writer отправляет `PUT` со сменой `display_name`
- **THEN** сервер отвечает 503 с `code` = `index-rebuilding` и `Retry-After`, и контакт не меняется

#### Scenario: Повтор после ожидания
- **WHEN** клиент повторяет тот же запрос по истечении `Retry-After` после снятия перегрузки
- **THEN** запрос выполняется обычным образом

### Requirement: API-21 Коды 401 и 403
Запрос без действительных учётных данных (bearer-токена или cookie сессии) MUST получать 401 с `WWW-Authenticate: Bearer` и `code` = `unauthenticated`. Запрос аутентифицированного субъекта без нужной роли или области токена MUST получать 403 с `code` = `forbidden`. Правила — по access-control (ACL).
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015, D-099, D-103
Источник: docs/research/03 §6.1 (API2, API5), §6.2

#### Scenario: Нет токена
- **WHEN** клиент вызывает `POST /api/v1/contacts:search` без `Authorization`
- **THEN** сервер отвечает 401 с `WWW-Authenticate: Bearer`

#### Scenario: Недостаточно прав
- **WHEN** reader отправляет `DELETE /api/v1/contacts/{id}`
- **THEN** сервер отвечает 403, и контакт не удаляется

### Requirement: API-22 Корзина: просмотр и восстановление
Writer и admin SHALL видеть корзину через `GET /api/v1/trash` с пагинацией (API-12, API-13; элементы по API-30) и восстанавливать контакт в пределах срока (CON-17) через `POST /api/v1/contacts/{id}:restore` с `If-Match`: 200 с контактом и новым ETag. Reader MUST получать 403; активный контакт — 409 `not-in-trash`, очищенный или просроченный — 404. [ПРЕДЛОЖЕНИЕ АГЕНТА: путь и 409]
Трассировка: CUJ-03, CUJ-09; ADR-0012; D-041, D-064

#### Scenario: Восстановление writer
- **WHEN** writer вызывает `POST /api/v1/contacts/{id}:restore` с `If-Match` из элемента корзины
- **THEN** сервер отвечает 200 с новым `ETag`, и контакт снова находится поиском

#### Scenario: Элемент корзины содержит версию
- **WHEN** writer запрашивает `GET /api/v1/trash`
- **THEN** каждый элемент содержит `id`, `display_name`, `version`, `deleted_at` и `purge_after`

#### Scenario: Reader открывает корзину
- **WHEN** reader запрашивает `GET /api/v1/trash`
- **THEN** сервер отвечает 403

#### Scenario: Восстановление активного контакта
- **WHEN** writer вызывает `:restore` для контакта, который не в корзине
- **THEN** сервер отвечает 409 с `code` = `not-in-trash`

### Requirement: API-23 Отмена своего удаления (заменено)
Требование заменено API-22 (D-041): отдельного окна отмены и ресурса `:undelete` нет, отмена удаления в UI — это восстановление из корзины. Запрос к `POST /api/v1/contacts/{id}:undelete` MUST обрабатываться как запрос к неописанному ресурсу.
Трассировка: CUJ-03; ADR-0012; D-041

#### Scenario: Вызов прежнего ресурса
- **WHEN** writer вызывает `POST /api/v1/contacts/{id}:undelete`
- **THEN** сервер отвечает 404, и состояние контакта не меняется

### Requirement: API-24 Немедленная очистка контакта (purge)
Admin SHALL очищать активный или удалённый контакт через `POST /api/v1/admin/contacts/{id}:purge`: ответ 200 с квитанцией `{purge_id, contact_id, status, erase_deadline}`, статус — по `GET /api/v1/admin/purges/{purge_id}`, гарантии — по PRV. Повтор для уже очищенного `id` MUST возвращать прежнюю квитанцию (по `contact_id` из `purge.journal`), неизвестный `id` — 404. [ПРЕДЛОЖЕНИЕ АГЕНТА: повтор]
Трассировка: CUJ-09; ADR-0012; D-012, D-076, D-120
Источник: docs/research/03 §6.5

#### Scenario: Очистка по запросу субъекта
- **WHEN** admin вызывает `:purge` для контакта
- **THEN** сервер отвечает 200 с `purge_id`, а `GET /api/v1/contacts/{id}` и корзина больше не возвращают контакт

#### Scenario: Повторная очистка
- **WHEN** admin повторно вызывает `:purge` для того же `id`
- **THEN** сервер отвечает 200 с тем же `purge_id`, найденным по `contact_id` перечитыванием `purge.journal` (записи контакта уже нет), и новая запись журнала purge не создаётся

#### Scenario: Writer пытается очистить
- **WHEN** writer вызывает `:purge`
- **THEN** сервер отвечает 403

### Requirement: API-25 Импорт как асинхронная задача
`POST /api/v1/imports?format=csv|ndjson&dry_run=…&on_conflict=create_always|skip_exact` с файлом в теле SHALL создавать задачу и отвечать 202 с `Location: /api/v1/jobs/{id}`. `GET /api/v1/jobs/{id}` MUST возвращать задачу по API-32 и ссылку на построчный отчёт без значений ПДн. Трассировка: CUJ-06; ADR-0010; D-016, D-053, D-084
Источник: docs/research/03 §4.8

#### Scenario: Запуск импорта
- **WHEN** writer отправляет CSV-файл в `POST /api/v1/imports?format=csv&dry_run=true`
- **THEN** сервер отвечает 202 с `Location` задачи

#### Scenario: Завершение импорта
- **WHEN** задача завершилась
- **THEN** `GET /api/v1/jobs/{id}` возвращает `status` = `succeeded` и счётчики, где принятые плюс отклонённые равны общему числу строк

#### Scenario: Чужая задача
- **WHEN** другой writer запрашивает эту задачу
- **THEN** сервер отвечает 404

### Requirement: API-26 Экспорт как асинхронная задача
Admin SHALL запускать экспорт через `POST /api/v1/exports` с `{"format":"csv"|"ndjson"}` и получать 202 с задачей. Готовый файл MUST отдаваться по `GET /api/v1/jobs/{id}/result` и отражать снимок на момент старта; до готовности — 409 `job-not-ready`, после удаления файла (срок или purge, PRV-16) — 410. - **WHEN** задача экспорта в NDJSON завершилась
- **THEN** `GET /api/v1/jobs/{id}/result` отвечает 200 с `Content-Type: application/x-ndjson`

#### Scenario: Экспорт от writer
- **WHEN** writer вызывает `POST /api/v1/exports`
- **THEN** сервер отвечает 403

#### Scenario: Результат удалён после purge
- **WHEN** контакт из готового файла экспорта очищен через purge
- **THEN** `GET /api/v1/jobs/{id}/result` отвечает 410

### Requirement: API-27 Административные ресурсы
Административные операции SHALL располагаться только под `/api/v1/admin/` и требовать роли admin: `status`, `users`, `tokens`, `backups`, `verifications`, `audit`, `purges`, `contacts/{id}:purge`, `subjects:search`, `subjects:erase`, `users/{id}:confirm`, `status:clear-degraded`, `clock:confirm` (API-39…API-41); корзина — API-22. Бэкап и проверка MUST быть задачами.
Трассировка: CUJ-07, CUJ-08, CUJ-10; ADR-0010, ADR-0011; D-017, D-025, D-041, D-046, D-089, D-117
Источник: docs/research/03 §6.1

#### Scenario: Состояние БД
- **WHEN** admin запрашивает `GET /api/v1/admin/status`
- **THEN** сервер отвечает 200 с числом контактов, размером хранилища, временем последнего бэкапа и режимом работы (`read-write` или `degraded-read-only`)

#### Scenario: Онлайн-бэкап
- **WHEN** admin вызывает `POST /api/v1/admin/backups`
- **THEN** сервер отвечает 202 с `Location` задачи, пара `<ts>.budb` и `<ts>.purge` пишется в `backup_dir` сервера, скачивания файла по API нет

#### Scenario: Повторная нормализация только офлайн
- **WHEN** admin ищет под `/api/v1/admin/` ресурс повторной нормализации телефонов
- **THEN** такого ресурса нет: `renormalize-phones` выполняется только офлайн (CLI-04)

#### Scenario: Reader обращается к admin
- **WHEN** reader запрашивает `GET /api/v1/admin/status`
- **THEN** сервер отвечает 403

### Requirement: API-28 Предпросмотр нормализации номера
`POST /api/v1/phones:normalize` с `{"raw_input":…}` SHALL возвращать 200 с `e164` и `extension` по правилам phone-normalization (PHN), ничего не сохраняя. Невозможный номер MUST давать 422 с тем же кодом поля, что и при создании контакта. Доступно с роли reader. [ПРЕДЛОЖЕНИЕ АГЕНТА]
Трассировка: CUJ-03, CUJ-05; ADR-0008, ADR-0010; D-010
Источник: docs/research/03 §1.5

#### Scenario: Национальный формат
- **WHEN** клиент отправляет `{"raw_input":"8 (916) 123-45-67 доб. 12"}`
- **THEN** сервер отвечает 200 с `e164` = `+79161234567` и `extension` = `12`

#### Scenario: Невозможный номер
- **WHEN** клиент отправляет `{"raw_input":"12"}`
- **THEN** сервер отвечает 422

### Requirement: API-29 Сессия веб-UI
Ресурс `/api/v1/session` SHALL управлять UI-сессией: `POST` с `{login, password}` — вход и cookie (ACL-11); `GET` — `{user, role, csrf_token, idle_expires_at, absolute_expires_at}`; `DELETE` — выход (ACL-13). UI MUST держать `csrf_token` только в памяти и передавать в `X-CSRF-Token` (ACL-14). Отказы входа — по ACL-15, ACL-16. [ПРЕДЛОЖЕНИЕ АГЕНТА: поля сроков]
Трассировка: CUJ-01, CUJ-10; ADR-0011, ADR-0016; D-068, D-106

#### Scenario: Вход
- **WHEN** пользователь отправляет `POST /api/v1/session` с верными логином и паролем
- **THEN** сервер отвечает 204 с `Set-Cookie` сессии

#### Scenario: Получение CSRF-токена
- **WHEN** UI после входа вызывает `GET /api/v1/session`
- **THEN** ответ 200 содержит роль пользователя, непустой `csrf_token` и оба срока сессии

#### Scenario: Выход
- **WHEN** UI вызывает `DELETE /api/v1/session` с заголовком `X-CSRF-Token`
- **THEN** сервер отвечает 204, и следующий запрос с той же cookie получает 401

#### Scenario: Неверный пароль
- **WHEN** пользователь отправляет `POST /api/v1/session` с неверным паролем
- **THEN** сервер отвечает 401 с `code` = `invalid-credentials`

### Requirement: API-30 Представление контакта в JSON
Контакт SHALL представляться полями contacts (CON): `id` — десятичная строка u64, `version` — целое число, `created` и `updated` — RFC 3339 в UTC с миллисекундами, телефоны — по CON-04. Элемент корзины MUST дополнительно содержать `deleted_at` и `purge_after` в том же формате. Числовой `id` в JSON MUST NOT использоваться. [ПРЕДЛОЖЕНИЕ АГЕНТА: формат времени]
Трассировка: CUJ-05; ADR-0007, ADR-0010; D-057, D-064, D-084

#### Scenario: Идентификатор строкой
- **WHEN** клиент читает контакт с `id`, равным 2^53 + 1
- **THEN** тело содержит `"id":"9007199254740993"`, и значение не теряет точность в JavaScript

#### Scenario: Время в ответе
- **WHEN** клиент читает контакт
- **THEN** `created` и `updated` имеют вид `2026-10-24T12:00:00.000Z`

### Requirement: API-31 Ответы при деградации хранилища
Пока хранилище в режиме «только чтение» после найденного повреждения или из-за нехватки места, чтения SHALL обслуживаться, а записи MUST отклоняться без выполнения: 503 `degraded-read-only` или 507 `insufficient-storage`. В fail-stop до выхода процесса (не дольше 5 с) все запросы MUST получать 503 `storage-failed`. [ПРЕДЛОЖЕНИЕ АГЕНТА: значения `code`]
Трассировка: CUJ-01, CUJ-03, CUJ-08; ADR-0005, ADR-0010; D-034, D-072, D-078, D-089

#### Scenario: Повреждение при работе
- **WHEN** во время работы найдена повреждённая страница, и затем reader ищет, а writer отправляет `PUT`
- **THEN** поиск получает 200, а `PUT` — 503 с `code` = `degraded-read-only`, и контакт не меняется

#### Scenario: Не хватает места
- **WHEN** перед фиксацией обнаружено, что на томе не хватает места
- **THEN** запись получает 507 с `code` = `insufficient-storage`, а чтения продолжают получать 200

#### Scenario: Fail-stop
- **WHEN** сброс на диск завершился ошибкой
- **THEN** до выхода процесса запросы получают 503 с `code` = `storage-failed`

### Requirement: API-32 Единая модель фоновых задач
Импорт, экспорт, бэкап и проверка целостности SHALL быть задачами одного вида `GET /api/v1/jobs/{id}`: `{id, kind, status, created, finished, counters, reason}`, где `status` — `queued`, `running`, `succeeded` или `failed`, а `reason` — `code` причины отказа. Состояние задач MUST переживать перезапуск сервера. [ПРЕДЛОЖЕНИЕ АГЕНТА: состав полей]
Трассировка: CUJ-06, CUJ-07; ADR-0010; D-064, D-084

#### Scenario: Успешная задача
- **WHEN** бэкап завершился без ошибок
- **THEN** `GET /api/v1/jobs/{id}` возвращает `kind` = `backup` и `status` = `succeeded`

#### Scenario: Перезапуск во время задачи
- **WHEN** сервер перезапущен, пока импорт был в состоянии `running`
- **THEN** после запуска задача имеет `status` = `failed` и `reason` = `interrupted`

#### Scenario: Снимок принудительно закрыт
- **WHEN** проверка целостности прервана из-за превышения срока снимка (PRV-07)
- **THEN** задача имеет `status` = `failed` и `reason` = `snapshot-expired`

#### Scenario: Экспорт прерван purge
- **WHEN** контакт очищен, пока шёл экспорт, начатый раньше (PRV-05, IMP-17)
- **THEN** задача имеет `status` = `failed` и `reason` = `contact-purged`

### Requirement: API-33 Повтор изменений и неизвестный исход
`PUT`, `DELETE` и `:restore` SHALL принимать необязательный `Idempotency-Key` по API-16 и API-17: повтор с тем же ключом после потерянного ответа MUST возвращать сохранённый ответ, а не 412. Если исход фиксации неизвестен (STO-12), сервер MUST отвечать 500 `outcome-unknown`, и клиент повторяет запрос с тем же ключом или перечитывает контакт. [ПРЕДЛОЖЕНИЕ АГЕНТА]
Трассировка: CUJ-03, CUJ-04, CUJ-05; ADR-0010; D-034, D-059

#### Scenario: Ответ на PUT потерян
- **WHEN** `PUT` с `If-Match: "3"` и ключом `K` применён, ответ потерян, и клиент повторяет тот же запрос с ключом `K`
- **THEN** сервер возвращает сохранённый ответ 200 с `ETag: "4"`, а не 412

#### Scenario: Исход неизвестен
- **WHEN** сброс при фиксации запроса завершился ошибкой после записи данных
- **THEN** клиент получает 500 с `code` = `outcome-unknown`, а не 200 и не ответ об отказе

### Requirement: API-34 Затирание данных субъекта в чужих контактах
Admin SHALL исполнять запрос субъекта ПДн через `POST /api/v1/admin/subjects:erase` с `{contact_ids, phones}`: контакты из `contact_ids` очищаются по API-24, а каждый номер из `phones` удаляется из всех остальных контактов, включая корзину, как изменение с новой `version`. Ответ 200 MUST содержать квитанции purge и `id` изменённых контактов; затирание — по PRV-18. [ПРЕДЛОЖЕНИЕ АГЕНТА: схема]
Трассировка: CUJ-09; ADR-0010, ADR-0012; D-102, D-121

#### Scenario: Семейный номер в чужом контакте
- **WHEN** admin вызывает `subjects:erase` с `{"contact_ids":["1050"],"phones":["+79161234567"]}`, а номер есть ещё в контакте `2001`
- **THEN** контакт `1050` очищен, у контакта `2001` номера `+79161234567` больше нет, а остальные его данные и номера сохранены

#### Scenario: Сохранённый ответ с номером субъекта
- **WHEN** ответ на изменение контакта `2001` с номером `+79161234567` хранится под ключом `K`, и admin выполняет `subjects:erase` для этого номера
- **THEN** запись ключа `K` заменена надгробием без ответа, а повтор с `K` получает 410 `purged`
- **AND** цифры номера не находятся в файлах базы не позднее 24 ч

#### Scenario: Writer вызывает затирание
- **WHEN** writer вызывает `POST /api/v1/admin/subjects:erase`
- **THEN** сервер отвечает 403, и данные не меняются

### Requirement: API-35 Регион нормализации в запросах
Операции, нормализующие телефон, SHALL принимать необязательный регион операции по PHN-08: поле `region` в теле `contacts:search` и `phones:normalize`, параметр `region` у `POST /api/v1/imports` и поле `phones[].region` при создании и изменении контакта. Без него MUST применяться регион по умолчанию (PHN-07). [ПРЕДЛОЖЕНИЕ АГЕНТА: имена полей]
Трассировка: CUJ-01, CUJ-03, CUJ-06; ADR-0008, ADR-0010; D-010, D-052

#### Scenario: Регион none
- **WHEN** клиент отправляет `phones:normalize` с `{"raw_input":"8 916 123-45-67","region":"none"}`
- **THEN** сервер отвечает 422 с кодом поля `phone.region_required`

#### Scenario: Регион по умолчанию
- **WHEN** клиент отправляет тот же ввод без `region`, а регион по умолчанию — `RU`
- **THEN** сервер отвечает 200 с `e164` = `+79161234567`

### Requirement: API-36 Коды тайм-аута поиска и исчерпания квоты
Поиск, прерванный по тайм-ауту (SRCH-16), SHALL получать 503 с `code` = `query-timeout` и `Retry-After`. Поиск или чтение при исчерпанной квоте выдачи (ACL-25) MUST получать 429 с `code` = `quota-exceeded` и `Retry-After`. Частичный результат не возвращается.
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-078, D-083, D-112, D-118

#### Scenario: Тайм-аут поиска
- **WHEN** поиск не завершился за `query_timeout_ms` (по умолчанию 2 с)
- **THEN** сервер отвечает 503 с `code` = `query-timeout` и заголовком `Retry-After`, тело без контактов

#### Scenario: Квота исчерпана
- **WHEN** токен исчерпал квоту выдачи за скользящий час и отправляет поиск
- **THEN** сервер отвечает 429 с `code` = `quota-exceeded` (не `rate-limited`) и заголовком `Retry-After`

### Requirement: API-37 CSRF для поиска и освобождение bearer-запросов
Все небезопасные методы с cookie-аутентификацией, включая `POST /api/v1/contacts:search`, SHALL проходить проверку CSRF по ACL-14. Запросы с bearer-токеном MUST быть освобождены от неё, поскольку браузер не добавляет такой заголовок сам.
Трассировка: CUJ-01, CUJ-05; ADR-0010, ADR-0011; D-068, D-113

#### Scenario: Поиск с cookie без CSRF-токена
- **WHEN** запрос `POST /api/v1/contacts:search` с cookie сессии не содержит `X-CSRF-Token`
- **THEN** сервер отвечает 403 с `code` = `csrf-failed`, поиск не выполняется

#### Scenario: Поиск с bearer-токеном
- **WHEN** интегратор отправляет `POST /api/v1/contacts:search` с заголовком `Authorization: Bearer` и без `X-CSRF-Token`
- **THEN** сервер отвечает 200, проверка CSRF не применяется

### Requirement: API-38 Префикс телефона без плюса — национальный номер
Сервер SHALL нормализовать префикс телефона в `POST /api/v1/contacts:search` с `field` = `phone` и `mode` = `prefix` только по PHN-17, который остаётся единственным источником правил; собственных правил API не вводит. Международный префикс MUST задаваться ведущим `+`.
Трассировка: CUJ-01, CUJ-05; ADR-0008, ADR-0010; D-052, D-113, D-116

#### Scenario: Префикс без плюса и без 8
- **WHEN** reader отправляет `{"field":"phone","mode":"prefix","value":"916"}` при регионе по умолчанию `RU`
- **THEN** сервер ищет по префиксу `+7916`

#### Scenario: Префикс с кодом страны без плюса
- **WHEN** reader отправляет `{"field":"phone","mode":"prefix","value":"7916"}` при регионе по умолчанию `RU`
- **THEN** сервер ищет по префиксу `+7916` по ветке `7` PHN-17, а не по `+77916`

#### Scenario: Международный префикс
- **WHEN** reader отправляет `{"field":"phone","mode":"prefix","value":"+4420"}`
- **THEN** сервер ищет по префиксу `+4420` независимо от региона по умолчанию

### Requirement: API-39 Подтверждение пользователя после restore
Admin SHALL снимать пометку `review_required` (ACL-27) вызовом `POST /api/v1/admin/users/{id}:confirm`: ответ 200 с учётной записью и событием аудита. Повтор для подтверждённого пользователя MUST возвращать 200 без изменений, неизвестный `id` — 404. Идентификатор пользователя совпадает с его логином.
Трассировка: CUJ-07, CUJ-10; ADR-0010, ADR-0011; D-113, D-117, D-118

#### Scenario: Подтверждение пользователя
- **WHEN** admin вызывает `POST /api/v1/admin/users/anna:confirm` для пользователя с `review_required`
- **THEN** сервер отвечает 200, пометка снята, в аудите есть событие, и `anna` входит с прежним паролем

#### Scenario: Неизвестный пользователь
- **WHEN** admin вызывает `POST /api/v1/admin/users/nobody:confirm`
- **THEN** сервер отвечает 404

#### Scenario: Writer пытается подтвердить
- **WHEN** writer вызывает `POST /api/v1/admin/users/anna:confirm`
- **THEN** сервер отвечает 403

### Requirement: API-40 Снятие degraded-read-only после повреждения
Admin SHALL вызывать `POST /api/v1/admin/status:clear-degraded`: сервер запускает онлайн-проверку (BKP-09) как задачу (API-32), отвечает 202 с `Location`, и режим снимается движком только если проверка завершилась `succeeded` (STO-40). Если режим включён не из-за повреждения, ответ MUST быть 409 `not-degraded`.
Трассировка: CUJ-07, CUJ-08; ADR-0005, ADR-0010; D-089, D-117, D-118

#### Scenario: Проверка прошла
- **WHEN** сервер в режиме degraded-read-only из-за повреждения, и admin вызывает `:clear-degraded`, а проверка не находит нарушений
- **THEN** сервер отвечает 202, задача завершается `succeeded`, и `GET /readyz` отвечает со `status` = `ok`

#### Scenario: Проверка нашла нарушения
- **WHEN** проверка по `:clear-degraded` находит повреждённую страницу
- **THEN** задача завершается `failed`, режим degraded-read-only сохраняется

#### Scenario: Режим не включён
- **WHEN** admin вызывает `:clear-degraded` на сервере в режиме `ok`
- **THEN** сервер отвечает 409 с `code` = `not-degraded`

### Requirement: API-41 Подтверждение скачка часов
Admin SHALL вызывать `POST /api/v1/admin/clock:confirm`, чтобы после паузы по OBS-21 возобновить автоочистку корзины и ротацию бэкапов: сервер сбрасывает признак паузы, принимает текущее расхождение часов за норму и пишет событие аудита. Если паузы нет, ответ 200 без изменений.
Трассировка: CUJ-07, CUJ-08, CUJ-09; ADR-0012, ADR-0013; D-081, D-117

#### Scenario: Возобновление после скачка
- **WHEN** автоочистка приостановлена из-за скачка часов, и admin вызывает `:confirm`
- **THEN** сервер отвечает 200, признак паузы равен 0, и автоочистка снова выполняется

#### Scenario: Паузы нет
- **WHEN** admin вызывает `:confirm`, пока пауза не включена
- **THEN** сервер отвечает 200, состояние не меняется

#### Scenario: Reader пытается подтвердить
- **WHEN** reader вызывает `POST /api/v1/admin/clock:confirm`
- **THEN** сервер отвечает 403
