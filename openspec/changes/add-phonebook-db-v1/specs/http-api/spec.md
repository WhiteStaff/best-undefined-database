# http-api

## Purpose
Программный HTTP-интерфейс BUDB `/api/v1` для интеграторов и веб-UI: ресурсы, ошибки, условные и идемпотентные запросы, пагинация, лимиты, фоновые задачи и совместимость версий. Семантику данных и поиска задают contacts (CON), phone-normalization (PHN), search (SRCH) и import-export (IMP), права — access-control (ACL), правила ПДн — data-privacy (PRV).

## ADDED Requirements

### Requirement: API-01 Версионированный базовый путь и формат JSON
Все операции SHALL располагаться под префиксом `/api/v1` и обмениваться `application/json` в UTF-8, кроме загрузки и выгрузки файлов. Запрос с неподдерживаемым Content-Type MUST получать 415, запрос неразрешённым методом — 405 с заголовком `Allow`.
Трассировка: CUJ-05; ADR-0010; D-030
Источник: docs/research/03 §4.1, §6.2

#### Scenario: Запрос в JSON принимается
- **WHEN** клиент отправляет `POST /api/v1/contacts` с `Content-Type: application/json` и корректным телом
- **THEN** сервер отвечает 201 с телом `application/json`

#### Scenario: Неподдерживаемый тип тела
- **WHEN** клиент отправляет `POST /api/v1/contacts` с `Content-Type: text/xml`
- **THEN** сервер отвечает 415 с `type` = `urn:budb:problem:unsupported-media-type`

#### Scenario: Неразрешённый метод
- **WHEN** клиент отправляет `PATCH /api/v1/contacts/{id}`
- **THEN** сервер отвечает 405 с заголовком `Allow: GET, PUT, DELETE`

### Requirement: API-02 Документ OpenAPI 3.1 отдаётся сервером
Сервер SHALL отдавать описание всего API в формате OpenAPI 3.1 по `GET /api/v1/openapi.json` без аутентификации. Этот документ — единственный источник правды о контракте: каждый ответ API MUST соответствовать его схемам, что проверяется контрактными тестами. [ПРЕДЛОЖЕНИЕ АГЕНТА: путь и доступ без аутентификации]
Трассировка: CUJ-05; ADR-0010; D-030
Источник: docs/research/03 §4.1, §6.1 (API9)

#### Scenario: Получение документа
- **WHEN** клиент без токена запрашивает `GET /api/v1/openapi.json`
- **THEN** сервер отвечает 200, а поле `openapi` в теле начинается с `3.1`

#### Scenario: Ответ расходится со схемой
- **WHEN** контрактный тест получает ответ, поле которого отсутствует в схеме OpenAPI
- **THEN** тест помечается как проваленный, и выпуск блокируется

### Requirement: API-03 Совместимость в рамках v1
В пределах `/api/v1` изменения MUST быть только аддитивными: новые необязательные поля, новые ресурсы, новые значения `type` ошибок. Удаление или переименование поля, смена типа или смысла поля SHALL выпускаться только в `/api/v2`, который какое-то время работает параллельно с v1. Клиент MUST игнорировать незнакомые поля ответа.
Трассировка: CUJ-05; ADR-0010; D-030
Источник: docs/research/03 §4.1 (AIP-185), §4.2

#### Scenario: Добавлено необязательное поле
- **WHEN** в ответ `GET /api/v1/contacts/{id}` добавляется новое необязательное поле
- **THEN** изменение выпускается в v1, а прежний клиент продолжает работать

#### Scenario: Ломающее изменение
- **WHEN** требуется переименовать поле `display_name`
- **THEN** переименование появляется только в `/api/v2`, а `/api/v1` отвечает в прежнем формате

### Requirement: API-04 Создание контакта
`POST /api/v1/contacts` с представлением контакта по правилам contacts (CON) SHALL создавать контакт и отвечать 201 с заголовками `Location: /api/v1/contacts/{id}` и `ETag`, а в теле — сохранённым контактом с нормализованными телефонами. Ответ 201 MUST отправляться только после долговечной фиксации по правилам storage-engine (STO).
Трассировка: CUJ-03, CUJ-05; ADR-0010, ADR-0007; D-009
Источник: docs/research/03 §4.3

#### Scenario: Успешное создание
- **WHEN** writer отправляет `POST /api/v1/contacts` с `{"display_name":"Анна Петрова","phones":[{"raw_input":"8 916 123-45-67","label":"mobile"}]}`
- **THEN** сервер отвечает 201 с `Location`, `ETag: "1"` и `phones[0].e164` = `+79161234567`

#### Scenario: Ошибка до фиксации
- **WHEN** фиксация записи на диск не завершилась
- **THEN** клиент не получает ответ 201

### Requirement: API-05 Чтение контакта
`GET /api/v1/contacts/{id}` SHALL возвращать 200 с представлением контакта и строгим `ETag: "<version>"`. При `If-None-Match` с текущим ETag сервер MUST отвечать 304. Несуществующий контакт и контакт в корзине MUST давать 404.
Трассировка: CUJ-01, CUJ-05; ADR-0010; D-009, D-012
Источник: docs/research/03 §4.3

#### Scenario: Контакт найден
- **WHEN** reader запрашивает `GET /api/v1/contacts/{id}` существующего контакта версии 3
- **THEN** сервер отвечает 200 с `ETag: "3"`

#### Scenario: Версия не изменилась
- **WHEN** клиент запрашивает тот же контакт с `If-None-Match: "3"`
- **THEN** сервер отвечает 304 без тела

#### Scenario: Контакт в корзине
- **WHEN** reader запрашивает контакт, перенесённый в корзину
- **THEN** сервер отвечает 404 с `type` = `urn:budb:problem:not-found`

### Requirement: API-06 Изменение контакта полной заменой
`PUT /api/v1/contacts/{id}` SHALL заменять изменяемые поля контакта целиком и при успехе отвечать 200 с новым `ETag` и сохранённым контактом. Частичное изменение (PATCH) в v1 не поддерживается. Ответ 200 MUST отправляться только после долговечной фиксации. [ПРЕДЛОЖЕНИЕ АГЕНТА: только PUT]
Трассировка: CUJ-03, CUJ-04; ADR-0010; D-009
Источник: docs/research/03 §4.3

#### Scenario: Успешная замена
- **WHEN** writer отправляет `PUT /api/v1/contacts/{id}` с `If-Match: "3"` и корректным телом
- **THEN** сервер отвечает 200 с `ETag: "4"`

#### Scenario: Изменение несуществующего контакта
- **WHEN** writer отправляет `PUT` на несуществующий `id` с `If-Match: "1"`
- **THEN** сервер отвечает 404

### Requirement: API-07 Удаление контакта в корзину
`DELETE /api/v1/contacts/{id}` SHALL переносить контакт в корзину и отвечать 204 с новым `ETag`. После этого контакт MUST не находиться поиском и чтением, а срок его хранения в корзине и очистку определяет data-privacy (PRV).
Трассировка: CUJ-03, CUJ-09; ADR-0010, ADR-0012; D-012
Источник: docs/research/03 §6.5

#### Scenario: Удаление
- **WHEN** writer отправляет `DELETE /api/v1/contacts/{id}` с `If-Match: "4"`
- **THEN** сервер отвечает 204, а `POST /api/v1/contacts:search` по его телефону больше не возвращает этот контакт

#### Scenario: Повторное удаление
- **WHEN** writer повторно отправляет `DELETE` на тот же `id`
- **THEN** сервер отвечает 404

### Requirement: API-08 Отказ 412 при несовпадении версии
Для `PUT`, `DELETE`, `:restore` и `:undelete` сервер SHALL сравнивать `If-Match` с текущим ETag строго. При несовпадении он MUST отвечать 412 с `type` = `urn:budb:problem:precondition-failed`, не меняя данные, и возвращать текущий ETag в заголовке `ETag`.
Трассировка: CUJ-04; ADR-0010; D-009
Источник: docs/research/03 §4.3 (RFC 9110 §13.1.1)

#### Scenario: Параллельная правка
- **WHEN** два клиента прочитали версию 4, первый успешно сохранил версию 5, а второй отправляет `PUT` с `If-Match: "4"`
- **THEN** второй получает 412 с заголовком `ETag: "5"`, а версия 5 остаётся без изменений

### Requirement: API-09 Отказ 428 без условия If-Match
Запрос `PUT`, `DELETE`, `:restore` или `:undelete` без заголовка `If-Match` MUST отклоняться кодом 428 с `type` = `urn:budb:problem:precondition-required` без изменения данных. `If-Match: *` SHALL считаться отсутствием условия.
Трассировка: CUJ-04, CUJ-05; ADR-0010; D-009
Источник: docs/research/03 §4.3 (RFC 6585)

#### Scenario: Изменение без If-Match
- **WHEN** клиент отправляет `PUT /api/v1/contacts/{id}` без `If-Match`
- **THEN** сервер отвечает 428, и контакт не меняется

#### Scenario: Подстановочное условие
- **WHEN** клиент отправляет `DELETE /api/v1/contacts/{id}` с `If-Match: *`
- **THEN** сервер отвечает 428

### Requirement: API-10 Поиск только через POST contacts:search
Поиск SHALL выполняться только через `POST /api/v1/contacts:search` с телом `{"field":"phone"|"name","mode":"exact"|"prefix","value":…,"page_size":…,"page_token":…}`; ровно один критерий на запрос. Пустой результат MUST давать 200 с пустым `contacts`. Семантика — по search (SRCH). [ПРЕДЛОЖЕНИЕ АГЕНТА: схема тела]
Трассировка: CUJ-01, CUJ-02, CUJ-05; ADR-0010; D-013
Источник: docs/research/03 §4.7

#### Scenario: Кто звонит
- **WHEN** reader отправляет `{"field":"phone","mode":"exact","value":"8 (916) 123-45-67"}`
- **THEN** сервер отвечает 200 со всеми контактами, у которых есть `+79161234567`

#### Scenario: Префикс имени
- **WHEN** reader отправляет `{"field":"name","mode":"prefix","value":"Сем","page_size":20}`
- **THEN** сервер отвечает 200 с не более чем 20 контактами и полем `next_page_token`

#### Scenario: Ничего не найдено
- **WHEN** по запросу нет совпадений
- **THEN** сервер отвечает 200 с `{"contacts":[],"next_page_token":""}`

### Requirement: API-11 ПДн и секреты не передаются в URL
API MUST NOT принимать имена, телефоны и токены в пути или query-строке. Любой неописанный в OpenAPI query-параметр MUST отклоняться кодом 400 с `type` = `urn:budb:problem:unknown-parameter`, а его значение MUST NOT попадать в логи.
Трассировка: CUJ-01, CUJ-05; ADR-0010, ADR-0011; D-013
Источник: docs/research/03 §4.7, §6.2

#### Scenario: Телефон в query
- **WHEN** клиент отправляет `GET /api/v1/contacts?phone=+79161234567`
- **THEN** сервер отвечает 400, а журнал запросов не содержит `79161234567`

#### Scenario: Токен в query
- **WHEN** клиент передаёт токен параметром `?access_token=…`
- **THEN** сервер отвечает 400 и не аутентифицирует запрос

### Requirement: API-12 Размер страницы
Списочные операции SHALL принимать необязательный `page_size`: при отсутствии или 0 используется 50, значение больше 500 уменьшается до 500, отрицательное или нецелое MUST давать 422 с кодом поля `page_size.invalid`.
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-024
Источник: docs/research/03 §4.4 (AIP-158)

#### Scenario: Размер по умолчанию
- **WHEN** клиент вызывает поиск без `page_size`
- **THEN** ответ содержит не более 50 контактов

#### Scenario: Слишком большой размер
- **WHEN** клиент передаёт `page_size: 10000`
- **THEN** ответ содержит не более 500 контактов

#### Scenario: Отрицательный размер
- **WHEN** клиент передаёт `page_size: -1`
- **THEN** сервер отвечает 422

### Requirement: API-13 Непрозрачный курсор страницы
`next_page_token` SHALL быть непрозрачным и защищённым от подделки; пустая строка означает конец выборки. Токен, изменённый клиентом, просроченный (старше 3 суток) или поданный с другими параметрами запроса, MUST давать 400 с `type` = `urn:budb:problem:invalid-page-token`. Токен не даёт прав: авторизация проверяется на каждом запросе.
Трассировка: CUJ-02, CUJ-05; ADR-0010; D-024
Источник: docs/research/03 §4.4 (AIP-158)

#### Scenario: Следующая страница
- **WHEN** клиент повторяет запрос с полученным `page_token` и теми же параметрами
- **THEN** сервер возвращает следующую страницу без повторов и пропусков записей, существовавших на обеих страницах

#### Scenario: Смена параметров
- **WHEN** клиент подаёт `page_token` вместе с другим `value`
- **THEN** сервер отвечает 400 с `invalid-page-token`

### Requirement: API-14 Ошибки в формате RFC 9457
Каждый ответ 4xx и 5xx SHALL иметь тип `application/problem+json` с полями `type`, `title`, `status` и при необходимости `detail`. `type` MUST быть стабильным машинным идентификатором вида `urn:budb:problem:<code>`; `title` и `detail` локализуются по `Accept-Language`. Стектрейсы и значения ПДн MUST NOT попадать в ответ. [ПРЕДЛОЖЕНИЕ АГЕНТА: схема URN]
Трассировка: CUJ-05; ADR-0010; D-013
Источник: docs/research/03 §4.2, §5.3

#### Scenario: Ресурс не найден
- **WHEN** клиент запрашивает несуществующий контакт с `Accept-Language: en`
- **THEN** сервер отвечает 404 с `type` = `urn:budb:problem:not-found` и английским `title`

#### Scenario: Внутренняя ошибка
- **WHEN** обработка запроса завершилась внутренней ошибкой
- **THEN** сервер отвечает 500 с `type` = `urn:budb:problem:internal` без стектрейса

### Requirement: API-15 Ошибки валидации с кодами полей
Нарушение правил данных SHALL давать 422 с `type` = `urn:budb:problem:validation-error` и массивом `errors[]` из `{pointer, code}`, где `pointer` — JSON Pointer на поле, а `code` — машинный код из CON, PHN или NAM. Незнакомые поля и поля только для чтения (`id`, `version`, `created`, `updated`) MUST давать 422; синтаксически неверный JSON — 400.
Трассировка: CUJ-03, CUJ-05; ADR-0010; D-022
Источник: docs/research/03 §4.2, §6.1 (API3)

#### Scenario: Невозможный номер
- **WHEN** writer создаёт контакт с телефоном `12`
- **THEN** сервер отвечает 422, и `errors` содержит элемент с `pointer` = `/phones/0/raw_input`

#### Scenario: Лишнее поле
- **WHEN** тело содержит `"note":"…"` или `"version":7`
- **THEN** сервер отвечает 422 и не сохраняет контакт

#### Scenario: Битый JSON
- **WHEN** тело запроса не является корректным JSON
- **THEN** сервер отвечает 400

### Requirement: API-16 Повтор запроса с Idempotency-Key
`POST /api/v1/contacts`, `POST /api/v1/imports` и `POST /api/v1/exports` SHALL принимать заголовок `Idempotency-Key`. Повтор с тем же ключом и тем же телом от того же субъекта в течение 24 ч MUST возвращать сохранённый ответ без повторного выполнения. Для `POST /api/v1/imports` ключ обязателен. [ПРЕДЛОЖЕНИЕ АГЕНТА: 24 ч и обязательность]
Трассировка: CUJ-05, CUJ-06; ADR-0010; D-030
Источник: docs/research/03 §4.5

#### Scenario: Повтор после обрыва связи
- **WHEN** клиент повторяет `POST /api/v1/contacts` с тем же `Idempotency-Key` и телом
- **THEN** сервер возвращает тот же 201 и тот же `Location`, а второй контакт не создаётся

#### Scenario: Ключ истёк
- **WHEN** клиент повторяет запрос с тем же ключом через 25 ч
- **THEN** сервер обрабатывает его как новый

### Requirement: API-17 Ошибки использования Idempotency-Key
Сервер SHALL отвечать: 400 `idempotency-key-missing`, если обязательный ключ не передан или некорректен; 422 `idempotency-key-reused`, если ключ уже использован с другим телом; 409 `idempotency-request-in-progress`, если исходный запрос с этим ключом ещё выполняется. Ни в одном из этих случаев операция MUST NOT выполняться.
Трассировка: CUJ-05, CUJ-06; ADR-0010; D-030
Источник: docs/research/03 §4.5

#### Scenario: Импорт без ключа
- **WHEN** writer отправляет `POST /api/v1/imports` без `Idempotency-Key`
- **THEN** сервер отвечает 400 и не создаёт задачу

#### Scenario: Другое тело с тем же ключом
- **WHEN** клиент повторно использует ключ с другим телом
- **THEN** сервер отвечает 422

#### Scenario: Параллельный повтор
- **WHEN** повтор приходит, пока исходный запрос ещё выполняется
- **THEN** сервер отвечает 409

### Requirement: API-18 Лимит размера тела
Сервер MUST отклонять кодом 413 с `type` = `urn:budb:problem:payload-too-large` JSON-тело больше 64 KiB и загрузку импорта больше 1 GiB, не читая тело дальше предела. Оба лимита SHALL настраиваться конфигурацией. [ПРЕДЛОЖЕНИЕ АГЕНТА: значения]
Трассировка: CUJ-05, CUJ-06; ADR-0010, ADR-0017; D-033
Источник: docs/research/03 §4.6, §6.1 (API4)

#### Scenario: Слишком большое тело
- **WHEN** клиент отправляет `POST /api/v1/contacts` с телом 100 KiB
- **THEN** сервер отвечает 413

#### Scenario: Тело в пределах лимита
- **WHEN** клиент отправляет корректное тело 2 KiB
- **THEN** запрос обрабатывается обычным образом

### Requirement: API-19 Ограничение частоты 429 с Retry-After
Сервер SHALL ограничивать частоту запросов на субъект аутентификации и на IP-адрес; по умолчанию 50 запросов/с с запасом 100 на токен. При превышении он MUST отвечать 429 с `Retry-After` в секундах и `type` = `urn:budb:problem:rate-limited`. [ПРЕДЛОЖЕНИЕ АГЕНТА: значения]
Трассировка: CUJ-05, CUJ-08; ADR-0010, ADR-0017; D-032
Источник: docs/research/03 §4.6, §6.1 (API4)

#### Scenario: Превышение лимита
- **WHEN** один токен отправляет 300 запросов за секунду
- **THEN** часть запросов получает 429 с заголовком `Retry-After`

#### Scenario: Обычная нагрузка
- **WHEN** токен отправляет 10 запросов в секунду
- **THEN** ни один из них не получает 429

### Requirement: API-20 Перегрузка 503 с Retry-After
Когда сервер не может принять запрос из-за перегрузки (очередь записей заполнена) или ещё не готов, он MUST отвечать 503 с `Retry-After` и `type` = `urn:budb:problem:overloaded` и SHALL не начинать выполнение такой операции, чтобы её повтор был безопасным.
Трассировка: CUJ-03, CUJ-08; ADR-0010, ADR-0017; D-032
Источник: docs/research/03 §4.6

#### Scenario: Очередь записей заполнена
- **WHEN** writer отправляет `PUT`, когда очередь фиксации заполнена
- **THEN** сервер отвечает 503 с `Retry-After`, и контакт не меняется

#### Scenario: Повтор после ожидания
- **WHEN** клиент повторяет тот же запрос по истечении `Retry-After` после снятия перегрузки
- **THEN** запрос выполняется обычным образом

### Requirement: API-21 Коды 401 и 403
Запрос без действительных учётных данных MUST получать 401 с `WWW-Authenticate: Bearer` и `type` = `urn:budb:problem:unauthenticated`. Запрос аутентифицированного субъекта без нужной роли MUST получать 403 с `type` = `urn:budb:problem:forbidden`. Правила ролей — по access-control (ACL).
Трассировка: CUJ-05, CUJ-10; ADR-0011; D-015
Источник: docs/research/03 §6.1 (API2, API5), §6.2

#### Scenario: Нет токена
- **WHEN** клиент вызывает `POST /api/v1/contacts:search` без `Authorization`
- **THEN** сервер отвечает 401 с `WWW-Authenticate: Bearer`

#### Scenario: Недостаточно прав
- **WHEN** reader отправляет `DELETE /api/v1/contacts/{id}`
- **THEN** сервер отвечает 403, и контакт не удаляется

### Requirement: API-22 Корзина: просмотр и восстановление
Admin SHALL видеть корзину через `GET /api/v1/admin/trash` с пагинацией (id, `display_name`, `deleted_at`, `purge_after`) и восстанавливать контакт через `POST /api/v1/admin/trash/{id}:restore` с `If-Match`; успех даёт 200 с контактом и новым ETag. Другим ролям MUST отвечать 403.
Трассировка: CUJ-03, CUJ-09; ADR-0012; D-012
Источник: docs/research/03 §6.5

#### Scenario: Восстановление
- **WHEN** admin вызывает `POST /api/v1/admin/trash/{id}:restore` для контакта в корзине
- **THEN** сервер отвечает 200, и контакт снова находится поиском

#### Scenario: Writer открывает корзину
- **WHEN** writer запрашивает `GET /api/v1/admin/trash`
- **THEN** сервер отвечает 403

### Requirement: API-23 Отмена своего удаления
Writer, удаливший контакт, SHALL иметь возможность отменить удаление через `POST /api/v1/contacts/{id}:undelete` с `If-Match` в течение 5 минут после удаления. Попытка другого субъекта MUST давать 403, попытка после окна — 409 с `type` = `urn:budb:problem:undo-window-expired`. [ПРЕДЛОЖЕНИЕ АГЕНТА: эндпоинт и окно]
Трассировка: CUJ-03; ADR-0012, ADR-0016; D-012
Источник: docs/research/03 §5.1 п. 6

#### Scenario: Отмена вовремя
- **WHEN** writer вызывает `:undelete` через 20 с после своего удаления
- **THEN** сервер отвечает 200 с контактом, и контакт снова находится поиском

#### Scenario: Окно истекло
- **WHEN** writer вызывает `:undelete` через 6 минут после удаления
- **THEN** сервер отвечает 409, и контакт остаётся в корзине

### Requirement: API-24 Немедленная очистка контакта (purge)
Admin SHALL выполнять немедленную очистку активного или удалённого контакта через `POST /api/v1/admin/contacts/{id}:purge`. Ответ 200 MUST содержать квитанцию `{purge_id, contact_id, status, erase_deadline}`; статус доступен по `GET /api/v1/admin/purges/{purge_id}`. Гарантии очистки — по data-privacy (PRV).
Трассировка: CUJ-09; ADR-0012; D-012
Источник: docs/research/03 §6.5 п. 1

#### Scenario: Очистка по запросу субъекта
- **WHEN** admin вызывает `:purge` для контакта
- **THEN** сервер отвечает 200 с `purge_id`, а `GET /api/v1/contacts/{id}` и корзина больше не возвращают контакт

#### Scenario: Writer пытается очистить
- **WHEN** writer вызывает `:purge`
- **THEN** сервер отвечает 403

### Requirement: API-25 Импорт как асинхронная задача
`POST /api/v1/imports?format=csv|ndjson&dry_run=…&on_conflict=…` с файлом в теле SHALL создавать задачу и отвечать 202 с `Location: /api/v1/jobs/{id}`. `GET /api/v1/jobs/{id}` MUST возвращать статус, счётчики и ссылку на построчный отчёт без значений ПДн. Задачу видят автор и admin. Семантика — по IMP.
Трассировка: CUJ-06; ADR-0010; D-016
Источник: docs/research/03 §4.8

#### Scenario: Запуск импорта
- **WHEN** writer отправляет CSV-файл в `POST /api/v1/imports?format=csv&dry_run=true`
- **THEN** сервер отвечает 202 с `Location` задачи

#### Scenario: Завершение импорта
- **WHEN** задача завершилась
- **THEN** `GET /api/v1/jobs/{id}` возвращает `status` = `succeeded` и счётчики, где принятые плюс отклонённые равны общему числу строк

#### Scenario: Чужая задача
- **WHEN** другой writer запрашивает эту задачу
- **THEN** сервер отвечает 404

### Requirement: API-26 Экспорт как асинхронная задача
Admin SHALL запускать экспорт через `POST /api/v1/exports` с `{"format":"csv"|"ndjson"}` и получать 202 с задачей. Готовый файл MUST отдаваться по `GET /api/v1/jobs/{id}/result` и отражать снимок данных на момент старта; до готовности ответ — 409 `job-not-ready`. Не-admin получает 403.
Трассировка: CUJ-06; ADR-0010; D-016
Источник: docs/research/03 §4.8, §6.1 (API6)

#### Scenario: Скачивание экспорта
- **WHEN** задача экспорта в NDJSON завершилась
- **THEN** `GET /api/v1/jobs/{id}/result` отвечает 200 с `Content-Type: application/x-ndjson`

#### Scenario: Экспорт от writer
- **WHEN** writer вызывает `POST /api/v1/exports`
- **THEN** сервер отвечает 403

### Requirement: API-27 Административные ресурсы
Административные операции SHALL располагаться только под `/api/v1/admin/` и требовать роли admin: `status`, `users`, `tokens`, `backups`, `verifications`, `audit`, `trash`, `purges`, `subjects:search`. Долгие операции (`backups`, `verifications`) MUST выполняться как задачи `/api/v1/jobs/{id}`.
Трассировка: CUJ-07, CUJ-08, CUJ-10; ADR-0010, ADR-0011; D-017, D-025
Источник: docs/research/03 §6.1 (API5)

#### Scenario: Состояние БД
- **WHEN** admin запрашивает `GET /api/v1/admin/status`
- **THEN** сервер отвечает 200 с числом контактов, размером хранилища и временем последнего бэкапа

#### Scenario: Онлайн-бэкап
- **WHEN** admin вызывает `POST /api/v1/admin/backups`
- **THEN** сервер отвечает 202 с `Location` задачи

#### Scenario: Reader обращается к admin
- **WHEN** reader запрашивает `GET /api/v1/admin/status`
- **THEN** сервер отвечает 403

### Requirement: API-28 Предпросмотр нормализации номера
`POST /api/v1/phones:normalize` с `{"raw_input":…}` SHALL возвращать 200 с `e164` и `extension` по правилам phone-normalization (PHN), ничего не сохраняя. Невозможный номер MUST давать 422 с тем же кодом поля, что и при создании контакта. Доступно с роли reader. [ПРЕДЛОЖЕНИЕ АГЕНТА]
Трассировка: CUJ-03, CUJ-05; ADR-0008, ADR-0010; D-010
Источник: docs/research/03 §1.5

#### Scenario: Национальный формат
- **WHEN** клиент отправляет `{"raw_input":"8 (916) 123-45-67 доб. 12"}`
- **THEN** сервер отвечает 200 с `e164` = `+79161234567` и `extension` = `12`

#### Scenario: Невозможный номер
- **WHEN** клиент отправляет `{"raw_input":"12"}`
- **THEN** сервер отвечает 422
