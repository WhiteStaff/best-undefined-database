# Tasks

Чек-лист реализации BUDB v1 по фазам. Как строить, описано в `design.md`; что строить — в спецификациях (ID требований). Формат задачи: что сделать — **Требования:** ID — **Готово:** критерий проверки. Решения D-034…D-060 важнее текста спецификаций, если он им противоречит (`design.md`, раздел «Решения, ещё не отражённые в спецификациях»). Каждая фаза приносит свои тесты и документацию; последняя фаза — только интеграционные crash-тесты.

## 1. Каркас и CI с политикой зависимостей

- [ ] 1.3 Добавить в CI проверки на каждое изменение: `cargo deny check bans`, `cargo build --locked`, `openspec validate --all --strict`, `node scripts/traceability.mjs --check`; любое нарушение блокирует слияние — **Требования:** BLD-05 — **Готово:** защищённая ветка не принимает PR с нарушением любой из проверок.
- [ ] 1.4 Матрица CI: Linux x86_64 и aarch64 (tier 1), Windows x86_64 и macOS aarch64 (tier 2); оговорки tier 2 в документации — **Требования:** BLD-09 — **Готово:** все четыре цели зелёные; в руководстве оператора есть раздел про rename и каталог на Windows.
- [ ] 1.5 Воспроизводимая сборка: `Cargo.lock` в репозитории, релиз только с `--locked` — **Требования:** BLD-11 — **Готово:** две сборки одного коммита на одной платформе дают одинаковый SHA-256 бинарника.
- [ ] 1.6 Ввести трейты `Storage`, `Clock`, `Rng`; движок не вызывает `std::fs`, системное время и ГПСЧ напрямую — **Требования:** BLD-12 — **Готово:** проверка в CI не находит прямых вызовов в крейте движка; есть реализации `OsDisk` и заглушка `SimDisk`.

## 2. CRC32C и формат страниц

- [ ] 2.1 Реализовать CRC32C (Castagnoli) табличным способом, аппаратный путь — опционально и только с совпадающим результатом — **Требования:** BLD-08 — **Готово:** тест-векторы RFC 3720 прил. B.4 (после 0.2) проходят; property-тест «аппаратный = табличный» на случайных буферах.
- [ ] 2.2 Кодирование страницы: заголовок с типом и CRC32C, ручное кодирование чисел без serde — **Требования:** STO-03 — **Готово:** юнит-тесты round-trip; страница с изменённым битом отвергается.
- [ ] 2.3 Заголовок файла (страница 0) и проверки при открытии — **Требования:** STO-01, STO-02 — **Готово:** сценарии STO-01 и STO-02 проходят; хеш файла до и после отказа совпадает.
- [ ] 2.4 Мета-страница: txid, корни трёх деревьев и каталога, freelist, отложенный список, `next_contact_id`, версии правил, счётчики (`design.md`, раздел 2) — **Требования:** STO-04 — **Готово:** round-trip; сценарий «Чередование слотов» проходит на SimDisk.
- [ ] 2.5 Фаззинг разбора страницы, мета-страницы и заголовка — **Требования:** BLD-16 — **Готово:** цели cargo-fuzz работают ≥ 1 ч за ночь без паники и зависаний; найденные входы лежат в регрессионном корпусе.

## 5. Восстановление и fault injection

- [ ] 5.1 Открытие и восстановление по `design.md`, раздел 4.1, включая правило отката D-035 — **Требования:** STO-17, STO-18 — **Готово:** сценарии STO-17 и STO-18 проходят; при откате растёт `budb_meta_fallback_total`, в логе оба txid.
- [ ] 5.2 Fail-stop по D-034: отказ текущим записям, «исход неизвестен» на шаге (4), 503 ≤ 5 с, выход с отдельным кодом; повреждение во время работы — тот же путь — **Требования:** STO-16, STO-19 — **Готово:** тест SimDisk с EIO на fsync: fsync не повторяется, чтения не обслуживаются, процесс выходит ≤ 5 с с ожидаемым кодом, после перезапуска состояние берётся с диска.
- [ ] 5.3 Полная модель сбоев SimDisk: потеря несброшенного, порванные записи по 512 Б, EIO, битовые ошибки; прогон по seed — **Требования:** BLD-12 — **Готово:** ≥ 1 000 seed на PR и ≥ 100 000 за ночь; любое падение воспроизводится по seed.
- [ ] 5.4 Ошибка на каждом i-м системном вызове коммита и открытия — **Требования:** BLD-13 — **Готово:** для каждого i: подтверждения нет, движок в fail-stop, после перезапуска состояние до или после транзакции и проходит verify.
- [ ] 5.5 Перебор состояний после сбоя в стиле ALICE по трассе коммита — **Требования:** BLD-14 — **Готово:** во всех сгенерированных состояниях видна последняя подтверждённая транзакция или более поздняя целиком.
- [ ] 5.6 Офлайн-верификатор (ядро BKP-08) и его запуск после каждого сценария надёжности — **Требования:** BLD-19 — **Готово:** внедрённая утечка страницы проваливает сборку.
- [ ] 5.7 Время открытия после сбоя — **Требования:** PERF-07 — **Готово:** p99 ≤ 1 с на 10^7 контактов после kill -9 на эталонном стенде.
- [ ] 5.8 Раздел руководства оператора о гарантиях долговечности — **Требования:** STO-23 — **Готово:** в нём есть оговорка о честном сбросе накопителя и ссылка на FAST 2013.

## 10. Корзина, purge и аудит

- [ ] 11.1 Онлайн-бэкап из снимка, компактная копия живых страниц, `<ts>.purge` рядом, атомарная запись — **Требования:** BKP-01, BKP-02, BKP-03 — **Готово:** бэкап под нагрузкой содержит ровно txid старта; kill -9 посреди бэкапа не оставляет файла с итоговым именем.

- [ ] 11.3 Restore офлайн с атомарной подменой и объединением всех доступных журналов purge (D-036) — **Требования:** BKP-05, BKP-06, BKP-07, PRV-10 — **Готово:** purge после бэкапа не «воскресает» ни поиском, ни побайтовым поиском; без журналов и без переопределения restore отказывает.
- [ ] 11.4 Verify офлайн и онлайн, отчёт без ПДн — **Требования:** BKP-08, BKP-09, BKP-10 — **Готово:** сценарии проходят; хеш файла после verify не меняется; онлайн-проверка не останавливает запись.
- [ ] 11.5 Офлайн-компактизация — **Требования:** BKP-11 — **Готово:** после удаления 50 % контактов файл уменьшается, txid и набор контактов прежние; kill -9 между fsync и rename оставляет прежний файл.
- [ ] 11.6 Ротация бэкапов (по умолчанию 30 дней, не больше 180, D-037); отказ restore истёкшего бэкапа — **Требования:** BKP-12, PRV-11 — **Готово:** сценарии проходят; срок 365 не даёт запуститься.
