# Design: add-phonebook-db-v1 — BUDB v1

Документ сводит в одно техническое решение ADR 0001–0017 (`docs/adr/`) и решения оркестратора D-001…D-060 (`docs/orchestrator-decisions.md`). Требования здесь не повторяются: на них даны ссылки по ID (`openspec/changes/add-phonebook-db-v1/specs/*/spec.md`). Зачем нужен продукт, описано в `proposal.md` (раздел «Why»).

Пометки: `[ПРЕДЛОЖЕНИЕ АГЕНТА]` — технический выбор автора этого документа, которого нет в журнале решений; `[ДОПУЩЕНИЕ]`, `[РАСЧЁТ]`, `[НЕ ПОДТВЕРЖДЕНО]` — как в `docs/adr/README.md`.

## Context

- **Текущее состояние.** Кода нет. Есть 15 спецификаций (270 требований, 487 сценариев, `docs/traceability.md`), ADR 0001–0017, `docs/cuj.md` и решения D-001…D-060.
- **Ограничения.** Хранение пишется с нуля: сторонние движки, KV, WAL и ORM запрещены, сторонние крейты — только по allowlist (D-021, D-038, D-060; ADR 0006). Язык — Rust stable без `unsafe` (D-020; ADR 0002). Один узел, цель 10^8 контактов, SLO проверяются на 10^7 (D-024). Полные гарантии долговечности — на Linux tier 1 (D-023; ADR 0014). Имена и телефоны — ПДн (D-012, D-013).
- **Приоритет источников.** Решения D-034…D-060 приняты после спецификаций. Если спецификация им противоречит, этот документ следует решению, а спецификацию исправит редактор после ревью (D-040: ID требований не меняются).

## Goals / Non-Goals

**Goals:**

- Одна архитектура, в которой каждое требование STO, BKP, PERF и BLD реализуется без противоречий с D-034…D-060.
- Протокол коммита и восстановления, который можно перечислить как последовательность системных вызовов и проверить перебором состояний (BLD-13, BLD-14).
- Физическое затирание ПДн не позднее T_purge = 24 ч, включая старые копии записи внутри файла (PRV-06, D-056).
- Порядок реализации, при котором фазы `tasks.md` закрывают требования по слоям.

**Non-Goals:**

- Границы продукта v1 — в `proposal.md` (раздел «Out of Scope (v1)»).
- Выбор политики вытеснения кэша, размеров пулов и пачек: значения по умолчанию и настройки, без изменения поведения (раздел «Open Questions»).
- Формат журналов ОС и конфигурация супервизора: задача эксплуатации; продукт требует только перезапуска процесса после выхода (D-034).

## Decisions

### 1. Компоненты и потоки

Один процесс `budb serve` (D-032; ADR 0017). HTTP-слой асинхронный (tokio, hyper, axum, tower), движок синхронный. Слои общаются через ограниченные каналы; при переполнении сервер отвечает 503, при превышении лимита клиента — 429 (D-059; PERF-14, API-19, API-20).

```
 Браузер: UI (TS + Web Components)   Интегратор / budb admin --server   Prometheus
        | cookie + CSRF                    | Bearer-токен                  | /metrics
        v                                  v                               v
+-------------------------------- budb serve (один процесс) ---------------------------------+
| статика UI из бинарника | HTTP API /api/v1 | admin API /api/v1/admin/* | /livez /readyz      |
| tower: аутентификация и роли (ACL), CSRF, лимит частоты -> 429, лимит тела -> 413,          |
|        problem+json (API-14), маскирование ПДн в логах (PRV-14)                              |
|              | чтения                                     | записи                           |
|              v                                            v                                  |
|  +-- пул читателей (N потоков) --+       +-- очередь писателя (ограничена) --+ -> 503      |
|  | снимок txid, keyset-курсор    |       | поток-писатель, group commit       |             |
|  +---------------+---------------+       +-----------------+------------------+             |
|                  v                                         v                                 |
|  +------------------------------ движок (трейт Storage) ------------------------------+    |
|  | реестр снимков | COW B+tree | аллокатор и freelist | кэш страниц + CRC32C | коммит |    |
|  +----------------------------------------------------------------------------------- +    |
|  фоновые: автоочистка корзины, затирание (purge), TTL ключей идемпотентности,              |
|           бэкап и verify (длинные снимки), импорт пачками через писателя, экспорт, ротация  |
+-------------+-------------------------------------------------------+----------------------+
              | pread / pwrite / fsync                                 | append + fsync
              v                                                        v
   data/budb.db (заголовок, 2 мета, деревья)            data/audit/*.log   data/purge.journal
              | копия живых страниц снимка                             | копия при каждом purge
              v                                                        v
   backups/<ts>.budb + <ts>.purge                       backups/purge.journal
```

- **Пул читателей.** Каждая операция чтения берёт снимок последнего подтверждённого txid (STO-09), выполняется и отпускает его. Интерактивный снимок живёт не дольше 30 с (STO-24, D-048). Размер пула по умолчанию — число vCPU `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
- **Поток-писатель.** Единственный (STO-08). Берёт из очереди пачку (по умолчанию ≤ 1000 операций, без ожидания набора — STO-13 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`), применяет операции и фиксирует пачку одним коммитом (раздел 3). Ёмкость очереди по умолчанию 4096 (PERF-14 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`).
- **Длинные операции** (бэкап, онлайн-verify, экспорт) работают на отдельных потоках с собственными снимками. Лимит 30 с на них не действует, но они ограничены T_purge (D-056). Импорт пишет через ту же очередь писателя пачками по 1000 записей (IMP-09), поэтому один писатель сохраняется.
- **Admin CLI.** `budb admin --server` вызывает admin API; `budb admin --db` работает с файлом напрямую под эксклюзивной блокировкой, когда сервер остановлен (D-055; CLI-03, CLI-04, STO-20).
- **Альтернативы** (ADR 0017): `spawn_blocking` на каждый запрос (нет единственного писателя и пачек), асинхронный движок (усложняет детерминированную симуляцию), «поток на соединение» без tokio.

### 2. Раскладка файла и деревьев

Страница — 4096 байт; у каждой есть заголовок с типом и CRC32C содержимого (STO-03; ADR 0003). Числа на диске кодируются вручную, без serde, bincode и rkyv (BLD-02, BLD-04).

| Страница | Содержимое | Требования |
|---|---|---|
| 0 | Заголовок: magic `BUDB`, версия формата (1), размер страницы, время создания, CRC32C. Пишется один раз | STO-01, STO-02 |
| 1, 2 | Слоты мета-страниц A и B: magic, версия, txid, корни `primary`, `name_idx`, `phone_idx`, корень каталога, корень freelist, корень списка отложенного освобождения, `next_contact_id`, версии правил ключа имени и нормализации телефонов, счётчики активных контактов и контактов в корзине, CRC32C | STO-04, NAM-09, PHN-15, D-055, D-057 |
| ≥ 3 | Страницы деревьев (ветви, листья), страницы переполнения, страницы freelist | STO-05, STO-10 |

Деревья. Все меняются одной транзакцией (STO-06, STO-07):

| Дерево | Ключ | Значение | Источник |
|---|---|---|---|
| `primary` | `id` (u64 big-endian) | Запись контакта: поля CON-01, телефоны CON-04 с версией правил и регионом (PHN-15), `version`, `created`, `updated`, `deleted_at` | D-009, D-055, D-057 |
| `name_idx` | `kind` (0 — полный ключ, 1 — слово) ‖ ключ имени UTF-8 ‖ `0x00` ‖ `id` | пусто | D-050, D-051; `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: формат ключа |
| `phone_idx` | цифры `e164` (ASCII) ‖ `0x00` ‖ `id` | число добавочных номеров с этим `e164` у контакта | D-009; `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: формат ключа |
| каталог → `users` | логин после case folding | роль, признак «отключён», хэш argon2, время смены пароля | D-055, ACL-01, ACL-05 |
| каталог → `api_tokens` | `token_id` | владелец, SHA-256 секрета, срок, признак отзыва | D-055, D-060, ACL-07…ACL-10 |
| каталог → `idempotency_keys` | субъект ‖ ключ | хэш тела, статус, сохранённый ответ, `contact_id`, время (TTL 24 ч) | D-055, API-16 |
| каталог → `trash_idx` | `deleted_at` ‖ `id` | пусто | D-055, CON-16, PRV-04 |
| каталог → `instance` | константы | секрет экземпляра для HMAC курсоров (256 бит из CSPRNG) | `[ПРЕДЛОЖЕНИЕ АГЕНТА]`, D-060 |
| каталог → `jobs` | `job_id` | тип, владелец, состояние, счётчики, без ПДн | `[ПРЕДЛОЖЕНИЕ АГЕНТА]`, IMP-05, IMP-10 |

- **Разделитель `0x00`.** Без него сравнение `ключ‖id` ставит id короткого ключа между длинными ключами. Байт `0x00` не встречается ни в ключе имени (U+0000 удаляется как Cc, NAM-03), ни в цифрах номера, поэтому порядок совпадает с SRCH-08: сначала ключ, затем `id`.
- **Корзина.** При удалении записи `name_idx` и `phone_idx` удаляются, а в `trash_idx` добавляется запись; restore возвращает их обратно `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Так поиск не видит корзину (SRCH-15) и не тратит время на фильтрацию. Выгрузка данных субъекта (PRV-15) ищет активные контакты по индексам, а контакты в корзине — перебором `trash_idx` (корзина мала, D-049). Инвариант STO-06 при этом читается как «каждый активный контакт представлен в обоих индексах».
- **Большие записи.** Худший случай записи — около 5,5 КиБ: `display_name` до 1024 Б, три части имени по 128 кодовых точек и 10 телефонов с `raw_input` до 64 кодовых точек `[РАСЧЁТ]` по D-022 и PHN-12. Это больше страницы, поэтому записи и ключи больше 1 КиБ выносятся в цепочку страниц переполнения, а в ветвях хранятся укороченные разделители `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Средняя запись около 70 Б (PERF-12) в переполнение не попадает.
- **Слова имени (D-051).** `display_name` после очистки (NAM-02) делится по White_Space и дефису. Для каждого слова, кроме первого, в `name_idx` добавляется запись `kind = 1`: первое слово уже покрыто префиксом полного ключа. Точный поиск (SRCH-04) читает только записи `kind = 0`. Префиксный поиск (SRCH-05) сливает два диапазона, упорядоченных по (совпавший ключ, `id`). Как убирать повторы контакта, который совпал и по полному ключу, и по слову, — вопрос к оркестратору (раздел «ВОПРОСЫ К ОРКЕСТРАТОРУ»).
- **Альтернативы** (ADR 0003, ADR 0007): отдельная сущность Phone со связью многие-ко-многим; служебные данные в отдельных файлах (отклонено D-055: две точки атомарности вместо одной); флаг «в корзине» в индексах (поиск фильтрует на чтении, индексы крупнее).

### 3. Протокол коммита

Протокол — 2PC по ADR 0005 (D-019): fsync страниц, запись мета-страницы, fsync. Шаги с номерами STO-11 обозначены как (1)…(4).

1. **Сбор пачки.** Писатель забирает из очереди до K операций (STO-13).
2. **Применение.** Каждая операция выполняется в COW-транзакции на копиях страниц в памяти: проверка версии (CON-13; 412 по API-08), выдача `id` из `next_contact_id` (D-057), изменение `primary`, `name_idx`, `phone_idx`, служебных деревьев. Перед каждой операцией ставится точка отката; отклонённая операция откатывается к ней и не влияет на остальные (STO-13) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Новые страницы берутся из freelist по правилу раздела 3.1, иначе файл растёт (по 64 МиБ `[ПРЕДЛОЖЕНИЕ АГЕНТА]`).
3. **(1) Запись страниц.** `pwrite` всех изменённых страниц с CRC32C, обновлённого freelist и затёртых нулями страниц, которые в этой транзакции переходят из отложенного списка в свободные (раздел 5). События аудита пачки дописываются в файл аудита с txid (раздел 6).
4. **(2) Сброс.** `fdatasync` на Linux, `fcntl(F_FULLFSYNC)` на macOS, `FlushFileBuffers` на Windows (STO-14; docs/research/02, §3.1–§3.3); файл аудита сбрасывается тоже. Ошибка — fail-stop без повтора (раздел 4.3).
5. **(3) Мета-страница.** Запись мета-страницы `txid + 1` в слот с меньшим txid (STO-04), чтобы мета-страница последнего подтверждённого коммита не перезаписывалась.
6. **(4) Сброс.** Ошибка — ответ «исход неизвестен» всем операциям пачки (STO-12) и fail-stop.
7. **Публикация.** Новый корень становится текущим снимком для новых читателей (STO-09). Только после этого клиенты получают подтверждение (STO-12, CON-10, API-04).
8. **Учёт освобождённого.** Страницы, которые транзакция T сделала недостижимыми, попадают в отложенный список с меткой T.

После create, rename и unlink выполняется fsync каталога (STO-15); на Windows rename выполняется с `MOVEFILE_WRITE_THROUGH` и считается best effort (ADR 0014). Режима без сброса нет (STO-21).

#### 3.1. Когда страницу можно переиспользовать

Страница, освобождённая транзакцией T, переиспользуется только при двух условиях `[ПРЕДЛОЖЕНИЕ АГЕНТА]`, уточняющих STO-10:

- нет активного снимка с txid < T (STO-10);
- последний подтверждённый txid ≥ T + 1, то есть переиспользовать страницу может только транзакция T + 2 или более поздняя: к этому моменту мета-страницы T − 1 уже нет. Мета-страница T − 1 ссылается на страницы, освобождённые в T. Если перезаписать их, пока эта мета-страница жива, то откат к ней по D-035 прочитает чужие страницы с верной CRC32C, и подмену не обнаружит никакая проверка.

Это то же рассуждение, что и принудительный коммит N+1 в D-056.

- **Альтернативы** (ADR 0005): 1PC с деревом контрольных сумм (как redb), асинхронная долговечность (запрещена D-019), повтор fsync (fsyncgate, docs/research/02, §3.4).

### 4. Восстановление и ошибки

#### 4.1. Открытие файла

1. Взять эксклюзивную блокировку; если она занята — ошибка «БД используется другим процессом» (STO-20).
2. Прочитать страницу 0: magic, версия, размер страницы, CRC32C (STO-01, STO-02). Ошибка — отказ без единого изменения файла.
3. Прочитать оба слота мета-страниц и проверить CRC32C, magic и версию (STO-17).
4. Выбрать валидный слот с наибольшим txid (`valid_max`). Если второй слот невалиден, применить D-035 `[ПРЕДЛОЖЕНИЕ АГЕНТА: способ различения]`:
   - поле txid отвергнутого слота читается и ≤ `valid_max` — слот старше, открыть `valid_max` и записать WARN;
   - поле txid читается и равно `valid_max + 1` — порванный последний коммит: открыть `valid_max`, записать событие с обоими txid (OBS-14), увеличить `budb_meta_fallback_total`, поднять алерт;
   - иначе (txid нечитаем или больше `valid_max + 1`) — считать это повреждением и отказать в открытии (STO-18).
5. Проверить CRC32C корней всех деревьев и каталога, достижимых из выбранной мета-страницы. При ошибке — отказ с номером страницы, без отката к старой мета-странице (STO-18; FAST'17, docs/research/02, §3.6).
6. Загрузить freelist и отложенный список. Активных снимков после перезапуска нет, поэтому отложенные страницы затираются нулями в первом коммите и переходят в свободные.
7. Если версия правил ключа имени в файле отличается от текущей, перестроить `name_idx` новой COW-транзакцией: новое дерево строится рядом, корень подменяется одним коммитом (NAM-10, NAM-11). До конца перестроения `/readyz` = 503, ход виден в метриках.
8. Удалить оставшиеся временные файлы бэкапа и компактизации со сбросом каталога (BKP-03).
9. `/readyz` = 200 (OBS-02). Журнал не переигрывается, поэтому открытие укладывается в p99 ≤ 1 с независимо от размера файла (PERF-07).

#### 4.2. Повреждение во время работы

Страница с неверной CRC32C, достижимая из снимка, даёт клиенту ошибку хранилища, а не пустой результат (STO-19, STO-03). Дальше — fail-stop по разделу 4.3.

#### 4.3. Fail-stop (D-034)

1. Движок перестаёт принимать записи. Операции в очереди получают отказ, операции текущей пачки — отказ или «исход неизвестен», если ошибка случилась на шаге (4).
2. Чтения из памяти не обслуживаются. `/readyz` и `/livez` отвечают 503 (OBS-01, OBS-02); метрика fail-stop = 1 (OBS-07); в лог пишется событие ERROR с txid и номером страницы (OBS-14).
3. Не позже чем через 5 с процесс завершается с отдельным кодом выхода. Его значение `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: 70 (`EX_SOFTWARE`); его нужно добавить к CLI-13.
4. Супервизор перезапускает процесс, восстановление идёт по разделу 4.1 только с диска.

- **Альтернативы** (ADR 0005): режим только для чтения из памяти (отклонён D-034: после ошибки fsync кэшу доверять нельзя), повтор fsync.

### 5. Purge и физическое затирание (D-056)

Цель — уничтожить значения ПДн контакта во всех файлах базы не позднее T_purge = 24 ч (PRV-05, PRV-06, CUJ-09).

1. **Запрос.** admin вызывает `POST /api/v1/admin/contacts/{id}:purge` (API-24) или `budb admin purge` (CLI-08). Сначала в журнал purge дописывается и сбрасывается запись `{purge_id, contact_id, time, actor}` без хэшей (D-042, PRV-09). Её копия дописывается в журнал в каталоге бэкапов, если он настроен (D-036).
2. **Транзакция N.** Удаляет запись из `primary`, `name_idx`, `phone_idx` и `trash_idx`, а также записи `idempotency_keys`, где сохранён ответ с этим `contact_id` `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: в сохранённом ответе есть ПДн. После коммита N контакт не находится ни поиском, ни чтением, ни в корзине (PRV-05). Клиент получает квитанцию `pending_erasure` с `erase_deadline` = время + 24 ч (PRV-08).
3. **Принудительный коммит N+1.** Сразу после N писатель фиксирует транзакцию N+1, даже пустую. Теперь ни одна мета-страница не ссылается на страницы, освобождённые в N.
4. **Ожидание читателей.** Реестр снимков помечает снимки с txid ≤ N сроком «до T_purge». Интерактивные снимки и так живут ≤ 30 с (STO-24). Бэкап, экспорт и verify, которые не успели завершиться, принудительно завершаются с ошибкой `snapshot-expired` (PRV-07); бэкап перезапускается на новом снимке (D-056).
5. **Затирание.** Как только самый старый снимок новее N, страницы, освобождённые в N, заполняются нулями и сбрасываются на устройство в ближайшем коммите (раздел 3, шаги 3–4).
6. **Старые копии.** В освобождённых страницах могут лежать и прежние версии записи, оставшиеся после правок контакта. Поэтому затирание при переходе страницы из отложенного списка в свободные применяется ко всем страницам, а не только к страницам purge `[ПРЕДЛОЖЕНИЕ АГЕНТА: zero-on-reclaim]`. К сроку T_purge в файле нет ни одной старой копии.
7. **Квитанция.** В журнал purge дописывается `{purge_id, erased_at}`, и статус квитанции становится `erased` (PRV-08). Тест побайтового поиска по всем файлам базы (PRV-06) входит в CI.
8. **Автоочистка корзины.** Фоновая задача раз в час `[ПРЕДЛОЖЕНИЕ АГЕНТА]` берёт из `trash_idx` контакты, у которых истёк срок 1…29 дней (D-049), и очищает их по шагам 1–7 с исполнителем `system`. Задержка после истечения срока ≤ 24 ч (PRV-04). Восстановление после истечения срока запрещено, даже если автоочистка ещё не прошла (CON-17).
9. **Restore.** После восстановления из бэкапа к файлу применяется объединение всех доступных журналов: текущего, копии в каталоге бэкапов и копии рядом с бэкапом. Restore офлайн, читателей нет, поэтому затирание и сброс выполняются до rename (BKP-07, PRV-10). Если нет ни одного журнала и не задано явное переопределение, restore отказывает (D-036).

- **Альтернативы** (ADR 0012): DELETE сразу означает purge; только логическое удаление; crypto-shredding. Затирание только страниц транзакции N без zero-on-reclaim не выполняет PRV-06 для старых копий записи.

### 6. Журналы аудита и purge

- **Журнал аудита.** Отдельные файлы только на добавление с ротацией (D-055), без значений ПДн (PRV-13). Изменения, события аутентификации, административные операции, экспорт и поиск данных субъекта пишутся по одному событию; обычные чтения и поиски — агрегатом на пользователя за минуту (D-045). События пачки записываются с txid до шага (3) и сбрасываются вместе с шагом (2) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Событие с txid больше подтверждённого при чтении журнала помечается «не зафиксировано». Ошибка записи или сброса журнала аудита обрабатывается как fail-stop `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: без аудита операция с ПДн не должна подтверждаться (вопрос к оркестратору).
- **Журнал purge.** Отдельный файл со своим заголовком (magic, версия формата) и записями с CRC32C; каждая запись сбрасывается сразу (D-036). Срок хранения — бессрочно `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: журнал нужен, пока существует хоть один бэкап старше записи.
- **Формат журналов** — собственный, как и формат страниц, без serde (BLD-02).

### 7. Поток CUJ-01 «кто звонит»

1. Оператор вводит номер. UI ждёт 250 мс после последнего нажатия (UI-02), распознаёт номер (UI-03) и отправляет `POST /api/v1/contacts:search` `{"field":"phone","mode":"exact","value":"8 (495) 123-45-67"}` с cookie сессии (ACL-11, D-043) и CSRF-токеном `[ПРЕДЛОЖЕНИЕ АГЕНТА: CSRF и для POST без изменения данных]`.
2. tower-слой: сессия, роль reader (ACL-03, ACL-04), лимит частоты (API-19), лимит тела (API-18).
3. Номер нормализуется с регионом операции или по умолчанию: `+74951234567` (PHN-02, PHN-06, PHN-08). Ошибка даёт 422 с кодом PHN-14 (SRCH-02).
4. Запрос уходит в пул читателей. Читатель берёт снимок txid T (STO-09), сканирует `phone_idx` в диапазоне `74951234567‖0x00‖*`, читает записи `primary` по найденным `id` и отдаёт до 20 контактов (SRCH-01, SRCH-07, SRCH-09). Снимок отпускается сразу.
5. Если результатов больше страницы, формируется keyset-курсор (`e164`, `id`), подписанный HMAC-SHA256 секретом экземпляра, со сроком 24 ч (D-048, SRCH-10).
6. Ответ 200: `id` десятичной строкой (D-057), `Cache-Control: no-store` (ACL-20). Метрика задержки поиска с меткой `phone/exact` (OBS-04) и счётчик в минутном агрегате аудита (D-045).
7. UI показывает список с подсветкой (UI-04), объявляет число найденных (UI-05) и по Enter открывает карточку (UI-06).

Бюджет: движок p99 ≤ 2 мс на прогретом кэше (PERF-04), API p99 ≤ 100 мс (PERF-08), весь путь — без прерывания разговора, ориентир NN/g до 1 с (`docs/cuj.md`, CUJ-01).

### 8. Поток CUJ-03 «добавить или изменить контакт»

1. Редактор заполняет форму. Для каждого телефона UI показывает предпросмотр `POST /api/v1/phones:normalize` (UI-08, API-28).
2. «Сохранить» отправляет `POST /api/v1/contacts` с `Idempotency-Key` (UI-09, API-16) или `PUT /api/v1/contacts/{id}` с `If-Match: "<version>"` (API-06).
3. tower-слой: сессия, роль writer, CSRF и `Sec-Fetch-Site` (ACL-14), лимиты.
4. Проверка данных вне писателя: очистка имени и ключ (NAM-01…NAM-05), нормализация телефонов (PHN), лимиты и правила (CON-01…CON-09). Ошибка — 422 с `errors[]` (API-15).
5. Проверка `Idempotency-Key`: повтор с тем же телом возвращает сохранённый ответ, другое тело — 422, запрос ещё выполняется — 409 (API-17).
6. Операция ставится в очередь писателя. Если очередь полна — 503 с `Retry-After`, и операция не выполнялась (API-20, PERF-14).
7. Писатель в пачке: для PUT сверяет версию (412 при несовпадении, API-08); для POST выдаёт `id` (D-057); пишет `primary` с `version` + 1, `name_idx` (полный ключ и слова), `phone_idx`, запись `idempotency_keys`; считает подсказку о дубликатах (≤ 10 контактов с тем же полным ключом или общим `e164`) по своему представлению транзакции (CON-18, D-051).
8. Коммит по разделу 3. Событие аудита изменения пишется с txid (PRV-12, D-045).
9. Ответ 201 с `Location` и `ETag: "1"` (API-04) или 200 с новым `ETag` (API-06), в теле — контакт и подсказка о дубликатах. При «исходе неизвестен» клиент повторяет запрос с тем же `Idempotency-Key`.
10. UI пишет «Сохранено» только после 201 или 200 (UI-09). На 412 показывает обе версии (UI-10); на 503 и 429 сохраняет ввод и предлагает «Повторить» (UI-23).

Бюджет: долговечная запись p99 ≤ 50 мс (PERF-06), ≥ 500 подтверждённых записей/с при group commit (PERF-11).

### 9. Бэкап, verify, компактизация

- **Бэкап** (BKP-01…BKP-04). Снимок txid T. Страницы, достижимые из снимка, копируются во временный файл в формате STO-01…STO-04, затем: fsync, rename, fsync каталога. Рядом пишется `<ts>.purge` — копия журнала purge на момент T, в той же последовательности сброса и rename `[ПРЕДЛОЖЕНИЕ АГЕНТА: отдельный файл рядом с бэкапом, а не дерево внутри бэкапа]` (D-036). Затем бэкап проверяется по BKP-08, и только после этого обновляется метрика времени последнего бэкапа (OBS-11). Ротация удаляет бэкапы старше 30 дней (настраивается, ≤ 180; D-037, BKP-12, PRV-11).
- **Verify** (BKP-08…BKP-10). CRC32C всех страниц, обе мета-страницы, порядок ключей, взаимное соответствие деревьев (с учётом корзины, раздел 2), учёт каждой страницы как достижимой, отложенной или свободной. Офлайн — только чтение; онлайн — на снимке, найденное повреждение переводит сервер в fail-stop. Периодическая онлайн-проверка (scrub) снижает остаточный риск D-035 `[ПРЕДЛОЖЕНИЕ АГЕНТА: раз в сутки]`.
- **Компактизация** (BKP-11). Только офлайн: копирование живых страниц в новый файл, fsync, rename, fsync каталога (D-018; паттерн etcd defrag, docs/research/02, §2.4 п. 6).
- **Альтернативы** (ADR 0013): копирование файла средствами ОС, только офлайн-бэкап, снимки ФС силами эксплуатации.

### 10. Нормализация и ключи

- **Телефоны** (ADR 0008; D-010, D-052, D-059). Порядок PHN-02. Регионы RU и `none`. Список кодов стран ITU закреплён в данных правил с датой ITU-T Operational Bulletin; таблица национальных длин — только для `+7`. Версия правил и регион сохраняются у каждого телефона (PHN-15).
- **Имена** (ADR 0009; D-050, D-051, D-058). Хранение — NFC (NAM-01). Ключ — NFKC_Casefold, затем ё→е. Таблица NFKC_Casefold генерируется при сборке из закреплённого `DerivedNormalizationProps.txt`, сверенного по контрольной сумме (D-039). Версия Unicode одна для таблиц `unicode-normalization` и для собственной таблицы; сборка падает, если версии расходятся (D-050, D-058). Идентификатор версии правил ключа включает версию Unicode (NAM-09).
- **Альтернативы** (ADR 0009): lowercase вместо case folding; NFD со снятием всей диакритики; ключ сортировки UCA/ICU.

### 11. HTTP API, безопасность, UI

- **API** (ADR 0010; D-013, D-044, D-047, D-048, D-059): `/api/v1`, OpenAPI 3.1 как единственный источник правды и контрактные тесты (API-02); ошибки `application/problem+json` с `type` = `urn:budb:problem:<code>`; ETag = `version`; 412 и 428; keyset-курсор 24 ч; страница 20, максимум 100; восстановление из корзины — `POST /api/v1/contacts/{id}:restore` для writer и admin (D-041).
- **Безопасность** (ADR 0011; D-015, D-043, D-055, D-060): пароли — argon2; токены `budb_<id>_<secret>`, в хранилище SHA-256 секрета (`sha2`); курсоры — HMAC (`hmac`); случайные значения — `getrandom`; TLS — rustls 1.2 и 1.3; сессии в памяти процесса, cookie по D-043.
- **UI** (ADR 0016; D-031, D-060): TypeScript, собранный закреплённым `tsc` в нативные ES-модули, без бандлера и CDN; ассеты встраиваются в бинарник; строгая CSP (ACL-19); поддерживаются две последние версии Chrome, Edge, Firefox и Safari.

## Risks / Trade-offs

- [Высокое усиление записи COW: около 16 страниц на одиночную запись, `[РАСЧЁТ]` docs/research/02, §2.3] → group commit (STO-13), импорт пачками по 1000 (IMP-09); бенчмарк как условие выпуска (PERF-16). ADR 0003.
- [Один писатель ограничивает пропускную способность записи] → цель ≥ 500 записей/с подтверждается бенчмарком (PERF-11); очередь с backpressure (PERF-14). ADR 0003, ADR 0017.
- [Долгие снимки удерживают страницы, файл растёт] → 30 с для интерактивных операций (STO-24), T_purge для бэкапа, экспорта и verify (D-056), метрика возраста снимка (OBS-09). ADR 0003.
- [Файл не уменьшается без офлайн-компактизации] → метрика свободного места (OBS-05), окно обслуживания для `budb admin compact` (BKP-11). ADR 0003.
- [Накопитель лжёт о сбросе кэша (FAST'13, docs/research/02, §3.5)] → оговорка в документации (STO-23), эталонный стенд с честным NVMe (PERF-02). ADR 0005.
- [Fail-stop останавливает запись при одной ошибке I/O] → выход ≤ 5 с, супервизор, открытие ≤ 1 с (D-034, PERF-07). ADR 0005.
- [Порча новейшей мета-страницы после подтверждения неотличима от порванного коммита: теряется одна подтверждённая транзакция] → только при txid = valid_max+1, метрика и алерт, ежедневный scrub, бэкапы (D-035). ADR 0003, ADR 0005.
- [Переиспользование страниц, на которые ссылается старшая мета-страница, сделало бы откат D-035 тихой порчей] → правило переиспользования раздела 3.1. ADR 0003.
- [Записи и ключи больше страницы ухудшают fanout] → страницы переполнения, укороченные разделители, фаззинг (BLD-16). ADR 0003, ADR 0007.
- [Затирание ПДн не достаёт старые копии записи] → zero-on-reclaim, побайтовый тест (PRV-06). ADR 0012.
- [Бэкапы содержат очищенные ПДн] → журналы purge применяются при restore (BKP-07, PRV-10), копия журнала рядом с бэкапом и в каталоге бэкапов, срок хранения ≤ 180 дней (D-036, D-037). ADR 0012, ADR 0013.
- [Результаты экспорта на сервере содержат ПДн контакта, очищенного после экспорта] → результат удаляется через 24 ч (PRV-16); UI предупреждает о ПДн (UI-14). Затирание файлов экспорта при purge в спецификации не требуется — вопрос к оркестратору. ADR 0012.
- [Версии Unicode в `unicode-normalization` и в собственной таблице разойдутся] → проверка при сборке (D-050, D-058); смена версии правил → автоматическая переиндексация (NAM-10). ADR 0009.
- [Переиндексация 10^8 имён при открытии надолго делает сервер неготовым] → прогресс в метриках, смена правил только в мажорных выпусках `[ПРЕДЛОЖЕНИЕ АГЕНТА]`; время на 10^8 измеряется в предрелизном прогоне (PERF-01). ADR 0009.
- [Перечислимые `id`] → авторизация каждой операции (ACL-04), одна книга (D-014, D-057). ADR 0007, ADR 0011.
- [Cookie без `Secure` на `http://127.0.0.1` может вести себя в браузерах по-разному `[НЕ ПОДТВЕРЖДЕНО]`] → e2e-тест UI на всех поддерживаемых браузерах (D-043). ADR 0011, ADR 0016.
- [Объём аудита при 5000 поисков/с ≈ 43 ГБ в сутки `[РАСЧЁТ]`] → агрегирование чтений (D-045). ADR 0012.
- [Цепочка поставок крейтов и npm] → allowlist для прямых зависимостей и denylist для всего графа, `--locked`, lock-файл с integrity (BLD-04, BLD-05, BLD-11, D-060). ADR 0006.
- [Windows и macOS: долговечность rename и каталога не подтверждена] → tier 2 с оговорками (BLD-09). ADR 0014.
- [Скачок системного времени сдвигает сроки корзины и курсоров] → время UTC от системных часов, `deleted_at` хранится в записи; оговорка в документации оператора `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. ADR 0012.

## Migration Plan

- **Первый выпуск.** Данных для миграции нет. Порядок развёртывания: `budb admin bootstrap --db <путь> --login <логин>` при остановленном сервере (ACL-21, CLI-12) → `budb serve --config budb.toml` под супервизором с автоматическим перезапуском (D-034) → настройка каталога бэкапов, ротации и алертов (`budb_meta_fallback_total`, fail-stop, возраст бэкапа, возраст снимка).
- **Версии формата.**
  - Файл БД и бэкап: поле версии формата в заголовке и мета-странице, v1 = 1. Неизвестная версия не открывается и файл не меняется (STO-02, BKP-06). Будущая миграция — отдельная офлайн-команда «копировать в новый файл → fsync → rename» по образцу компактизации; её введёт новый ADR.
  - Журналы аудита и purge: собственный заголовок с версией; новая версия читает старую.
  - Правила ключа имени: версия хранится в мета-странице; при расхождении — автоматическая переиндексация при открытии (NAM-10, NAM-11).
  - Правила нормализации телефонов: версия у каждого телефона; пересчёт — командой администратора (PHN-16).
  - HTTP API: в `/api/v1` только аддитивные изменения; ломающие — в `/api/v2`, который работает параллельно (API-03).
- **Откат.** Откат бинарника безопасен, только если версия формата и версии правил не менялись. Иначе — restore из бэкапа, сделанного до обновления (BKP-05, BKP-07).

## Open Questions

Вопросы, ответы на которые не меняют спецификации и фазы `tasks.md`; их можно решить при реализации:

- политика вытеснения кэша страниц (CLOCK или LRU) и минимальный размер кэша (PERF-09);
- значения по умолчанию: размер пула читателей, K и T для group commit, шаг роста файла, порог переполнения;
- частота фоновой автоочистки корзины и scrub в пределах сроков D-049 и D-056;
- значение отдельного кода выхода при fail-stop (предложено 70).

## ВОПРОСЫ К ОРКЕСТРАТОРУ

Эти вопросы меняют спецификации. До ответа в документе действует вариант с пометкой `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.

1. **Повторы в префиксном поиске по словам (D-051).** Контакт «Иван Иванов» совпадает с префиксом «иван» и полным ключом, и вторым словом. Убирать повтор (как?) или выдавать пары «совпавшее слово + контакт», как SRCH-03 для телефонов? По какому ключу упорядочивать: по совпавшему слову или по полному ключу?
2. **Различение порванной и испорченной мета-страницы (D-035).** Можно ли доверять полю txid в слоте с неверной CRC32C? Предложено: txid читается и равен `valid_max + 1` → откат; иначе → отказ в открытии.
3. **Индексы и корзина (D-055, STO-06).** Предложено удалять записи `name_idx` и `phone_idx` при переносе в корзину и восстанавливать их при restore; инвариант STO-06 — для активных контактов.
4. **Хранение заданий** (IMP-05, IMP-10): дерево `jobs` в каталоге, как служебные деревья D-055?
5. **Ошибка записи журнала аудита:** fail-stop, как для файла БД?
6. **Затирание файлов результатов экспорта и `idempotency_keys` при purge** — входит ли в PRV-06?
7. **Префиксный поиск по телефону с национальным префиксом** («8916» → «+7916») и **набор маркеров добавочного номера** — в D-052 и D-059 не решены (вопрос 8 в `docs/adr/README.md`).
8. **CSRF для `POST :search`:** проверять ли CSRF-токен на POST, которые не меняют данные?
