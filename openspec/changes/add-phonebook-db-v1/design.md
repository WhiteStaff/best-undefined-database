# Design: add-phonebook-db-v1 — BUDB v1

Документ сводит в одно техническое решение ADR 0001–0018 (`docs/adr/`) и решения оркестратора D-001…D-118 (`docs/orchestrator-decisions.md`). Требования здесь не повторяются: на них даны ссылки по ID (`openspec/changes/add-phonebook-db-v1/specs/*/spec.md`). Зачем нужен продукт, описано в `proposal.md` (раздел «Why»); исходный текст ДЗ — в `docs/assignment.md`.

Пометки: `[ПРЕДЛОЖЕНИЕ АГЕНТА]` — технический выбор автора этого документа, которого нет в журнале решений; `[ДОПУЩЕНИЕ]`, `[РАСЧЁТ]`, `[НЕ ПОДТВЕРЖДЕНО]` — как в `docs/adr/README.md`.

## Context

- **Текущее состояние.** Кода нет. Есть 15 спецификаций (`docs/traceability.md`), ADR 0001–0018, `docs/cuj.md`, решения D-001…D-118, четыре ревью раунда 1 (`docs/reviews/round1-*.md`) и Goldfish-ревью раунда 2 (`docs/reviews/round2-goldfish.md`); разбор — `docs/reviews/GOLDFISH.md`.
- **Ограничения.** Хранение пишется с нуля: сторонние движки, KV, WAL и ORM запрещены, сторонние крейты — только по allowlist (D-021, D-038, D-060, D-066, D-082, D-097; ADR 0006). Язык — Rust stable; `unsafe` запрещён везде, кроме изолированного крейта `budb-sys` (D-020, D-090; ADR 0002, ADR 0018). Один узел, цель 10^8 контактов, SLO проверяются на 10^7 (D-024, пересчёт D-094). Полные гарантии долговечности — на Linux tier 1 (D-023; ADR 0014). Имена и телефоны — ПДн (D-012, D-013).
- **Приоритет источников.** Решения D-034…D-118 приняты после того, как спецификации были написаны. Редакторы вносят их в спецификации без смены ID (D-040); журналы правок — `docs/reviews/round1-fixlog-*.md`. Пока правка не внесена, при расхождении действует решение, и этот документ следует ему. Если расходятся два решения, главнее решение с большим номером: D-116 главнее D-113 в части правил префикса, D-117 главнее D-113 в части подтверждения пользователей после restore. Таблицы ниже — сводка; полный текст решений — в `docs/orchestrator-decisions.md`.

## Goals / Non-Goals

**Goals:**

- Одна архитектура, в которой каждое требование STO, BKP, PERF и BLD реализуется без противоречий с D-034…D-118.
- Протокол коммита и восстановления, который можно перечислить как последовательность системных вызовов и проверить перебором состояний (BLD-13, BLD-14).
- Обнаружение не только случайной порчи страниц, но и потерянных и промахнувшихся записей (D-085).
- Физическое затирание ПДн не позднее T_purge = 24 ч, включая старые копии записей и производные формы ключей (PRV-06, D-056, D-077, D-102).
- Единственный узел продолжает обслуживать чтения при порче страницы и при нехватке места (D-072, D-078, D-089).
- Порядок реализации, при котором фазы `tasks.md` закрывают требования по слоям.

**Non-Goals:**

- Границы продукта v1 — в `proposal.md` (раздел «Out of Scope (v1)»).
- Выбор политики вытеснения кэша, размеров пулов и пачек: значения по умолчанию и настройки, без изменения поведения (раздел «Open Questions»).
- Формат журналов ОС и конфигурация супервизора: задача эксплуатации; продукт требует только перезапуска процесса после выхода с нарастающей задержкой (D-034, D-072).
- Соответствие оператора требованию о сертифицированных средствах уничтожения ПДн (D-105).

## Decisions

### 1. Компоненты и потоки

Один процесс `budb serve` (D-032; ADR 0017). HTTP-слой асинхронный (tokio, hyper, axum, tower), движок синхронный. Слои общаются через ограниченные каналы; при переполнении сервер отвечает 503, при превышении лимита клиента — 429 (D-059; PERF-14, API-19, API-20).

```
 Браузер: UI (TS + Web Components)   Интегратор / budb admin --server   Prometheus
        | cookie + X-CSRF-Token            | Bearer-токен                  | токен с областью metrics
        v                                  v                               v
+-------------------------------- budb serve (один процесс) ---------------------------------+
| статика UI из бинарника | HTTP API /api/v1 | admin API /api/v1/admin/* | /livez /readyz      |
| /problems/<code> (страницы ошибок) | /metrics                                              |
| tower: аутентификация, роли и области токенов (ACL), CSRF, public_origin и доверенные      |
|        прокси, лимит частоты и квота выдачи -> 429, лимит тела -> 413,                     |
|        problem+json с полем code (API-14), маскирование ПДн в логах (PRV-14)               |
|              | чтения                                     | записи                           |
|              v                                            v                                  |
|  +-- пул читателей (N потоков) --+       +-- очередь писателя (ограничена) --+ -> 503      |
|  | снимок txid, тайм-аут 2 с,    |       | поток-писатель, group commit,      |             |

|  +---------------+---------------+       +-----------------+------------------+             |
|                  v                                         v                                 |
|  +------------------------------ движок (трейт Storage) ------------------------------+    |
|  | реестр снимков | COW B+tree | free_db | кэш страниц + CRC32C/page_no/txid | коммит |    |
|  +---------------------------------+--------------------------------------------------+    |
|                                    | безопасный API                                         |
|                         budb-sys (единственный крейт с unsafe: FFI, CRC32C intrinsics)       |
```

- **Пул читателей.** Каждая операция чтения берёт снимок последнего подтверждённого txid (STO-09), выполняется и отпускает его. Запрос ограничен тайм-аутом 2 с, интерактивный снимок — 30 с (STO-24, D-048, D-078). Отзыв снимка кооперативный: при каждой загрузке страницы читатель проверяет флаг отзыва и прерывается с ошибкой `snapshot-expired` (D-092, STO-31). Размер пула по умолчанию — число vCPU `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
- **Поток-писатель.** Единственный (STO-08). Берёт из очереди пачку (по умолчанию ≤ 1000 операций, без ожидания набора — STO-13 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`), применяет операции и фиксирует пачку одним коммитом (раздел 3). Ёмкость очереди по умолчанию 4096 (PERF-14 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`). Пока есть страницы, ждущие затирания, писатель сам выполняет служебные коммиты по таймеру (D-070, STO-28).
- **Длинные операции** (бэкап, онлайн-verify, экспорт) работают на отдельных потоках с собственными снимками. Лимит 30 с на них не действует, но их снимки отзываются в T_purge − 1 ч = 23 ч (D-076, STO-24) и при превышении лимита объёма удерживаемых страниц (D-093, STO-32). Импорт пишет через ту же очередь писателя пачками по 1000 записей (IMP-09), поэтому один писатель сохраняется.
- **Admin CLI.** `budb admin --server` вызывает admin API; `budb admin --db` работает с файлом напрямую под эксклюзивной блокировкой, когда сервер остановлен (D-055; CLI-03, CLI-04, STO-20).
- **Альтернативы** (ADR 0017): `spawn_blocking` на каждый запрос (нет единственного писателя и пачек), асинхронный движок (усложняет детерминированную симуляцию), «поток на соединение» без tokio.

### 2. Раскладка файла и деревьев

Страница — 4096 байт. Заголовок каждой страницы — {magic и тип, `page_no`, `write_txid`, CRC32C по всей странице} (D-085; STO-03; ADR 0005). Указатель на дочернюю страницу и корень в мета-странице — пара (`page_no`, ожидаемый `write_txid`) (D-085; STO-25). При чтении с диска проверяются CRC32C, равенство `page_no` запрошенному номеру и равенство `write_txid` ожидаемому из указателя, причём `write_txid` не больше txid снимка. Так обнаруживаются misdirected write (по адресу лежит чужая валидная страница) и lost write (на месте осталась прежняя валидная версия), которые одна CRC32C не ловит (FAST'17, FAST'13; EX1-01). Числа на диске кодируются вручную, без serde, bincode и rkyv (BLD-02, BLD-04).

| Страница | Содержимое | Требования |
|---|---|---|
| 0 | Заголовок: magic `BUDB`, версия формата (1), размер страницы, время создания, CRC32C. Пишется один раз при атомарном создании файла | STO-01, STO-02, STO-36 |
| 1, 2 | Слоты мета-страниц A и B: magic, версия, txid, `page_count` (high-water mark файла), `db_lineage_id`, корни (`page_no`, `write_txid`) деревьев `primary`, `name_idx`, `phone_idx`, каталога и `free_db`, `next_contact_id`, версии правил ключа имени и нормализации телефонов, счётчики активных контактов и контактов в корзине, CRC32C | STO-04, STO-26, STO-27, STO-38, STO-39, NAM-09, PHN-15, D-055, D-057, D-086, D-091, D-095 |
| ≥ 3 | Страницы деревьев (ветви, листья), страницы переполнения, страницы `free_db` | STO-05, STO-10, STO-27 |

Страницы с номером ≥ `page_count` считаются невыделенными: verify их не учитывает, а открытие на запись обрезает файл до `page_count` (D-086; STO-26). Рост файла становится частью состояния только с новой мета-страницей, поэтому хвост, выращенный незафиксированной транзакцией, — не утечка.

Деревья. Все меняются одной транзакцией (STO-06, STO-07):

| Дерево | Ключ | Значение | Источник |
|---|---|---|---|
| `primary` | `id` (u64 big-endian) | Запись контакта: поля CON-01, телефоны CON-04 с версией правил и регионом (PHN-15), `version`, `created`, `updated`, `deleted_at` | D-009, D-055, D-057 |
| `name_idx` | `kind` (0 — полный ключ, 1 — слово) ‖ ключ имени UTF-8 ‖ `0x00` ‖ `id` | пусто | D-050, D-051; `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: формат ключа |
| `phone_idx` | цифры `e164` (ASCII) ‖ `0x00` ‖ `id` | число добавочных номеров с этим `e164` у контакта | D-009; `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: формат ключа |
| `free_db` | `freeing_txid` (u64 big-endian) | список `page_no`, освобождённых транзакцией | D-091; STO-27 (FREE_DBI в LMDB) |
| каталог → `users` | логин после case folding | роль, признак «отключён», хэш argon2, время смены пароля | D-055, ACL-01, ACL-05 |
| каталог → `api_tokens` | `token_id` | владелец, области (в т. ч. `metrics`), SHA-256 секрета, срок, признак отзыва, квота выдачи | D-055, D-060, D-083, D-103, ACL-07…ACL-10, ACL-24, ACL-25 |
| каталог → `idempotency_keys` | субъект аутентификации ‖ ключ | хэш тела, статус, сохранённый ответ, `contact_id`, время (TTL 24 ч); после purge — надгробие без ответа и ПДн: хэш тела, признак `purged`, прежний TTL | D-055, D-116, API-16, API-33 |
| каталог → `trash_idx` | `deleted_at` ‖ `id` | пусто | D-055, CON-16, PRV-04 |
| каталог → `instance` | константы | ключ экземпляра для AEAD-шифрования курсоров (256 бит из CSPRNG) | D-082; `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: место хранения ключа |
| каталог → `jobs` | `job_id` | тип, владелец, состояние (`queued`/`running`/`succeeded`/`failed` + `reason`), счётчики, без ПДн | D-064, D-084, IMP-05, IMP-10, API-32 |

- **`free_db`** (D-091). Свободные и отложенные страницы учитываются в COW-дереве `free_db(freeing_txid → [page_no])`. Его собственные страницы выделяются и освобождаются в том же коммите, что и изменения деревьев; рекурсия «выделение страницы под `free_db` меняет `free_db`» замыкается внутри одной транзакции `[ПРЕДЛОЖЕНИЕ АГЕНТА: по образцу LMDB — выделять страницы под `free_db` из уже свободных до записи нового списка, а излишек возвращать в следующей транзакции]`. Инвариант STO-27: каждая страница < `page_count` входит ровно в одно множество — достижима из деревьев или каталога; страница `free_db`; отложена с меткой T; свободна. Это же проверяет verify (BKP-08).
- **Разделитель `0x00`.** Без него сравнение `ключ‖id` ставит id короткого ключа между длинными ключами. Байт `0x00` не встречается ни в ключе имени (U+0000 удаляется как Cc, NAM-03), ни в цифрах номера, поэтому порядок совпадает с SRCH-08: сначала ключ, затем `id`.
- **Корзина** (D-064). При удалении записи `name_idx` и `phone_idx` удаляются, а в `trash_idx` добавляется запись; restore возвращает их обратно. Так поиск не видит корзину (SRCH-15) и не тратит время на фильтрацию. Выгрузка данных субъекта (PRV-15) ищет активные контакты по индексам, а контакты в корзине — перебором `trash_idx` (корзина мала, D-049). Инвариант STO-06 читается как «каждый активный контакт представлен в обоих индексах».
- **Большие записи.** Худший случай записи — около 5,5 КиБ: `display_name` до 1024 Б, три части имени по 128 кодовых точек и 10 телефонов с `raw_input` до 64 кодовых точек `[РАСЧЁТ]` по D-022 и PHN-12. Это больше страницы, поэтому записи и ключи больше 1 КиБ выносятся в цепочку страниц переполнения, а в ветвях хранятся укороченные разделители `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Средняя запись — около 140–170 Б `[РАСЧЁТ]` EX1-12 (а не 70 Б, как в первой оценке) — в переполнение не попадает. Разделители производны от ключей, поэтому purge переписывает и их (D-077, раздел 5).
- **Слова имени (D-051, D-062, D-074).** `display_name` после очистки (NAM-02) делится по White_Space и дефису. Для каждого слова, кроме того, с которого начинается полный ключ, в `name_idx` добавляется запись `kind = 1`: оно уже покрыто префиксом полного ключа. Если ключ начинается с разделителя («-Анна»), первое слово индексируется (NAM-13, D-118). Точный поиск (SRCH-04) читает только записи `kind = 0`. Префиксный поиск (SRCH-05) сливает два диапазона: класс ранга 0 (префикс полного ключа), затем класс 1 (префикс слова); повторы контакта убираются по `id`; класс 0 упорядочен по полному ключу имени, класс 1 — по наименьшему ключу совпавшего слова (D-112, SRCH-05), внутри ключа — по `id`. Курсор = (класс ранга, ключ, `id`) (D-074); так страницу класса 1 можно выдать, не собирая все совпадения по слову (EX1-20).
- **Альтернативы** (ADR 0003, ADR 0007): отдельная сущность Phone со связью многие-ко-многим; служебные данные в отдельных файлах (отклонено D-055: две точки атомарности вместо одной); флаг «в корзине» в индексах (поиск фильтрует на чтении, индексы крупнее); freelist вне дерева (отклонено D-091: рекурсия и учёт страниц не определены).

### 3. Протокол коммита

Протокол — 2PC по ADR 0005 (D-019): fsync страниц, запись мета-страницы, fsync. Шаги с номерами STO-11 обозначены как (1)…(4).

1. **Сбор пачки.** Писатель забирает из очереди до K операций (STO-13). Если очередь пуста, а в `free_db` есть страницы, ждущие затирания или перехода в свободные, писатель по таймеру начинает служебную транзакцию без операций (D-070, STO-28) `[ПРЕДЛОЖЕНИЕ АГЕНТА: таймер 60 с]`.
2. **Применение.** Каждая операция выполняется в COW-транзакции на копиях страниц в памяти: проверка версии (CON-13; 412 по API-08), выдача `id` из `next_contact_id` (D-057, STO-39), изменение `primary`, `name_idx`, `phone_idx`, служебных деревьев. Перед каждой операцией ставится точка отката; отклонённая операция откатывается к ней и не влияет на остальные (STO-13) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Новые страницы берутся из `free_db` по правилу раздела 3.1. Иначе файл растёт: новый регион заранее заполняется нулями и сбрасывается отдельной операцией до использования (STO-33; шаг 64 МиБ `[ПРЕДЛОЖЕНИЕ АГЕНТА]`). ENOSPC при этом или при предварительной проверке места — не fail-stop: операция получает 507, движок переходит в degraded-read-only (D-072, раздел 4.3).
3. **(1) Запись страниц.** `pwrite` всех изменённых страниц с заголовком (`page_no`, `write_txid` = txid транзакции) и CRC32C, новых страниц `free_db` и страниц, которые в этой транзакции затираются нулями (раздел 5). Параллельно в журнал аудита дописываются записи намерений пачки с txid, `boot_id` и `db_lineage_id` (D-080, D-095; раздел 6). ENOSPC при этой дозаписи — не fail-stop, а путь D-072: 507 и degraded-read-only (D-117, PRV-22).
4. **(2) Сброс.** `fdatasync` на Linux, `fcntl(F_FULLFSYNC)` на macOS, `FlushFileBuffers` на Windows (STO-14; docs/research/02, §3.1–§3.3). Журнал аудита сбрасывается параллельно со сбросом файла данных, поэтому последовательных сбросов на коммит два: этот и шаг (4) (D-094). Ошибка любого из сбросов — fail-stop без повтора (раздел 4.3).
5. **(3) Мета-страница.** Запись мета-страницы `txid + 1` (с новым `page_count`) в слот с меньшим txid (STO-04), чтобы мета-страница последнего подтверждённого коммита не перезаписывалась. Ошибка записи — тоже «исход неизвестен» и fail-stop: частично записанная или попавшая в кэш ОС мета-страница N+1 может пережить перезапуск (STO-34, STO-12).
6. **(4) Сброс.** Ошибка — ответ «исход неизвестен» всем операциям пачки (STO-12; на HTTP — API-33) и fail-stop.
7. **Публикация.** Новый корень становится текущим снимком для новых читателей (STO-09). Только после этого клиенты получают подтверждение (STO-12, CON-10, API-04).
8. **Учёт освобождённого.** Страницы, которые транзакция T сделала недостижимыми, записываются в `free_db` с ключом `freeing_txid` = T (D-091). Запись входит в страницы той же транзакции (шаг 3) и становится видимой вместе с мета-страницей T; реестр отложенных страниц в памяти обновляется после публикации (шаг 7). Освобождённая страница попадает в затирание и переиспользование по разделу 3.1 и STO-29 (D-102), а рекурсия «страницы под `free_db` меняют `free_db`» замыкается внутри транзакции (раздел 2).

После create, rename и unlink выполняется fsync каталога (STO-15). На Windows rename выполняется через `MoveFileExW` с `MOVEFILE_WRITE_THROUGH` из крейта `budb-sys` (D-090, ADR 0018) и считается best effort (ADR 0014). Новый файл БД создаётся атомарно: временный файл → заголовок и оба слота → fsync → rename → fsync каталога (STO-36). Режима без сброса нет (STO-21).

#### 3.1. Когда страницу можно переиспользовать

Страница, освобождённая транзакцией T, переиспользуется (и затирается) только при трёх условиях, уточняющих STO-10:

- нет активного снимка с txid < T, и все отозванные читатели уже сняли регистрацию (STO-10, D-092);
- последний подтверждённый txid ≥ T + 1, то есть переиспользовать страницу может только транзакция T + 2 или более поздняя: к этому моменту мета-страницы T − 1 уже нет. Мета-страница T − 1 ссылается на страницы, освобождённые в T. Если перезаписать их, пока эта мета-страница жива, откат к ней по D-035 и D-063 прочитает чужие страницы; теперь такую подмену обнаружит проверка `write_txid` по D-085, но откат всё равно станет невозможен;
- правило действует и после перезапуска: отложенные страницы, загруженные из `free_db` при открытии, подчиняются тому же условию T + 2 (D-087; раздел 4.1).

EX1 проверило это правило и подтвердило его корректность. Это то же рассуждение, что и принудительный коммит N+1 в D-056.

- **Альтернативы** (ADR 0005): 1PC с деревом контрольных сумм (как redb), асинхронная долговечность (запрещена D-019), повтор fsync (fsyncgate, docs/research/02, §3.4).

### 4. Восстановление и ошибки

#### 4.1. Открытие файла

1. Взять эксклюзивную блокировку; если она занята — ошибка «БД используется другим процессом» (STO-20).
2. Прочитать страницу 0: magic, версия, размер страницы, CRC32C (STO-01, STO-02). Ошибка — отказ без единого изменения файла.
3. Прочитать оба слота мета-страниц и проверить CRC32C, magic и версию (STO-17).
4. Выбрать мета-страницу по D-063: полям слота с неверной CRC32C не доверять (txid из него не читается).
   - Валидны оба слота — открыть слот с наибольшим txid (`valid_max`).
   - Валиден ровно один слот (txid V) — второй считается порванным коммитом V + 1: открыть V, записать событие с V (OBS-14), увеличить `budb_meta_fallback_total`, поднять алерт (STO-17, D-035). Остаточный риск — битовая порча после подтверждения неотличима от порванного коммита — снижают scrub и бэкапы (D-035).
   - Невалидны оба — отказ в открытии с ошибкой повреждения (STO-18).
5. Проверить CRC32C, `page_no` и `write_txid` корней всех деревьев, каталога и `free_db`, достижимых из выбранной мета-страницы (D-085). При ошибке — отказ с номером страницы, без отката к старой мета-странице и без единого изменения файла (STO-18; FAST'17, docs/research/02, §3.6). Проверка идёт до обрезки, поэтому отказ не меняет файл (GF3-17).
6. Если файл длиннее `page_count` выбранной мета-страницы, обрезать его до `page_count` и сбросить (D-086, STO-26).
7. Переписать выбранную мета-страницу на её место тем же содержимым и сбросить файл до готовности (D-088, STO-34). Так содержимое, оставшееся после неудачного fsync только в кэше ОС, попадает на диск (ATC'20, EX1-04). Любая ошибка — отказ в открытии.
8. Загрузить `free_db`. Активных снимков после перезапуска нет, но правило T + 2 раздела 3.1 по-прежнему действует (D-087): страницы, освобождённые последней транзакцией, достижимы из второй мета-страницы и не трогаются до коммита T + 2. Остальные отложенные страницы затираются нулями в первых коммитах по K страниц (STO-29) и не задерживают `/readyz` (GF2-29).
9. Открыть журналы аудита и purge: порванная последняя запись с неверной CRC32C отбрасывается, неверная CRC32C в середине — явная ошибка (STO-37). Для намерений аудита упавшего запуска (тот же `db_lineage_id`, прежний `boot_id`) с txid больше восстановленного дописать компенсирующие записи `rolled_back` (D-080, D-095). Сгенерировать новый `boot_id` (STO-38).
10. Повторить идемпотентно каждую запись журнала purge в состоянии `pending` (D-076; раздел 5). Если база откроется в degraded-read-only (шаг 13), записи остаются `pending` до снятия режима или restore (D-117, PRV-23).
11. Если версия правил ключа имени в файле отличается от текущей, перестроить `name_idx` новой COW-транзакцией: новое дерево строится рядом, корень подменяется одним коммитом (NAM-10, NAM-11). До конца перестроения недоступен поиск по имени; ход виден в метриках.
12. Удалить оставшиеся временные файлы бэкапа и компактизации со сбросом каталога (BKP-03).
13. Если свободного места на ФС меньше жёсткого порога `hard_free_space_mib` (128 МиБ; ниже мягкого `min_free_space_mib` = 1024 МиБ — только алерт и пометка в `/readyz`, STO-41, D-118) или сохранился признак повреждения из degraded-read-only, открыть базу в режиме degraded-read-only (D-072, D-089, STO-35); признак повреждения переживает перезапуск в файле-маркере (D-109) и снимается только по STO-40 (`budb admin recover --clear-degraded`, D-117).
14. `/readyz` = 200 (OBS-02). Журнал не переигрывается, поэтому открытие укладывается в p99 ≤ 1 с независимо от размера файла, если не нужна переиндексация (PERF-07).

#### 4.2. Повреждение во время работы (D-078, D-089)

Страница, достижимая из снимка, которая не проходит проверки CRC32C, `page_no` или `write_txid` (STO-03, STO-25), даёт клиенту ошибку хранилища 500, а не пустой результат (STO-19). Процесс не завершается: движок записывает событие с номером страницы и переходит в режим degraded-read-only (STO-35):

- записи получают 503 (API-31); чтения, не задевающие испорченную страницу, обслуживаются;
- `/readyz` отвечает 200 со статусом `degraded-read-only` и причиной в теле, чтобы единственный узел не выпадал из балансировщика (D-089, OBS-02);
- метрика режима и алерт (OBS-16);
- режим снимает только администратор: `budb admin recover --clear-degraded` или `POST /api/v1/admin/status:clear-degraded` запускают verify, и режим снимается лишь при успешной проверке (D-117, STO-40, API-40, CLI-21); либо restore в новый файл;
- purge в этом режиме записывается как `pending` и выполняется после снятия режима или restore (раздел 5, PRV-23).

Почему не выход процесса, как в D-034: открытие проверяет только корни, поэтому после перезапуска первый же запрос к испорченному листу снова уронил бы процесс — цикл рестартов, который FAST'17 описывает как «repeatedly crash until manual intervention» (EX1-05, GF2-14).

#### 4.3. Fail-stop (D-034, D-065, D-072)

Fail-stop наступает только при ошибке записи или сброса файла БД, при ошибке записи или сброса журнала аудита (D-065; ENOSPC журнала — не fail-stop, D-117) и при ENOSPC или EIO во время сброса (D-072).

1. Движок перестаёт принимать записи. Операции в очереди получают отказ, операции текущей пачки — отказ, а если ошибка случилась на шаге (3) или (4) — «исход неизвестен» (STO-12, API-33).
2. Чтения из памяти не обслуживаются. `/readyz` и `/livez` отвечают 503 (OBS-01, OBS-02); метрика fail-stop = 1 (OBS-07); в лог пишется событие ERROR с txid и номером страницы (OBS-14).
3. Не позже чем через 5 с процесс завершается с отдельным кодом выхода. Код — 70 (`EX_SOFTWARE`), закреплён в CLI-13 (D-110).
4. Супервизор перезапускает процесс с нарастающей задержкой (D-072); восстановление идёт по разделу 4.1 только с диска, а шаг 7 (D-088) вытесняет на диск то, что осталось в кэше ОС.

ENOSPC, обнаруженный до шага (3) — при расширении файла или предварительной проверке места, — не fail-stop: записи получают 507, движок переходит в degraded-read-only по разделу 4.2, чтения продолжаются; этот режим снимается сам, когда место освобождено `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (D-072, STO-33, STO-35). Метрика и алерт свободного места на ФС — OBS-18. ENOSPC на ФС журнала аудита идёт тем же путём (D-117, PRV-22): иначе после перезапуска fail-stop повторялся бы в цикле; fail-stop по журналу аудита наступает только при EIO или ошибке fsync.

- **Альтернативы** (ADR 0005): режим только для чтения из памяти после ошибки fsync (отклонён D-034: после ошибки fsync кэшу доверять нельзя), повтор fsync, выход процесса при порче во время работы (отклонён D-078: цикл рестартов).

### 5. Purge и физическое затирание (D-056, D-069, D-070, D-075…D-077, D-102, D-116, D-117)

Цель — уничтожить значения ПДн контакта во всех файлах базы не позднее T_purge = 24 ч (PRV-05, PRV-06, CUJ-09). Purge — техническая мера внутри файлов BUDB, а не сертифицированное средство защиты информации по 152-ФЗ ст. 19 ч. 2 п. 3.1; выполнение этого требования — задача оператора (D-105, PRV-19).

1. **Запрос.** admin вызывает `POST /api/v1/admin/contacts/{id}:purge` (API-24) или `budb admin purge` (CLI-08). Повтор purge того же `id` возвращает прежнюю квитанцию (D-076, API-24).
2. **Запись «pending».** До транзакции N в журнал `purge.journal` дописывается и сбрасывается запись `{purge_id, contact_id, created_at контакта, time, actor, state = pending}` без хэшей (D-042, D-075, D-076; PRV-09). Её копия дописывается в журнал в каталоге бэкапов `backups/purge.journal`, если он настроен (D-036, D-069). Ошибка записи журнала — purge не подтверждается.
3. **Транзакция N.** Удаляет запись из `primary`, `name_idx`, `phone_idx` и `trash_idx`, а записи `idempotency_keys`, ссылающиеся на `contact_id`, заменяет надгробиями без ПДн — ключ, субъект, хэш тела, признак `purged`, прежний TTL 24 ч; повтор запроса с таким ключом получает 410 `purged`, а не создаёт контакт заново (D-065, D-116; API-16). Все живые страницы, где есть производные формы ПДн контакта — записи, ключи и разделители во внутренних узлах, полученные из этих ключей, — переписываются по COW (D-077, STO-30). После коммита N контакт не находится ни поиском, ни чтением, ни в корзине (PRV-05), и ни одна живая страница не содержит его производных форм. Клиент получает квитанцию `pending_erasure` с `erase_deadline` = время + 24 ч (PRV-08).
4. **Служебный коммит N+1.** Сразу после N писатель фиксирует транзакцию N+1, даже пустую (STO-28). Теперь ни одна мета-страница не ссылается на страницы, освобождённые в N.
5. **Результаты экспорта и загрузки.** Снимки экспорта с txid ≤ N принудительно закрываются, задания получают `failed` с `reason` = `contact-purged` (D-116, IMP-17), готовые файлы результатов экспорта и все хранящиеся файлы загрузки импорта удаляются, активное задание импорта получает `failed` с тем же `reason` (D-065, D-084, D-113; PRV-07, PRV-16, IMP-18, API-26).
6. **Ожидание читателей.** Остальные снимки с txid ≤ N отзываются кооперативно не позднее T_purge − 1 ч = 23 ч (D-076, D-092; STO-24, STO-31). Интерактивные снимки и так живут ≤ 30 с. Бэкап и verify, которые не успели завершиться, получают `snapshot-expired` (PRV-07); бэкап перезапускается на новом снимке (D-056).
7. **Затирание.** Как только условия раздела 3.1 выполнены, страницы, освобождённые в N, заполняются нулями и сбрасываются в ближайшем коммите — пользовательском или служебном по таймеру (D-070). Так затирание укладывается в T_purge даже на простаивающей системе.
8. **Все освобождённые страницы.** Затирание применяется ко всем освобождённым страницам, а не только к страницам purge (D-102, STO-29): старые версии записи после PUT тоже исчезают из файла не позднее T_purge, не больше K страниц за коммит (D-109). Операция `subjects:erase` (API-34, CLI-19, PRV-18) очищает контакты субъекта и удаляет его телефон из чужих контактов обычной транзакцией изменения; старые значения затираются этим же механизмом.
9. **Запись «done».** После затирания и fsync в журнал purge дописывается `{purge_id, state = done, erased_at}`, и статус квитанции становится `erased` (PRV-08). При открытии записи `pending` без `done` выполняются повторно — шаги 3–9 идемпотентны (D-076; раздел 4.1, шаг 10).
10. **Проверка.** Тест PRV-06 и verify ищут по всему каталогу данных каждую производную форму: `display_name` в NFC, ключ NFKC_Casefold, ключи слов, цифры `e164`, `raw_input` (D-077). Тест входит в CI и в crash-тесты 17.3.
11. **Автоочистка корзины.** Фоновая задача раз в час `[ПРЕДЛОЖЕНИЕ АГЕНТА]` берёт из `trash_idx` контакты с истёкшим сроком 1…29 дней (D-049) и очищает их по шагам 2–9 с исполнителем `system`. Задержка после истечения срока, включая физическое затирание, ≤ 24 ч (PRV-04, D-111), итого корзина живёт ≤ 30 суток. Восстановление после истечения срока запрещено, даже если автоочистка ещё не прошла (CON-17). Если настенные и монотонные часы расходятся больше чем на 1 ч, автоочистка приостанавливается, поднимается алерт, а возобновляет её только подтверждение admin: `budb admin clock confirm` или `POST /api/v1/admin/clock:confirm` (D-081, D-117; OBS-21, API-41, CLI-22).
12. **Restore.** После восстановления из бэкапа применяется объединение журналов purge: копии рядом с бэкапом (`<ts>.purge`), журнала в каталоге бэкапов и файла из `--purge-journal`. Запись применяется, только если совпадают и `id`, и `created_at` (D-075). Если доказать актуальность журнала нельзя (каталог бэкапов не настроен или недоступен, `--purge-journal` не задан), restore отказывает; флаг `--accept-purge-gap` разрешает продолжить и пишет событие аудита (D-069; BKP-07, BKP-16, PRV-10). Restore офлайн, читателей нет, поэтому затирание и сброс выполняются до rename. Записи `pending`, оставшиеся от purge в degraded-read-only, применяются тем же объединением (PRV-23).
13. **Purge в degraded-read-only (D-117, PRV-23).** Транзакции записи в этом режиме отклоняются, поэтому по шагу 1 пишется только запись `pending` в `purge.journal` (шаг 2, с fsync и копией в каталоге бэкапов); если запись журнала невозможна, purge не подтверждается. Квитанция имеет статус `pending_erasure` и `erase_deadline`; до выполнения транзакции N контакт остаётся в файле и читается. Транзакцию N движок выполняет сам после снятия режима (STO-40) или после restore (шаг 12); дальше шаги 3–9. Гарантия T_purge в этом режиме не действует, поэтому метрика возраста самого старого `pending` (OBS-22) даёт алерт при возрасте больше 12 ч, а руководство оператора требует restore в пределах 24 ч.

- **Альтернативы** (ADR 0012): DELETE сразу означает purge; только логическое удаление; crypto-shredding. Затирание только страниц транзакции N не выполняет PRV-06 для старых копий записи и разделителей (D-077, D-102).

### 6. Журналы аудита и purge

- **Журнал аудита** (D-100, заменяет D-045). Отдельные файлы только на добавление с ротацией (D-055), без значений ПДн (PRV-13). По одному событию с `contact_id` пишутся: чтение по `id`, результаты точного поиска, `subjects:search`, все изменения, события аутентификации и административные операции. Экспорт — одно событие на задачу и отдельный список экспортированных `contact_id` без ПДн (D-118, PRV-24). Агрегируются на пользователя за минуту только префиксные поиски typeahead (PRV-12).
- **Сброс событий чтения и агрегатов** (D-117, PRV-21). Агрегаты typeahead сбрасываются в журнал раз в 60 с и при штатной остановке; при аварийном завершении теряется до 60 с агрегатов, это документируется. События чтения дописываются сразу, без fsync, и сбрасываются тем же таймером (D-118). Так чтение по `id` не ждёт fsync и укладывается в PERF-04; намерения изменений по-прежнему сбрасываются в каждом коммите (раздел 3).
- **Намерения и компенсация** (D-080, D-095). Записи пачки — намерения с txid, `boot_id` и `db_lineage_id` — дописываются до шага (3) и сбрасываются параллельно с шагом (2) (раздел 3). При восстановлении для намерений упавшего запуска в той же линии с txid больше восстановленного дописывается запись `rolled_back`. Restore начинает новую линию (новый `db_lineage_id`, BKP-14), поэтому события, подтверждённые в прежней линии и потерянные из-за restore, не помечаются ложно как откаченные (EX1-13).
- **Отказ журнала аудита** (D-065, D-117). Ошибка записи или сброса (EIO, ошибка fsync) — изменение не подтверждается, fail-stop (раздел 4.3). ENOSPC на ФС журнала — путь D-072: записи получают 507, движок в degraded-read-only, чтения продолжаются, их события копятся в ограниченном буфере в памяти и дописываются после появления места; при переполнении буфера чтения ПДн получают 507 (PRV-22, D-118).
- **Журнал purge.** Один файл `purge.journal` со своим заголовком (magic, версия формата) и записями с CRC32C; каждая запись сбрасывается сразу (D-036, D-084). Состояния записи — `pending` и `done` (D-076). Порванный хвост обоих журналов обрабатывается по STO-37. Срок хранения — бессрочно `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: журнал нужен, пока существует хоть один бэкап старше записи.
- **Формат журналов** — собственный, как и формат страниц, без serde (BLD-02).

### 7. Поток CUJ-01 «кто звонит»

1. Оператор вводит номер. Поле поиска получает фокус при открытии и по клавише «/» (D-106, UI-25). UI ждёт 250 мс после последнего нажатия (UI-02) и распознаёт номер (UI-03). Цифры проходят нормализацию префикса по региону по умолчанию: «8 916 12» → `+791612` (D-066, D-074). Полный номер (E.164 целиком или не менее 10 национальных цифр) ищется в режиме `exact`, короткий — в режиме `prefix` (GF1-04, GF2-01; D-116, UI-03); ветки нормализации префикса задаёт только PHN-17. UI отправляет `POST /api/v1/contacts:search` `{"field":"phone","mode":"exact","value":"8 (495) 123-45-67"}` с cookie сессии (ACL-11, D-043, D-101) и заголовком `X-CSRF-Token` (D-068); CSRF обязателен и для этого POST без изменения данных (D-113, ACL-14, API-37).
2. tower-слой: сессия, роль reader (ACL-03, ACL-04), лимит частоты и квота выдачи (API-19, ACL-25; D-073, D-083), лимит тела (API-18).
3. Номер нормализуется с регионом операции или по умолчанию: `+74951234567` (PHN-02, PHN-06, PHN-08). Ошибка даёт 422 с кодом PHN-14 (SRCH-02).
4. Запрос уходит в пул читателей. Читатель берёт снимок txid T (STO-09), сканирует `phone_idx` в диапазоне `74951234567‖0x00‖*`, читает записи `primary` по найденным `id` и отдаёт до 20 контактов (SRCH-01, SRCH-07, SRCH-09). Снимок отпускается сразу; запрос ограничен 2 с (D-078).
5. Если результатов больше страницы, формируется keyset-курсор (`e164`, `id`), зашифрованный AEAD ChaCha20-Poly1305 ключом экземпляра, со сроком 24 ч (D-048, D-082, SRCH-10). Цифр номера в курсоре не видно.
6. Ответ 200: `id` десятичной строкой (D-057), `Cache-Control: no-store` (ACL-20). Метрика задержки поиска с меткой `phone/exact` (OBS-04). Точный поиск пишется в аудит отдельным событием с `contact_id` результатов (D-100).
7. UI показывает список с подсветкой (UI-04) и кнопкой копирования номера (D-106, UI-26), объявляет число найденных (UI-05) и по Enter открывает карточку (UI-06).

Бюджет: движок p99 ≤ 2 мс на прогретом кэше (PERF-04), API p99 ≤ 100 мс (PERF-08), весь путь — без прерывания разговора, ориентир NN/g до 1 с (`docs/cuj.md`, CUJ-01).

### 8. Поток CUJ-03 «добавить или изменить контакт»

1. Редактор заполняет форму. Для каждого телефона UI показывает предпросмотр `POST /api/v1/phones:normalize` (UI-08, API-28).
2. «Сохранить» отправляет `POST /api/v1/contacts` с `Idempotency-Key` (UI-09, API-16) или `PUT /api/v1/contacts/{id}` с `If-Match: "<version>"` (API-06) и, по API-33, тоже с `Idempotency-Key`.
3. tower-слой: сессия, роль writer, CSRF и `Sec-Fetch-Site` против `public_origin` (ACL-14, D-101), лимиты.
4. Проверка данных вне писателя: очистка имени и ключ (NAM-01…NAM-05), нормализация телефонов (PHN), лимиты и правила (CON-01…CON-09). Поля `id`, `version`, `created`, `updated` в теле игнорируются (D-071, CON-19, API-15). Ошибка — 422 с `errors[]` и `code` (API-15, D-099).
5. Проверка `Idempotency-Key`: повтор с тем же телом возвращает сохранённый ответ, другое тело — 422, запрос ещё выполняется — 409 (API-17).
6. Операция ставится в очередь писателя. Если очередь полна — 503 с `Retry-After`, и операция не выполнялась (API-20, PERF-14). В degraded-read-only — 503 или 507 (API-31).
7. Писатель в пачке: для PUT сверяет версию (412 при несовпадении, API-08); для POST выдаёт `id` (D-057); пишет `primary` с `version` + 1, `name_idx` (полный ключ и слова), `phone_idx`, запись `idempotency_keys`; считает подсказку о дубликатах (≤ 10 контактов с тем же полным ключом или общим `e164`) по своему представлению транзакции (CON-18, D-051).
8. Коммит по разделу 3. Намерение аудита изменения пишется с txid, `boot_id` и `db_lineage_id` (PRV-12, D-080, D-095, D-100).
9. Ответ 201 с `Location` и `ETag: "1"` (API-04) или 200 с новым `ETag` (API-06), в теле — контакт и подсказка о дубликатах. При «исходе неизвестен» (500 `outcome-unknown`, API-33) клиент повторяет запрос с тем же `Idempotency-Key`.
10. UI пишет «Сохранено» только после 201 или 200 (UI-09). На 412 показывает обе версии (UI-10); на 503 и 429 сохраняет ввод и предлагает «Повторить» (UI-23).

Бюджет: долговечная запись p50 ≤ 15 мс, p99 ≤ 60 мс (PERF-06, D-094), ≥ 500 подтверждённых записей/с при group commit (PERF-11).

### 9. Бэкап, verify, компактизация

- **Бэкап** (BKP-01…BKP-04, BKP-17). Снимок txid T. Страницы, достижимые из снимка, копируются во временный файл в формате STO-01…STO-04 (с перенумерацией и переадресацией указателей), затем: fsync, rename, fsync каталога. Во время копирования считаются число записей каждого дерева и скользящая контрольная сумма логических записей (D-096). Рядом пишется `<ts>.purge` — копия журнала purge на момент T, в той же последовательности сброса и rename `[ПРЕДЛОЖЕНИЕ АГЕНТА: отдельный файл рядом с бэкапом, а не дерево внутри бэкапа]` (D-036). Затем бэкап проверяется по BKP-08 и сверяется со снимком по сохранённым счётчикам и контрольной сумме (D-096, BKP-04), и только после этого обновляется метрика времени последнего бэкапа (OBS-11). Периодический бэкап встроен в сервер (BKP-17). Ротация удаляет бэкапы старше 30 дней (настраивается, ≤ 180; D-037, BKP-12, PRV-11) и приостанавливается при скачке часов (D-081).
- **Restore** (BKP-05…BKP-07, BKP-13…BKP-16). Офлайн, в новый файл с атомарной подменой. Применяет журналы purge по разделу 5, шаг 12 (D-069, D-075). Задаёт `next_contact_id` = max(значение из бэкапа, наибольший `id` в журнале purge + 1, наибольший `id` в журнале аудита + 1) (D-075, BKP-13). Начинает новую линию `db_lineage_id` (D-095, BKP-14). Отзывает все API-токены и сессии и пишет событие аудита; учётные записи и пароли из бэкапа сохраняются (D-079, BKP-15). Все пользователи, кроме admin, указанного в `--as-admin`, получают `review_required`: вход блокирован до `budb admin users confirm <id>|--all` (офлайн или онлайн) или `POST /api/v1/admin/users/{id}:confirm` (D-113, D-117; ACL-27, CLI-20, API-39). RTO для 10^7 записей ≤ 10 мин на эталонном стенде `[ДОПУЩЕНИЕ]` (D-066, PERF-18).
- **Verify** (BKP-08…BKP-10). CRC32C, `page_no` и `write_txid` всех страниц (D-085), обе мета-страницы, `page_count` (D-086), порядок ключей, взаимное соответствие деревьев (с учётом корзины, раздел 2), инвариант учёта страниц STO-27, поиск производных форм очищенных контактов (D-077). Офлайн — только чтение; онлайн — на снимке, найденное повреждение переводит сервер в degraded-read-only (раздел 4.2), а не в fail-stop. Периодическая онлайн-проверка (scrub) снижает остаточный риск D-035 `[ПРЕДЛОЖЕНИЕ АГЕНТА: раз в сутки; читать в обход кэша страниц, EX1-19]`.
- **Компактизация** (BKP-11). Только офлайн: копирование живых страниц в новый файл, fsync, rename, fsync каталога (D-018; паттерн etcd defrag, docs/research/02, §2.4 п. 6). `db_lineage_id` сохраняется (STO-38).
- **Альтернативы** (ADR 0013): копирование файла средствами ОС, только офлайн-бэкап, снимки ФС силами эксплуатации.

### 10. Нормализация и ключи

- **Телефоны** (ADR 0008; D-010, D-052, D-059, D-066). Порядок PHN-02. Регионы RU и `none`. Список кодов стран ITU закреплён в данных правил с датой ITU-T Operational Bulletin; таблица национальных длин — только для `+7`. Маркеры добавочного номера: «доб.», «ext», «x», «#», «;ext=» (D-066). Префикс запроса нормализуется по региону по умолчанию (D-066). Версия правил и регион сохраняются у каждого телефона (PHN-15); пересчёт — командой `budb admin renormalize-phones` (D-073, CLI-17).
- **Имена** (ADR 0009; D-050, D-051, D-058, D-098). Хранение — NFC (NAM-01). Ключ — NFKC_Casefold, затем ё→е. Таблица NFKC_Casefold генерируется при сборке из закреплённого `DerivedNormalizationProps.txt`, сверенного по контрольной сумме (D-039, BLD-23). Версия Unicode — 18.0, одна для таблиц `unicode-normalization` 0.1.26 и для собственной таблицы; сборка падает, если версии расходятся (D-098, BLD-24). Идентификатор версии правил ключа включает версию Unicode (NAM-09).
- **Альтернативы** (ADR 0009): lowercase вместо case folding; NFD со снятием всей диакритики; ключ сортировки UCA/ICU.

### 11. HTTP API, безопасность, UI

- **API** (ADR 0010; D-013, D-047, D-048, D-059, D-068, D-071, D-099): `/api/v1`, OpenAPI 3.1 как единственный источник правды и контрактные тесты (API-02). Ошибки — `application/problem+json`: `type` = `{public_origin}/problems/<code>`, по этому адресу BUDB отдаёт страницу описания ошибки; обязательное поле `code` — стабильный идентификатор, клиенты сравнивают ошибки по нему (D-099, заменяет D-044; API-14). ETag = `version`; 412 и 428; keyset-курсор 24 ч, зашифрованный AEAD (D-082); страница 20, максимум 100; восстановление из корзины — `POST /api/v1/contacts/{id}:restore` для writer и admin (D-041); сессии UI — `POST/GET/DELETE /api/v1/session` (D-068, API-29); единая модель задач `queued`/`running`/`succeeded`/`failed` (D-084, API-32); `subjects:erase` (D-102, API-34).
- **Безопасность** (ADR 0011; D-015, D-043, D-055, D-060, D-066, D-079, D-082, D-083, D-101, D-103, D-104):
  - пароли — argon2; токены `budb_<id>_<secret>`, в хранилище SHA-256 секрета (`sha2`); случайные значения — `getrandom`;
  - курсоры — AEAD ChaCha20-Poly1305 (`chacha20poly1305`, D-082) вместо подписи HMAC: подпись не скрывала цифры номера и ключ имени (EX2-02, GF2-07);
  - `public_origin` задаёт `Secure` и `__Host-` у cookie и эталон для проверок `Origin` и `Sec-Fetch-*`; IP клиента из `X-Forwarded-For` — только от `trusted_proxies` (D-101, ACL-23);
  - область токена `metrics` — только `GET /metrics`; Prometheus не получает admin-токен (D-103, ACL-24);
  - квота выданных контактов — в одном месте, ACL-25: на токен и сессию любой роли, поиск и чтение по `id`, 10 000 в час по умолчанию; алерт на перебор; полный экспорт — только admin и в квоту не входит (D-083, D-118);
  - жёсткой блокировки входа нет: прогрессивная задержка по (логин, IP), лимит по IP, алерт (D-104, ACL-15);
  - TLS — rustls, минимум 1.2 по умолчанию, 1.3 предпочтителен (D-066); сессии в памяти процесса, 30 мин бездействия и 8 ч абсолютный срок (D-066), cookie по D-043 и D-101; после restore все токены и сессии отозваны (D-079), а вход пользователей блокирован до подтверждения admin, кроме выполнившего restore (D-113, D-117, ACL-27).
- **UI** (ADR 0016; D-031, D-060, D-106): TypeScript, собранный закреплённым `tsc` в нативные ES-модули, без бандлера и CDN; ассеты встраиваются в бинарник; строгая CSP (ACL-19); поддерживаются две последние версии Chrome, Edge, Firefox и Safari. Предупреждение об истечении сессии за 2 мин с кнопкой «Продлить» (WCAG 2.2.1, UI-24); автофокус поиска и «/» (UI-25); копирование номера из списка (UI-26).

### 12. Изоляция `unsafe`: крейт `budb-sys` (D-090, ADR 0018)

- Во всех крейтах рабочего пространства стоит `#![forbid(unsafe_code)]`, кроме одного — `budb-sys`.
- `budb-sys` содержит только FFI и intrinsics: `MoveFileExW` с `MOVEFILE_WRITE_THROUGH` (Windows), аппаратную CRC32C с определением возможностей процессора во время выполнения, любые вызовы `libc`. Наружу он отдаёт безопасный API; движок вызывает его без `unsafe`.
- У каждого `unsafe`-блока — комментарий `// SAFETY:`; тесты под Miri, где он применим; любое изменение крейта проходит ревью двумя рецензентами (BLD-20).
- Аппаратная CRC32C обязана совпадать с табличной (BLD-08); табличная реализация остаётся эталоном и запасным путём.
- Причина — EX1-06: функции `libc` и `windows-sys` — это `unsafe fn`, а std не даёт `MOVEFILE_WRITE_THROUGH` и выбора аппаратной CRC32C во время выполнения. Прежнее «`forbid(unsafe_code)` во всех крейтах» (D-020, ADR 0002) противоречило allowlist и STO-15.

### 13. SLO и ёмкость (D-024, пересчёт D-094)

| Показатель | Цель | Требование | Основание |
|---|---|---|---|
| Точный поиск в движке, p99 | ≤ 2 мс тёплый кэш, ≤ 10 мс холодный | PERF-04 | D-024 |
| Префиксный поиск, limit 50, p99 | ≤ 50 мс | PERF-05 | D-024 |
| Долговечная запись | p50 ≤ 15 мс, p99 ≤ 60 мс | PERF-06 | D-094 (было p99 ≤ 50 мс) |
| Открытие после сбоя, p99 | ≤ 1 с без переиндексации | PERF-07 | D-024 |
| Поиск через API, p99 | ≤ 100 мс | PERF-08 | D-024 |
| Пропускная способность | ≥ 5 000 поисков/с, ≥ 500 подтверждённых записей/с (group commit) | PERF-11 | D-024, D-094 |
| Размер файла | ≤ 4 ГБ на 10^7, ≤ 40 ГБ на 10^8 | PERF-12 | D-094 (было ≤ 3 ГБ на 10^7, около 25 ГБ на 10^8) |
| RTO restore 10^7 | ≤ 10 мин `[ДОПУЩЕНИЕ]` | PERF-18 | D-066 |

- **Усиление записи.** Одиночный коммит переписывает около 55–70 страниц, а не около 16, как в первой оценке (D-094; `[РАСЧЁТ]` EX1-10). В оценку входят пути в `primary`, `name_idx` (полный ключ и ключи слов D-051), `phone_idx`, `idempotency_keys`, корень каталога, страницы `free_db`, мета-страница и затирание освобождённых страниц (D-102). Group commit делит эти записи на все операции пачки; фактическое значение публикуется в отчёте бенчмарка (PERF-17).
- **Сбросы.** На коммит — два последовательных сброса: данные вместе с параллельным сбросом намерений аудита, затем мета-страница (D-094). При сбросе около 5 мс коммит занимает около 10 мс, а p50 ожидания около 1,5 коммита — около 15 мс (`[РАСЧЁТ]` по методу EX1-11; при трёх последовательных сбросах выходило около 22 мс), отсюда новая цель p50 ≤ 15 мс.
- **Размер записи.** Около 140–170 Б на запись `primary` и 2–2,5 записи `name_idx` на контакт `[РАСЧЁТ]` EX1-12; с заполнением страниц около 90 % это даёт ≤ 4 ГБ на 10^7.
- Все цели — условие выпуска (PERF-16) и подтверждаются бенчмарком на эталонном стенде (4 vCPU, 8 ГБ RAM, NVMe; PERF-02).

## Risks / Trade-offs

- [Высокое усиление записи COW: около 55–70 страниц на одиночный коммит, `[РАСЧЁТ]` EX1-10] → group commit (STO-13), импорт пачками по 1000 (IMP-09), отчёт об усилении записи (PERF-17), бенчмарк как условие выпуска (PERF-16). D-094, ADR 0003.
- [Один писатель ограничивает пропускную способность записи] → цель ≥ 500 записей/с подтверждается бенчмарком (PERF-11); очередь с backpressure (PERF-14). ADR 0003, ADR 0017.
- [Долгие снимки удерживают страницы, файл растёт] → 30 с для интерактивных операций (STO-24), T_purge − 1 ч для бэкапа, экспорта и verify (D-076), лимит объёма 25 % файла (D-093, STO-32), кооперативный отзыв (D-092), метрики возраста снимка и удержания (OBS-09, OBS-17). ADR 0003.
- [Файл не уменьшается без офлайн-компактизации] → метрика свободного места (OBS-05), окно обслуживания для `budb admin compact` (BKP-11). ADR 0003.
- [Накопитель лжёт о сбросе кэша (FAST'13, docs/research/02, §3.5)] → оговорка в документации (STO-23), эталонный стенд с честным NVMe (PERF-02). ADR 0005.
- [Потерянные и промахнувшиеся записи принимаются за валидные страницы] → `page_no` и `write_txid` в заголовке, ожидаемый `write_txid` в указателе (D-085), модель сбоев SimDisk с такими отказами (D-097). ADR 0005, ADR 0015.
- [После ошибки fsync кэш ОС хранит данные, которых нет на диске (ATC'20)] → переписывание мета-страницы при открытии (D-088), тесты на реальном ядре через dm-error и dm-flakey (D-097). ADR 0005.
- [Fail-stop останавливает запись при одной ошибке I/O] → выход ≤ 5 с, супервизор с нарастающей задержкой, открытие ≤ 1 с (D-034, D-072, PERF-07). ADR 0005.
- [Порча одной страницы роняла бы процесс в цикле рестартов] → degraded-read-only без выхода, `/readyz` = 200 со статусом (D-078, D-089). ADR 0005.
- [Полный диск выключал бы телефонную книгу] → предвыделение региона, 507 и degraded-read-only до шага (3), метрика и алерт места на ФС (D-072, STO-33, OBS-18). ADR 0005.
- [Порча новейшей мета-страницы после подтверждения неотличима от порванного коммита: теряется одна подтверждённая транзакция] → откат только при единственной валидной мета-странице, метрика и алерт, ежедневный scrub, бэкапы (D-035, D-063). ADR 0003, ADR 0005.
- [Переиспользование страниц, на которые ссылается старшая мета-страница, сделало бы откат D-035 невозможным] → правило переиспользования раздела 3.1, в том числе после перезапуска (D-087). ADR 0003.
- [Записи и ключи больше страницы ухудшают fanout] → страницы переполнения, укороченные разделители, фаззинг (BLD-16). ADR 0003, ADR 0007.
- [Затирание ПДн не достаёт старые копии записи и разделители ветвей] → затирание всех освобождённых страниц (D-102), перезапись страниц с производными формами (D-077), побайтовый тест по всем формам (PRV-06). ADR 0012.
- [Сбой посреди purge даёт квитанцию, которая врёт] → состояния `pending` и `done`, повтор при запуске (D-076). ADR 0012.
- [Бэкапы содержат очищенные ПДн] → журналы purge применяются при restore, защита от разрыва журнала (D-069), сопоставление по `id` и `created_at` (D-075), срок хранения ≤ 180 дней (D-036, D-037). ADR 0012, ADR 0013.
- [Повторная выдача `id` после restore удалила бы чужой контакт] → `next_contact_id` из максимума бэкапа и журналов (D-075). ADR 0012.
- [Restore возвращает отозванные токены] → отзыв всех токенов и сессий после restore (D-079), вход пользователей только после подтверждения admin (D-113, D-117). ADR 0011.
- [Purge в degraded-read-only не укладывается в T_purge] → запись `pending` в `purge.journal`, автоматическое выполнение после снятия режима или restore, алерт при возрасте больше 12 ч, restore в пределах 24 ч (D-117, PRV-23, OBS-22). ADR 0012.
- [Заполненная ФС журнала аудита вызывала бы цикл fail-stop] → ENOSPC идёт по пути D-072, fail-stop только при EIO или ошибке fsync (D-117, PRV-22). ADR 0005.
- [Purge не является сертифицированным СЗИ] → ограничение документируется, выполнение — задача оператора (D-105). ADR 0012.
- [Версии Unicode в `unicode-normalization` и в собственной таблице разойдутся] → Unicode 18.0 закреплён, проверка при сборке (D-098, BLD-24); смена версии правил → автоматическая переиндексация (NAM-10). ADR 0009.
- [Переиндексация 10^8 имён при открытии надолго отключает поиск по имени] → прогресс в метриках, смена правил только в мажорных выпусках `[ПРЕДЛОЖЕНИЕ АГЕНТА]`; время на 10^8 измеряется в предрелизном прогоне (PERF-01). ADR 0009.
- [Перечислимые `id` и массовая выгрузка reader] → авторизация каждой операции (ACL-04), квота выдачи и алерт на перебор (D-083), аудит каждого чтения по `id` (D-100). ADR 0007, ADR 0011.
- [Cookie без `Secure` на `http://127.0.0.1` может вести себя в браузерах по-разному `[НЕ ПОДТВЕРЖДЕНО]`; за TLS-прокси cookie уходила без `Secure`] → `public_origin` (D-101), e2e-тест UI на всех поддерживаемых браузерах (D-043). ADR 0011, ADR 0016.
- [Объём аудита по каждому событию (D-100)] → агрегируются только префиксные поиски typeahead; ротация; реальная нагрузка колл-центра на порядки ниже ёмкости 5 000 поисков/с (EX2, разногласие персон п. 1). ADR 0012.
- [Собственный `unsafe` в `budb-sys`] → один крейт, `SAFETY`, Miri, ревью двумя рецензентами (D-090, ADR 0018).
- [Цепочка поставок крейтов и npm] → allowlist для прямых зависимостей и denylist для всего графа, `--locked`, lock-файл с integrity (BLD-04, BLD-05, BLD-11, D-060). ADR 0006.
- [Windows и macOS: долговечность rename и каталога не подтверждена] → tier 2 с оговорками (BLD-09), `MOVEFILE_WRITE_THROUGH` через `budb-sys` (D-090). ADR 0014.
- [Скачок системного времени сдвигает сроки корзины, бэкапов и курсоров] → при расхождении настенных и монотонных часов больше 1 ч автоочистка корзины и ротация бэкапов приостанавливаются до подтверждения admin, алерт (D-081). ADR 0012, ADR 0013.

## Migration Plan

- **Первый выпуск.** Данных для миграции нет. Порядок развёртывания: `budb admin bootstrap --db <путь> --login <логин>` при остановленном сервере (ACL-21, CLI-12) → `budb serve --config budb.toml` под супервизором с автоматическим перезапуском и нарастающей задержкой (D-034, D-072); в конфигурации задаются `public_origin` и `trusted_proxies` (D-101, CLI-18) → выпуск токена с областью `metrics` для Prometheus (D-103) → настройка каталога бэкапов, периодического бэкапа, ротации и алертов (`budb_meta_fallback_total`, fail-stop, degraded-read-only, свободное место на ФС, возраст бэкапа, возраст снимка, удержание страниц).
- **Версии формата.**
  - Файл БД и бэкап: поле версии формата в заголовке и мета-странице, v1 = 1. Формат v1 включает заголовок страницы с `page_no` и `write_txid`, указатели с ожидаемым `write_txid`, `page_count`, `db_lineage_id` и `free_db` (D-085, D-086, D-091, D-095). Неизвестная версия не открывается и файл не меняется (STO-02, BKP-06). Будущая миграция — отдельная офлайн-команда «копировать в новый файл → fsync → rename» по образцу компактизации; её введёт новый ADR.
  - Журналы аудита и purge: собственный заголовок с версией; новая версия читает старую.
  - Правила ключа имени: версия хранится в мета-странице; при расхождении — автоматическая переиндексация при открытии (NAM-10, NAM-11).
  - Правила нормализации телефонов: версия у каждого телефона; пересчёт — `budb admin renormalize-phones` (PHN-16, CLI-17).
  - HTTP API: в `/api/v1` только аддитивные изменения; ломающие — в `/api/v2`, который работает параллельно (API-03).
- **Откат.** Откат бинарника безопасен, только если версия формата и версии правил не менялись. Иначе — restore из бэкапа, сделанного до обновления (BKP-05, BKP-07); после restore администратор выпускает токены заново (D-079) и подтверждает пользователей (D-117, ACL-27).

## Open Questions

Вопросы, ответы на которые не меняют спецификации и фазы `tasks.md`; их можно решить при реализации:

- политика вытеснения кэша страниц (CLOCK или LRU) и минимальный размер кэша (PERF-09);
- значения по умолчанию: размер пула читателей, K и T для group commit, шаг роста файла, порог переполнения, таймер служебных коммитов, K страниц затирания за коммит;
- частота фоновой автоочистки корзины и scrub в пределах сроков D-049 и D-056;
- способ замыкания рекурсии выделения страниц под `free_db` (раздел 2, предложен вариант LMDB).

## ВОПРОСЫ К ОРКЕСТРАТОРУ

Эти вопросы меняют спецификации. До ответа в документе действует вариант с пометкой `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Закрытые вопросы вычеркнуты, рядом — решение.

1. ~~**Повторы в префиксном поиске по словам (D-051).** Убирать повтор или выдавать пары? По какому ключу упорядочивать?~~ — закрыт D-062 и D-074: повтор убирается по `id`; сначала префикс полного ключа, затем слова; курсор (класс ранга, ключ, `id`).
2. ~~**Различение порванной и испорченной мета-страницы (D-035).** Можно ли доверять полю txid в слоте с неверной CRC32C?~~ — закрыт D-063: нельзя; одна валидная → откат, обе невалидны → отказ.
3. ~~**Индексы и корзина (D-055, STO-06).**~~ — закрыт D-064: записи индексов удаляются при переносе в корзину и возвращаются при restore; STO-06 — для активных контактов.
4. ~~**Хранение заданий** (IMP-05, IMP-10).~~ — закрыт D-064: дерево `jobs` в каталоге; файлы результатов живут 24 ч.
5. ~~**Ошибка записи журнала аудита:** fail-stop?~~ — закрыт D-065: да, изменение не подтверждается, fail-stop.
6. ~~**Затирание файлов результатов экспорта и `idempotency_keys` при purge.**~~ — закрыт D-065 и D-084: purge удаляет результаты экспорта, снимок экспорта закрывается; записи `idempotency_keys` с D-116 заменяются надгробиями без ПДн, а не удаляются.
7. ~~**Префиксный поиск по телефону с национальным префиксом и маркеры добавочного номера.**~~ — закрыт D-066 (и D-074 для UI-03).
8. ~~**CSRF для `POST :search`:** проверять ли CSRF-токен на POST, которые не меняют данные? D-068 задаёт передачу токена (`X-CSRF-Token`), но не говорит, на каких запросах он обязателен. `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: на всех POST с cookie-сессией.~~ — закрыт D-113: CSRF обязателен на каждом небезопасном методе с cookie-аутентификацией, включая `POST :search`; запросы с bearer-токеном освобождены (ACL-14, API-37).
9. ~~**Порядок внутри класса «префикс слова» (EX1-20).** D-062 требует сортировать совпадения по слову по полному ключу имени, а это значит собрать все совпадения по слову до выдачи страницы (дорого для коротких префиксов). `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: внутри класса 1 сортировать по (ключ слова, `id`) — тогда курсор D-074 работает без полного сбора.~~ — закрыт D-112: класс 1 упорядочивается по наименьшему ключу совпавшего слова, затем по `id` (SRCH-05).

Отдавать позиции с сервера или подсвечивать в UI по упрощённому правилу? Решения нет; редактор http-api оставил вопрос открытым (`docs/reviews/round1-fixlog-interface.md`).~~ — закрыт D-113: позиции подсветки вычисляются на клиенте; предложение EX2-13 об отдаче позиций сервером отклонено.
