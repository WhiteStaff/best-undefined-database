# Журнал решений заказчика-оркестратора

Человек-заказчик заявил, что в процессе не участвует. Поэтому все решения заказчика принимает оркестратор (Elephant) как прокси заказчика, и он же закрывает человеческий гейт цикла EGM (D-008). В отчёте это нужно указать прямо: гейт закрыт оркестратором, а не человеком. Агенты-исполнители (Goldfish) этих решений не меняют. Если решение противоречит фактам или другому решению, агент пишет вопрос в раздел «ВОПРОСЫ К ОРКЕСТРАТОРУ».

Формат записи: ID, решение, обоснование (Why), ссылка на исследование (`docs/research/0N`, раздел), ADR (`docs/adr/`, индекс — `docs/adr/README.md`), статус. Если обоснование оркестратор не указал, так и написано. Обоснования D-005, D-006, D-007, D-013, D-014, D-017, D-021, D-022, D-025…D-029 оркестратор добавил 2026-10-24 вместе с решениями D-030…D-033. Решения перечислены по номерам.

Решения D-034…D-060 оркестратор принял 2026-10-24 после того, как были написаны спецификации, ADR 0001–0017 и `docs/cuj.md`; агент перенёс их сюда из рабочего журнала оркестратора. В том журнале у этих решений нет ссылок на исследования и ADR: агент подобрал их по теме решения. Ответы на вопросы из `docs/adr/README.md` отмечены там же, в разделе «ВОПРОСЫ К ОРКЕСТРАТОРУ». Спецификации ещё не приведены в соответствие с D-034…D-060: правки внесёт отдельный редактор после ревью. До этого при расхождении действует решение, а не текст спецификации. Если новое решение заменяет часть старого, это указано в поле «Статус» у обоих.

### D-001. Модель оркестрации
- **Решение:** модель оркестрации — Elephant+Goldfish (Dave Rensin, Google, 2026-04-27). Claude — Elephant: полный контекст, решения, память. Каждый агент — Goldfish: свежий контекст, узкая задача.
- **Обоснование:** этого требует пользователь, и это совпадает с источником принципа.
- **Исследование:** docs/research/01-principles-and-openspec.md, §A2.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-002. Git-репозиторий
- **Решение:** в проекте выполняется `git init`. Коммиты в удалённый репозиторий не отправляются.
- **Обоснование:** история изменений спецификации — доказательство для отчёта.
- **Исследование:** docs/research/01-principles-and-openspec.md, §C1.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-003. Версия и инициализация OpenSpec
- **Решение:** версия OpenSpec CLI закреплена: `@fission-ai/openspec@1.15.0`. Инициализация: `init --tools claude --language "Russian" --profile core`. Контекст проекта хранится в `openspec/config.yaml`, в поле `context:`.
- **Обоснование:** в версии 1.15 файла `project.md` больше нет.
- **Исследование:** docs/research/01-principles-and-openspec.md, §B1, §B3, §C1.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-004. Язык спецификаций
- **Решение:** текст спецификаций пишется по-русски. Нормативные слова SHALL/MUST остаются английскими и пишутся заглавными. Сценарии используют **WHEN**/**THEN** (по-английски, как принято).
- **Обоснование:** этого требуют `validate --strict` и документация OpenSpec.
- **Исследование:** docs/research/01-principles-and-openspec.md, §B5, §B6.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-005. Формат ADR
- **Решение:** ADR пишутся в формате MADR 4.0 со статусами по Nygard. Файлы: `docs/adr/NNNN-kebab-title.md`. ADR никогда не переписываются: их замещают новыми (supersede).
- **Обоснование:** MADR даёт структурированный шаблон с рассмотренными вариантами (Considered Options), а модель Nygard — неизменяемость записей и сквозную нумерацию.
- **Исследование:** docs/research/01-principles-and-openspec.md, §A3, §C2 п. 3.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-006. Ревью Goldfish
- **Решение:** ревью Goldfish запускаются вручную как субагенты. Роли — в стиле EGM: Comprehension, Critic, Readiness. Внешний плагин не устанавливается. Журнал ревью — `docs/reviews/GOLDFISH.md`.
- **Обоснование:** нет внешней зависимости; свежих субагентов достаточно.
- **Исследование:** docs/research/01-principles-and-openspec.md, §A2, §C2 п. 2.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-007. Технологическая нейтральность поведенческих спецификаций
- **Решение:** поведенческие спецификации не зависят от технологий. Язык, стек и движок описываются в ADR и `design.md`. Входное условие «написано с нуля на <ЯЗЫК>» оформляется одним явным требованием-ограничением со ссылкой на ADR.
- **Обоснование:** спецификации проверяемы независимо от стека; ADR можно заменить (supersede), не трогая спецификации. Исключения для четырёх capability — D-030.
- **Исследование:** docs/research/01-principles-and-openspec.md, §C2 п. 3; docs/research/02-storage-engine-and-language.md, §6.1.
- **ADR:** ADR 0001 (ограничение «с нуля на Rust» — ADR 0002, ADR 0006)
- **Статус:** Принято 2026-10-24.

### D-008. Человеческий гейт цикла EGM
- **Решение:** пользователь заявил, что не участвует. Поэтому гейт закрывает оркестратор как прокси заказчика. В отчёте это указывается честно: «гейт закрыт оркестратором, а не человеком».
- **Обоснование:** пользователь заявил о неучастии.
- **Исследование:** docs/research/01-principles-and-openspec.md, §A2 (условие остановки, `human_review_gate`), §C2 п. 2.
- **ADR:** ADR 0001
- **Статус:** Принято 2026-10-24.

### D-009. Модель данных
- **Решение:** модель строится вокруг агрегата Contact. Поля: `id`; `display_name` (NFC, обязательно); необязательные части имени; `phones[0..n]`; `version`; `created`/`updated`. Каждый телефон содержит `e164`, `extension`, `raw_input`, `label` (`mobile`/`home`/`work`/`other`) и `is_primary`. Поиск по номеру идёт через инвертированный индекс `e164 → [contact_id]`. Один телефон может принадлежать многим контактам (семейный телефон). Дубликаты разрешены, система показывает подсказку «возможные дубликаты». Слияние (merge) откладывается до v2.
- **Обоснование:** так делают vCard и Google People; это самый простой непротиворечивый агрегат.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §2.6, §3.1, §8.3, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 1; docs/research/02-storage-engine-and-language.md, §9 Q2.
- **ADR:** ADR 0007
- **Статус:** Принято 2026-10-24.

### D-010. Нормализация телефонов
- **Решение:** нормализация телефонов пишется с нуля, без libphonenumber. Шаги: NFKC; удаление разделителей; разбор международного префикса `+`/`00`/`810`. Регион по умолчанию настраивается; по умолчанию RU (`8XXXXXXXXXX` → `+7`). Проверяется только, что номер возможен: код страны входит в список ITU (все страны), всего не больше 15 цифр. Таблица национальных длин в v1 есть только для `+7`; её можно расширять. isValid и тип номера — вне скоупа.
- **Обоснование:** libphonenumber нужны постоянно обновляемые метаданные; кроме того, действует ограничение «с нуля».
- **Исследование:** docs/research/03-domain-api-ui-security.md, §1.1–§1.5, §8.1, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 2; docs/research/02-storage-engine-and-language.md, §9 Q4.
- **ADR:** ADR 0008
- **Статус:** Принято 2026-10-24.

### D-011. Ключ поиска по имени
- **Решение:** ключ поиска по имени строится так: NFKC → полный Unicode default case folding (C+F, без тюркских правил) → замена ё→е. Общего удаления диакритики нет. Правила построения ключа версионируются. Порядок по ключу — бинарный. Сортировка по UCA/ICU — вне скоупа. Режимы поиска: точный и по префиксу (плюс поиск по префиксу телефона).
- **Обоснование:** отдельно не указано. В тексте решения сказано, что общее удаление диакритики ломает «й».
- **Исследование:** docs/research/03-domain-api-ui-security.md, §2.1–§2.5, §8.2; docs/research/02-storage-engine-and-language.md, §8 ADR-005, §9 Q3.
- **ADR:** ADR 0009
- **Статус:** Принято 2026-10-24. Порядок построения ключа «NFKC → case folding» заменён решением D-050.

### D-012. Удаление, корзина и очистка
- **Решение:** DELETE переносит контакт в корзину, откуда его можно восстановить. По истечении срока хранения корзина очищается автоматически. Срок по умолчанию 7 дней; его можно настроить, но не больше 30 дней (152-ФЗ, ст. 21). Для запросов субъектов данных у администратора есть команда «очистить сейчас». Она физически перезаписывает освобождённые страницы и сегменты журнала. Журнал очисток (purge journal) применяется повторно при восстановлении из бэкапа. Журнал аудита не содержит значений ПДн.
- **Обоснование:** отдельно не указано. В тексте решения верхняя граница срока обоснована ссылкой на 152-ФЗ, ст. 21.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §6.5, §8.6, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 3.
- **ADR:** ADR 0012
- **Статус:** Принято 2026-10-24. Частично заменено: верхняя граница срока корзины — D-049 (1…29 дней плюс не больше 24 ч до purge); состав журнала purge — D-042 (без хэшей).

### D-013. ПДн не передаются в URL
- **Решение:** ПДн не передаются в URL. Поиск выполняется через `POST /api/v1/contacts:search` с JSON в теле запроса. Собственные логи маскируют телефоны и имена.
- **Обоснование:** URL попадают в логи прокси, access-логи и историю браузера (OWASP API; минимизация по 152-ФЗ).
- **Исследование:** docs/research/03-domain-api-ui-security.md, §4.7, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 4.
- **ADR:** ADR 0010 (маскирование в логах — также ADR 0012)
- **Статус:** Принято 2026-10-24.

### D-014. Одна телефонная книга на экземпляр
- **Решение:** на один экземпляр приходится одна телефонная книга. Мультиарендность (multi-tenancy) — вне скоупа v1.
- **Обоснование:** контроль объёма; мультиарендность в ДЗ не требуется.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §6.1 (API1), «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 5.
- **ADR:** ADR 0007, ADR 0011
- **Статус:** Принято 2026-10-24.

### D-015. Аутентификация
- **Решение:** используются локальные учётные записи с ролями reader/writer/admin. В UI вход по логину и паролю, после него выдаётся сессионная cookie (`__Host-`, CSRF-токен, проверка `Sec-Fetch-Site`). В API используются bearer-токены; в хранилище они лежат в виде хешей. Пароли хешируются, а TLS работает через проверенные криптобиблиотеки. Собственную криптографию писать нельзя; это явное исключение в политике зависимостей.
- **Обоснование:** отдельно не указано. В тексте решения сказано: никогда не писать собственную криптографию.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §6.2, §6.3, §6.4, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 6.
- **ADR:** ADR 0011 (крипто-исключение — ADR 0006)
- **Статус:** Принято 2026-10-24.

### D-016. Состав полей и форматы импорта/экспорта

- **Исследование:** docs/research/03-domain-api-ui-security.md, §4.8, §6.5 (п. 4 «Минимизация»), «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 8.

### D-017. Admin CLI и встраиваемая библиотека
- **Решение:** Admin CLI входит в v1. Встраиваемая библиотека — только внутренний слой, а не публичный контракт.
- **Обоснование:** для CUJ-07 и CUJ-10 нужен скриптуемый инструмент администратора; публичная библиотека удвоила бы поверхность API.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §4.10, §8.4.
- **ADR:** ADR 0010, ADR 0017
- **Статус:** Принято 2026-10-24.

### D-018. Движок хранения
- **Решение:**
  - Структура: copy-on-write B+tree с теневой страничной адресацией (shadow paging).
  - Две мета-страницы, у каждой свой CRC32C и txid. По результатам ALICE атомарной записи указателя доверять нельзя.
  - mmap не используется (CIDR'22). Вместо него — `pread`/`pwrite` и собственный кэш страниц.
  - Страницы по 4 KiB, CRC32C на каждой странице.
  - Три дерева в одном файле, меняются одной атомарной транзакцией: `primary(id)`, `name_idx(key‖id)`, `phone_idx(digits‖id)`.
  - Один писатель и читатели на MVCC-снимках.
  - Свободные страницы переиспользуются только после того, как их перестал видеть самый старый живой читатель.
  - Group commit.
  - Офлайн-уплотнение: копирование → fsync → rename → fsync каталога.
- **Обоснование:** альтернативы отклонены:
  - Bitcask — нет префиксного поиска, около 21 ГБ RAM при 10^8 записей;
  - B+tree с WAL — больше кода восстановления и обработка порванных страниц;
  - LSM — усиление записи около 33×, сложное уплотнение.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §2.1–§2.4, §3.6, §8 ADR-001.
- **ADR:** ADR 0003, ADR 0004, ADR 0005
- **Статус:** Принято 2026-10-24.

### D-019. Долговечность
- **Решение:**
  - Подтверждение записи — только после цепочки: fsync страниц → запись мета-страницы → fsync.
  - После create/rename/unlink выполняется fsync каталога.
  - Ошибка fsync — это fail-stop, без повтора (fsyncgate). После перезапуска данные восстанавливаются с диска.
  - Порванная или незафиксированная транзакция откатывается к последней корректной мета-странице.
  - Повреждение зафиксированных данных — явная ошибка и никогда не тихий откат (FAST'17).
  - Гарантии действуют, только если устройство честно сбрасывает кэш (FAST'13); это документируется.
  - Режим подтверждения без долговечности в v1 ЗАПРЕЩЁН.
- **Обоснование:** отдельно не указано. В тексте решения есть ссылки на fsyncgate, FAST'17 и FAST'13.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §3.1–§3.8, §8 ADR-002, §9 Q8.
- **ADR:** ADR 0005
- **Статус:** Принято 2026-10-24.

### D-020. Язык реализации

- **Исследование:** docs/research/02-storage-engine-and-language.md, §5.1–§5.3, §8 ADR-003.
- **ADR:** ADR 0002
- **Статус:** Принято 2026-10-24.

### D-021. Политика зависимостей NFR-SCRATCH
- **Решение:** зависимости ограничены allowlist; его соблюдение проверяет cargo-deny.
  - Разрешены: tokio, hyper/axum, serde/serde_json (только для API, НЕ для формата на диске), clap, tracing, unicode-normalization, libc/windows-sys, проверенная криптография по D-015 (rustls, argon2).
  - Только для тестов: proptest, cargo-fuzz, rand_chacha.
  - Запрещены: любые крейты СУБД, KV, индексов, WAL, транзакций, движков запросов и ORM (rusqlite, rocksdb, lmdb/heed, sled, redb, fjall, tantivy…); bincode/rkyv для формата на диске; memmap2.
  - CRC32C — собственная реализация, проверенная по тест-векторам RFC 3720.
  - Таблица case folding генерируется из закреплённого `CaseFolding.txt` (данные UCD, Unicode 16.0).
- **Обоснование:** критерий «с нуля» должен проверяться механически (cargo-deny); HTTP и криптографию не переписываем — это не ядро БД и высокий риск.

### D-024. Масштаб, нагрузка и SLO
- **Решение:**
  - Цель проектирования — 10^8 контактов на одном узле (файл около 25 ГБ).
  - SLO проверяются на 10^7 записей на эталонном железе: 4 vCPU, 8 ГБ RAM, NVMe.
  - Профиль нагрузки: 95% чтений, 5% записей [ДОПУЩЕНИЕ, источника нет].
  - Цели по пропускной способности: не меньше 5 000 поисков/с и не меньше 500 зафиксированных записей/с (group commit); их нужно подтвердить бенчмарком.
  - SLO движка: точный поиск p99 ≤ 2 мс на прогретом кэше и ≤ 10 мс на холодном; префиксный поиск с limit 50 — p99 ≤ 50 мс; долговечная запись — p99 ≤ 50 мс; повторное открытие после сбоя — p99 ≤ 1 с.
  - SLO API (HTTP, в том же ЦОД): поиск p99 ≤ 100 мс; доступность — SLI на основе CUJ.
- **Обоснование:** отдельно не указано. В тексте решения профиль нагрузки помечен как допущение без источника.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §0.1, §7.1–§7.4, §8 ADR-007, §9 Q7; docs/research/03-domain-api-ui-security.md, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 7.
- **ADR:** нет отдельного ADR; SLO развёрнуты в `docs/cuj.md`, используются в ADR 0003, ADR 0005, ADR 0017

### D-034. Поведение при fail-stop (STO-16, OBS-01)
- **Решение:** при ошибке fsync или при повреждении, обнаруженном во время работы:
  - движок отклоняет записи, которые выполняются в этот момент; запись, находящаяся на шаге 4 коммита, получает ответ «исход неизвестен»;
  - в течение льготного периода не дольше 5 с сервер отвечает 503;
  - затем процесс ЗАВЕРШАЕТСЯ с отдельным кодом выхода;
  - супервизор перезапускает процесс, состояние восстанавливается с диска;
  - чтения из памяти НЕ обслуживаются.
- **Обоснование:** прецедент PANIC в PostgreSQL; после ошибки fsync состоянию кэша доверять нельзя; повторное открытие занимает ≤ 1 с.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §3.4, §3.8 DUR-4.
- **ADR:** ADR 0005 (также ADR 0017)
- **Статус:** Принято 2026-10-24. Отвечает на вопрос 5 из `docs/adr/README.md`; отменяет `[ПРЕДЛОЖЕНИЕ АГЕНТА]` в STO-16 об обслуживании чтений в fail-stop.

### D-035. Повреждение новейшей мета-страницы
- **Решение:**
  - Писатель один, поэтому потерять можно не больше одной транзакции.
  - Автоматический откат к более старой мета-странице разрешён только для txid = valid_max+1.
  - Такой откат ОБЯЗАТЕЛЬНО записывается в лог с обоими txid, увеличивает метрику `budb_meta_fallback_total` и вызывает алерт.
  - Остаточный риск документируется: битовую порчу после подтверждения нельзя отличить от порванного коммита. Риск снижают периодические verify/scrub и бэкапы.
- **Обоснование:** отдельно не указано. В тексте решения: при одном писателе потерять можно не больше одной транзакции.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §2.1 (c), §3.6, §3.8 DUR-6, DUR-7.
- **ADR:** ADR 0003, ADR 0005
- **Статус:** Принято 2026-10-24.

### D-043. Атрибуты cookie сессии
- **Решение:**
  - С TLS cookie ОБЯЗАТЕЛЬНО имеет префикс `__Host-` и атрибуты `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`.
  - На loopback без TLS (режим разработки по умолчанию) — те же атрибуты, но без `__Host-` и `Secure`.
  - Поведение браузеров на `http://127.0.0.1` помечено `[НЕ ПОДТВЕРЖДЕНО]` и должно проверяться e2e-тестом UI.
- **Обоснование:** оркестратор не указал.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §6.2, §6.3.
- **ADR:** ADR 0011, ADR 0016
- **Статус:** Принято 2026-10-24. Уточняет D-015 для loopback без TLS.

### D-045. Детализация журнала аудита
- **Решение:**
  - Отдельное событие аудита пишется на каждое изменение, событие аутентификации, административную операцию, экспорт и поиск данных субъекта.
  - Обычные чтения и поиски по умолчанию агрегируются: одна запись на пользователя за минуту со счётчиками по типам.
  - Запись каждого чтения отдельным событием включается конфигурацией.
- **Обоснование:** 5000 поисков/с × ~100 Б ≈ 43 ГБ в сутки `[РАСЧЁТ]`; ст. 19 152-ФЗ выполняется подотчётной агрегированной записью `[ДОПУЩЕНИЕ — не юридическая консультация]`.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §6.5 п. 3.
- **ADR:** ADR 0012
- **Статус:** Принято 2026-10-24.

### D-048. Курсор пагинации

### D-055. Размещение служебных данных
- **Решение:**
  - Служебные данные лежат в том же файле БД, в дополнительных B+tree, учтённых в одном каталоге деревьев: `users`, `api_tokens` (хэши), `idempotency_keys` (TTL 24 ч), `trash_idx(deleted_at‖id)`. Корзина — это поле `deleted_at` в записи `primary`.
  - UI-сессии хранятся только в памяти: после перезапуска нужен повторный вход.
  - Журнал аудита и журнал purge — отдельные файлы только на добавление, со сбросом на устройство и ротацией, без ПДн.
  - Admin CLI: онлайн-операции идут через admin API, офлайн-операции — напрямую по файлу под эксклюзивной блокировкой.
- **Обоснование:** оркестратор не указал.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §2.4 п. 7, §3.8 DUR-9.
- **ADR:** ADR 0011, ADR 0012, ADR 0013, ADR 0017
- **Статус:** Принято 2026-10-24. Отвечает на вопросы 1 и 4 из `docs/adr/README.md`.

### D-056. Механика purge
- **Решение:**
  - Транзакция purge N освобождает страницы. Затем движок принудительно выполняет коммит N+1, чтобы старая мета-страница больше не ссылалась на них.
  - Страницы заполняются нулями и сбрасываются на устройство, как только txid самого старого читателя > N.
  - T_purge = 24 ч. Читатели и бэкапы, которые блокируют затирание дольше, завершаются принудительно (бэкап перезапускается).
  - «Сегменты журнала» неприменимы: WAL нет. Формулировку нужно исправить.
  - Снимки бэкапа, экспорта и проверки освобождены от лимита 30 с, но ограничены сроком T_purge.
- **Обоснование:** оркестратор не указал.
- **Исследование:** docs/research/02-storage-engine-and-language.md, §2.4 п. 5; docs/research/03-domain-api-ui-security.md, §6.5 п. 1.
- **ADR:** ADR 0012, ADR 0003 (также ADR 0013)
- **Статус:** Принято 2026-10-24. Уточняет D-012 в части «сегментов журнала». Отвечает на вопросы 2 и 3 из `docs/adr/README.md`.

### D-057. Формат `id` контакта
- **Решение:** `id` контакта — u64, монотонный, никогда не переиспользуется. В JSON передаётся десятичной строкой (защита от потери точности в JS после 2^53).
- **Обоснование:** 8 Б вместо 16 Б × 3 дерева × 10^8 ≈ 2,4 ГБ экономии; перечислимость допустима (одна книга, авторизация на всех операциях).
- **Исследование:** docs/research/02-storage-engine-and-language.md, §7.1, §7.2; docs/research/03-domain-api-ui-security.md, §3.1, §6.1 (API1).
- **ADR:** ADR 0007
- **Статус:** Принято 2026-10-24. Отвечает на вопрос 6 из `docs/adr/README.md`.

### D-058. Версия Unicode, пробелы, минимальный префикс
- **Решение:**
  - Для нормализации и casefold закрепляется ОДНА версия Unicode — новейшая из поддерживаемых закреплённым крейтом unicode-normalization на момент начала реализации (≥ 16.0). Она записывается в BLD и в версию правил ключа имени.
  - По данным исследования, текущей может быть версия 18.0; это нужно проверить на ревью (fact-check).
  - Пробелы: обрезка по краям и схлопывание Unicode White_Space → U+0020.
  - Минимальный префикс: для имени ≥ 1 кодовой точки, для телефона ≥ 3 цифр.
- **Обоснование:** оркестратор не указал.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §2.1, §2.2, §2.4, §4.7.
- **ADR:** ADR 0009 (также ADR 0006)
- **Статус:** Принято 2026-10-24. Уточняет версию Unicode в D-021 и D-050. Отвечает на вопрос 7 из `docs/adr/README.md`.

### D-059. Телефоны и детали API
- **Решение:**
  - RU принимает 10-значный национальный номер (9XXXXXXXXX → +79XXXXXXXXX) и 11-значный 7XXXXXXXXXX как `[ДОПУЩЕНИЕ]`.
  - Список кодов стран ITU закрепляется по дате ITU-T Operational Bulletin.
  - Пара (e164, ext) уникальна в пределах контакта; если телефоны есть, `is_primary` ровно у одного.
  - Детали API утверждены: OpenAPI 3.1, RFC 9457, 412/428, keyset-пагинация по AIP-158, `Idempotency-Key`.
  - 503 — сервер перегружен или не готов; 429 — превышен лимит частоты для клиента.
- **Обоснование:** оркестратор не указал.
- **Исследование:** docs/research/03-domain-api-ui-security.md, §1.1, §1.4, §3.1, §4.1–§4.6.

- **Статус:** Принято 2026-10-24. Отвечает на вопрос 9 из `docs/adr/README.md` и частично на вопрос 8.
