## 1. Comprehension: пересказ своими словами

BUDB — однопользовательская по развёртыванию (один экземпляр = одна телефонная книга) база имён и телефонов, написанная с нуля на Rust без сторонних движков хранения. Главные сценарии: «кто звонит с этого номера» и «какой телефон у этого человека». Пользователи — три роли: reader (оператор, ищет и читает), writer (редактор, создаёт, правит, удаляет в корзину, импортирует), admin (корзина, purge, экспорт, пользователи, бэкапы, аудит). Кроме людей в UI есть интеграторы через HTTP API и оператор через CLI.

**Ключевые гарантии.** Подтверждённая запись не теряется при kill -9 и потере питания (на Linux, на накопителе с честным сбросом кэша). Ошибка ввода-вывода приводит к fail-stop: процесс завершается и восстанавливается с диска, повторов fsync нет. Цель — 10^8 контактов на узле; SLO проверяются на 10^7: точный поиск в движке p99 ≤ 2 мс, через API p99 ≤ 100 мс, запись p99 ≤ 50 мс, ≥ 5 000 поисков/с и ≥ 500 записей/с. Имена и телефоны считаются ПДн: удалённый контакт лежит в корзине 1…29 дней, purge физически затирает данные в файле не позднее 24 ч, журнал purge повторно применяется при restore, аудит и логи не содержат ПДн.

**Хранение.** Один файл со страницами 4 КиБ, у каждой страницы CRC32C. Страница 0 — заголовок, страницы 1 и 2 — две чередующиеся мета-страницы. Данные лежат в copy-on-write B+tree: `primary` (по `id`), `name_idx`, `phone_idx` и служебные деревья в каталоге (пользователи, токены, ключи идемпотентности, корзина, задания). Один поток-писатель собирает операции в пачки (group commit). Коммит: запись страниц → fsync → мета-страница → fsync. Читатели работают на MVCC-снимках. Освобождённые страницы переиспользуются с задержкой и при этом затираются нулями (zero-on-reclaim). Кэш страниц собственный, mmap запрещён.

**Поиск.** По телефону — после нормализации в E.164 (регионы RU и `none`), точно или по префиксу цифр с кодом страны. По имени — по ключу NFKC_Casefold с заменой ё→е, точно или по префиксу полного ключа и каждого слова. Порядок бинарный, страница 20 (максимум 100), keyset-курсор с HMAC живёт 24 ч.

**API и UI.** REST-подобный `/api/v1` с OpenAPI 3.1, ошибками RFC 9457, ETag/If-Match, `Idempotency-Key`, лимитами 413/429/503 и асинхронными заданиями импорта, экспорта и бэкапа. UI — TypeScript и Web Components без фреймворков, встроен в бинарник, соответствует WCAG 2.2 AA, поддерживает ru/en. В UI есть поиск при вводе, карточка, форма с предпросмотром номера, конфликт версий, корзина, импорт с пробным прогоном, экспорт и страница состояния. CLI: `budb serve` и `budb admin …` в онлайн-режиме (через API) и офлайн-режиме (с файлом).

**В v1 нет:** мультиарендности, merge дубликатов, vCard, заметок, сортировки UCA, нескольких узлов и репликации, онлайн-компактизации, миграции формата, PATCH, OIDC/LDAP, регионов кроме RU и `none`.

### 1.1. Где пришлось угадывать

1. **CUJ-01…CUJ-10.** Понятны только CUJ-01 («кто звонит»), CUJ-02 («какой телефон») и, в общих чертах, CUJ-03 и CUJ-07 («не теряться»). Смысл CUJ-04…CUJ-10 приходится выводить из того, где на них ссылаются (CUJ-09 — видимо, ПДн и purge, CUJ-10 — учётные записи). Персоны («оператор», «редактор») нигде не определены.
2. **D-NNN и ADR-NNNN.** Требования ссылаются примерно на 60 решений и 17 ADR. Таблица в `design.md` пересказывает только D-034…D-060, по одной строке на решение. Без расшифровки остаются D-022 (лимиты), D-029 («ровно список D-029»), D-033 (конфигурация), D-044, D-046 (состав admin-ресурсов) и D-054 («`raw_input` из файла»).
3. **Какой текст действует.** Действует правило «решение важнее спецификации». Значит, нормой служит не текст требования, а его сочетание с однострочной записью в таблице. Где запись неполна, норма неизвестна (см. GF1-09, GF1-08).
4. **«Субъект»** означает две разные вещи: субъект аутентификации (API-16, API-19) и субъект ПДн (PRV-15, CLI-09).
5. **Пометка `[ПРЕДЛОЖЕНИЕ АГЕНТА]`** стоит внутри нормативных MUST/SHALL примерно в 60 местах. В `design.md` сказано, что до ответа такой вариант действует. Неясно, утверждён ли он и может ли команда его менять.
6. **Режим поиска в UI для CUJ-01.** `design.md` §7 отправляет `mode: exact`, а UI-03 — поиск «по префиксу телефона». Какой режим реально использует оператор, непонятно.
7. **Корзина после D-041.** Writer «просматривает корзину», но эндпоинта для этого нет: `/api/v1/admin/trash` по API-27 доступен только admin.
8. **T и K в group commit.** K — размер пачки. Под T, видимо, понимается «ожидание набора» из STO-13, но прямо это не сказано. Термин `T_purge` при этом определён.
9. **Состояния заданий.** Используются `queued/running/completed/failed` (IMP-05) и `succeeded` (API-25). Неясно, это одно и то же или разные машины состояний.

## 4. Итоговая оценка: `not-ready`

**Что готово.** Ядро хранения описано очень хорошо. Протокол коммита, выбор мета-страницы, fail-stop, правило переиспользования страниц, перебор состояний после сбоя и критерии тестов надёжности конкретны и проверяемы. Трассировка полная: все 270 требований упомянуты в задачах. Нормализация телефонов и имён снабжена конкретными тест-векторами. Фазы 1–6 из `tasks.md` команда может начать завтра, задав только вопросы 14 и 15. GF1-12 нужно учесть в задаче 4.2.

**Почему не готово.**
1. Пакет сам признаёт, что спецификации расходятся с 27 решениями, а норма определяется однострочниками из таблицы. Ряд решений (D-041, D-048, D-036, D-046, D-054) описан не настолько, чтобы реализовать их однозначно (GF1-01, GF1-08, GF1-09, GF1-10).
2. Главный пользовательский путь CUJ-01 в UI противоречив: префикс телефона без национального формата при национальном вводе (GF1-04).
3. Префиксный поиск по словам — часть CUJ-02 — не имеет определённого результата (GF1-02).
4. В API нет аутентификации для UI (GF1-03), поэтому фазы 9 и 14 начать нельзя.
5. Две гарантии ПДн, ради которых введены D-036 и D-056, в описанном виде могут не выполняться: «воскрешение» при restore (GF1-10) и затирание на простаивающей базе (GF1-11).

**Условие перехода в `ready-with-nits`:** закрыть четыре blocker, выполнить задачу 0.1 с учётом GF1-05…GF1-09, ответить на вопросы 5, 6 и 8 к оркестратору и исправить GF1-10, GF1-11, GF1-12.
