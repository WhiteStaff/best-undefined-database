# Critical User Journeys (CUJ) BUDB

Документ задаёт 10 критических пользовательских путей BUDB (D-028). Каждое требование спецификаций OpenSpec трассируется к одному из них строкой `Трассировка: CUJ-NN` (`openspec/config.yaml`).

Пометки: `[ДОПУЩЕНИЕ]` — допущение автора; `[НЕ ПОДТВЕРЖДЕНО]` — не проверено по первоисточнику; `[ПРЕДЛОЖЕНИЕ АГЕНТА]` — числа или правила, которых нет в журнале решений (`docs/orchestrator-decisions.md`); они ждут утверждения оркестратором.

## 1. Методика и источники

* **Google SRE Workbook, «Implementing SLOs», раздел «Modeling User Journeys»** — https://sre.google/workbook/implementing-slos/ . CUJ — «a sequence of tasks that is a core part of a given user's experience»; SLO пишутся «in terms of user-centric actions»; измеримое событие пути «becomes just another SLI». SLI задаётся как доля хороших событий среди допустимых; в меню SLI есть durability — «proportion of records written that can be successfully read» (docs/research/01, §A1; docs/research/03, §7.1, [S56]).
* **Google SRE Book, «Service Level Objectives»** — https://sre.google/sre-book/service-level-objectives/ . Задержку смотреть по высоким перцентилям; «Have as few SLOs as possible»; не подгонять цель под текущую производительность (docs/research/03, §7.1, [S57]).
* **Google SRE Workbook, «Example SLO Document»** — https://sre.google/workbook/slo-document/ . Окно 4 недели, у каждого SLO свой error budget = 100 % − цель (docs/research/03, §7.1, [S58]).
* **The Art of SLOs** (воркшоп Google CRE, CC-BY-4.0) — https://sre.google/resources/practices-and-processes/art-of-slos/ . Уточнение SLI от общей спецификации (что важно пользователю) к измеримой реализации (как измеряем) (docs/research/03, §7.1, [S59]).
* **Bargas-Avila J. A. (Google UX)**, Mind the Product — https://www.mindtheproduct.com/measuring-critical-user-journeys-javier-andres-bargas-avila-ux-research-director-google/ ; https://www.mindtheproduct.com/product-development-and-ux-critical-user-journeys/ . CUJ = пользователь + цель + задачи (задачи без привязки к фичам); одной «completion rate» мало (docs/research/01, §A1; docs/research/03, §7.1, [S61]).
* **Google Cloud, «A practical guide to setting SLOs»** — https://cloud.google.com/blog/products/management-tools/practical-guide-to-setting-slos (docs/research/03, §7.1, [S60]).

Отклонение от методики: Bargas-Avila советует 5–7 целей на продукт (docs/research/01, §A1). Здесь 10 путей, потому что CUJ покрывают все вводные ДЗ плюс эксплуатационные сценарии (D-028).

### 1.1. Общие условия измерения

* **Эталонный стенд:** 4 vCPU, 8 ГБ RAM, NVMe, 10^7 записей; цель проектирования — 10^8 записей на одном узле (D-024).
* **Профиль нагрузки:** 95 % чтений, 5 % записей `[ДОПУЩЕНИЕ, источника нет]` (D-024).
* **SLO движка** измеряются внутри процесса, без сети; **SLO API** — по HTTP в том же ЦОД (D-024).
* **Накопитель** честно исполняет flush; на HDD и сетевых ФС SLO не гарантируются (docs/research/02, §7.4; D-019).
* **Платформа:** SLO и гарантии долговечности действуют на tier 1 (Linux, D-023).
* **Окно SLO:** скользящие 28 дней `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §7.4; ориентир — 4 недели в примере SLO-документа [S58]).
* **Допустимые события** для доступности: все запросы, кроме отвергнутых по вине клиента (400, 401, 403, 404 на несуществующий ресурс, 413, 415, 422) и 429 по лимиту клиента; ответы 5xx (включая 503 при переполнении очередей, D-032) — плохие события `[ПРЕДЛОЖЕНИЕ АГЕНТА]`. Ответ «ничего не найдено» на поиск — хорошее событие.

## CUJ-01. Кто звонит (телефон → имена)

* **Персона:** P1, оператор колл-центра.
* **Цель:** во время звонка узнать, кто звонит, по номеру на экране.
* **Шаги (задачи):**
  1. Ввести или вставить номер в любом привычном формате («8 (916) 123-45-67», «+7 916 1234567»).
  2. Увидеть список контактов, у которых есть этот номер, с именем и меткой телефона.
  3. Открыть карточку нужного контакта.
* **Критерий успеха:** оператор видит все контакты с этим номером за время, которое не прерывает разговор (NN/g: до 1 с поток мысли не прерывается, docs/research/03, §5.1, [S39]); номер в национальном формате найден так же, как в E.164.
* **SLI:**
  * доступность — доля допустимых запросов поиска по телефону без ответа 5xx;
  * задержка API — доля поисков по телефону, обслуженных сервером быстрее 100 мс;
  * задержка движка — доля точных поисков быстрее 2 мс на тёплом кэше и быстрее 10 мс на холодном;
  * корректность — доля поисков, вернувших ровно множество контактов с данным E.164 (модельные тесты).
* **SLO:**
  * API: поиск p99 ≤ 100 мс (D-024);
  * движок: точный поиск p99 ≤ 2 мс на прогретом кэше и ≤ 10 мс на холодном (D-024);
  * пропускная способность ≥ 5 000 поисков/с (D-024, подтвердить бенчмарком);
  * доступность 99,9 % `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §7.4, CUJ-1);
  * корректность 100 % в модельных тестах.
* **Capabilities:** phone-normalization, search, http-api, web-ui, access-control, data-privacy, storage-engine, performance-capacity, observability.
* **Крайние и негативные случаи:**
  * номер не найден — пустой результат, а не ошибка;
  * «невозможный» номер (неизвестный код страны, больше 15 цифр) — ошибка валидации с понятной причиной (D-010);
  * полноширинные цифры, NBSP и скобки — нормализуются (D-010);
  * номер с добавочным: совпадение по `e164`, добавочный показывается отдельно;
  * один номер у нескольких контактов (семейный телефон) — возвращаются все (D-009);
  * контакт в корзине не показывается (D-012) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * номер не попадает в URL и в логи (D-013);
  * превышение лимита запросов — 429 с `Retry-After`; переполнение очереди движка — 503 (D-032);
  * у пользователя нет роли reader — 403.

## CUJ-02. Найти телефон по имени (префикс)

* **Персона:** P1, оператор колл-центра.
* **Цель:** найти телефон человека, зная начало его имени.
* **Шаги (задачи):**
  1. Начать печатать имя.
  2. Увидеть список подходящих контактов с подсвеченным совпадением.
  3. Выбрать контакт с клавиатуры.
  4. Скопировать номер или позвонить.
* **Критерий успеха:** нужный контакт появляется в первых результатах без учёта регистра и различия «ё/е» (D-011); вся задача укладывается в 1 с от последнего нажатия (порог NN/g, docs/research/03, §7.4, CUJ-2).
* **SLI:**
  * задержка движка — доля префиксных поисков (limit 50) быстрее 50 мс;
  * задержка API — доля поисков, обслуженных сервером быстрее 100 мс;
  * задержка UI — доля вводов, после которых список отображён не позже 1 с от последнего нажатия (включая debounce 200–300 мс, docs/research/03, §5.1, [S38]);
  * корректность — доля префиксных поисков, совпавших с моделью в памяти.
* **SLO:**
  * движок: префиксный поиск с limit 50 p99 ≤ 50 мс (D-024);
  * API: поиск p99 ≤ 100 мс (D-024);
  * UI: 99 % вводов — список за ≤ 1 с `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §7.4, CUJ-2);
  * корректность 100 % в модельных тестах.
* **Capabilities:** name-normalization, search, http-api, web-ui, access-control, storage-engine, performance-capacity.
* **Крайние и негативные случаи:**
  * «Семенов» находит «Семёнов», «СЕМЁНОВ» находит «семенов» (D-011);
  * «Йо» не находит «Ио»: «й» не теряет бреве (D-011, docs/research/03, §2.3);
  * больше 50 совпадений — курсорная пагинация (`[ПРЕДЛОЖЕНИЕ АГЕНТА]`, docs/research/03, §4.4);
  * минимальная длина префикса не задана в журнале — вопрос к оркестратору;
  * лишние пробелы по краям и внутри имени не мешают поиску `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §2.4);
  * имя с HTML-разметкой отображается как текст (D-031, docs/research/03, §6.4);
  * имя не попадает в URL и в логи (D-013);
  * работа только с клавиатуры и со скринридером (WCAG 2.2 AA, docs/research/03, §5.2).

## CUJ-03. Добавить или изменить контакт с подтверждением долговечности

* **Персона:** P5, редактор справочника.
* **Цель:** внести или исправить контакт и быть уверенным, что он сохранён.
* **Шаги (задачи):**
  1. Открыть форму, ввести имя и телефоны (до 10), увидеть предпросмотр E.164.
  2. Сохранить.
  3. Получить подтверждение.
  4. Сразу найти контакт поиском.
* **Критерий успеха:** подтверждение приходит только после долговечной фиксации (D-019); подтверждённый контакт находится сразу (read-your-writes) и после аварийного перезапуска.
* **SLI:**
  * долговечность — доля подтверждённых записей, которые читаются после подтверждения, в том числе после kill -9 и эмуляции потери питания (docs/research/03, §7.1, [S56]: durability);
  * задержка — доля долговечных записей быстрее 50 мс;
  * read-your-writes — доля поисков сразу после подтверждения, которые видят запись.
* **SLO:**
  * 100 % подтверждённых записей переживают kill -9 и потерю питания (проверяется тестами отказов, D-019, D-026);
  * долговечная запись p99 ≤ 50 мс (D-024);
  * ≥ 500 зафиксированных записей/с при group commit (D-024, подтвердить бенчмарком);
  * read-your-writes 100 %.
* **Capabilities:** contacts, phone-normalization, name-normalization, storage-engine, http-api, web-ui, access-control, performance-capacity, build-constraints.
* **Крайние и негативные случаи:**
  * `display_name` пустое, 257 кодовых точек или больше 1024 байт UTF-8 — ошибка валидации (D-022);
  * 11 телефонов, добавочный длиннее 10 цифр — ошибка (D-022);
  * дубликат имени или номера разрешён, но система показывает подсказку «возможные дубликаты» (D-009);
  * сбой до подтверждения — после перезапуска транзакции нет целиком; сбой после подтверждения — она есть целиком (D-019);
  * ошибка fsync — подтверждения нет, fail-stop без повтора (D-019);
  * повтор запроса создания после таймаута с тем же `Idempotency-Key` не создаёт второй контакт `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §4.5);
  * у пользователя роль reader — 403.

## CUJ-04. Обнаружение конфликта одновременного редактирования

* **Персона:** P5, редактор справочника.
* **Цель:** не затереть правку коллеги, сделанную одновременно.
* **Шаги (задачи):**
  1. Два редактора открывают один контакт.
  2. Первый сохраняет изменение.
  3. Второй сохраняет своё на основе старой версии.
  4. Второй видит сообщение о конфликте, перезагружает актуальные данные и повторяет правку.
* **Критерий успеха:** вторая запись не перезаписывает первую молча; редактор понимает, что произошло.
* **SLI:** доля конфликтующих записей (изменение или удаление на основе устаревшей версии), отклонённых, а не применённых.
* **SLO:** 100 % (корректность; docs/research/03, §7.4, CUJ-4).
* **Capabilities:** contacts, http-api, web-ui, storage-engine.
* **Крайние и негативные случаи:**
  * изменение без указания версии — отказ (428 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`, docs/research/03, §4.3);
  * устаревшая версия — отказ (412 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`, RFC 9110, docs/research/03, §4.3);
  * удаление на основе устаревшей версии — тоже конфликт;
  * контакт удалён в корзину, пока второй редактировал — второй получает понятную ошибку;
  * два изменения в одной пачке group commit с одной исходной версией — применяется ровно одно.

## CUJ-05. Интегратор подключается через API

* **Персона:** P2, разработчик-интегратор.
* **Цель:** подключить CRM или АТС к BUDB по опубликованному контракту.
* **Шаги (задачи):**
  1. Прочитать контракт API и quickstart.
  2. Получить токен у администратора.
  3. Выполнить создание, чтение, изменение, поиск и пагинацию.
  4. Обработать ошибки в машиночитаемом виде.
* **Критерий успеха:** ответы сервера соответствуют опубликованному контракту; ошибки предсказуемы; интеграция возможна без чтения исходников.
* **SLI:**
  * доля ответов, соответствующих опубликованной схеме (контрактные тесты);
  * доступность — доля допустимых запросов без 5xx;
  * время до первого успешного вызова по quickstart.
* **SLO:**
  * 100 % контрактных тестов (docs/research/03, §7.4, CUJ-5);
  * доступность 99,9 % `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §7.4);
  * первый успешный вызов ≤ 15 мин по quickstart `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (юзабилити-цель из docs/research/03, §7.4, CUJ-5);
  * задержки поиска — как в CUJ-01 и CUJ-02 (D-024).
* **Capabilities:** http-api, access-control, contacts, search, observability.
* **Крайние и негативные случаи:**
  * нет токена или он неверен — 401; не хватает роли — 403 (D-015);
  * токен в URL не принимается (docs/research/03, §6.2);
  * лишнее поле в теле — отказ (docs/research/03, §6.1, API3) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * подделанный или чужой токен страницы — отказ (docs/research/03, §4.4);
  * слишком большой `page_size` уменьшается до максимума (docs/research/03, §4.4) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * неподдерживаемый метод — 405, Content-Type — 415 (docs/research/03, §6.2);
  * в ответах об ошибках нет стектрейсов (docs/research/03, §4.2).

## CUJ-06. Массовый импорт и экспорт

* **Персона:** P2 (импорт из внешней системы), P3 (экспорт для миграции).
* **Цель:** загрузить большой справочник и надёжно повторить загрузку при сбое; выгрузить всё для миграции.
* **Шаги (задачи):**
  1. Подготовить файл CSV (RFC 4180) или NDJSON (D-016).
  2. Запустить импорт (по API или через Admin CLI), при желании — пробный прогон.
  3. Следить за статусом.
  4. Получить отчёт: сколько принято, сколько отклонено и почему (построчно).
  5. Экспортировать базу в CSV или NDJSON.
* **Критерий успеха:** счётчики сходятся (принято + отклонено = всего); повтор не создаёт дублей; экспорт и обратный импорт дают ту же базу.
* **SLI:**
  * доля импортов, завершившихся с корректными счётчиками;
  * доля повторных импортов с тем же ключом идемпотентности, не создавших дублей;
  * доля round-trip-проверок `import(export(db)) == db`.
* **SLO:**
  * ≥ 99,9 % импортов с корректными счётчиками (docs/research/03, §7.4, CUJ-6);
  * повтор без дублей — 100 %;
  * round-trip — 100 % (docs/research/03, §7.4, кандидат CUJ-10);
  * пропускная способность импорта ≥ 500 записей/с (10^6 записей за ≤ 34 мин) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: нижняя граница из цели ≥ 500 зафиксированных записей/с (D-024); в исследовании число не определено (docs/research/03, §7.4: «X»).
* **Capabilities:** import-export, contacts, phone-normalization, name-normalization, http-api, admin-cli, access-control, data-privacy, storage-engine, performance-capacity.
* **Крайние и негативные случаи:**
  * строка с неверным номером или слишком длинным именем — отклоняется со ссылкой на номер строки, остальные принимаются;
  * битая кодировка, незакрытые кавычки CSV, строка NDJSON с переводом строки внутри JSON (docs/research/03, §4.8);
  * тот же ключ идемпотентности с другим телом — 422 (docs/research/03, §4.5) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * файл больше лимита — 413 (docs/research/03, §4.6);
  * экспорт согласован на момент начала (снимок) и не видит записей, сделанных во время выгрузки (docs/research/03, §4.8);
  * ячейки CSV, начинающиеся с `=`, `+`, `-`, `@` (CSV-инъекция) — конфликт с номерами `+7…` не решён (docs/research/03, §6.4, `[НЕ ПОДТВЕРЖДЕНО]`), вопрос к оркестратору;
  * экспорт — только admin (docs/research/03, §6.1, API6) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`; импорт по URL не поддерживается (API7);
  * сбой процесса во время импорта: уже подтверждённые пачки сохранены, повтор по ключу идемпотентности продолжает без дублей `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.

## CUJ-07. Бэкап, восстановление и восстановление после сбоя

* **Персона:** P3, администратор БД.
* **Цель:** не потерять данные при сбое процесса, питания или носителя.
* **Шаги (задачи):**
  1. Сделать онлайн-бэкап без остановки сервиса (D-025).
  2. Проверить бэкап на целостность.
  3. При потере данных — остановить сервер, восстановить из бэкапа (журнал очисток применяется повторно, D-012).
  4. После аварийного перезапуска — убедиться, что сервер открылся и готов (`/readyz`).
* **Критерий успеха:** после сбоя процесса или питания все подтверждённые записи на месте; бэкап проверяем и восстанавливается; повреждение данных обнаруживается явно, а не маскируется откатом.
* **SLI:**
  * доля бэкапов, прошедших проверку и пробное восстановление;
  * доля подтверждённых транзакций, сохранившихся после сбоя процесса или питания (RPO);
  * доля повторных открытий после сбоя быстрее 1 с;
  * доля внедрённых повреждений зафиксированных страниц, обнаруженных как ошибка (а не как откат).
* **SLO:**
  * 100 % бэкапов проверяемы (docs/research/03, §7.4, CUJ-7);
  * RPO = 0 для подтверждённых транзакций после сбоя процесса и потери питания на tier 1 (D-019, D-023);
  * повторное открытие после сбоя p99 ≤ 1 с (D-024);
  * 100 % внедрённых повреждений обнаружены (D-019, D-026);
  * RTO восстановления из бэкапа < 1 мин для 10^6 записей `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §7.4, CUJ-7); для эталонных 10^7 записей число не выбрано — вопрос к оркестратору.
* **Capabilities:** backup-restore, storage-engine, admin-cli, observability, data-privacy, performance-capacity, build-constraints.
* **Крайние и негативные случаи:**
  * бэкап во время потока записей — согласован на txid начала;
  * сбой во время бэкапа — нет файла, который выглядит готовым;
  * повреждённый байт в бэкапе — проверка сообщает номер страницы;
  * kill -9 и потеря питания в любой точке коммита (перебор, D-026);
  * порванная мета-страница — открытие по второй валидной (D-018);
  * повреждение подтверждённой страницы — явная ошибка и режим без записи, никогда не тихий откат (D-019);
  * ошибка fsync — fail-stop, без повтора (D-019);
  * восстановление при работающем сервере — отказ (эксклюзивная блокировка, docs/research/02, §2.4 п. 7);
  * диск заполнен — запись не подтверждается, уже подтверждённое не теряется `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * tier 2 (Windows, macOS): гарантии с оговорками (D-023).

## CUJ-08. Мониторинг состояния и ёмкости

* **Персона:** P3, администратор БД.
* **Цель:** понять, здорова ли БД и когда кончится место.
* **Шаги (задачи):**
  1. Открыть страницу состояния в UI или опросить `/metrics`, `/livez`, `/readyz`.
  2. Увидеть число записей, размер файла, время последнего бэкапа и проверки, задержки, ошибки.
  3. Получить алерт до исчерпания ресурса.
* **Критерий успеха:** готовность отражает реальное состояние; метрики свежие; ни одна метрика не содержит ПДн.
* **SLI:**
  * свежесть — доля опросов, в которых возраст метрик не больше 15 с;
  * точность готовности — доля проверок пробера, в которых `/readyz` совпадает с результатом синтетической операции записи и чтения.
* **SLO:**
  * свежесть метрик ≤ 15 с (docs/research/03, §7.4, CUJ-8);
  * точность готовности 99,9 % `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (в исследовании число не задано).
* **Capabilities:** observability, http-api, web-ui, admin-cli, access-control, performance-capacity, storage-engine.
* **Крайние и негативные случаи:**
  * после fail-stop `/readyz` сообщает «не готов» (D-019) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * `/metrics` без роли admin — отказ (docs/research/03, §4.9) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * в метках и значениях метрик нет имён и телефонов (D-013);
  * рост файла из-за долгого снимка или бэкапа виден в метриках (docs/research/02, §2.4 п. 5);
  * повреждение данных — отдельный сигнал, а не «просто не готов».

## CUJ-09. Удаление ПДн по запросу субъекта

* **Персона:** P4, ответственный за ПДн.
* **Цель:** исполнить запрос субъекта на уничтожение данных в срок 152-ФЗ.
* **Шаги (задачи):**
  1. Найти контакты субъекта.
  2. Выполнить «очистить сейчас» (purge) — команда администратора (D-012).
  3. Получить подтверждение очистки.
  4. Проверить запись в журнале аудита (без значений ПДн).
* **Критерий успеха:** после очистки содержимое невозможно восстановить ни поиском, ни чтением файлов хранилища (152-ФЗ, ст. 3 п. 8, docs/research/03, §6.5); восстановление из старого бэкапа не возвращает данные (D-012).
* **SLI:**
  * доля очисток, после которых данные не находятся поиском;
  * доля очисток, после которых побайтовое сканирование файлов хранилища не находит содержимое;
  * доля восстановлений из бэкапа, после которых очищенные контакты отсутствуют;
  * доля записей корзины, очищенных автоматически не позже срока хранения.
* **SLO:**
  * 100 %: сразу после подтверждения данные не находятся поиском;
  * 100 %: содержимое отсутствует в файлах хранилища не позже T_purge = 24 ч `[ПРЕДЛОЖЕНИЕ АГЕНТА]` (docs/research/03, §7.4, CUJ-9; в D-012 срок не задан);
  * 100 % восстановлений повторно применяют журнал очисток (D-012);
  * автоматическая очистка корзины — по истечении срока хранения: по умолчанию 7 дней, не больше 30 дней (D-012; 152-ФЗ, ст. 21);
  * 0 значений ПДн в журнале аудита и логах (D-012, D-013).
* **Capabilities:** data-privacy, contacts, storage-engine, backup-restore, admin-cli, access-control, observability.
* **Крайние и негативные случаи:**
  * у субъекта несколько контактов (дубликаты) — очищаются все выбранные;
  * контакт уже в корзине — очищается из корзины;
  * страницы контакта видит идущий бэкап или долгий читатель — поведение не решено, вопрос к оркестратору;
  * бэкапы, сделанные до очистки, содержат данные — они «beyond use», субъект информируется (ICO, docs/research/03, §6.5) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * purge несуществующего id — понятная ошибка, без утечки информации;
  * purge без роли admin — 403;
  * сбой процесса посреди очистки — после перезапуска очистка либо завершена, либо повторяема `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.

## CUJ-10. Администратор управляет пользователями и доступом

* **Персона:** P3, администратор БД.
* **Цель:** выдать людям и программам ровно нужные права и быстро отозвать их.
* **Шаги (задачи):**
  1. Создать первого администратора через Admin CLI (D-017; docs/research/03, §6.2).
  2. Создать пользователей с ролями reader/writer/admin (D-015).
  3. Выпустить bearer-токен для интеграции; секрет показывается один раз `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
  4. Изменить роль или отозвать токен.
  5. Проверить события в журнале аудита.
* **Критерий успеха:** каждое действие разрешено или запрещено строго по роли; отозванный токен перестаёт работать; события безопасности записаны без ПДн.
* **SLI:**
  * доля решений доступа, совпавших с матрицей ролей (тесты);
  * доля запросов с отозванным токеном, отклонённых;
  * доля событий безопасности (вход, отказ, выдача и отзыв токена, смена роли), попавших в аудит.
* **SLO:**
  * 100 % решений доступа по матрице ролей;
  * 100 % запросов с отозванным токеном отклоняются, начиная со следующего запроса после отзыва `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * 100 % событий безопасности в аудите, 0 значений ПДн (D-012).
* **Capabilities:** access-control, admin-cli, web-ui, http-api, data-privacy, observability.
* **Крайние и негативные случаи:**
  * перебор паролей — ограничение неудачных попыток (docs/research/03, §6.1, API2);
  * истёкшая сессия UI — повторный вход (docs/research/03, §6.2);
  * изменяющий запрос из UI без CSRF-токена или с `Sec-Fetch-Site: cross-site` — отказ (D-015);
  * удаление или понижение последнего администратора — отказ `[ПРЕДЛОЖЕНИЕ АГЕНТА]`;
  * токен и пароль не появляются в логах и в файле БД в открытом виде (D-015);
  * смена роли действует со следующего запроса `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
