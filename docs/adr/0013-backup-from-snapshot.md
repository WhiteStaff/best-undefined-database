# 0013. Бэкап из MVCC-снимка, восстановление и проверка целостности

## Status

Accepted, 2026-10-24. Решение D-025 (с учётом D-012: повторное применение журнала очисток; D-018: снимки COW).

## Context and Problem Statement

Администратор должен сделать бэкап без остановки сервиса, проверить его и восстановиться после сбоя или потери данных (CUJ-07). 152-ФЗ, ст. 19 ч. 2 п. 7 называет восстановление ПДн, изменённых или уничтоженных вследствие НСД, одной из мер защиты (docs/research/03, §6.5, [S50]). COW B+tree даёт снимки из структуры (ADR 0003).

Как делать согласованный бэкап на ходу, как восстанавливаться и как проверять целостность?

## Decision Drivers

* Согласованность бэкапа без остановки записи (D-025).
* Проверяемость: каждый бэкап можно проверить до того, как он понадобится.
* Повреждение обнаруживается явно (ADR 0005).
* Удалённые данные не воскресают после восстановления (D-012).

## Considered Options

1. **Онлайн-бэкап из MVCC-снимка: копирование страниц, достижимых из снимка, в новый файл → fsync → rename → fsync каталога; офлайн-восстановление; офлайн- и онлайн-проверка** — выбрано.
2. **Копирование файла средствами ОС** (`cp`) при работающем сервере.
3. **Только офлайн-бэкап** с остановкой сервиса.
4. **Снимок файловой системы или тома** (LVM, ZFS) силами эксплуатации.

## Decision Outcome

Выбран вариант 1 (D-025): в v1 входят онлайн-бэкап, согласованный за счёт MVCC-снимка; восстановление; проверка (офлайн- и онлайн-проверка целостности).

Устройство (по docs/research/02, §2.4 п. 6, §4, паттерн bbolt/etcd):

* **Бэкап** открывает читающий снимок на txid T и копирует в новый файл все страницы, достижимые из корней этого снимка, плюс две мета-страницы для T; затем fsync файла → rename во временное имя назначения → fsync каталога (docs/research/02, §2.4 п. 6, [S52]; DUR-3).
* **Проверка** (как `PRAGMA integrity_check`, docs/research/02, §4, [S33]): CRC32C всех страниц, упорядоченность ключей, согласованность трёх деревьев (каждый id из индексов есть в primary и наоборот), учёт freelist. Офлайн — по файлу; онлайн — по снимку работающей БД.
* **Восстановление** — офлайн: заменить файл БД проверенной копией и повторно применить журнал очисток (D-012, ADR 0012).
* Повреждённый бэкап отвергается при проверке, а не при восстановлении `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.

Как Admin CLI запускает онлайн-бэкап, если файл БД эксклюзивно заблокирован процессом сервера (docs/research/02, §2.4 п. 7, DUR-9), в журнале не решено. `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: онлайн-операции (бэкап, онлайн-проверка) CLI выполняет через admin-API работающего сервера; офлайн-операции (восстановление, офлайн-проверка, уплотнение) — напрямую по файлу, когда сервер остановлен. Вынесено в вопросы (см. также ADR 0017).

Обоснование (D-025): COW делает снимки дешёвыми; это нужно для CUJ-07.

### Consequences

* Good, потому что бэкап согласован на момент txid T без остановки записи.
* Good, потому что бэкап-файл имеет тот же формат, что и БД, и проверяется тем же верификатором.
* Good, потому что бэкап заодно уплотняет: копируются только живые страницы `[ДОПУЩЕНИЕ]`.
* Bad, потому что долгий бэкап удерживает снимок, и страницы, освобождённые после T, не переиспользуются — файл БД растёт на время бэкапа (docs/research/02, §2.4 п. 5); исследование предлагает лимит длительности читающей транзакции (например, 30 с), который бэкап на 25 ГБ превысит — исключение для бэкапа не решено (вопрос).
* Bad, потому что очистка (purge) не может перезаписать страницы, которые видит идущий бэкап (ADR 0012).
* Bad, потому что RPO восстановления из бэкапа — время с момента последнего бэкапа; RPO = 0 действует только для восстановления после сбоя процесса (ADR 0005).
* Bad, потому что срок хранения и ротация бэкапов в журнале не заданы (исследование предлагает не дольше 6 месяцев, docs/research/03, §6.5 п. 2, вывод исследователя).

### Confirmation

* Тест: во время бэкапа идёт поток записей; проверка бэкапа проходит, а его содержимое равно состоянию модели на txid T (property-тест, ADR 0015).
* Тест: повреждённый байт в бэкап-файле → проверка сообщает о повреждении с номером страницы.
* Тест: бэкап → purge → restore → очищенный контакт не находится (ADR 0012).
* Тест внедрения сбоя на каждом системном вызове бэкапа: незавершённый бэкап не оставляет файла, который выглядит готовым (rename только после fsync).
* SLO CUJ-07 (docs/cuj.md): 100 % бэкапов проходят проверку и пробное восстановление.

## Pros and Cons of the Options

### Онлайн-бэкап из снимка

* Good: согласованность, без остановки, тот же формат.
* Bad: долгий снимок удерживает страницы.

### Копирование файла ОС на ходу

* Good: ничего писать не нужно.
* Bad: копия не согласована — писатель меняет файл во время копирования `[ДОПУЩЕНИЕ]`.

### Только офлайн-бэкап

* Good: максимально просто.
* Bad: простой сервиса; противоречит D-025 (онлайн-бэкап входит в v1).

### Снимок ФС/тома

* Good: быстро.
* Bad: зависит от инфраструктуры; согласованность требует fsync и заморозки `[ДОПУЩЕНИЕ]`; не проверяется движком.
