# 0007. Модель данных: агрегат Contact с вложенными телефонами

## Status

Accepted, 2026-10-24. Решения D-009, D-014, D-016, D-022.

## Context and Problem Statement

BUDB — БД имён и телефонов. У человека бывает несколько телефонов, один номер бывает у нескольких людей (семейный телефон), у имён нет фиксированного числа частей, имена не уникальны (docs/research/03, §2.6, «Falsehoods about names» [S15]; §3.1). Имя и телефон — персональные данные, поэтому лишние поля нежелательны (docs/research/03, §6.5).

Какой агрегат хранить, как связать имя и телефон, какие поля и лимиты допустимы?

## Decision Drivers

* Простота и непротиворечивость агрегата (D-009).
* Поиск в обе стороны: имя → телефоны, телефон → имена (D-028: CUJ-01, CUJ-02).
* Минимизация ПДн (152-ФЗ ст. 5 ч. 5; GDPR ст. 5(1)(c), docs/research/03, §6.5).
* Предсказуемая раскладка страниц: запись не больше 1/3 страницы 4 KiB (docs/research/02, §7.1).
* Близость к стандартам: vCard и Google People API (docs/research/03, §3.1).

## Considered Options

1. **Contact с вложенным списком телефонов + инвертированный индекс `e164 → [contact_id]`** — выбрано.
2. **Отдельная сущность Phone со связью многие-ко-многим (ContactPhone)**, метка на связи.
3. **Плоская пара «имя — телефон»**, одна запись на пару.

## Decision Outcome

Выбран вариант 1 (D-009).

**Contact:**

* `id` — суррогатный идентификатор; только он задаёт идентичность (docs/research/03, §2.6). Формат id в журнале решений не зафиксирован — вопрос к оркестратору (исследование 03, §3.1 и §6.1 API1, предлагает неперечисляемый ULID/UUIDv7; исследование 02, §7.1 считало размеры для 8-байтного id).
* `display_name` — обязательное, в NFC, 1–256 кодовых точек и не больше 1024 байт UTF-8 (D-022).
* необязательные `given_name`, `family_name`, `middle_name` — не больше 128 кодовых точек каждое (D-022); для идентичности не используются (docs/research/03, §2.6).
* `phones[0..n]` — не больше 10 (D-022).
* `version` — номер версии для обнаружения конфликтов (ETag, ADR 0010; CUJ-04).
* `created`/`updated` — метки времени.

**Phone** (вложен в Contact):

* `e164` — каноническая строка `+` и 1–15 цифр; хранится строго E.164 (D-022, docs/research/03, §1.1);
* `extension` — не больше 10 цифр (D-022);
* `raw_input` — исходный ввод (для повторной нормализации при смене правил, docs/research/03, §1.2);
* `label` — `mobile` / `home` / `work` / `other` (D-009);
* `is_primary` — признак основного номера.

**Связи и индексы:** поиск по номеру — через инвертированный индекс `e164 → [contact_id]` (D-009); физически это дерево `phone_idx(digits‖id)` (ADR 0003). Один номер может принадлежать многим контактам.

**Дубликаты** разрешены; система показывает подсказку «возможные дубликаты». Слияние (merge) — v2 (D-009). Критерий «возможного дубликата» в журнале не задан; `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: совпадение поискового ключа имени (ADR 0009) или хотя бы одного `e164` с существующим контактом (по мотивам docs/research/03, §3.1).

**Чего нет:** свободного поля «заметка» (минимизация, D-016); vCard — v2 (D-016); мультиарендности — один экземпляр, одна телефонная книга (D-014).

`[ПРЕДЛОЖЕНИЕ АГЕНТА]` (в журнале не зафиксировано, вопрос к оркестратору): пара `(e164, extension)` уникальна в пределах одного контакта (docs/research/03, §3.1); у контакта не больше одного телефона с `is_primary = true`.

Обоснование (D-009): так делают vCard и Google People; это самый простой непротиворечивый агрегат. Обоснование лимитов (D-022): ограниченный размер записи даёт предсказуемую раскладку страниц и SLO; 256 кодовых точек хватает для длинных имён. Обоснование одной книги на экземпляр (D-014): контроль объёма; мультиарендность в ДЗ не требуется.

### Consequences

* Good, потому что весь контакт читается и пишется одной записью первичного дерева и меняется атомарно вместе с индексами (ADR 0003).
* Good, потому что максимальная запись около 1203 Б меньше 1/3 страницы; overflow-страницы не нужны (docs/research/02, §7.1, расчёт исследователя для 8-байтного id).
* Good, потому что «один номер у нескольких людей» поддержан индексом без отдельной сущности.
* Bad, потому что общий номер дублируется в каждом контакте; метка у одного номера может быть разной у разных контактов, и это нормально, но единого «владельца» номера нет.
* Bad, потому что без merge дубликаты накапливаются; есть только подсказка.
* Bad, потому что `raw_input` хранит ввод пользователя как есть; это тоже ПДн, и они подпадают под purge (ADR 0012).

### Confirmation

* Валидация входа: тесты на границы 0/1/256/257 кодовых точек и 1024/1025 байт для `display_name`, 128/129 для частей имени, 10/11 телефонов, 10/11 цифр добавочного номера (capability `contacts`).
* Property-тест: для любого набора контактов поиск по `e164` возвращает ровно те контакты, в которых этот номер есть (модель в памяти, ADR 0015).
* Ревью схем API: нет поля «заметка»; `id`, `version`, `created`, `updated` только для чтения (docs/research/03, §6.1 API3).

## Pros and Cons of the Options

### Вложенные телефоны + инвертированный индекс

* Good: просто, близко к vCard и People API (docs/research/03, §3.1, [S19], [S20]).
* Bad: общий номер дублируется.

### Phone как отдельная сущность (многие-ко-многим)

* Good: честнее моделирует «общий домашний номер», метка на связи (docs/research/03, §3.1).
* Bad: две сущности и связь; транзакции и purge сложнее (удалить контакт ≠ удалить номер).

### Плоская пара «имя — телефон»

* Good: тривиальная структура.
* Bad: контакт без телефона невозможен; правка имени требует обновить все пары.
