# 0017. Runtime, потоки и конфигурация: один бинарник `budb`, async HTTP + синхронный движок, TOML

## Status

Accepted, 2026-10-24. Решения D-032, D-033.

## Context and Problem Statement

HTTP-сервер удобно писать асинхронно (tokio/axum, docs/research/02, §5.1, [S58]), а движок — синхронный: один писатель и читатели на MVCC-снимках (ADR 0003), блокирующие `pread`/`pwrite`/fsync (ADR 0004, 0005). Исследование отмечает, что их нужно разделить (docs/research/02, §8 ADR-003, оценка исследователя). Под нагрузкой очередь к писателю не должна расти бесконечно. Сервер и Admin CLI (D-017) нужно поставлять и настраивать единообразно.

Как устроить процессы и потоки, связь async↔sync, поведение при перегрузке и конфигурацию?

## Decision Drivers

* Один писатель и group commit (D-018, ADR 0005).
* Предсказуемые хвосты задержек поиска (D-024).
* Явное поведение при перегрузке вместо бесконечных очередей.
* Простая поставка: один исполняемый файл.
* Читаемая конфигурация с переопределением в контейнерах `[ДОПУЩЕНИЕ]`.

## Considered Options

Потоки и связь с HTTP:

1. **Async HTTP (tokio/axum) + синхронный движок: один выделенный поток-писатель с очередью group commit и пул потоков-читателей; связь через ограниченные каналы; при переполнении — backpressure и 503/429** — выбрано.
2. **Async HTTP + вызов движка через `spawn_blocking`** на каждый запрос.
3. **Полностью асинхронный движок** (асинхронный I/O внутри движка).
4. **Синхронный HTTP-сервер «поток на соединение»** без tokio.

Конфигурация:

1. **Файл TOML + переопределение переменными окружения** — выбрано.
2. Только флаги командной строки.
3. Только переменные окружения.
4. YAML или JSON.

## Decision Outcome

**Бинарник и подкоманды (D-032):** один бинарник `budb` с подкомандами `serve` (HTTP-сервер: API и встроенный UI, ADR 0016) и `admin` (Admin CLI, D-017). CLI — clap (ADR 0006).

**Потоки (D-032):**

* HTTP — tokio/axum.
* Движок синхронный: **один выделенный поток-писатель** с очередью group commit (ADR 0005) и **пул потоков-читателей** на MVCC-снимках (ADR 0003).
* Связь async↔sync — через **ограниченные каналы**; при переполнении — backpressure и ответ 503/429.

`[ПРЕДЛОЖЕНИЕ АГЕНТА]` (вопрос к оркестратору): переполнение очереди движка (перегрузка сервера в целом) → **503** с `Retry-After`; превышение лимита конкретного клиента (rate limit по токену или IP) → **429** с `Retry-After` (docs/research/03, §4.6, [S24]). Размеры очередей, размер пула читателей и параметры пачки group commit (до K операций или T мс, docs/research/02, §3.7) — настраиваемые, значения по умолчанию не выбраны.

**Конфигурация (D-033):** файл TOML с переопределением через переменные окружения; крейт `toml` добавлен в allowlist (ADR 0006). `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: приоритет «значения по умолчанию < файл < переменные окружения»; путь к файлу задаётся флагом `--config`; переменные окружения с префиксом `BUDB_`; неизвестный ключ или недопустимое значение (например, срок корзины > 30 дней, ADR 0012) — ошибка при запуске, а не молчаливое игнорирование; секреты (пароль TLS-ключа и т. п.) не печатаются в логах.

**Admin CLI и эксклюзивная блокировка.** Файл БД эксклюзивно блокируется одним процессом (docs/research/02, §2.4 п. 7, DUR-9). `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: `budb admin` выполняет онлайн-операции через admin-API работающего сервера, а офлайн-операции (восстановление, офлайн-проверка, уплотнение, создание первого администратора до первого запуска) — напрямую по файлу при остановленном сервере (ADR 0013). Вынесено в вопросы.

Почему не `spawn_blocking`: он не даёт единственного писателя и пачек group commit без отдельной очереди; число блокирующих задач ограничивается пулом tokio, а не политикой движка `[ДОПУЩЕНИЕ]`. Почему не асинхронный движок: усложняет движок и детерминированную симуляцию (ADR 0015) `[ДОПУЩЕНИЕ]`. Почему не «поток на соединение»: HTTP-стек пришлось бы писать или брать другой, а tokio/hyper/axum уже в allowlist (D-021).

### Consequences

* Good, потому что движок остаётся синхронным и детерминированно тестируемым; async-код не проникает в него.
* Good, потому что перегрузка видна клиенту сразу (503/429 с `Retry-After`), а память не растёт под очередями.
* Good, потому что один бинарник проще поставлять; CLI и сервер используют один и тот же внутренний слой движка (D-017).
* Good, потому что TOML читаем, а переменные окружения удобны в контейнерах `[ДОПУЩЕНИЕ]`.
* Bad, потому что пропускная способность записи ограничена одним потоком-писателем (цель ≥ 500 записей/с, D-024).
* Bad, потому что неверно выбранные размеры очередей дают либо лишние 503, либо рост хвостов задержек; значения нужно подбирать бенчмарком.
* Bad, потому что два источника конфигурации (файл и окружение) требуют однозначного правила приоритета и его тестов.

### Confirmation

* Нагрузочный тест: при заполненной очереди писателя новые записи получают 503 с `Retry-After`, процесс не растёт по памяти, уже принятые записи подтверждаются только после fsync.
* Тест: поток-писатель единственный — две записи никогда не фиксируются параллельно (проверка в симуляции, ADR 0015).
* Бенчмарк на эталонном стенде: ≥ 5 000 поисков/с и ≥ 500 зафиксированных записей/с при профиле 95/5 (D-024).
* Тест конфигурации: значение из переменной окружения перекрывает значение из файла; неизвестный ключ — ошибка запуска.
* cargo-deny: `toml` в allowlist, других парсеров конфигурации нет (ADR 0006).

## Pros and Cons of the Options

### Async HTTP + писатель + пул читателей + ограниченные каналы

* Good: единственный писатель, group commit, явный backpressure.
* Bad: больше кода связки.

### spawn_blocking

* Good: минимум кода.
* Bad: нет естественной точки для пачек и единственного писателя `[ДОПУЩЕНИЕ]`.

### Асинхронный движок

* Good: нет переключений между мирами.
* Bad: сложнее движок и симуляция `[ДОПУЩЕНИЕ]`.

### Поток на соединение

* Good: простая модель.
* Bad: не использует разрешённый HTTP-стек; плохо масштабируется по числу соединений `[ДОПУЩЕНИЕ]`.

### TOML + переменные окружения

* Good: читаемый файл и удобные переопределения.
* Bad: два источника, нужно правило приоритета.

### Только флаги / только окружение / YAML или JSON

* Good: меньше зависимостей (флаги — clap уже есть; JSON — serde_json уже есть).
* Bad: длинные командные строки; плоские переменные плохо выражают вложенность; YAML — ещё одна зависимость; JSON без комментариев неудобен для людей `[ДОПУЩЕНИЕ]`.
