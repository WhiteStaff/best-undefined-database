# 0018. Изоляция `unsafe` в крейте `budb-sys`

## Status

Accepted, 2026-10-24. Решение D-090. Частично заменяет ADR 0002: правило «`#![forbid(unsafe_code)]` во всех крейтах» из ADR 0002 и D-020 заменено правилом этого ADR. Остальные решения ADR 0002 (Rust stable, MSRV ≥ 1.89, edition 2024, отклонённые языки) действуют.

## Context and Problem Statement

ADR 0002 запретил `unsafe` во всех крейтах и предположил, что системные вызовы можно делать через std и тонкие привязки `libc` и `windows-sys`, потому что «`unsafe` внутри привязок» (там же это помечено `[ДОПУЩЕНИЕ]`). Ревью эксперта по хранению опровергло это допущение (EX1-06):

* функции `libc` и `windows-sys` (`libc::fcntl`, `MoveFileExW` и др.) объявлены как `unsafe fn`; вызвать их можно только из `unsafe`-блока в нашем собственном крейте;
* std не даёт `MOVEFILE_WRITE_THROUGH` для rename на Windows, а он нужен для долговечной атомарной подмены (STO-14, STO-15; fact-check EX1 F4: `std::fs::rename` на Windows этот флаг не использует);
* аппаратную CRC32C с выбором реализации во время выполнения без `unsafe` не получить: intrinsics безопасны только там, где фича процессора включена на этапе компиляции (fact-check EX1 F16, подтверждено частично, вторичный источник);
* `fallocate` и `F_BARRIERFSYNC` в std тоже нет (EX1, рубрика п. 8).

Значит, требование BLD-07 «`forbid(unsafe_code)` во всех крейтах» несовместимо с BLD-02 (`libc`, `windows-sys` в allowlist), STO-15 (`MOVEFILE_WRITE_THROUGH`) и BLD-08 (аппаратная CRC32C). Как сохранить безопасность памяти и проверяемость, не отказываясь от нужных системных вызовов?

## Decision Drivers

* Безопасность памяти — главный довод в пользу Rust (ADR 0002, D-020).
* Долговечность rename на Windows (STO-15, ADR 0014) и производительность CRC32C (BLD-08).
* Проверяемость: граница `unsafe` должна находиться механически, а не по ревью всего кода.
* Минимальная поверхность `unsafe`: только FFI и intrinsics, никакой собственной работы с сырыми указателями в движке.

## Considered Options

1. **Один изолированный крейт `budb-sys`** с `unsafe`, `forbid(unsafe_code)` во всех остальных крейтах — выбрано.
2. **Оставить `forbid(unsafe_code)` везде** и отказаться от `MOVEFILE_WRITE_THROUGH`, аппаратной CRC32C и вызовов `libc`.
3. **Разрешить `unsafe` по месту** в любом крейте с комментарием `SAFETY`.
4. **Взять сторонний «безопасный» крейт-обёртку** (например, для CRC32C или файловых операций).

## Decision Outcome

Выбран вариант 1 (D-090):

* `#![forbid(unsafe_code)]` стоит во всех крейтах рабочего пространства, кроме одного — `budb-sys`.
* `budb-sys` содержит только FFI и intrinsics:
  * `MoveFileExW` с `MOVEFILE_WRITE_THROUGH` (Windows);
  * аппаратные intrinsics CRC32C с определением возможностей процессора во время выполнения; результат обязан совпадать с табличной реализацией (BLD-08);
  * любые вызовы `libc`.
* `budb-sys` наружу отдаёт только безопасный API; остальные крейты вызывают его без `unsafe`.
* У каждого `unsafe`-блока есть комментарий `// SAFETY:` с инвариантами, на которых держится корректность.
* Тесты `budb-sys` прогоняются под Miri там, где он применим (FFI Miri не исполняет; intrinsics и обвязка вокруг них — по возможности).
* Любое изменение `budb-sys` проходит ревью двумя рецензентами.
* Новый `unsafe` вне `budb-sys` по-прежнему возможен только через новый ADR.

Почему не вариант 2: без `MOVEFILE_WRITE_THROUGH` долговечность rename на Windows ещё слабее (ADR 0014), а без `libc` нельзя сделать `fcntl`/`fallocate`; табличная CRC32C медленнее аппаратной. Почему не вариант 3: граница `unsafe` размывается, проверить её механически нельзя. Почему не вариант 4: сторонний крейт переносит `unsafe` в чужой код и расширяет allowlist (ADR 0006); для CRC32C это ещё и противоречит правилу «собственная реализация» (D-021).

### Consequences

* Good, потому что весь `unsafe` проекта сосредоточен в одном небольшом крейте, и его можно проверить целиком.
* Good, потому что движок, домен, сервер и CLI сохраняют `forbid(unsafe_code)` и гарантии компилятора.
* Good, потому что становятся доступны `MOVEFILE_WRITE_THROUGH`, аппаратная CRC32C и вызовы `libc`, нужные STO-14, STO-15 и BLD-08.
* Bad, потому что в проекте появляется собственный `unsafe`: ошибка в `budb-sys` может нарушить безопасность памяти всего процесса.
* Bad, потому что Miri не исполняет FFI, и часть `budb-sys` проверяется только ревью и интеграционными тестами.
* Neutral: ADR 0002 частично заменён; правило BLD-07 нужно переформулировать (редактор спецификаций, D-090).

### Confirmation

* CI проверяет, что `#![forbid(unsafe_code)]` (или lint `unsafe_code = "forbid"`) действует в каждом крейте, кроме `budb-sys`, и что ключевое слово `unsafe` встречается только в `budb-sys` `[ПРЕДЛОЖЕНИЕ АГЕНТА: способ проверки]`.
* CI проверяет, что перед каждым `unsafe`-блоком в `budb-sys` есть комментарий `// SAFETY:` (lint `clippy::undocumented_unsafe_blocks`) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
* Property-тест «аппаратная CRC32C = табличная» на случайных буферах (BLD-08, `tasks.md` 2.1).
* Прогон Miri для тестов `budb-sys`, где он применим.
* Правило ревью двумя рецензентами для изменений в `budb-sys` закреплено в настройках защищённой ветки (CODEOWNERS) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.

## Pros and Cons of the Options

### Один изолированный крейт `budb-sys`

* Good: граница `unsafe` проверяется механически; нужные системные вызовы доступны.
* Bad: собственный `unsafe` в проекте; нужна дисциплина ревью.

### `forbid(unsafe_code)` везде

* Good: никакого собственного `unsafe`.
* Bad: нельзя вызвать `libc` и `windows-sys`, хотя они в allowlist; нет `MOVEFILE_WRITE_THROUGH` и аппаратной CRC32C (EX1-06).

### `unsafe` по месту

* Good: просто писать.
* Bad: `unsafe` расползается по движку; механической границы нет.

### Сторонний крейт-обёртка

* Good: `unsafe` не в нашем коде.
* Bad: расширение allowlist; для CRC32C противоречит D-021; качество чужого `unsafe` не контролируется.
