# 0003. Движок хранения: copy-on-write B+tree с двумя мета-страницами

## Status

Accepted, 2026-10-24. Решение D-018 (с учётом D-024 и D-025).

## Context and Problem Statement

BUDB хранит контакты (ADR 0007) и ищет точно и по префиксу в двух направлениях: имя → телефоны и телефон → имена (D-011, D-028: CUJ-01, CUJ-02). Цель проектирования — 10^8 контактов на одном узле, файл около 25 ГБ; SLO проверяются на 10^7 записей (D-024). Профиль нагрузки — 95 % чтений и 5 % записей `[ДОПУЩЕНИЕ, источника нет]` (D-024). Надёжность — главное требование (ADR 0005), использовать существующие движки нельзя (ADR 0006). Онлайн-бэкап должен быть согласованным (D-025).

Какую структуру хранения написать с нуля, чтобы получить упорядоченные индексы, простое и доказуемое восстановление после сбоя и дешёвые снимки для читателей и бэкапа?

## Decision Drivers

* Нужен упорядоченный индекс: префиксный поиск по имени и по цифрам телефона (docs/research/02, §0.1).
* Корректность восстановления важнее скорости записи (D-019).
* Объём кода «с нуля» должен быть посильным (docs/research/02, §2.2, оценка исследователя).
* Снимки для читателей и онлайн-бэкапа (D-025, CUJ-07).
* RAM на 10^8 записей: внутренние узлы должны помещаться в память (docs/research/02, §7.2).

## Considered Options

1. **(a) Bitcask** — append-only лог и хеш-таблица keydir в RAM.
2. **(b) B+tree с обновлением страниц на месте и WAL** (как SQLite/PostgreSQL).
3. **(c) Copy-on-write B+tree с теневой страничной адресацией и двумя мета-страницами** (как LMDB/bbolt/redb) — выбрано.
4. **(d) LSM-tree с WAL** (как LevelDB/RocksDB).

## Decision Outcome

Выбран вариант (c) (D-018):

* **Структура:** copy-on-write B+tree с теневой страничной адресацией (shadow paging). Изменённые страницы пишутся в новое место; старые не перезаписываются, пока их видит хоть один читатель (docs/research/02, §2.1 (c), [S3], [S4]).
* **Две мета-страницы**, у каждой свой CRC32C и txid. При открытии выбирается валидная мета-страница с наибольшим txid. Атомарной записи указателя не доверяем: ALICE нашёл у LMDB единственную уязвимость именно в предположении об атомарности финальной записи указателя (docs/research/02, §2.1 (c), [S25]).
* **Страницы по 4 KiB, CRC32C на каждой странице** (docs/research/02, §2.4 п. 3).
* **Три дерева в одном файле**, меняются одной атомарной транзакцией: `primary(id)`, `name_idx(key‖id)`, `phone_idx(digits‖id)`.
* **Один писатель и читатели на MVCC-снимках**; снимок — корень дерева на конкретном txid (docs/research/02, §2.2, [S3], [S4]). Модель потоков — ADR 0017.
* **Переиспользование свободных страниц** только после того, как их перестал видеть самый старый живой читатель (docs/research/02, §2.4 п. 5).
* **Group commit** (протокол — ADR 0005).
* **Офлайн-уплотнение:** копирование живого дерева → fsync → rename → fsync каталога (паттерн etcd defrag, docs/research/02, §2.4 п. 6, [S52]).
* **Без mmap**, собственный кэш страниц — ADR 0004.
* **Эксклюзивная блокировка файла** одним процессом (docs/research/02, §2.4 п. 7, §3.8 DUR-9).

Почему отклонены альтернативы (D-018):

* (a) Bitcask — нет префиксного поиска (хеш-индекс, [S1]); около 21,5 ГБ RAM при 10^8 записей с вторичными индексами в памяти (docs/research/02, §2.2, расчёт исследователя).
* (b) B+tree с WAL — больше кода восстановления: redo/undo, checkpoint, защита от порванных страниц (full_page_writes, [S10]); MVCC нужно делать отдельно (docs/research/02, §2.1 (b)).
* (d) LSM — усиление записи около 33× в примере RocksDB Tuning Guide ([S7]); сложная компактизация и манифест; у LevelDB ALICE нашёл уязвимости при дозаписи лога и компактизации ([S25]) (docs/research/02, §2.1 (d)).

### Consequences

* Good, потому что восстановление без переигровки журнала: достаточно выбрать новейшую валидную мета-страницу (docs/research/02, §8 ADR-001, [S3], [S5]); отсюда SLO повторного открытия p99 ≤ 1 с (D-024).
* Good, потому что снимки достаются из структуры — это основа онлайн-бэкапа (D-025, ADR 0013).
* Good, потому что префиксный поиск естественен для упорядоченного дерева.
* Good, потому что внутренние узлы трёх деревьев на 10^8 записей занимают около 155 МБ и помещаются в RAM (docs/research/02, §7.2, расчёт исследователя).
* Bad, потому что высокое усиление записи на одиночном коммите: около 16 страниц по 4 KiB на запись ≈ 70 Б, WA ≈ 900×; group commit из 100 вставок снижает его примерно до 200× (docs/research/02, §2.3, расчёт исследователя). Это главный компромисс выбора (RUM-гипотеза, [S9]).
* Bad, потому что файл не уменьшается без уплотнения (docs/research/02, §2.1 (c), [S3]).
* Bad, потому что писатель один: пропускная способность записи ограничена одним потоком (цель ≥ 500 записей/с, D-024).
* Bad, потому что долгие читатели (в том числе бэкап) удерживают страницы, и файл растёт; нужен лимит длительности читающей транзакции (docs/research/02, §2.4 п. 5). Конкретный лимит и исключение для бэкапа не решены — вопрос к оркестратору.

### Confirmation

* Офлайн-верификатор проверяет CRC всех страниц, упорядоченность ключей, согласованность трёх деревьев (каждый id из индексов есть в primary и наоборот) и учёт freelist (docs/research/02, §4, «Офлайн-верификатор»); запускается в CI после каждого сценария (ADR 0015).
* Модельные property-тесты сравнивают поиск (включая префиксный) с моделью в памяти (ADR 0015).
* Бенчмарк на эталонном стенде (4 vCPU, 8 ГБ RAM, NVMe, 10^7 записей) подтверждает SLO из D-024 (capability `performance-capacity`).
* Ревью: спецификация `storage-engine` МОЖЕТ называть эти механизмы (D-030).

## Pros and Cons of the Options

### (a) Bitcask

* Good: простое восстановление по CRC хвоста; 1 seek на чтение (docs/research/02, §2.2, [S1]).
* Bad: нет префиксного поиска; keydir обязан помещаться в RAM (docs/research/02, §2.1 (a), [S1], [S2]).

### (b) B+tree + WAL

* Good: зрелый подход, умеренное усиление записи.
* Bad: сложное восстановление, защита от порванных страниц, отдельный MVCC (docs/research/02, §2.2).

### (c) COW B+tree, две мета-страницы

* Good: простое восстановление, снимки из структуры, префиксный поиск (docs/research/02, §2.2).
* Bad: усиление записи, один писатель, рост файла (docs/research/02, §2.3, §8 ADR-001).

### (d) LSM + WAL

* Good: оптимизирован под запись.
* Bad: усиление записи 10–33×, префиксные сканы по уровням, сложная компактизация (docs/research/02, §2.2, [S7]).

## Изменения после ревью 2026-10-24

По D-005 принятый ADR не переписывается: текст выше оставлен как был, а решения, принятые после его написания и затрагивающие этот ADR, перечислены здесь (разбор ревью раунда 1 — `docs/reviews/GOLDFISH.md`, полный текст решений — `docs/orchestrator-decisions.md`). Этот раздел добавлен решением D-114: ADR 0003, 0006, 0013, 0014, 0015, 0016 и 0017 ранее были затронуты решениями только в деталях. При расхождении с текстом выше действует этот раздел.

* **Повреждение новейшей мета-страницы (D-035).** Писатель один, поэтому потерять можно не больше одной транзакции. Автоматический откат к более старой мета-странице разрешён только для txid = valid_max+1. Такой откат ОБЯЗАТЕЛЬНО записывается в лог с обоими txid, увеличивает метрику…
* **Курсор пагинации (D-048).** Курсор — keyset (ключ сортировки + id), непрозрачный, действителен 24 ч и НЕ привязан к снимку: каждая страница читается на свежем снимке. Гарантия: для неизменившихся элементов нет дубликатов и пропусков. Из SRCH-11 нужно убрать «все страницы с одного…
* **Механика purge (D-056).** Транзакция purge N освобождает страницы. Затем движок принудительно выполняет коммит N+1, чтобы старая мета-страница больше не ссылалась на них. Страницы заполняются нулями и сбрасываются на устройство, как только txid самого старого читателя > N. T_purge =…
* **Правило отката к старой мета-странице (D-063).** Полям слота с неверной CRC доверять нельзя. Если валидна ровно одна мета-страница (txid V), второй слот считается порванным коммитом V+1: автоматический откат с записью в лог, метрикой и алертом. Если обе мета-страницы невалидны — отказ в открытии.
* **Затирание на простаивающей системе (D-070).** если есть ожидающий purge, движок по таймеру выполняет внутренние пустые (no-op) коммиты, чтобы затирание завершилось в пределах T_purge = 24 ч даже без пользовательских записей.
* **Purge производных форм (D-077).** Коммит purge переписывает (COW) все страницы, где есть ключи очищенного контакта, включая разделители внутренних узлов, производные от этих ключей. Тест PRV-06 и verify сканируют весь файл на каждую производную форму: `display_name` в NFC, ключ NFKC_Casefold…
* **Заголовок страницы и указатель на дочернюю страницу (D-085).** Заголовок страницы = {magic/тип, `page_no`, `write_txid`, CRC32C по всей странице}. Указатель на дочернюю страницу = (`page_no`, ожидаемый `write_txid`). Так обнаруживаются misdirected и lost writes (FAST'17, FAST'13). Это формат v1.
* **Число страниц файла в мета-странице (D-086).** мета-страница хранит `page_count` — high-water mark файла. Страницы с номером ≥ `page_count` verify не учитывает, а при открытии файл обрезается до `page_count`.
* **Отложенные страницы после перезапуска (D-087).** исправить `design.md` §4.1 шаг 6: после перезапуска отложенные страницы по-прежнему подчиняются правилу переиспользования T+2.
* **Freelist как COW-дерево `free_db` (D-091).** freelist — COW-дерево `free_db(freeing_txid → [page_no])` по образцу FREE_DBI в LMDB. Его собственные страницы учитываются в том же коммите.
* **Кооперативный отзыв снимка (D-092).** отзыв снимка кооперативный. Читатель проверяет флаг отзыва при каждой выборке страницы и прерывается с ошибкой. Страницы переиспользуются только после того, как читатель снял регистрацию.
* **Лимит объёма удерживаемых страниц (D-093).** лимит объёма страниц, удерживаемых снимками (по умолчанию 25 % файла, настраивается), тоже запускает отзыв самого старого читателя.
* **Пересчёт SLO и ёмкости (D-094).** Признано усиление записи около 55–70 страниц на коммит. Долговечная запись: p50 ≤ 15 мс, p99 ≤ 60 мс. fsync намерения аудита идёт параллельно с fsync данных, последовательных сбросов два. ≥ 500 записей/с через group commit — без изменений. Размер файла: ≤ 4…
* **Затирание всех освобождённых страниц; `subjects:erase` (D-102).** Zero-on-free: ВСЕ освобождённые страницы заполняются нулями, как только их перестают удерживать (тот же асинхронный механизм, что и для purge, ≤ T_purge). После PUT в файле не остаётся старых ПДн. Операция стирания данных субъекта `subjects:erase` также…
* **Перезапись мета-страницы на месте и `db_lineage_id` (D-107).** Выбранный слот мета-страницы при открытии переписывается на месте с fsync (STO-34), другой слот получает следующий коммит (STO-04); `db_lineage_id` хранится в мета-странице (STO-38).
* **Срок корзины и единые имена (D-111).** Затирание корзины включено в срок: ≤ 24 ч после истечения срока корзины вместе с физическим zero-fill, итого ≤ 30 суток.
