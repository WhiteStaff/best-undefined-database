# 0008. Нормализация телефонов: собственный разбор и проверка «возможного номера»

## Status

Accepted, 2026-10-24. Решения D-010, D-022.

## Context and Problem Statement

Оператор вставляет номер в любом формате — «8 (916) 123-45-67», «+7 916 1234567», полноширинными цифрами (CUJ-01). Хранится строго E.164 (D-022), а поиск идёт по строке цифр (ADR 0003). Эталонная библиотека libphonenumber требует постоянно обновляемых метаданных (docs/research/03, §1.3), а политика «с нуля» (ADR 0006) ограничивает зависимости.

Как превращать ввод в E.164 и что считать допустимым номером?

## Decision Drivers

* Хранить канонический вид для точного и префиксного поиска (docs/research/02, §0.1; docs/research/03, §1.1).
* Не зависеть от постоянно меняющихся метаданных (docs/research/03, §1.3).
* Принимать национальный ввод с регионом по умолчанию (D-022).
* Детерминированность и тестируемость правил.

## Considered Options

1. **Собственный разбор + проверка «возможности» (код страны ITU, ≤ 15 цифр), таблица длин только для `+7`** — выбрано.
2. **Строгий E.164 на входе** (только `+` и цифры, без национальных форматов).
3. **Порт libphonenumber** с полными метаданными (isValidNumber, тип номера).
4. **Хранить ввод как есть**, без нормализации.

## Decision Outcome

Выбран вариант 1 (D-010). Шаги разбора:

1. **NFKC** — полноширинные цифры становятся ASCII (docs/research/03, §1.5 п. 1, [S10]).
2. **Удаление разделителей** (пробел, `-`, `.`, `(`, `)`, `/`, NBSP) и отделение добавочного номера по маркерам (`;ext=`, `ext`, `ext.`, `x`, `доб.`, `#`) (docs/research/03, §1.5 п. 1). Точный набор маркеров в журнале не зафиксирован — `[ПРЕДЛОЖЕНИЕ АГЕНТА]` взять набор из исследования.
3. **Разбор международного префикса** `+` / `00` / `810` (D-010).
4. **Регион по умолчанию** настраивается; по умолчанию RU: `8XXXXXXXXXX` → `+7XXXXXXXXXX` (D-010; транковый префикс 8 — docs/research/03, §1.4, [S6]).
5. **Проверка «возможного номера»:** код страны входит в список ITU (все страны), всего не больше 15 цифр (D-010; docs/research/03, §1.1, [S1], [S8]). Таблица национальных длин в v1 есть только для `+7` (национальный номер РФ — 10 цифр, docs/research/03, §1.4, [S6]); таблицу можно расширять.
6. Результат хранится как `e164`, добавочный номер — отдельно (≤ 10 цифр), исходный ввод — в `raw_input` (D-022, ADR 0007).

Вне скоупа: isValid (проверка диапазонов) и тип номера (D-010); короткие номера и форматирование по шаблонам стран (docs/research/03, §1.5 п. 5).

Не решено в журнале и вынесено в вопросы: `7XXXXXXXXXX` (11 цифр без `+`) — исследование помечает правило `[НЕ ПОДТВЕРЖДЕНО]` (docs/research/03, §1.4); `10 цифр` → `+7` — рекомендация исследования; нормализация префикса для префиксного поиска («8916» → «+7916»); версия списка кодов стран ITU (последнее найденное издание 2016 года плюс Operational Bulletins, docs/research/03, §1.1, [S8]).

Обоснование (D-010): libphonenumber нужны постоянно обновляемые метаданные; кроме того, действует ограничение «с нуля».

### Consequences

* Good, потому что правила короткие, детерминированные и полностью покрываются таблицей тест-примеров.
* Good, потому что «возможный номер» не устаревает так быстро, как «валидный»: libphonenumber-js сам предпочитает `isPossible()` — «its strength is in its weakness» (docs/research/03, §1.3, [S5]).
* Good, потому что `+7` у России и Казахстана общий, и проверка длины для `+7` покрывает оба (docs/research/03, §1.1, [S6]).
* Bad, потому что несуществующий, но «возможный» номер будет принят; тип номера неизвестен.
* Bad, потому что `00` как международный префикс верен не везде (в NANP это не IDD, docs/research/03, §1.3, [S4]); при регионе по умолчанию не RU правила могут ошибаться.
* Bad, потому что номера длиннее 15 цифр (встречаются, например, в Германии) будут отвергнуты (docs/research/03, §1.1, [S2]).
* Bad, потому что список кодов стран ITU нужно обновлять вручную.

### Confirmation

* Таблица тест-векторов «ввод → e164 / extension / ошибка» для всех правил выше, включая полноширинные цифры, `810`, `00`, добавочные номера и номер из 16 цифр (capability `phone-normalization`).
* Property-тест: нормализация идемпотентна — нормализация уже нормализованного `e164` даёт тот же `e164` `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
* Ревью: в зависимостях нет libphonenumber-подобных крейтов (cargo-deny, ADR 0006).

## Pros and Cons of the Options

### Собственный разбор + «возможный номер»

* Good: без внешних метаданных, детерминированно.
* Bad: принимает несуществующие номера.

### Строгий E.164 на входе

* Good: минимум кода.
* Bad: противоречит D-022 (национальные форматы принимаются); оператору неудобно (CUJ-01).

### Порт libphonenumber

* Good: полная проверка и тип номера (docs/research/03, §1.3, [S3]).
* Bad: большие постоянно меняющиеся метаданные (около 80–145 КБ даже у упрощённой версии, docs/research/03, §1.3, [S5]); противоречит D-010.

### Ввод как есть

* Good: ничего не теряется.
* Bad: поиск по номеру невозможен без канонической формы.
