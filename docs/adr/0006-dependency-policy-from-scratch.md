# 0006. Политика зависимостей «с нуля» (NFR-SCRATCH)

## Status

Accepted, 2026-10-24. Решения D-021 (с исключением для криптографии из D-015 и добавлением `toml` по D-033; веб-UI без UI-фреймворков и CDN — D-031).

## Context and Problem Statement

Входное условие ДЗ: БД написана с нуля, существующие СУБД, KV-хранилища, движки индексов, WAL и транзакций использовать нельзя. При этом HTTP, TLS и хеширование паролей переписывать опасно и не нужно: это не ядро БД (D-015).

Где проходит граница «с нуля» и как проверять её механически, а не на ревью?

## Decision Drivers

* Критерий «с нуля» должен проверяться механически, в CI (D-021).
* Собственную криптографию писать нельзя (D-015).
* Формат на диске специфицируется и пишется вручную, без библиотек сериализации (docs/research/02, §6.3).
* Минимальная цепочка поставок (D-031).

## Considered Options

1. **Allowlist крейтов + проверка `cargo deny check bans`** в CI; явный denylist как подстраховка — выбрано.
2. **Только denylist** (запрещаем известные движки, остальное можно).
3. **Ноль сторонних зависимостей**, включая HTTP, TLS и криптографию.
4. **Ручное ревью** зависимостей без автоматической проверки.

## Decision Outcome

Выбран вариант 1 (D-021). Правило NFR-SCRATCH (по формулировке docs/research/02, §6.1): весь код постоянного хранения — формат файла и страниц, B+tree и дисковые индексы, аллокатор страниц и freelist, протокол коммита и восстановления, MVCC и снимки, кэш страниц, поиск — пишется в этом проекте. Сторонние библиотеки допустимы только из allowlist; в режиме allow всё, что не в списке, запрещено (docs/research/02, §6.2, [S57]).

**Разрешены (runtime):**

* tokio, hyper/axum — HTTP (ADR 0017);
* serde/serde_json — только для API, НЕ для формата на диске;
* clap — CLI;
* tracing — логирование;
* unicode-normalization — нормализация Unicode (ADR 0008, 0009);
* libc/windows-sys — тонкие привязки к ОС;
* проверенная криптография по D-015: rustls (TLS), argon2 (хеш паролей) — ADR 0011;
* toml — разбор файла конфигурации (D-033, ADR 0017).

**Только для тестов:** proptest, cargo-fuzz, rand_chacha (ADR 0015).

**Запрещены:** любые крейты СУБД, KV, индексов, WAL, транзакций, движков запросов и ORM (rusqlite, rocksdb, lmdb/heed, sled, redb, fjall, tantivy и т. п.); bincode/rkyv для формата на диске; memmap2 (ADR 0004). Полный denylist-фрагмент — docs/research/02, §6.3.

**Пишется самостоятельно:**

* CRC32C — собственная реализация, проверенная по тест-векторам RFC 3720 (D-021; что тест-векторы находятся именно в RFC 3720, исследование помечает `[НЕ ПОДТВЕРЖДЕНО]`, docs/research/02, §9 Q5);
* таблица case folding генерируется из закреплённого `CaseFolding.txt` (данные UCD, Unicode 16.0, D-021) — ADR 0009.

**Веб-UI** (D-031, ADR 0016): без UI-фреймворков и CDN; ассеты встраиваются в бинарник средствами std (`include_bytes!`/`include_str!`, docs/research/02, §6.2). Инструменты сборки TypeScript — вопрос к оркестратору (см. ADR 0016).

Обоснование (D-021): критерий «с нуля» должен проверяться механически (cargo-deny); HTTP и криптографию не переписываем — это не ядро БД и высокий риск.

### Consequences

* Good, потому что нарушение политики ломает сборку CI, а не ждёт ревью.
* Good, потому что allowlist защищает и от транзитивных зависимостей: всё, чего нет в списке, запрещено (docs/research/02, §6.2, [S57]).
* Good, потому что формат на диске описан нами и не зависит от версий чужих сериализаторов.
* Bad, потому что транзитивные зависимости разрешённых крейтов (tokio, hyper, rustls и др.) придётся перечислить после фиксации `Cargo.lock` (docs/research/02, §6.2); allowlist в D-021 их не перечисляет — вопрос к оркестратору.
* Bad, потому что крейты, которые исследование предлагало (`tower`, `tower-http`, `tracing-subscriber`, `thiserror`, `tempfile`, `criterion`, `proptest-state-machine`, docs/research/02, §6.2), в D-021 не названы; без решения оркестратора они запрещены.
* Bad, потому что каждое добавление крейта требует нового решения и ADR (docs/research/02, §8 ADR-004).
* Bad, потому что для хеширования API-токенов, CSPRNG и HMAC курсоров пагинации (ADR 0010, 0011) нужен конкретный крейт; D-021 называет только rustls и argon2 — вопрос к оркестратору.

### Confirmation

* CI выполняет `cargo deny check bans` с `deny.toml` в режиме allowlist; сборка падает на любом крейте вне списка (docs/research/02, §6.2, [S57]).
* Юнит-тест CRC32C на тест-векторах; тест сравнивает сгенерированную таблицу case folding с закреплённым файлом `CaseFolding.txt` (контрольная сумма файла хранится в репозитории) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
* Ревью: `serde` не используется в модулях формата на диске (поиск по исходникам модулей движка) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`.
* Требование-ограничение в capability `build-constraints` ссылается на этот ADR.

## Pros and Cons of the Options

### Allowlist + cargo-deny

* Good: механическая проверка, защита от транзитивных зависимостей.
* Bad: нужно поддерживать список.

### Только denylist

* Good: меньше работы.
* Bad: новый движок с незнакомым именем пройдёт незамеченным; существование каждого крейта из denylist не проверялось (docs/research/02, §6.3, `[НЕ ПОДТВЕРЖДЕНО]`).

### Ноль зависимостей

* Good: максимальная «чистота».
* Bad: собственный TLS и криптография запрещены D-015 как высокий риск.

### Ручное ревью

* Good: гибкость.
* Bad: критерий не проверяется механически, что противоречит D-021.
