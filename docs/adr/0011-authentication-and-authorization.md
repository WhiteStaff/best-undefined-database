# 0011. Аутентификация и авторизация: локальные учётные записи, роли, cookie-сессия для UI и bearer-токены для API

## Status

Accepted, 2026-10-24. Решения D-015, D-014 (с учётом D-021: крипто-исключение в политике зависимостей).

## Context and Problem Statement

В BUDB работают оператор и редактор через UI, интегратор через API, администратор и ответственный за ПДн (docs/research/03, §7.3). Одна телефонная книга на экземпляр (D-014). Сломанная аутентификация и авторизация на уровне функций — риски API2 и API5 OWASP API Top 10 (docs/research/03, §6.1, [S41]). Администратор управляет пользователями и доступом (CUJ-10).

Как пользователи и программы подтверждают личность и какие права у них есть?

## Decision Drivers

* Разделение прав: чтение, изменение, администрирование (docs/research/03, §6.2).
* Защита UI от CSRF и XSS (docs/research/03, §6.4).
* Никакой собственной криптографии (D-015).
* Секреты не хранятся в открытом виде; токены не передаются в URL (docs/research/03, §6.2, [S42]).

## Considered Options

1. **Локальные учётные записи с ролями reader/writer/admin; UI — логин/пароль + cookie-сессия; API — bearer-токены, хранящиеся как хеши** — выбрано.
2. **Только API-токены**, в UI токен вставляется в форму.
3. **Внешний провайдер (OIDC/SSO).**
4. **mTLS-сертификаты клиентов.**

## Decision Outcome

Выбран вариант 1 (D-015):

* **Роли:** reader (поиск и чтение), writer (+ создание, изменение, удаление, импорт), admin (+ экспорт, токены и пользователи, бэкапы, метрики, purge, аудит) — распределение действий по ролям по docs/research/03, §6.2 `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: D-015 называет роли, но не матрицу прав.
* **UI:** вход по логину и паролю, затем сессионная cookie с префиксом `__Host-`, CSRF-токен и проверка `Sec-Fetch-Site` (D-015). Атрибуты `Secure; HttpOnly; SameSite=Strict; Path=/`, ID сессии из CSPRNG (≥ 64 бит, лучше 128), idle-таймаут 15–30 мин, абсолютный 4–8 ч (docs/research/03, §6.2, [S47]) — значения из рекомендации OWASP; конкретные числа не выбраны оркестратором (вопрос).
* **API:** `Authorization: Bearer <token>`; в хранилище лежат только хеши токенов (D-015); токен не передаётся в URL (docs/research/03, §6.2, [S42]).
* **Пароли** хешируются проверенной библиотекой (argon2, D-021); **TLS** — через rustls (D-021). Собственную криптографию писать нельзя; это явное исключение в политике зависимостей (D-015, ADR 0006).
* **Первый администратор** создаётся через Admin CLI (docs/research/03, §6.2; D-017).
* **Аудит** событий безопасности (вход, отказ, выдача и отзыв токена) — без значений ПДн (D-012; docs/research/03, §6.5 п. 3).
* **TLS 1.3 по умолчанию, TLS 1.2 допустим, 1.0/1.1 отключены** (RFC 8996, docs/research/03, §6.3, [S43]) `[ПРЕДЛОЖЕНИЕ АГЕНТА]`: версии в журнале не зафиксированы. Режим без TLS — только на loopback для разработки (docs/research/03, §6.3).

Где хранятся пользователи, хеши токенов и сессии (в том же файле БД в отдельных деревьях или отдельно), в журнале не решено: D-018 называет только три дерева. Вынесено в вопросы.

### Consequences

* Good, потому что UI не требует «помнить или переписывать» токен: вход по паролю, вставка из менеджера паролей работает (WCAG 2.2 SC 3.3.8, docs/research/03, §5.1 п. 9, [S35]).
* Good, потому что утечка хранилища не раскрывает токены и пароли — там только хеши.
* Good, потому что CSRF закрыт двумя механизмами, а `SameSite` — дополнительный уровень (docs/research/03, §6.4, [S44]).
* Bad, потому что появляются хранение паролей, блокировка перебора и сброс пароля — это заметно расширяет спецификацию (docs/research/03, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 6).
* Bad, потому что для хеширования токенов (SHA-256 подходит для высокоэнтропийных секретов — docs/research/03, §6.2; что OWASP прямо требует хешировать API-ключи, `[НЕ ПОДТВЕРЖДЕНО]`), CSPRNG и HMAC нужен крейт вне текущего allowlist — вопрос к оркестратору (ADR 0006).
* Bad, потому что XSS обходит любую CSRF-защиту (docs/research/03, §6.4, [S44]); защита UI держится на ADR 0016 (без `innerHTML`, строгая CSP).

### Confirmation

* Тест матрицы прав: для каждой пары «роль × эндпоинт/команда» — ожидаемый результат (разрешено / 403); неаутентифицированный запрос — 401 (capability `access-control`).
* Тест: отозванный токен отклоняется на следующем запросе (CUJ-10, docs/cuj.md).
* Тест хранения: в файле БД и логах нет открытых паролей и токенов (поиск известной строки по файлу).
* Тест CSRF: изменяющий запрос из UI без CSRF-токена или с `Sec-Fetch-Site: cross-site` отклоняется.
* Проверка заголовков cookie: `__Host-`, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`.

## Pros and Cons of the Options

### Локальные учётные записи + cookie + bearer

* Good: удобный вход в UI, отдельный механизм для программ.
* Bad: больше спецификации (пароли, сессии).

### Только API-токены

* Good: меньше кода (docs/research/03, «ВОПРОСЫ К ОРКЕСТРАТОРУ» п. 6).
* Bad: оператору неудобно; токен в браузере сложнее защитить `[ДОПУЩЕНИЕ]`.

### OIDC/SSO

* Good: централизованное управление доступом.
* Bad: внешняя зависимость и инфраструктура; исследование не рассматривало `[ДОПУЩЕНИЕ]`.

### mTLS

* Good: сильная аутентификация программ.
* Bad: неудобно для операторов в браузере; управление сертификатами `[ДОПУЩЕНИЕ]`.
