# 0009. Поисковый ключ имени: NFKC → full case folding → ё→е

## Status

Accepted, 2026-10-24. Решение D-011 (с учётом D-021: таблица case folding из закреплённого `CaseFolding.txt`, и D-022: лимиты).

## Context and Problem Statement

Оператор начинает печатать имя и ждёт подсказок (CUJ-02). Он не обязан помнить регистр, букву «ё» («Семенов» вместо «Семёнов», docs/research/03, §2.3, [S18]) и форму записи символов. Префиксный поиск определён только после того, как определено сравнение строк (docs/research/02, §0.1). Полная сортировка по UCA/ICU сложна и нестабильна между версиями (docs/research/03, §2.5, [S12]).

Как строить ключ индекса `name_idx(key‖id)` (ADR 0003) из `display_name`, чтобы точный и префиксный поиск были предсказуемыми?

## Decision Drivers

* Регистронезависимость и эквивалентность «ё/е» для русского.
* Не ломать «й»: общее удаление диакритики превращает «й» в «и» (docs/research/03, §2.3, [S14c]).
* Стабильность и версионируемость правил ключа.
* Реализуемость «с нуля» без ICU (ADR 0006).

## Considered Options

1. **NFKC → полный default case folding (C+F, без тюркских правил) → замена ё→е; бинарный порядок** — выбрано.
2. **lowercase вместо case folding.**
3. **NFD + удаление всех комбинирующих знаков** (общее удаление диакритики).
4. **Ключ сортировки UCA/ICU** (уровень 1 или 2).

## Decision Outcome

Выбран вариант 1 (D-011):

* `display_name` хранится в NFC (D-009, docs/research/03, §2.1: W3C рекомендует NFC для контента).
* **Ключ = NFKC → полный default case folding (статусы C+F, без T) → замена ё→е.** NFKC применяется только к ключу, не к отображаемому имени (docs/research/03, §2.1). Полное свёртывание даёт `ß → ss`, `Σ`/`ς → σ`, `Ё → ё` (docs/research/03, §2.2, [S11]).
* **Общего удаления диакритики нет**, чтобы не сломать «й» (D-011; docs/research/03, §2.3).
* **Правила построения ключа версионируются**; версия хранится с индексом, при её смене индекс перестраивается (docs/research/03, §2.5).
* **Порядок по ключу — бинарный.** Сортировка по UCA/ICU — вне скоупа (D-011).
* **Режимы поиска:** точный (равенство ключей) и по префиксу ключа; плюс поиск по префиксу телефона (ADR 0008).
* Таблица case folding генерируется из закреплённого `CaseFolding.txt` (D-021: Unicode 16.0). Расхождение: исследование 03 (§2.1, §2.2) цитирует Unicode 18.0.0 — какую версию закреплять и как согласовать её с версией таблиц `unicode-normalization`, вынесено в вопросы.

Не решено в журнале и вынесено в вопросы (`[ПРЕДЛОЖЕНИЕ АГЕНТА]` в скобках):

* обрезка и схлопывание `White_Space` в `display_name` до построения ключа (да, по docs/research/03, §2.4 и docs/research/02, §8 ADR-005);
* повторная нормализация после case folding, потому что свёртывание не всегда сохраняет нормальную форму (docs/research/03, §2.2, определение D145 `[НЕ ПОДТВЕРЖДЕНО]`) (да: NFKC ещё раз после свёртывания);
* поиск по началу каждого слова, а не только по началу всей строки (docs/research/03, §8.2 называет это опцией) (нет в v1);
* индексируются ли части имени (`given_name` и др.) или только `display_name` (docs/research/03, §2.6) (только `display_name`).

### Consequences

* Good, потому что «СЕМЁНОВ», «семенов» и «Семёнов» дают один ключ и находятся одним запросом.
* Good, потому что ключ не зависит от локали и одинаков на всех платформах.
* Good, потому что бинарный порядок кириллицы и латиницы по кодовым точкам почти совпадает с алфавитным, кроме «ё», которую свёртка в «е» ставит на место (docs/research/03, §2.5).
* Bad, потому что турецкие `ı` и `i` не совпадают, а `İ` даёт лишний комбинирующий знак (docs/research/03, §2.2).
* Bad, потому что «é» и «e» — разные ключи: латинская диакритика не снимается.
* Bad, потому что NFKC стирает часть различий (`ﬁ` → `fi`, `Ⅳ` → `IV`) — для ключа это допустимо, для отображения нет (docs/research/03, §2.1).
* Bad, потому что транслитерация (Ivanov ↔ Иванов), фонетический и нечёткий поиск отсутствуют (docs/research/03, §8.2).

### Confirmation

* Таблица тест-векторов ключа: «Семёнов»/«СЕМЕНОВ» → один ключ; «Йода» ≠ «Иода»; `ß` → `ss`; `ς` и `σ` совпадают; полноширинные буквы складываются (capability `name-normalization`).
* Тест генератора: таблица свёртывания совпадает с закреплённым `CaseFolding.txt` (статусы C+F) (ADR 0006).
* Property-тест: ключ идемпотентен — ключ ключа равен ключу `[ПРЕДЛОЖЕНИЕ АГЕНТА]`; префиксный поиск совпадает с моделью в памяти (ADR 0015).
* Проверка: при смене версии правил ключа индекс помечается к перестройке, а поиск не возвращает результатов по старому ключу молча.

## Pros and Cons of the Options

### NFKC → full case folding → ё→е

* Good: регистр и «ё» учтены, «й» сохранена, реализуемо по таблице UCD.
* Bad: латинская диакритика различается.

### lowercase

* Good: просто.
* Bad: `str.lower()` оставляет `ß` без изменений, а `casefold()` даёт `ss` (docs/research/03, §2.2, [S13]); конечная сигма не совпадает с обычной.

### Удаление всей диакритики

* Good: «é» = «e».
* Bad: «й» превращается в «и» (docs/research/03, §2.3).

### UCA/ICU

* Good: лингвистически правильный порядок, «ё» и «е» равны на первичном уровне (docs/research/03, §2.3, [S14]).
* Bad: большой объём, tailoring по языкам, порядок не фиксирован между версиями (docs/research/03, §2.5, [S12]); вне скоупа по D-011.
